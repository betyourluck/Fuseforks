# Spec: 予算の予約 — `try_reserve` を load から CAS 予約へ（あるいは、上限の訂正だけで閉じる）

**ID**: 38
**Date**: 2026-08-14
**Status**: **Done**（2026-08-15。P0〜P5 完了・**実機の検収 4 件すべて観測**。
rev3 = 査読 2 系統（採用 14 / 訂正して採用 3 / 反証 2）+ 承認査読の磨き 5 点）
**Branch**: **2 段階**（利用者査読の裁定）— P0（契約の凍結）だけ rev2 承認後に
main 直コミット。P1 以降は着手日の `YYYYMMDD_reserve` へ積み（**日付は Spec の日付ではなく
着手日** — 前例 `20260813_vng` も 8/13 着手の意）、P1/P3 のテスト合格をゲートに合流。**D0 が「やらない」に倒れたら
ブランチごと捨てる**（main 直だとロールバックが revert の列になる）

## Goal

Spec 11 の天井の**超過上限を「同時に飛ぶ本数 × 1 呼び出しの実費」から
「飛行中の正の見積もり誤差の総和」へ縮める** — あるいは、
**縮めない判断を根拠つきで凍結する**。どちらの場合でも成果物は
「上限がいくつで、なぜそれを受け入れるか」が台帳に載ること。

~~「1 呼び出し分へ縮める」~~ **rev2 で訂正**（村査読 1 / 利用者査読 S1）:
見積もりで予約する以上、超過は「1 呼び出し分」ではなく
**飛行中の各呼び出しの正の見積もり誤差の総和**（≤ 同時数 × 最大正誤差）。
見積もりが常に実費以上なら 0 だが、それは保証できない（RAG・大添付で
直前実測から桁が跳ねる）。**rev1 の Goal 自体が、反証したはずの
「因果 1 本の数え」をもう一度やっていた。**

起点は実機ではなく **TLC の反証**（2026-08-14・`specs/tla/BudgetOvershootBound`。
`failures.md` #105）。`BudgetPool::try_reserve` は load しかしない（予約しない）
ので、波が N 体へ撒くと残額 1 milli でも N 体が同時に通る。

**これは拡張か収縮か**: 機構としては拡張（予約と返金の経路が増える）。
だから D0 に「作らない」側の選択肢を 2 つ明示して置く。

## 現況（実測 2026-08-14。**参照は関数名** — 行番号は同日の自分の編集でもうズレた）

| | 事実 |
|---|---|
| `BudgetPool::try_reserve` | `load > 0` のみ。**予約しない** |
| `run_plan`（delegation.rs） | 波は JoinSet で N 体 spawn・**全員が同一の Arc<BudgetPool>**（doc は「新 pool を作ると天井が人数倍」と**逆側の race だけ**注釈している） |
| `try_reserve` の呼び出し点 | **本番 3 箇所**（`run_turn` の周回境界 = ラウンド前 + まとめ呼び出し前 / `deliver_and_wait` 冒頭の配送前検査）。`.rs` 全体では 11 件で残り 8 件はテスト（村査読の二重測定と一致） |
| `debit_milli` | fetch_update + saturating_sub。**加算（返金）の経路は存在しない** |
| プールの寿命 | **プロセス内メモリ。再起動で復元しない**（Spec 12 の凍結「復元しないもの = 波・予算・MCP 接続・稼働状態」）— D2 の Drop 議論の前提になる |
| TLC | `SpecCurrent` は `OvershootAtMostOneCall` 違反（3 体で spent=3・天井 1）/ `SpecReserving`（CAS 予約）は緑 |
| 実機 | 天井付近で波を撒いた走行は**未観測**。過去ログから遡って数えることもできない — 境界時点の残高がどの行にも出ず、失敗ターンは行そのものを出さない（#103） |

**害の現れ方**: 天井 1M・9 体の波・1 呼び出し実効 100K なら、最悪で
天井 + 900K ≈ **名目の 1.9 倍**を払ってから止まる。天井は Spec 11 の
安全弁なので、壊れ方が安全側に倒れない唯一の場所にある。

## 決めること

### D0. そもそも機構を足すか（**本 Spec の主戦場**）

| 選択肢 | 中身 | 判定 |
|---|---|---|
| (1) 足す | CAS 予約 + 返金ガード（D1/D2） | **推し** |
| (2) 足さない | 台帳の訂正（2026-08-14 済み）+ 上限式の契約凍結だけで閉じる | 生きた選択肢として残す |
| (3) 同時実行数を絞る | `tokio::sync::Semaphore` で波の並列度を制限し、上限を N×Cmax に**確定**させる（村査読 6 の追加軸） | **却下** |

**(3) を却下する理由**: 天井の**境界でしか起きない事象**のために、
**天井に遠い通常運転の並列度を常時削る** — 並列委譲（`plan`）はこの村の
中核価値で、Spec 21 が D2 ハイライトを「一度 60fps を割った機構を
最適化してまで入れるとフレーム予算を常時払い続ける」と閉じたのと同型。
境界の問題は境界で払う（予約は残額が逼迫したときしか他者を止めない）。

**(2) の完了定義**（rev2 で追加 — 村査読 4 / 利用者査読 S1 分岐）:
P0 のみ実施。`token_budget` へ「上限 = 天井 + 同時数 × 1 呼び出しの実費。
縮めない判断」を凍結し、S1/S2 は**非適用**と明記して Done。
README の予算の節へ利用者向けの 1 行（「多人数の波では天井を
最大で同時数 × 1 呼び出しぶん超えることがある」）を足す。

**(1) を推す理由**: これは頻度未知の事象ではなく**構造の穴**（天井付近で
波を撒けば必ず起きる）。「頻度を見てから」を当てるのは Spec 34 で
2 回踏んだ誤りの 3 回目になる。直した形の正しさは TLC で確認済み。

### D1. 予約額をいくらにするか

| 案 | 額 | 利点 | 害 |
|---|---|---|---|
| (a) | 固定の最小額（床 = 1_000_000 milli = 1,000 実効トークン） | 判断が 1 つ | 実効 100K 級には過小で上限はほぼ縮まない |
| (b) | **その個体の直前の呼び出しの実効値**（初回は (a) の床） | 実測に追従・既にある統計の再利用 | 下記 2 つ |
| (c) | 天井の割合 | — | **却下**。~~N は予約時点で知り得ない~~ → rev2 で理由を差し替え（利用者査読 5）: `run_plan` は N を知っているので渡せる。**却下の本当の理由は責務分離** — 予約側が N を受け取ると波の実装と `BudgetPool` が結合し、波でない単体の周回境界でも N を捏造して渡す羽目になる |

**推し**: (b)。外れても安全側 — ただし rev2 で「安全側」の中身を精密化:

- **過大予約の帰結は「早めに止まる」で終わらない**（利用者査読の技術注記を
  訂正して採用）。CAS では同額の 2 体が同時に通ることは**ない**（片方の
  CAS が先に減らし、もう片方は残額不足で落ちる）。落ちた側は
  budget_exhausted で**確定**し、**返金で残高が戻っても再依頼しない**
  （「自動の再依頼はしない」の凍結）— つまり**波の答えが欠けたまま
  束ねられる**。これが (b) の本当の代償で、D3 の文言が正直であることの
  重要度を上げる
- **初回の波には効かない**（利用者査読・技術 4）。全員が床値スタートなら
  初回 9 体波の超過は現行とほぼ同じ。**P0 契約へ「初回波は固定床のため
  上限縮小が効かない。2 回目以降で収束」を明記**する
- 負荷の急変（短文の直後に大 RAG）では過小に外れる（村査読 6 の発振指摘）。
  外れた分は超過に出る — Goal の上限式（正誤差の総和）はこれを含む
- **直前実測の置き場は個体ごとの共有 `AtomicU64`**（rev3 で確定 —
  承認査読 c）。個体ローカル（`run_turn` の引数）では**ターンをまたぐ初回
  ラウンドへ持ち越せない**（`run_turn` はターンごとに新品）。書くのは
  `commit` だけ・読むのは `try_reserve` の直前だけ・ロックは足さない

### D2. 予約の所有権 — `ReservationGuard`（rev2 で API を凍結。利用者査読 Critical 2）

rev1 は「debit で清算」と「Drop で返金」を両立させる所有権を書いておらず、
**二重返金**（debit 後に Drop がもう一度返す）が書けてしまう形だった。凍結する形:

```rust
fn try_reserve(&self, estimate_milli: u64) -> Option<ReservationGuard>;
impl ReservationGuard {
    /// self を move で消費する。actual > estimate なら差額を debit、
    /// actual < estimate なら差額を返金。以後 Drop は何もしない。
    fn commit(self, actual_milli: u64);
}
impl Drop for ReservationGuard {
    /// commit されなかったパスでのみ Drop が走る。予約の全額を返す。
    /// （commit は self を move で消費するので、commit 後に Drop は
    ///   呼ばれない — committed フラグは不要。rev3・承認査読 a）
    fn drop(&mut self) { /* refund(reserved) */ }
}
```

- **`estimate > ceiling` は即 `None`**（rev3・承認査読 e）。天井より大きい
  予約を部分的に引くと残高を負方向へ持っていける — 部分適用は書かない
- **返金は天井で飽和させる**（`fetch_update` + `min(ceiling)`。利用者査読・
  技術 3）。会計が正しければ数学的には超えないが、並列返金の一時的な
  天井超えが後続の debit の超過を隠す形を防御的に塞ぐ
- **Drop が走らないケースはプールの寿命の外**（村査読 3 への**部分反証**）:
  `process::exit` / `panic="abort"` / SIGKILL では確かに Drop は走らないが、
  **プールはプロセス内メモリで再起動で復元しない**（Spec 12 の凍結）ので、
  プロセスが死ねば漏れた予約ごとプールが消える。**実効天井が縮んだまま
  残る経路は存在しない**
- **`JoinSet::abort` で Drop が走るのは仮説**（rev3 で断定を降ろした —
  abort は future を drop するので走る*はず*だが、tokio 文書は明言して
  いない。査読 2 系統でも結論が割れた）。**P1 の実測テストで機械で決める**。
  推奨手順（承認査読）: Guard に `Arc<AtomicBool>` を持たせ Drop で true、
  `pending().await` 中のタスクを `abort_all` → `join_next` ループ後に
  フラグを確認
- **abort・切断時の under-debit は残る**（村査読 3・7 の生き残る半分）:
  途中で落ちた呼び出しの実費はプロバイダ側で発生済みでも usage が返らず
  清算できない。**これは予約の有無と独立で、現行と同じ**（#103 の領域。
  本 Spec では退行させないことだけを約束し、直さない）。
  **追記（2026-08-16）**: #103 のうち **usage が返る失敗**（出力上限で切れた応答）は
  Spec 外で塞いだ — `LlmError::usage()` が `Some` なら呼び出し地点で成功と同じ
  `commit` を通す（`tests/failed_turn_settlement.rs`）。この行の
  「usage が返らず清算できない」側だけが残っている

### D3. 尽きの分類は据え置き・**System 行の文言は分ける**（rev2 で改訂。村査読 5）

分類（budget_exhausted）・色は据え置き。ただし**過大予約の早止まり**を
「予算を使い切りました」と出すのは嘘になる — 実費は使い切っていない。
文言を「次の呼び出しぶんの予算を確保できません（残 X）」の形へ。
`reserved=` / `estimate=` を `turn:` 系の計器へ出すかは P4 で決める
（利用者査読 5 — 早止まりの「なぜ」がログから読めないと診断できない）。

## P1 実装記録（2026-08-14・ブランチ `20260814_reserve`）

- **旧 `try_reserve()` は `has_remaining()` へ改名**（呼び出し点 3 + テスト 8 を
  機械的改名 — 挙動不変）。予約しないのに予約を名乗っていたのが #105 の嘘の
  起点なので、実態の名前にした。P2 で `run_turn` の 2 箇所だけが新
  `try_reserve(estimate)` へ移り、`deliver_and_wait` は `has_remaining` に残る
- **`ReservationGuard<'a>` は借用で持つ**（`Arc` を要求しない — 波のタスク内では
  future が Arc と guard を両方所有する自己完結形で足りる）。`commit` の
  Drop 無効化は `mem::forget`（`unsafe_code = "forbid"` の下で safe・
  フィールドは Copy）。`commit_usage(&Usage)` も足した — P2 の配線が
  実効 milli 換算を自分で書かずに済む
- **契約の不足を 1 つ精密化**（実装が凍結を読んで初めて見えた —
  Spec 15 P2 と同じ形）: 「残額 >= estimate なら Some」は estimate=0・残額 0 で
  **Some を返す読みになり、exhaustion の門を迂回する**。拒否側へ倒し、
  契約へ 1 行足した（残額 0 のときは estimate 0 でも None）
- **abort 仮説の実測決着**: `join_set_abort_runs_drop_and_refunds` が緑 —
  **`JoinSet::abort` で Drop は走り、予約は全額返金される**（判定は残高の
  復元 400 → 0 で読む。フラグの proxy ではなく返金そのものを観測）。
  待ちループは**有界**にした — 無限 while だとミューテーション (i) で
  赤ではなくハングになり、実装のデッドロックと区別が付かない（#86）
- **ミューテーション 2 本、どちらも予測を先に書いて実測が一致**:
  - (i) CAS → load 観測化: **予測 5 本 → 実測 5 本ちょうど**（settle /
    remaining_short / drop_refund / **parallel = TLC の反証経路
    ReserveByLoad ×3 の実装再現** / abort の reserved_seen）
  - (ii) Drop の返金除去: **予測 2 本 → 実測 2 本ちょうど**（drop_refund /
    abort）。commit 経路は Drop を通らないので他 18 本は緑のまま
- 新設テスト 7 本（budget 20 本）・clippy 警告ゼロ

## P2 実装記録（2026-08-14）

- **配線は `run_turn` の 2 箇所**（周回境界 + まとめ呼び出し）。`deliver_and_wait`
  は `has_remaining` のまま。予約 → LLM → `commit(actual)` で、**`?` の早期脱出は
  guard の Drop が全額返す**
- **見積もりの置き場は `agent_loop` が持つ `Arc<AtomicU64>`**（`Shared` の表に
  しなかったのは、周回ごとにロックを取らないため = 契約の「ロックは足さない」）。
  `handle_message` → `run_turn` へ引数で降ろす。**停止で消えるのは仕様**
  （次の起動は床から）
- **書くのは清算した所だけ** — 予約時に書くと、失敗して返金した呼び出しの
  見積もりが次へ引き継がれる
- **`reserve_estimate_milli` に天井の頭打ちを足した**（契約に無かった穴）。
  `max(直前, 床)` だけだと、**1 度でも天井超えの呼び出しをした個体が
  `estimate > ceiling` で永久に通らなくなる**（天井の小さい村ほど踏む）。
  純関数 + 単体 2 本で留めた

**テストの形を 1 度間違えて、書き直した**:

- 初版は結合テスト 2 本。**2 本目は自分のコメントが「返金の証明にならない」と
  認めていた** — 依頼ごとに新しい予算なので、1 通目の返金は 2 通目に効かない。
  判定にならない項目は書かない（#68）ので撤去し、単体（`spent_effective` の
  400 → 0）へ寄せた
- 1 本目（配送前の門）は**時間依存**（`drain_until_quiet`）で、**凍結したい
  規則は配線の事実**なのに波の挙動で確かめていた。`probe_approval_pruning.rs`
  の前例に倒し、**ソース走査**（`tests/budget_reserve_wiring.rs`）へ。
  **対の側も同時に留める** — 「配送前は予約しない」だけだと、全部を
  `has_remaining` へ戻すミューテーションが緑のまま通る
- ミューテーション 2 方向とも**対応する 1 本だけ**が赤（門を予約へ → 前者 /
  呼び出し側を観測へ → 後者）

`what_we_send_is_what_the_next_turn_replays_as_history` と
`the_room_log_declares_it_is_an_excerpt_and_how_to_get_the_full_text` が
**1 度だけ**落ちた。単独・結合単独・全体の再走ではいずれも緑。
**P2 への帰属は未確定**（P1 の全体走行 2 回も緑だが、それは不在の証明に

## P3 実装記録（2026-08-15）

**新設 `specs/tla/BudgetReservationSettlement`**（safe / double-refund /
no-refund の 3 cfg）。`BudgetOvershootBound` は `CallCost` が定数で
**予約額と実費が常に一致する世界**しか見ていなかった — こちらは
`Actuals = {1, 3}` に対し `Estimate = 2` で、**過大予約（返金が要る）と
過小予約（追加の debit が要る）を非決定に起こす**。

- **主眼は会計** — `AccountingHolds`（飽和していない限り
  `残額 = 天井 − 払い済み − 予約中`）。**多く返せば大きくなり、返し忘れれば
  小さくなる**ので、二重返金と返し忘れが同じ 1 本で落ちる
- **double-refund が depth 3 で違反** = **`committed` フラグ設計を退けた
  承認査読 (a) の機械の裏づけ**。フラグはこの経路を型で消せない
- **no-refund も depth 3 で違反**（Rust 側のミューテーション (ii) の形式版）
- safe は **173 states / 92 distinct / depth 9 で全割り込み順序が緑**

**モデルの誤りを 2 回踏んで、どちらも SAFE 側が教えた**:

1. **不変条件のほうが誤っていた** — 初版は現在の状態だけで
   「天井を超えていなければ帳尻が合う」と書いたが、**一度でも飽和（0 での
   張り付き）が起きると、その後の返金では帳尻が戻らない**。履歴を持つ
   `saturated` 変数を足し、飽和後は問わない形にした（実装の事実であって欠陥ではない）
2. **`saturated' = saturated \/ A \/ B` が代入ではなく論理式だった** —
   TLA+ では `=` が `\/` より強く結合するので `(saturated' = saturated) \/ A \/ B`。
   TLC は「`saturated` が割り当てられていない」と名指しで落ちた

**どちらも「壊れた版が VIOLATED になること」だけを見ていたら見つからない。**
double-refund と no-refund は最初から（誤ったモデルでも）赤かった。
**赤い側だけで満足すると、モデルが壊れていても気づかない** — 対で回す規律が
守っているのは「判別しているか」だけでなく「モデルが正しいか」でもある。

## P4 実装記録（2026-08-15）

**D3（System 行の文言）が P2 まで未着手だったのでここで入れた** — Tasks が
D3 をどの Phase にも割り当てていなかった（決定は書いたが作業にしていない）。

- 文言を「**使い切ったため**」→「**次の呼び出しぶんの予算（上限は実効 N
  トークン）を確保できなかったため**」へ（日英とも）。予約は次の 1 呼び出しぶんを
  先に確保するので、**実費を使い切る前に止まる**ことがある。新しい文言は
  尽きた場合も早止まりの場合も正しい
- **計器 `budget stop: agent=… ceiling=… remaining=… estimate=… reason=…`**
  を打ち切りの 2 箇所へ。`reason` は **`exhausted` / `reserve_short`** の 2 値 —
  利用者の次の手が違う（天井を上げる / 撒く人数を減らす）ので同じ文言に畳めない。
  **打ち切った周にしか出ない**ので通常運転では 1 行も増えない
- そのために `BudgetPool::remaining_milli()` を足した。doc に
  **「門の判定には使わない」**と書いた — ここを読んで分岐すると観測と判定が
  2 本に割れて #105 の形へ戻る
- 台帳: `token_budget.exhaustion`（文言 + 計器）/ `failures.md` #105（着地）/
  CLAUDE.md の Spec 11 節（塞いだこと + **代償は波の欠け**）/
  **DETAIL 日英の予算の節へ「欠け」の 1 行**（README ではなく DETAIL —
  予算の説明は 2026-08-09 の分割で DETAIL 側にあり、README には無い）

**テストは 2 段**（`budget_reserve_wiring.rs` の走査 + `budget_stop_log.rs` の
実ログ）。後者は診断ログの宛先がプロセスで 1 つなので**1 バイナリ 1 テスト**
（`grep_include_log.rs` の前例）。**負の対照つき** — 予約が通った周では
1 行も増えないことを同じテストで見る（#90）。ミューテーション（`reason` を
1 値へ畳む）で赤を確認。

**書式を 1 度壊した** — Python のヒアドキュメント経由で Rust の文字列リテラルを
書いたら**行継続が消えて 30 個の空白がログ行に埋まった**。走査テストへ
「連続空白を残さない」を足して機械で留めた。**生成した文字列でコードを書き換える
ときは、書いた結果を読むまで「書けた」と言わない**（#87 の同型が Rust 側で出た形）。

## P5 実機記録（2026-08-15。**検収 4 件とも観測 = Done**）

天井は**システム設定 > コスト管理**から変え、読むのは `fuseforks.log`。

| | 天井 | 決定的な 1 行 |
|---|---|---|
| **A** | 5,000 | `budget stop: ceiling=5000 remaining=0 estimate=5000 reason=exhausted`（r1 完了の **13 ms 後** = LLM を呼んでいない）。**予測 4 欄すべて一致** |
| **B''** | 13,000 | `budget stop: ceiling=13000 remaining=1566 estimate=8482 reason=reserve_short` |
| **C** | 45,000 | `plan wave: tasks=2` → `agent_10 … reserve_short` / `agent_8 … exhausted` → `plan bundle: tasks=2 chars=3754`（**ミュゼ 1 本ぶん**） |
| **D** | 1,000,000 | 2 ラウンドのターンが完走し、**`budget stop:` が 1 行も出ない**（負の対照） |

**B'' の `reason=reserve_short` が本命。** この行は**旧実装には原理的に存在しない**
（load 観測では「残額はあるが確保できない」という事態が無い）ので、
**行が出たこと自体が予約経路の証明**になる（Spec 20 検収 5' と同じ読み方）。
`remaining=1566` は同時に **D3 で文言を変えた理由の実物** — 旧文言
「予算を使い切ったため」はこの瞬間**嘘**だった。

**設計していなかった収穫が 3 つ**:

- **clamp が効いている**（A の `estimate=5000` = 天井で頭打ち）。P2 で契約の穴として
  足したもので、**無ければこの個体は以後どの因果でも 1 度も走れない**
- **同じ因果で 2 値が並んだ**（C）— `agent_10` が `reserve_short remaining=4220`、
  `agent_8` が `exhausted remaining=0`。**計器を 2 値に分けた判断の最良の実証**で、
  1 値に畳んでいたらこの 2 つは同じ行になっていた
- **hop=2 の孫まで同じ財布**（C の `agent_10` は ルナが委譲した先で `ceiling=45000` が同じ）。
  `a_handoff_inherits_the_same_budget_pool` がテストで留めていた性質が、
  **予約経路でも保たれている**ことを実機で観測

### 天井を 4 回外した — P5 で一番大きい観測

検収の天井を **50,000 → 8,000 → 13,000**、C で **15,000 → 30,000 → 45,000** と
引き直した。**毎回同じ誤り**で、**「1 呼び出しの実効」を単一の数字で代表させた**:

| 回 | 使った数字 | 何を見落としたか |
|---|---|---|
| B | 全ターンの中央値 **12,584** | **キャッシュ 0% の gemini のターンが混ざった母集団**を個体に当てた（3.5 倍過大） |
| B' | その個体のキャッシュ済みの回 **4,275** | **36 分空いて冷えた回 8,700** を見落とした（2 倍過小） |
| C | ミュゼの実測 | **進行役はザリ**（システムプロンプト 12,415 字・実効 7.8〜20.9K/呼び出し）で、**個体が違えば 3 倍違う** |

**実効コストを動かす軸は 3 つあり、単一の代表値は存在しない**:

1. **個体**（システムプロンプトの大きさ）— ミュゼ 3〜8.7K 対 ザリ 7.8〜20.9K
2. **キャッシュ率**（直前に同じ prefix を送ったか）— 同一個体で 2 倍
3. **ラウンド数**（履歴が伸びる）— ターン内で単調増加

**天井は「1 呼び出し × 何回」ではなく「その個体のターン 1 本 × 何ターン」で考える。**
DETAIL の推奨値（6 体で 1,000,000）はターン建てで書かれており、**そちらが正しい単位**。
皮肉なことに、**同じセッションの前半で「gemini 3.7 はキャッシュが効かない」を
見つけたのは自分自身**で、その事実が中央値を押し上げていたのに天井を選ぶときに使わなかった。

### 初回床の限界に数字が付いた

`RESERVE_FLOOR_MILLI` = **1,000 実効**に対し、実測の 1 呼び出しは個体により
**3,000〜20,900**。**各個体の「起動後 1 回目」だけは 3〜20 倍の過小予約**になる。
契約に「初回波は縮小が効かない」と凍結してあるとおりだが、**どれだけ効かないかの
数字は P5 で初めて出た**。床を上げるかは **P0 契約の変更**なので本 Spec では触らない。
