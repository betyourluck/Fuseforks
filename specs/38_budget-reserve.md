# Spec: 予算の予約 — `try_reserve` を load から CAS 予約へ（あるいは、上限の訂正だけで閉じる）

**Date**: 2026-08-14
**Status**: Draft（rev3・**P0 Approve 済み**。rev2 = 査読 2 系統反映（採用 14 /
訂正して採用 3 / 反証 2）→ rev3 = 承認査読の最終磨き 5 点を全採用）
**Branch**: **2 段階**（利用者査読の裁定）— P0（契約の凍結）だけ rev2 承認後に
main 直コミット。P1 以降は着手日の `YYYYMMDD_reserve` へ積み（**日付は Spec の日付ではなく
着手日** — 前例 `20260813_vng` も 8/13 着手の意）、P1/P3 のテスト合格をゲートに合流。**D0 が「やらない」に倒れたら
ブランチごと捨てる**（main 直だとロールバックが revert の列になる）

## Goal

Spec 11 の天井の**超過上限を「同時に飛ぶ本数 × 1 呼び出しの実費」から
「飛行中の正の見積もり誤差の総和」へ縮める** — あるいは、
**縮めない判断を根拠つきで凍結する**。どちらの場合でも成果物は
「上限がいくつで、なぜそれを受け入れるか」が台帳に載ること。

~~「1 呼び出し分へ縮める」~~ **rev2 で訂正**（村査読 1 / 利用者査読 S1）:
見積もりで予約する以上、超過は「1 呼び出し分」ではなく
**飛行中の各呼び出しの正の見積もり誤差の総和**（≤ 同時数 × 最大正誤差）。
見積もりが常に実費以上なら 0 だが、それは保証できない（RAG・大添付で
直前実測から桁が跳ねる）。**rev1 の Goal 自体が、反証したはずの
「因果 1 本の数え」をもう一度やっていた。**

起点は実機ではなく **TLC の反証**（2026-08-14・`specs/tla/BudgetOvershootBound`。
`failures.md` #105）。`BudgetPool::try_reserve` は load しかしない（予約しない）
ので、波が N 体へ撒くと残額 1 milli でも N 体が同時に通る。

**これは拡張か収縮か**: 機構としては拡張（予約と返金の経路が増える）。
だから D0 に「作らない」側の選択肢を 2 つ明示して置く。

## 現況（実測 2026-08-14。**参照は関数名** — 行番号は同日の自分の編集でもうズレた）

| | 事実 |
|---|---|
| `BudgetPool::try_reserve` | `load > 0` のみ。**予約しない** |
| `run_plan`（delegation.rs） | 波は JoinSet で N 体 spawn・**全員が同一の Arc<BudgetPool>**（doc は「新 pool を作ると天井が人数倍」と**逆側の race だけ**注釈している） |
| `try_reserve` の呼び出し点 | **本番 3 箇所**（`run_turn` の周回境界 = ラウンド前 + まとめ呼び出し前 / `deliver_and_wait` 冒頭の配送前検査）。`.rs` 全体では 11 件で残り 8 件はテスト（村査読の二重測定と一致） |
| `debit_milli` | fetch_update + saturating_sub。**加算（返金）の経路は存在しない** |
| プールの寿命 | **プロセス内メモリ。再起動で復元しない**（Spec 12 の凍結「復元しないもの = 波・予算・MCP 接続・稼働状態」）— D2 の Drop 議論の前提になる |
| TLC | `SpecCurrent` は `OvershootAtMostOneCall` 違反（3 体で spent=3・天井 1）/ `SpecReserving`（CAS 予約）は緑 |
| 実機 | 天井付近で波を撒いた走行は**未観測**。過去ログから遡って数えることもできない — 境界時点の残高がどの行にも出ず、失敗ターンは行そのものを出さない（#103） |

**害の現れ方**: 天井 1M・9 体の波・1 呼び出し実効 100K なら、最悪で
天井 + 900K ≈ **名目の 1.9 倍**を払ってから止まる。天井は Spec 11 の
安全弁なので、壊れ方が安全側に倒れない唯一の場所にある。

## 決めること

### D0. そもそも機構を足すか（**本 Spec の主戦場**）

| 選択肢 | 中身 | 判定 |
|---|---|---|
| (1) 足す | CAS 予約 + 返金ガード（D1/D2） | **推し** |
| (2) 足さない | 台帳の訂正（2026-08-14 済み）+ 上限式の契約凍結だけで閉じる | 生きた選択肢として残す |
| (3) 同時実行数を絞る | `tokio::sync::Semaphore` で波の並列度を制限し、上限を N×Cmax に**確定**させる（村査読 6 の追加軸） | **却下** |

**(3) を却下する理由**: 天井の**境界でしか起きない事象**のために、
**天井に遠い通常運転の並列度を常時削る** — 並列委譲（`plan`）はこの村の
中核価値で、Spec 21 が D2 ハイライトを「一度 60fps を割った機構を
最適化してまで入れるとフレーム予算を常時払い続ける」と閉じたのと同型。
境界の問題は境界で払う（予約は残額が逼迫したときしか他者を止めない）。

**(2) の完了定義**（rev2 で追加 — 村査読 4 / 利用者査読 S1 分岐）:
P0 のみ実施。`token_budget` へ「上限 = 天井 + 同時数 × 1 呼び出しの実費。
縮めない判断」を凍結し、S1/S2 は**非適用**と明記して Done。
README の予算の節へ利用者向けの 1 行（「多人数の波では天井を
最大で同時数 × 1 呼び出しぶん超えることがある」）を足す。

**(1) を推す理由**: これは頻度未知の事象ではなく**構造の穴**（天井付近で
波を撒けば必ず起きる）。「頻度を見てから」を当てるのは Spec 34 で
2 回踏んだ誤りの 3 回目になる。直した形の正しさは TLC で確認済み。

### D1. 予約額をいくらにするか

| 案 | 額 | 利点 | 害 |
|---|---|---|---|
| (a) | 固定の最小額（床 = 1_000_000 milli = 1,000 実効トークン） | 判断が 1 つ | 実効 100K 級には過小で上限はほぼ縮まない |
| (b) | **その個体の直前の呼び出しの実効値**（初回は (a) の床） | 実測に追従・既にある統計の再利用 | 下記 2 つ |
| (c) | 天井の割合 | — | **却下**。~~N は予約時点で知り得ない~~ → rev2 で理由を差し替え（利用者査読 5）: `run_plan` は N を知っているので渡せる。**却下の本当の理由は責務分離** — 予約側が N を受け取ると波の実装と `BudgetPool` が結合し、波でない単体の周回境界でも N を捏造して渡す羽目になる |

**推し**: (b)。外れても安全側 — ただし rev2 で「安全側」の中身を精密化:

- **過大予約の帰結は「早めに止まる」で終わらない**（利用者査読の技術注記を
  訂正して採用）。CAS では同額の 2 体が同時に通ることは**ない**（片方の
  CAS が先に減らし、もう片方は残額不足で落ちる）。落ちた側は
  budget_exhausted で**確定**し、**返金で残高が戻っても再依頼しない**
  （「自動の再依頼はしない」の凍結）— つまり**波の答えが欠けたまま
  束ねられる**。これが (b) の本当の代償で、D3 の文言が正直であることの
  重要度を上げる
- **初回の波には効かない**（利用者査読・技術 4）。全員が床値スタートなら
  初回 9 体波の超過は現行とほぼ同じ。**P0 契約へ「初回波は固定床のため
  上限縮小が効かない。2 回目以降で収束」を明記**する
- 負荷の急変（短文の直後に大 RAG）では過小に外れる（村査読 6 の発振指摘）。
  外れた分は超過に出る — Goal の上限式（正誤差の総和）はこれを含む
- **直前実測の置き場は個体ごとの共有 `AtomicU64`**（rev3 で確定 —
  承認査読 c）。個体ローカル（`run_turn` の引数）では**ターンをまたぐ初回
  ラウンドへ持ち越せない**（`run_turn` はターンごとに新品）。書くのは
  `commit` だけ・読むのは `try_reserve` の直前だけ・ロックは足さない

### D2. 予約の所有権 — `ReservationGuard`（rev2 で API を凍結。利用者査読 Critical 2）

rev1 は「debit で清算」と「Drop で返金」を両立させる所有権を書いておらず、
**二重返金**（debit 後に Drop がもう一度返す）が書けてしまう形だった。凍結する形:

```rust
fn try_reserve(&self, estimate_milli: u64) -> Option<ReservationGuard>;
impl ReservationGuard {
    /// self を move で消費する。actual > estimate なら差額を debit、
    /// actual < estimate なら差額を返金。以後 Drop は何もしない。
    fn commit(self, actual_milli: u64);
}
impl Drop for ReservationGuard {
    /// commit されなかったパスでのみ Drop が走る。予約の全額を返す。
    /// （commit は self を move で消費するので、commit 後に Drop は
    ///   呼ばれない — committed フラグは不要。rev3・承認査読 a）
    fn drop(&mut self) { /* refund(reserved) */ }
}
```

- **`estimate > ceiling` は即 `None`**（rev3・承認査読 e）。天井より大きい
  予約を部分的に引くと残高を負方向へ持っていける — 部分適用は書かない
- **返金は天井で飽和させる**（`fetch_update` + `min(ceiling)`。利用者査読・
  技術 3）。会計が正しければ数学的には超えないが、並列返金の一時的な
  天井超えが後続の debit の超過を隠す形を防御的に塞ぐ
- **Drop が走らないケースはプールの寿命の外**（村査読 3 への**部分反証**）:
  `process::exit` / `panic="abort"` / SIGKILL では確かに Drop は走らないが、
  **プールはプロセス内メモリで再起動で復元しない**（Spec 12 の凍結）ので、
  プロセスが死ねば漏れた予約ごとプールが消える。**実効天井が縮んだまま
  残る経路は存在しない**
- **`JoinSet::abort` で Drop が走るのは仮説**（rev3 で断定を降ろした —
  abort は future を drop するので走る*はず*だが、tokio 文書は明言して
  いない。査読 2 系統でも結論が割れた）。**P1 の実測テストで機械で決める**。
  推奨手順（承認査読）: Guard に `Arc<AtomicBool>` を持たせ Drop で true、
  `pending().await` 中のタスクを `abort_all` → `join_next` ループ後に
  フラグを確認
- **abort・切断時の under-debit は残る**（村査読 3・7 の生き残る半分）:
  途中で落ちた呼び出しの実費はプロバイダ側で発生済みでも usage が返らず
  清算できない。**これは予約の有無と独立で、現行と同じ**（#103 の領域。
  本 Spec では退行させないことだけを約束し、直さない）

### D3. 尽きの分類は据え置き・**System 行の文言は分ける**（rev2 で改訂。村査読 5）

分類（budget_exhausted）・色は据え置き。ただし**過大予約の早止まり**を
「予算を使い切りました」と出すのは嘘になる — 実費は使い切っていない。
文言を「次の呼び出しぶんの予算を確保できません（残 X）」の形へ。
`reserved=` / `estimate=` を `turn:` 系の計器へ出すかは P4 で決める
（利用者査読 5 — 早止まりの「なぜ」がログから読めないと診断できない）。

## Stories（rev2 で D0 の分岐に対応）

- S1. **D0=(1)**: 天井付近で 9 体の波を撒いても、超過が
  「飛行中の正の見積もり誤差の総和」に収まる（2 回目以降の波）。
  **D0=(2)**: 上限式が契約に凍結され、README に利用者向けの警告が載る
- S2. **D0=(1) のみ**: 予約したターンが `?` / return / abort（future の drop）で
  落ちても残高が漏れない。**プロセス死は対象外**（プールごと消える —
  Spec 12 の凍結の帰結であって本 Spec の穴ではない）
- S3. 天井に遠い通常運転では、挙動もログも 1 行も変わらない

  **+ abort 実測テスト**（JoinSet::abort で Drop が走ることを機械で確定 —
  査読 2 系統で結論が割れた点を実測で決める）
- **P2**（ブランチ）: **配線は `run_turn` の 2 箇所だけ**（rev1 の「3 箇所」は

  **予約しないことをテストで凍結**（親切心で 3 箇所目を予約に変えると、
  配送拒否のたびに返金が要る形が黙って生える）
- **P3**（ブランチ）: TLC を `estimate ≠ actual` の**非決定性**へ拡張
  （`CallCost` 定数の単純化を外す — 返金の正しさ・under-debit の射程も
  機械で留まる）。対で回し直し、実測を .cfg へ
- **P4**: 台帳（`data_contract` / CLAUDE.md Spec 11 節 / #105 へ着地を追記）+
  計器判断（`reserved=` を出すか）+ **README の予算の節へ 1 行**
  （「天井付近では波の一部が予算不足で**欠ける**ことがある」— 過大予約の
  早止まりは再依頼しないので、束ねに欠けが出るのは仕様。承認査読 d）
- **P5**: 実機 — 小天井 + 多体の波。**読み方**: 統制した走行なら `turn:` 行の

  現況の「過去ログから遡れない」と矛盾しない — 遡れないのは境界時点の
  残高が行に出ない + 失敗ターンが行を出さないためで、**統制走行では
  自分で境界を作るから読める**（利用者査読 4 の因果注記）
