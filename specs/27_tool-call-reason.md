# Spec: ツール呼び出しの理由表示 — 何をしたかの隣に、なぜしたかを 1 行

**Date**: 2026-08-07
**Status**: **rev3 承認 → P0〜P3 完了**（2026-08-07）。
**残る P4 の 2 件は利用者判断で保留**（2026-08-08。下記 P4 の記録）。

**rev2 の査読で D2 の判定基準が割れていることが出た。基準を純化した結果、
`remember` の扱いは表を変えずに根拠だけが入れ替わった** — 「引数が自然言語か」
ではなく「**引数が既に別の形で画面へ出ているか**」。
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

**この村を作った人以外が使うとき、サーヴァントが黙って副作用を起こしていないことを
画面で確かめられるようにする。**

起点は利用者（2026-08-07）—「**同梱ツールの理由表示は、他のユーザーは安心できるから
必須**」。公開までのマイルストーン 6 件のうち、v0.1.0（public）に入れる 1 件目。

現状、会話ペインに出ているのは**ツール名と成否だけ**。
`CoreEvent::ToolInvoked { agent_id, tool, ok }` は 3 欄しか運んでおらず
（`event.rs:137`）、**引数も理由も 1 バイトも画面に届いていない**。
`grep` が 5 回走ったことは分かるが、何を探したのかも、なぜ探したのかも読めない。

この欄は「エージェントが何をしたかは会話ログに現れない」を埋めるために置かれた
（`event.rs:134` の doc）。**置いた目的に対して、運んでいる情報が足りていない。**

## 現況（実測 2026-08-07。`concordia.log` の 969 呼び出し / 355 ターン）

**この Spec の判断はここから出ている。**「安いから入れる」ではなく、
**どこが高いかまで分かったうえで入れる。**

| | 実測 |
|---|---|
| ツール呼び出し | **2.73 本 / ターン**（969 / 355） |
| 出力トークン / ターン | **中央 900**（平均 1,879・最大 20,011。強く歪む） |
| 実効トークン / ターン | **中央 14,936** |
| 出力 ×4 が実効に占める割合 | `cached=0` で **19.3%** / キャッシュ 50% 以上で **28.8%** |

**理由 30 字 ≈ 25 出力トークンとすると +68 トークン / ターン**（2.73 × 25）＝
出力の **+7.6%**、実効の **+1.5〜2.2%**。

**「30 字 ≈ 25 トークン」だけは実測ではなく仮定。** ログから読めるのは
呼び出し回数と出力トークン数までで、**まだ存在しない文字列の長さは測れない**。
実測に置き換えるのは P4 の検収 5（`reason_chars` の分布）。

**この結論は字数→トークンの換算に頑健。** 日本語を最悪の 2 トークン/字で見積もっても
実効 **+4〜5%** で、どちらに転んでも「測るまでもなく安い」側に落ちる。
**ゆえに単発の実走は踏まない** — 1 回の走行は 355 ターンの分布より弱い証拠しか
出さない。

### コストは引数が小さいツールに集中する

| ツール | `args_chars` 中央 | 理由 30 字の相対 | 呼び出し比率 |
|---|---|---|---|
| `fd` | **32** | **+94%** | 14% |
| `rag` | 41 | +73% | 1% |
| `file` | 45 | +67% | 20% |
| `grep` | **66** | +45% | **34%** |
| `run` | 86 | +35% | 7% |
| `sd` | 182 | +16% | 3% |
| `remember` | 207 | +14% | 3% |
| `room_log` | 17 | +176% | <1% |
| **`ask_*`** | **551〜1,353** | **+2%** | 5% |
| **`plan`** | **1,604** | **+2%** | 2% |

**引数が小さいツールが呼び出しの 69% を占める**（`fd` + `file` + `grep` + `rag`）。
そしてそこがまさに**いま画面から何も読めないツール** — 静かに読むだけのもの。
**安心が要る場所と、理由が効く場所が一致している。**

### 測って分かった、測る前の見立ての誤り

起票前、私は「この数字で `ask` を含めるかが決まる」と書いた。**決まらなかった** —
**コストはどちらでも 2% で、判断材料にならない**。`ask` / `plan` を外す根拠は
コストではなく**画面に既に出ていること**（D2）。**#83 と同型: 選択肢の値段を
測ったが、測っていない軸のほうが答えを決めていた。**

### 呼び出し回数はカバレッジの尺度にならない（rev3 で追加）

rev2 の査読は「`remember` は 3% だから外しても 69% → 66% でほぼ変わらない」と
書いた。**この数え方が誤り** — **1 回あたりの取り返しのつかなさが違う**。
`fd` 136 回は読むだけで痕跡を残さないが、**`remember` 26 回は
`Memory.md` へ書き、以後の全ターンのプロンプトに残る**。
**カバレッジを呼び出し回数で測ると、静かで重い副作用ほど軽く見える。**

## 決定

### D1 理由はモデルが書く。事実（引数）の表示ではない

**利用者裁定**（2026-08-07）—「`run` も同梱ツールと同じで理由でいい」。

**私は引数由来の事実表示を先に推し、採られなかった。** 推した理由は
「なぜ」がモデルの自己申告であるのに対し「何を」は起きたことだから、という
`failures.md` #84 の一般化（**引用できることは、従うことの証拠にならない**）。
**採られなかった理由のほうが強い** — ツールごとに出るものが違うと、
**読む側が毎回書式を覚え直す**。安心のための表示が、読む負荷を増やしては本末転倒。

**ただし性質は契約と UI に書く**: **理由はモデルの自己申告であって監査証跡ではない。**
Spec 14 の「バッジは由来であって現在の中身を保証しない」と同じ形で、
**書いていないことが嘘になる**のを防ぐ。理由が正しいことは誰も保証しない。

### D2 対象の基準は「引数が既に別の形で画面へ出ているか」

**rev2 の基準「引数が自然言語の依頼文そのものか」は割れていた**（査読 1）。
その基準だと `remember`（中央 207 字の自然言語）が除外側へ寄るのに、
表では対象に入っていた。**純化した基準はこれ**:

> **その呼び出しの引数が、既に別の形で画面に出ているか。**
> 出ているなら理由は重複。出ていないなら理由が唯一の手掛かり。

| 区分 | 対象 | 根拠 |
|---|---|---|
| **入れる** | `grep` / `file` / `fd` / `run` / `sd` / `yq` / `remember` / `rag` / `room_log` | 引数が画面に出ない。**呼び出しの大半を占める** |
| **入れない** | `ask_*` / `handoff_*` / `plan` | **引数が発話として会話ペインに出る**（`chatRows.ts` が `from.kind === "agent"` の行を描く）。理由を足すと、**画面に既にある文章の隣にその要約が並ぶ** |
| **入れない** | `McpTool` 由来 | **他人のスキーマ**。こちらが宣言していない欄を生やして転送すると、`additionalProperties: false` のサーバーが拒否する |

**`remember` は対象の中心であって、境界例ではない。** `AgentMessage` を 1 通も
生まないので画面に出ず、しかも**書いた内容が以後の全ターンのプロンプトに残る**。
**Goal（黙って副作用を起こしていないことを確かめる）に対して、
ここを外すのは最も外してはいけない 1 本を外すこと**になる。

**新しい自前ツールは既定で対象**になる（画面に出るものだけ外す）。
**例外リストは 3 種だけ**で、増えるとしたら「発話を生むツール」を足したときだけ。

**`ask` / `plan` を外すことは Spec 08 の凍結とも衝突しない** —
「束ねの文言・`plan` のツール説明は 1 字も変えない」（`data_contract.yaml:612`）に
触れずに済む。**ただし「凍結を避けるために外した」のではない** —
外す独立の根拠が先にあり、結果として凍結にも触れなかった。
**この順序を記録しておく**（凍結が理由だと読まれると、凍結が解けたときに
`ask` へ足す誤りが生える）。

### D3 上限 60 字。超過は切り詰め。数えるのは文字数

**60 字の根拠**: 利用者の例「プログラム修正前の確認のため」は **14 字**。
実際の理由はほぼ 20〜40 字に収まる。**100 字だと中央ペインで折り返し、
ツール行が 2 行になる** — それは「1 行の理由」ではなく滝ログの入口
（利用者の言葉「thinking のような滝ログはいらない」）。

**典型の長さを決めるのは上限ではなくスキーマの説明文。** 説明に
「20〜40 字程度で」と書き、**60 字は外れ値だけを止める天井**として置く。

**超過は拒否せず切り詰める。** これは表示物で実行の前提ではない。
拒否すると**理由を長く書いた個体のツール呼び出しが落ちる**＝
表示のための機能が実行を壊す。**書き換え系の「上限超は拒否」（`sd` の diff）とは
別の契約の話**で、あちらは*出力の完全性*、こちらは*表示の見た目*
（`failures.md` #58 — 規律はどの契約の節に書いたかで射程が決まる）。

**手順を 1 つに固定する**（査読 6 — 曖昧なまま実装すると `len()` バグの再演）:

1. **トリム**（前後の空白を落とす）
2. **数える**（`chars().count()`）
3. **切り詰め** — **60 字は `…` を含む最終的な表示長**。超過時は **59 字 + `…`**
4. **トリム後に空なら `Omitted` 扱い**（空白だけの理由を「書いた」と数えない）

**`reason_chars` はトリム後・切り詰め前の文字数**（D6・検収 5）。
**切り詰め後を出すと検収 5 が死ぬ** — モデルが上限を超えて書いているかを
見る項目なのに、全部 60 に貼り付いて何も測れない。
**トリムを先に置くのは、前後の空白付きの秘密が字数として漏れるのを防ぐため**
（査読の末尾の指摘）。

**数えるのは `chars().count()`。** この村は `MAX_*_CHARS` をバイト長 `len()` と
突き合わせる誤りを**査読で 2 回**踏んでいる（Spec 16 / Spec 17）。
**60 字を `len()` で実装すると日本語 20 字で切れ、テストが ASCII だけなら通る。**

### D4 未記入でも実行は通す。必須にしない

スキーマ上 `required` に**入れない**。埋めない個体・古いモデルの呼び出しが
バリデーションで落ちると、**理由を出すための機能がツールを使えなくする**。

未記入でも**行は消さない**。**消すと「ツールが走ったこと」まで見えなくなり、
`ToolInvoked` を置いた元の目的が壊れる。** 表示の区別は D10。

### D5 注入点は `ToolRegistry::specs_for`。`AgentTool::spec()` の既定ではない

**`McpTool` も `AgentTool` を実装している**（`mcp.rs:209`。実装は全 11 個 =
自前 9 + `McpTool` + テスト用 `Dummy`）。既定の `spec()` に注入すると
**外部サーバーのスキーマにこちらの欄が生える**。

**合成側（`ask` / `handoff` / `plan` / `room_log`）は `AgentTool` を実装していない**
— `orchestrator.rs` の 5395 / 5918 / 5953 / 6058 で `ToolSpec` を直接組む。
**ゆえに合成側へ理由欄が生える経路は無い**（rev2 の査読 2 はここを
「もし実装していたら」と仮定したが、実装していない）。

**それでも注入点は `specs_for` へ置く。根拠は別**:
**`RunTool` は `spec_for` を上書きしている**（Spec 15 — 実行可能な登録だけを
列挙するため）。`spec()` の既定に注入すると **`run` にだけ乗らない**。
**`specs_for` は全部が通る唯一の漏斗**なので、ここへ置けば罠ごと消える。

```rust
/// 理由欄を提示するか。既定は真。
/// **`McpTool` だけが偽** — 外部が宣言したスキーマにこちらの欄を足さない。
fn wants_reason(&self) -> bool { true }
```

**説明文の定数はコード上 1 箇所**（`specs_for` の注入元）。
**9 箇所に複製しない**ので、ドリフトの余地が構造的に無い。

### D6 ログには字数だけを出す。本文は出さない

`failures.md` #71 — **計器がモデルの出力を記録して、利用者の秘密がログへ平文で
残った**（`Authorization: Bearer outcast_sk_…`）。理由は自然言語なので秘密が
入る確率は低いが**ゼロではない**。`tool:` 行が `args_chars` しか書かない
既存の規律をそのまま延ばし、**`reason_chars=N` だけを足す**。

**画面には出す。** 画面はスクリーンショットされるが、それは**人が見せると決めて
撮ったもの**で、自動で残り続けるログとは性質が違う。

### D7 既定 ON

安心のための表示なので、**見せない既定には意味が無い**。
システム設定の追加候補にある「ツール実行ログを会話で非表示にする」は
**この行ごと消す**スイッチで、理由だけを消す軸は作らない（軸を増やすと
「ツール行は出るが理由が出ない」状態が生まれ、**理由が無いのか設定で消したのかが
画面から読めなくなる**）。

### D8 届かない先は永続共有・永続保存・未来の自分。届くのは同じターンの同じ個体のループ内だけ

**利用者裁定**（2026-08-07）—「**理由はユーザーだけにわかればよく、途中経過は
他のエージェントはあまり知る必要はない**」。

**rev2 の見出し「理由が届くのは利用者だけ」は本文と矛盾していた**（査読 4）—
直後の表が「同じターンの後続の周回には届く」と書いており、そこは利用者ではない。

**これは既に構造で成立している。コードを 1 行も足さない。**

| 経路 | 届くか | 根拠 |
|---|---|---|
| 他のサーヴァント（広場ログ） | **届かない** | `Shared.log` は `AgentMessage`＝発話だけ。ツール呼び出しは載らない |
| 次のターンの自分（履歴） | **届かない** | `push_exchange(sent, replied)`（`world.rs:99`）は**送った文字列と返した本文の対だけ** |
| 保存（`session_store`） | **届かない** | `SessionRecord::exchange(agent_id, sent, replied)`（`orchestrator.rs:426`）も同じ 2 つ |
| 同じターンの後続の周回 | **届く（意図的）** | ツールループの `messages` に積まれ round 2..N で再送。**そこに積まれないとツール呼び出しが成立しない**。同じ個体で、キャッシュ前置に載るので ×0.1 |

**4 行目は漏れではなく設計。** 契約にもそう書く — **書かないと、次に読む人が
「ここも塞ぐべき穴」と読んでツールループを壊す。**

**ゆえに要るのは実装ではなく凍結。** この村は「編集ゼロのものこそ、次に読む人が
**対応漏れと読んで分岐を足しに来る**」を繰り返し踏んでいる（Spec 25 P1 の
ワイルドカード 6 箇所）。**「理由も広場ログに出せば他のサーヴァントが状況を
把握できて親切」は、実装する人には良く見える。**

やると何が壊れるかを書いておく: **毎ターンの可変注入が 1 本増える**
（#45 / 論文 1 の品質仮説の疑いの筋）。**しかも本 Spec のコスト計算が崩れる** —
測ったのは「呼んだ個体が 1 回書く」費用であって、
「全員の可変文脈へ毎ターン載る」費用ではない。

### D9 説明文で読み手を明かさない。求めるのは行為の記述

**D8 から危険が 1 つ生まれる。** 読み手が利用者だと決まると、
スキーマの説明に「**利用者が読みます**」と書くのが自然になる。
**が、それは「安心させるための文章」を誘発しうる。**
目的が安心である表示に対してモデルへ「人間が読む」と教えると、
**正確さより印象を最適化する側へ倒れる余地**ができる
（#84 の系 — **自己申告は事実の記録ではない**）。

**求めるのは行為の記述**にする。「利用者が読むので分かりやすく」ではなく、
**「次に何を確かめるために呼ぶのかを 20〜40 字で」**。
**読み手を明かさずに書式だけ指定すれば、宛先を意識した文章になりにくい。**

**これは保証ではなく傾向**（#84 の一般化そのもの）。**保証だと書かない。**

### D10 空欄は 2 種類ある。`Option<String>` では区別できない

**査読 5 の指摘。rev2 のままでは P2 が実装不能だった。**
`reason: Option<String>` の `None` が「モデルが書かなかった」と
「外部ツールなので聞けない」の**両方を指してしまう**。

```rust
enum ReasonState {
    Written { text: String },  // モデルが書いた（トリム済み・切り詰め済み）
    Omitted,                   // 尋ねたが書かなかった
    Unsupported,               // McpTool 由来で、そもそも尋ねていない
    Excluded,                  // この村の判断で対象外（合成側）— P1 で追加
}
```

**フロントが推測しない**のが要点。`wants_reason` はコア側にしか無く、
**MCP 接続は動的**なので、**フロントには「このツールは理由を持てるはずか」を
知る手段が無い**。判定材料をワイヤで運ぶ。

表示は **`Omitted` = 「理由なし」/ `Unsupported` = 「外部ツール」/
`Excluded` = 理由の行を出さない**（S3）。

**`Excluded` は P1 の実装で足した。rev3 の凍結（3 値）では足りなかった。**
合成側（`ask` / `plan` / `room_log`）も **`ToolInvoked` を発行する**
（`orchestrator.rs` の emit は分岐の**後ろ**にある）。3 値だと合成側を
`Unsupported` に落とすしかなく、**`ask_agent_3` に「外部ツール」と出る** —
**画面のラベルが嘘になる**。**契約を書いた時点で「発行するのは registry 経由の
呼び出しだけ」と暗に仮定しており、そこを数えていなかった。**

### D11 `ok` は監査証跡ではない。理由と対で書く

**査読 7。rev2 の未決は「`ok=false` のとき」と書いていたが射程が狭かった** —
同梱ツールは失敗を `Err` ではなく **`Ok(<エラー文>)` で返す**ので
（`failures.md` #41、`orchestrator.rs:4329` の doc が明記）、
**`ok=true` のまま失敗している行が常態**。

契約へ D1 と対で書く:

> **`ok` はツールの返り値が `Ok` かどうかであって、副作用が成功したかではない。**
> **理由と同じく監査証跡ではない。**

**UI のラベルは「成功 / 失敗」と書かない** —「**返った / エラーで返った**」。
**理由は「意図」として成否と視覚的に分離する**（査読の提案）。
理由の文面自体に成否を読み込ませない。

**却下したもの（覆すときに覆したと分かるように記録する）**:
査読は「結果本文が `Error:` / `失敗` / `not found` を含むなら `ok` を偽に倒す
正規化層」を提案したが、**採らない**。

1. **Spec 08 が「分類は文言 parse でなく型で運ぶ」を凍結している**
   （刻み手は `handle_message` の 1 箇所）
2. **偽陽性が壊滅的。** `grep "Error:"` は**一致行を返すのが仕事**で、
   結果に `Error:` が入るのは成功。`file read` でログを読めば「失敗」が入る。
   **読み取り系は本文を返すのが仕事なので、本文に何が入るかを機構が
   決めつけられない。** 実測で `grep` は呼び出しの 34%、`file` は 20%
3. **#41 の一般化は診断であって処方ではない** — 「失敗を戻り値の型に載せていない
