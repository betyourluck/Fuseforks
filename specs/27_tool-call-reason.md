# Spec: ツール呼び出しの理由表示 — 何をしたかの隣に、なぜしたかを 1 行

**ID**: 27
**Date**: 2026-08-07
**Status**: **rev2**（利用者裁定で D8 / D9 を新設）。未承認。査読待ち。
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

**この村を作った人以外が使うとき、サーヴァントが黙って副作用を起こしていないことを
画面で確かめられるようにする。**

起点は利用者（2026-08-07）—「**同梱ツールの理由表示は、他のユーザーは安心できるから
必須**」。公開までのマイルストーン 6 件のうち、v0.1.0（public）に入れる 1 件目。

現状、会話ペインに出ているのは**ツール名と成否だけ**。
`CoreEvent::ToolInvoked { agent_id, tool, ok }` は 3 欄しか運んでおらず
（`event.rs:137`）、**引数も理由も 1 バイトも画面に届いていない**。
`grep` が 5 回走ったことは分かるが、何を探したのかも、なぜ探したのかも読めない。

この欄は「エージェントが何をしたかは会話ログに現れない」を埋めるために置かれた
（`event.rs:134` の doc）。**置いた目的に対して、運んでいる情報が足りていない。**

## 現況（実測 2026-08-07。`concordia.log` の 969 呼び出し / 355 ターン）

**この Spec の判断はここから出ている。**「安いから入れる」ではなく、
**どこが高いかまで分かったうえで入れる。**

| | 実測 |
|---|---|
| ツール呼び出し | **2.73 本 / ターン**（969 / 355） |
| 出力トークン / ターン | **中央 900**（平均 1,879・最大 20,011。強く歪む） |
| 実効トークン / ターン | **中央 14,936** |
| 出力 ×4 が実効に占める割合 | `cached=0` で **19.3%** / キャッシュ 50% 以上で **28.8%** |

**理由 30 字 ≈ 25 出力トークンとすると +68 トークン / ターン**（2.73 × 25）＝
出力の **+7.6%**、実効の **+1.5〜2.2%**。

**「30 字 ≈ 25 トークン」だけは実測ではなく仮定。** ログから読めるのは
呼び出し回数と出力トークン数までで、**まだ存在しない文字列の長さは測れない**。
実測に置き換えるのは P4 の検収 5（`reason_chars` の分布）。

**この結論は字数→トークンの換算に頑健。** 日本語を最悪の 2 トークン/字で見積もっても
実効 **+4〜5%** で、どちらに転んでも「測るまでもなく安い」側に落ちる。
**ゆえに単発の実走は踏まない** — 1 回の走行は 355 ターンの分布より弱い証拠しか
出さない。

### コストは引数が小さいツールに集中する

| ツール | `args_chars` 中央 | 理由 30 字の相対 | 呼び出し比率 |
|---|---|---|---|
| `fd` | **32** | **+94%** | 14% |
| `rag` | 41 | +73% | 1% |
| `file` | 45 | +67% | 20% |
| `grep` | **66** | +45% | **34%** |
| `run` | 86 | +35% | 7% |
| `sd` | 182 | +16% | 3% |
| `remember` | 207 | +14% | 3% |
| `room_log` | 17 | +176% | <1% |
| **`ask_*`** | **551〜1,353** | **+2%** | 5% |
| **`plan`** | **1,604** | **+2%** | 2% |

**引数が小さいツールが呼び出しの 69% を占める**（`fd` + `file` + `grep` + `rag`）。
そしてそこがまさに**いま画面から何も読めないツール** — 静かに読むだけのもの。
**安心が要る場所と、理由が効く場所が一致している。**

### 測って分かった、測る前の見立ての誤り

起票前、私は「この数字で `ask` を含めるかが決まる」と書いた。**決まらなかった** —
**コストはどちらでも 2% で、判断材料にならない**。`ask` / `plan` を外す根拠は
コストではなく**重複**（下記 D2）。**#83 と同型: 選択肢の値段を測ったが、
測っていない軸のほうが答えを決めていた。**

## 決定

### D1 理由はモデルが書く。事実（引数）の表示ではない

**利用者裁定**（2026-08-07）—「`run` も同梱ツールと同じで理由でいい」。

**私は引数由来の事実表示を先に推し、採られなかった。** 推した理由は
「なぜ」がモデルの自己申告であるのに対し「何を」は起きたことだから、という
`failures.md` #84 の一般化（**引用できることは、従うことの証拠にならない**）。
**採られなかった理由のほうが強い** — ツールごとに出るものが違うと、
**読む側が毎回書式を覚え直す**。安心のための表示が、読む負荷を増やしては本末転倒。

**ただし性質は契約と UI に書く**: **理由はモデルの自己申告であって監査証跡ではない。**
Spec 14 の「バッジは由来であって現在の中身を保証しない」と同じ形で、
**書いていないことが嘘になる**のを防ぐ。理由が正しいことは誰も保証しない。

### D2 対象は自前のツールのうち引数が理由を含まないものだけ

| 区分 | 対象 | 根拠 |
|---|---|---|
| **入れる** | `grep` / `file` / `fd` / `run` / `sd` / `yq` / `remember` / `rag` / `room_log` | 引数から意図が読めない。呼び出しの大半を占める |
| **入れない** | `ask_*` / `handoff_*` / `plan` | **引数が自然言語の依頼文そのもの**（中央 551〜1,604 字）。理由を足しても情報が 1 ビットも増えない |
| **入れない** | `McpTool` 由来 | **他人のスキーマ**。こちらが宣言していない欄を生やして転送すると、`additionalProperties: false` のサーバーが拒否する |

**`ask` / `plan` を外すことは Spec 08 の凍結とも衝突しない** —
「束ねの文言・`plan` のツール説明は 1 字も変えない」（`data_contract.yaml:612`）に
触れずに済む。**ただし「凍結を避けるために外した」のではない** —
外す独立の根拠（重複）が先にあり、結果として凍結にも触れなかった。
**この順序を記録しておく**（凍結が理由だと読まれると、凍結が解けたときに
`ask` へ足す誤りが生える）。

### D3 上限 60 字。超過は切り詰め。数えるのは文字数

**60 字の根拠**: 利用者の例「プログラム修正前の確認のため」は **14 字**。
実際の理由はほぼ 20〜40 字に収まる。**100 字だと中央ペインで折り返し、
ツール行が 2 行になる** — それは「1 行の理由」ではなく滝ログの入口
（利用者の言葉「thinking のような滝ログはいらない」）。

**典型の長さを決めるのは上限ではなくスキーマの説明文。** 説明に
「20〜40 字程度で」と書き、**60 字は外れ値だけを止める天井**として置く。

**超過は拒否せず切り詰める**（末尾に `…`）。これは表示物で実行の前提ではない。
拒否すると**理由を長く書いた個体のツール呼び出しが落ちる**＝
表示のための機能が実行を壊す。**書き換え系の「上限超は拒否」（`sd` の diff）とは
別の契約の話**で、あちらは*出力の完全性*、こちらは*表示の見た目*
（`failures.md` #58 — 規律はどの契約の節に書いたかで射程が決まる）。

**数えるのは `chars().count()`。** この村は `MAX_*_CHARS` をバイト長 `len()` と
突き合わせる誤りを**査読で 2 回**踏んでいる（Spec 16 / Spec 17）。
**60 字を `len()` で実装すると日本語 20 字で切れ、テストが ASCII だけなら通る。**

### D4 未記入でも実行は通す。必須にしない

スキーマ上 `required` に**入れない**。埋めない個体・古いモデルの呼び出しが
バリデーションで落ちると、**理由を出すための機能がツールを使えなくする**。

未記入は画面に**「理由なし」**と出す（行を消さない）。**消すと「ツールが走ったこと」
まで見えなくなり、`ToolInvoked` を置いた元の目的が壊れる。**

### D5 注入点を `AgentTool::spec()` の既定にしない

**`McpTool` も `AgentTool` を実装している**（`mcp.rs:209`。実装は全 11 個 =
自前 9 + `McpTool` + テスト用 `Dummy`）。既定の `spec()` に注入すると
**外部サーバーのスキーマにこちらの欄が生える**。

処方は**既定 true のオプトアウト 1 本**（`spec_for` の前例と同じ形）:

```rust
/// 理由欄を提示するか。既定は真。
/// **`McpTool` だけが偽** — 外部が宣言したスキーマにこちらの欄を足さない。
fn wants_reason(&self) -> bool { true }
```

**実装の罠を 1 つ先に書いておく**: **`spec_for` を上書きしているツールは
既定の `spec()` を通らない**（Spec 15 の `run` が該当）。
注入が 1 箇所で済むかは P1 で実装して確かめる。**済まないなら
`ToolRegistry::specs_for` の側（全部が通る唯一の漏斗）へ移す。**

### D6 ログには字数だけを出す。本文は出さない

`failures.md` #71 — **計器がモデルの出力を記録して、利用者の秘密がログへ平文で
残った**（`Authorization: Bearer outcast_sk_…`）。理由は自然言語なので秘密が
入る確率は低いが**ゼロではない**。`tool:` 行が `args_chars` しか書かない
既存の規律をそのまま延ばし、**`reason_chars=N` だけを足す**。

**画面には出す。** 画面はスクリーンショットされるが、それは**人が見せると決めて
撮ったもの**で、自動で残り続けるログとは性質が違う。

### D8 理由が届くのは利用者だけ。他のサーヴァントへは渡さない

**利用者裁定**（2026-08-07）—「**理由はユーザーだけにわかればよく、途中経過は
他のエージェントはあまり知る必要はない**」。

**これは既に構造で成立している。コードを 1 行も足さない。**

| 経路 | 届くか | 根拠 |
|---|---|---|
| 他のサーヴァント（広場ログ） | **届かない** | `Shared.log` は `AgentMessage`＝発話だけ。ツール呼び出しは載らない |
| 次のターンの自分（履歴） | **届かない** | `push_exchange(sent, replied)`（`world.rs:99`）は**送った文字列と返した本文の対だけ** |
| 保存（`session_store`） | **届かない** | `SessionRecord::exchange(agent_id, sent, replied)`（`orchestrator.rs:426`）も同じ 2 つ |
| 同じターンの後続の周回 | **届く** | ツールループの `messages` に積まれ round 2..N で再送。**同じ個体**で、キャッシュ前置に載るので ×0.1 |

**ゆえに要るのは実装ではなく凍結。** この村は「編集ゼロのものこそ、次に読む人が
**対応漏れと読んで分岐を足しに来る**」を繰り返し踏んでいる（Spec 25 P1 の
ワイルドカード 6 箇所）。**「理由も広場ログに出せば他のサーヴァントが状況を
把握できて親切」は、実装する人には良く見える。**

やると何が壊れるかを書いておく: **毎ターンの可変注入が 1 本増える**
（#45 / 論文 1 の品質仮説の疑いの筋）。**しかも本 Spec のコスト計算が崩れる** —
測ったのは「呼んだ個体が 1 回書く」費用であって、
「全員の可変文脈へ毎ターン載る」費用ではない。

### D9 説明文で読み手を明かさない。求めるのは行為の記述

**D8 から危険が 1 つ生まれる。** 読み手が利用者だと決まると、
スキーマの説明に「**利用者が読みます**」と書くのが自然になる。
**が、それは「安心させるための文章」を誘発しうる。**
目的が安心である表示に対してモデルへ「人間が読む」と教えると、
**正確さより印象を最適化する側へ倒れる余地**ができる
（#84 の系 — **自己申告は事実の記録ではない**）。

**求めるのは行為の記述**にする。「利用者が読むので分かりやすく」ではなく、
**「次に何を確かめるために呼ぶのかを 20〜40 字で」**。
**読み手を明かさずに書式だけ指定すれば、宛先を意識した文章になりにくい。**

**これは保証ではなく傾向**（#84 の一般化そのもの）。**保証だと書かない。**

### D7 既定 ON

安心のための表示なので、**見せない既定には意味が無い**。
システム設定の追加候補にある「ツール実行ログを会話で非表示にする」は
**この行ごと消す**スイッチで、理由だけを消す軸は作らない（軸を増やすと
「ツール行は出るが理由が出ない」状態が生まれ、**理由が無いのか設定で消したのかが
画面から読めなくなる**）。

## Stories

- S1 サーヴァントがツールを走らせたとき、**何のために走らせたか**が会話ペインで読める
- S2 理由を書かない個体でも、**ツールはこれまでどおり動く**
- S3 MCP 由来のツールで理由が空でも、**「理由が無い」ではなく「聞けない」**と読める
- S4 理由を長く書いた個体の呼び出しが**落ちない**
- S5 ツール行は**1 行に収まる**（滝ログにしない）

- **P4 実機確認** — 4 件。**合格側と不合格側の両方で読めるか、書く前に数えた**

  1. `grep` / `file` / `fd` が走ったとき、**理由が 1 行で出る**。
     負の対照 = **`ask` で理由の行が出ない**（対象外なので出ないのが正）
  2. **MCP 由来のツールが走ったとき、理由の欄が「聞けない」と読める形で出る**。
     `MCP_DOCKER__fetch` は実測で 79 回走っているので踏みやすい
  3. **理由を書かない個体でツールが動く**。負の対照 = 同じ個体で
     理由を書く個体と並べる（**書かない実装でも緑になる**のを防ぐ）
  4. **`tool:` 行に `reason_chars` が出て、本文は出ていない**。

## Notes

1. **これは「使わない人は払わない」の形にならない。** Spec 23（画像）・
   Spec 24（補完）・Spec 25（MCP）は**使わない村の固定費がゼロ**だったが、
   本 Spec は既定 ON で全員に乗る。**乗せると決めたのは Goal が
   「他のユーザーの安心」だから** — 払うのは村の持ち主で、受け取るのは
   その村を使う人。**受益者と支払者が違う唯一の Spec**。

   **費用は 2 種類あり、混ぜて書かない**:

   | | 誰に・いつ | 大きさ |
   |---|---|---|
   | **(a) スキーマの定義** | **全員・毎ターン** | **誤差**。安定プレフィックスなのでキャッシュに載り実効 ×0.1。9 本 × 40 トークン ≈ 360 → 実効 36 |
   | **(b) 理由の本文** | **ツールを呼んだターンだけ** | **+1.5〜2.2%**（現況の節の計算） |

   **「全員の毎ターン」なのは (a) で、そちらは誤差。1.5〜2.2% は (b) で、
   そちらは全ターンではない** — ツールを 1 本も呼ばないターンは 1 トークンも
   増えない。**この 2 つを 1 文に混ぜると、既定 ON の是非を判断できなくなる。**

2. **D7 の「既定 ON」は不変条件に触れない。** `batch_start_invariant`
   （開いただけで課金が始まる作りにしない）は**起動と課金**の話で、
   本 Spec が増やすのは**すでに走っているターンの中の出力**。
   ツールを 1 本も呼ばないターンは 1 トークンも増えない。

3. **`rag` と `room_log` を入れた根拠は非対称。** `rag` は引数が
   中央 41 字で意図が読めない（入れる）。`room_log` は引数が **id だけの 17 字**で、
   **理由の相対コストは最大（+176%）だが呼び出しは 2 件**。
   **相対が大きいことは、絶対が小さいことを打ち消さない** —
   ここで相対だけを見て外すと、**いちばん意図が読めないツールが外れる**。

4. **Gemini のスキーマ整形を通ることを確かめる。** `gemini.rs` の
   `parameters_or_none` は `properties` が空なら**スキーマごと落とす**、
   `sanitize_schema` は未知のキーを削る。**理由欄は素の
   `{"type":"string","description":"…"}` なので通るはずだが、
   通ることをテストで留める**（通らないと Gemini 系の村だけ理由が空になり、
   「モデルが書かない」と誤読される）。

5. **表示位置は P2 の実機で動きうる。** Spec 24 の補完 UI は実機の指摘で
   3 回直っている。**1 行に収める**（S5）だけを凍結し、
   行の中の配置は実装で決める。

## 未決（査読で裁定がほしい）

- **D2 の対象から `remember` を外すか。** `remember` の引数は
  中央 207 字の自然言語（覚える内容そのもの）で、**`ask` / `plan` と同じ
  「引数が理由を含む」側に寄る**。入れたのは「自前のツールは全部入れる」
  という一貫性のためだが、**重複を根拠に外したものと基準が食い違う**。
- **理由を書かせる文言をどこに置くか。** 各ツールの `reason` の
  `description` に書くか、システムプロンプト側に 1 文置くか。
  **前者は 9 箇所に同じ文が生える**が、後者は**安定プレフィックスを
  1 文伸ばす**（全員・毎ターン・キャッシュ込み）。
- **`ok=false` のときの理由をどう読ませるか。** 同梱ツールは失敗を
  `Err` ではなく `Ok(<エラー文>)` で返すので（`failures.md` #41）、
  **`ok=true` のまま失敗している行がある**。理由は「やろうとしたこと」なので
  失敗しても正しく残るが、**画面では「理由どおりに成功した」と読まれうる**。
