# Spec: トークン予算 — 依頼の因果に掛ける自動の天井

**ID**: 11
**Date**: 2026-08-02
**Status**: **rev2 査読承認（2026-08-02 LGTM）→ P0 完了**
（data_contract の `token_budget` ブロック凍結 + `PlanTaskState` へ
`budget_exhausted` 加算）。実装は P1 から。
LGTM 時の微細 2 点も P0 で確定 — (1) 欠落見積もりの分母は

**Branch**: なし（main へ Phase 単位で直接コミット — Spec 01〜10 と同じプロセス）

rev2 で入った差分（査読 2026-08-02、7 点すべて受諾）:

- **R1 TOCTOU の解消** — 「検査と減算は atomic」は実装不可能な記述だった
  （check → LLM 呼び出し（数秒〜数十秒）→ usage で減算、の間は原理的に
  atomic にできない）。不変条件 3 を「try_reserve は atomic / consume は
  atomic / 飛行中 1 呼び出し分のオーバーシュートは許容して数える」に書き直し
- **R2 数の型** — Rust の Atomic に浮動小数は無い（AtomicF64 不在）。
  内部表現を **milli 実効トークン**（×1000 の整数）に凍結し、丸めは切り上げ
- **R3 usage 欠落の見積もり** — 入力だけでなく**出力欠落も** chars ÷ 4 で
  見積もる（ツール結果が支配的なターンで 0 見積もりになる穴）。
  cached 区分が無いプロバイダは全量を未キャッシュ扱い

  `cancel` と `budget` は別フィールド。天井は `Option<u64>`（0 と欠落を
  型で区別）
- **R5 歯止めの優先順位を凍結** — cancel（interrupted）> budget_exhausted >
  RepeatGuard > hop / rounds 上限。人の明示停止が最優先、次に資源の事実
- **R6 既定値の射程** — D2 は rev1 案で確定: 新規 world.json のみ
  Some(1,000,000) / 既存は None のまま / 起動ログは **WARN へ昇格**して
  次の道を書く。README へ村規模別の推奨値ガイドを P4 に追加。
  D1 も固定で確定 — 重みは P0 で code constant として凍結し、
  「モデル別の重み設定を作らない」を不変条件へ昇格
- **R7 転送の予算引き継ぎテスト** — 転送先が誤って新 BudgetPool を作らない
  （同一 Arc を指す）ことを結合テストで固定。delegation-fanout race は
  先行実装（arXiv:2606.04056、実在確認済み）の典型障害 11 件の型

## Goal

依頼 1 つの因果（ユーザー発話または予定の発火から、ask / plan / 転送で連鎖する
全ターン）に**トークン建ての天井**を掛け、超えたら周回境界で協調的に打ち切る。
燃焼対策 3 点（CLAUDE.md「次の作業」）の最後の 1 つ:

1. RepeatGuard（同一失敗の検出）— **Done**。繰り返しを止めるが、繰り返さない
   浪費（巨大ファイルの逐次読み・広すぎる調査）は止められない
2. Spec 10（割り込み停止）— **Done**。人が気づいて止める線。人が見ていない
   時間には効かない
3. **本 Spec** — 人が見ていなくても発火する、コスト建ての自動の天井

起点は利用者の村の運用図（8 段フロー）。人が関与するのは最初と最後だけ、
という自律度は**自動の天井があって初めて安全**（2026-08-02 優先度引き上げ）。
外部の傍証: VMAO（arXiv:2603.11445）の実測でクエリの 75% 以上が品質基準では
なくリソース制約で打ち切られている — 自律的なマルチエージェントは天井が
実質の停止条件になる。天井の無い村は、天井の代わりに財布で止まる。

### 立場の宣言

- **強制はハーネス、申告はしない。** Anthropic の Task Budgets は
  claude-sonnet-5 で使えるが、モデルへの申告であって強制ではなく、
  Gemini 系には存在しない。天井は全プロバイダに等しく効く場所 =
  周回境界（RepeatGuard・Spec 10 と同じ点）に置く
- **残額をモデルに毎ラウンド見せない。** 毎ラウンド変わる数字の注入は
  プロンプトキャッシュの前方一致を割り（#42/#45 で払った代償の逆行）、
  毎ターン可変注入の品質仮説（論文 1）の疑いの筋を増やす。v1 は黙って数え、
  黙って止める。打ち切り文に事実と次の道を書く（#44 の規律）
- **自動の再依頼はしない。** 予算が尽きたら止まって報告する。続けるかは
  人（または依頼元の進行役の、次の明示的な依頼）が決める。
  Replan を採らないのと同じ判断
- **設定 UI は作らない（v1）。** 天井は world.json の 1 フィールド +
  既定値。変えたい要望が実測されるまでダイアログを増やさない

## Stories

### S1: 暴走に天井が効く

ワーカーが巨大ファイルを繰り返し読み、RepeatGuard に掛からない形（毎回別の
引数）でトークンを燃やす。予算が尽きた周回境界でそのターンは打ち切られ、
会話ペインに System の 1 行が出る。村は止まらない — 稼働は残り、
次の依頼には普通に応じる。

### S2: 健全な長仕事は止まらない

キャッシュが効いた長いツールループ（例: 実測 87〜99% cached の調査ターン）は、
素のトークン数は大きいが**実費は小さい**。数えは実費に比例する形
（下記「実効トークン」）にし、健全な仕事を誤って打ち切らない。

### S3: 波の途中で尽きる

plan の波の途中で予算が尽きたら、以後の LLM 呼び出しと新規配送を始めない。
既に答え終わったタスクは answered のまま、止められたタスクは新分類で確定し、
束ねは揃わなかった事実を添えて依頼元へ返る（Spec 10 の「race の勝敗が分類を
変えない」と同じ規律）。

### S4: 予定の発火にも同じ天井

Spec 07 の予定発火も因果の根であり、発火 1 回ごとに同じ予算が付く。
毎週木曜の定期依頼が暴走しても、その週の発火 1 回分の予算で止まる。
これが「人が見ていない時間の安全」の本体。

### S5: 打ち切り文の先に道がある

予算切れの通知は「何が起き、いくら使い、続けるにはどうするか」を書く
（#44 — 歯止めの先に道が無いと、打ち切りがターン全滅に化ける）。

## 機構の要点（Phase 0 で凍結する不変条件の候補）

1. **予算は因果に 1 つ。** 根（ユーザー発話 1 通の宛先 1 体ごと /
   予定の発火 1 回）で生まれ、封筒（ask / plan / 転送）で共有され、
   途中で増えない。同報は宛先ごとに別の根 = 別の予算。
   **`Envelope.budget` は `cancel` と独立のフィールド**
   （`Option<Arc<BudgetPool>>`）— cancel が None の配送でも予算は運ぶ。
   転送・波の全配送は**同一の Arc** を指す（新しい pool を作った瞬間に
   天井が蒸発する。delegation-fanout race — 先行実装 arXiv:2606.04056 が
   カタログ化した 63 インシデント中 11 件がこの型）
2. **数えは「実効トークン」= 実測 usage の重み付き和。**
   `未キャッシュ入力 ×1 + キャッシュ済み入力 ×0.1 + 出力 ×4`。
   重みは固定 — **モデル別・村別の重み設定を作らないことも不変条件**。
   重みは data_contract の `token_budget` ブロックへ **code constant として
   凍結**し、変えるときは Spec 改定であって設定ではない。価格比の接地:
   Anthropic cache read ≈ 0.1 / OpenAI 自動キャッシュ ≈ 0.5 / Gemini ≈ 0.25 —
   0.1 は Anthropic 寄りだが `cached << uncached << output` の大小関係は
   全プロバイダ共通で、桁のヒューズという用途には足りる。
   素のトークン数を使わないのは、キャッシュ済み入力が支配的な
   健全ターン（S2）を過大に数えるため。
   **内部表現は milli 実効トークン**（Atomic に浮動小数は無い）:
   `milli = 未キャッシュ ×1000 + キャッシュ済み ×100 + 出力 ×4000`、
   純関数の戻りは `(milli + 999) / 1000` の**切り上げ**（保守側）。
   **usage 欠落の見積もり規程**: prompt_tokens 欠落 = 送信 UTF-8 バイト数 ÷ 4 /
   completion_tokens 欠落 = **0 ではなく**受信 UTF-8 バイト数 ÷ 4（ツール結果が
   支配的なターンで 0 見積もりになる穴を塞ぐ）/ cached 区分が無い
   プロバイダ = 全量を未キャッシュ扱い（保守側）。分母がバイト数
   （`s.len()`）で文字数でないのは P0 確定 — 文字数 ÷ 4 は日本語で
   約 4 倍の過小見積もりになる
3. **検査は周回境界（LLM 呼び出しの前）、オーバーシュートは 1 呼び出し分許容。**
   `try_reserve()`（残額 0 なら打ち切り、判定は atomic）→ LLM 呼び出し →
   `consume(usage)`（fetch_sub、atomic）。check と減算の間に飛行時間が挟まる
   ため一体の atomic にはできない — 飛行中の 1 呼び出しが天井を超えても
   その応答は捨てず、超過分も数える（次の周回境界で確実に止まる）。
   尽きの観測は AtomicBool の CAS で一回性を保証（並列ワーカーが同時に
   尽きを観測しても、打ち切りの記録は 1 系統）
4. **尽きたら、新しい LLM 呼び出しと新しい配送を始めない。**
   飛行中の応答・ツール結果は正常に受け取り記録する（Spec 10 出口と同型）
5. **分類は新値で運ぶ。** `Reply.kind` / `PlanTaskState` に
   `budget_exhausted` を追加（加算的変更 — Spec 10 の
   `interrupted` と同じ回帰テストを付ける）。人が止めた `interrupted`
   （注意色・失敗ではない）と混ぜない — 天井が止めたのは資源の事実で、
   色は失敗系に倒す
6. **打ち切りの System 行は事実 + 次の道。** 「予算（実効 N トークン）を
   使い切ったため打ち切りました。ここまでの結果は上の通りです。続きが
   要るなら改めて依頼してください（予算は依頼ごとに新しく付きます）」
7. **稼働は降ろさない。** 閉じるのはターンだけ（Spec 10 不変条件と同じ）。
   予算切れの直後の新しい依頼は新しい予算で普通に走る
8. **天井の値は world.json の村レベル 1 フィールド**（`tokenBudget`、
   実効トークン建て、**型は `Option<u64>`**）。`None` = 天井なし /
   `Some(n)` = 天井あり — **0 というマジック値は使わない**（`Some(0)` は
   読み込み時に「即打ち切りの村」ではなく不正値として `None` へ倒し
   debug ログへ 1 行）。**既定 1,000,000 の書き込みは新規 world.json の
   作成時だけ**。既存の村は `None` のまま触らない（昨日まで完走していた
   8 段フローを今日から止めない — 挙動を黙って変えるならそれは
   パッチではなくメジャー改定）。根拠: 健全な 6 体依頼の実効換算 ≈ 250K の
   約 4 倍で、#41 型の暴走（素 2M）は確実に止まる。
   **`None` の村は起動時に WARN で 1 行**（INFO ではなく）、文言は次の道込み:
   「トークン予算なし（天井なし）— world.json の tokenBudget に
   1000000（推奨）を設定できます」。安全装置は opt-in でも、危険な状態を
   警告で可視化すれば実質 opt-out に近づく（unsafe を許す Rust と同じ構え）
9. **歯止めの優先順位**（同じ周回境界で複数が同時に成立したときの分類）:
   **cancel（interrupted）> budget_exhausted > RepeatGuard > hop / rounds 上限**。
   人の明示停止が最優先、次に資源の事実。検査もこの順で行い、先に成立した
   歯止めが `Reply.kind` を確定する（race の勝敗が分類を変えない — Spec 10 と
   同じ規律を静的な順序で担保する）

## 検証の設計（実装の前に決める）

- 計量の純関数（usage → milli 実効トークン → u64 切り上げ）: 重み・丸め・
  欠落 usage の三規程（prompt 欠落 = 送信 chars ÷ 4 / completion 欠落 =
  受信 chars ÷ 4（0 にしない）/ cached 区分なし = 全量未キャッシュ）を単体で
- BudgetPool: 並列減算（fetch_sub）・try_reserve と consume の分離下での
  オーバーシュート許容（飛行中 1 呼び出し分を超えて漏れない）・尽きの一回性
  （CAS — 2 スレッドが同時に尽きを観測しても打ち切り記録は 1 系統）・
  因果間の独立
- 結合: S1（1 体の暴走が止まりターンだけ閉じる）/ S2（cached 支配の
  ループが止まらない）/ S3（波の途中で尽き、answered と budget_exhausted が
  混在して束ねが返る）/ S4（予定発火の因果に予算が付く）/
  **転送先の封筒が同一の Arc を指す**（新 pool を作った瞬間に天井が蒸発する —
  delegation-fanout race の再現を止めるテスト）/ 同報が宛先ごとに独立 /
  **cancel と budget が同周回で同時成立したら kind は interrupted**
  （不変条件 9 の順序）
- world.json の読み込み: `Some(0)` が `None` へ正規化され debug ログに
  1 行出る / `None` の村の起動 WARN 行に推奨値と設定先が書いてある
- 加算的変更の回帰: 旧 7 値がそのまま読め、`budget_exhausted` が
  snake_case で往復する（Spec 10 の同型テストを拡張）
- 実機: 天井を小さく（例 50K）した村で調査依頼 → 会話ペインの System 行と
  作業状況ペインの新分類セルを観測。天井を戻して健全依頼が完走することも観測

## Notes（rev2 — D1〜D6 は査読で全決着。決定と残置理由）

- **D1 実効トークンの重み — 固定で確定**（査読承認）。重みは config ではなく
  data_contract の code constant として P0 で凍結し、将来変えるときは
  Spec 改定。モデル別設定にすると world.json に weights ブロックが生え
  （「設定を増やさない」に真っ向から反する）、BudgetPool のテスト行列が
  プロバイダ数 × 重みパターンに膨れる。課金の厳密性は追わない —
  Task Budgets 自体が示唆であって強制でない世界で、ハーネス側だけ
  課金厳密性を追う意味が薄い。「桁のヒューズ」が正しい用途規定
- **D2 既定値の適用 — 欠落 = 天井なしを維持で確定**（査読承認）。
  安全既定（既存の村へ 1M を書き足す）を採らないのは、それが
  後方互換破壊だから — 昨日まで完走していた 8 段フローが今日から
  budget_exhausted で止まるのは、main 直コミットのパッチ運用でやってよい
  変更ではない。緩和は 3 点セット: `Option<u64>` で危険な状態を型で可視化 /
  起動 WARN（INFO でない）に次の道を書く / 新規 world.json だけ
  Some(1,000,000)。**検討して見送った例外**: 予定発火（S4）だけ天井なしでも
  1M を強制する分岐 — 本 Spec の主目的（人が見ていない時間の安全）には
  最も適合するが、「同じ村で依頼元によって天井が違う」という説明の複雑さが
  v1 に見合わない。一律 None + WARN で始め、実運用で予定の暴走が観測されたら
  再検討
- **D3 日次・村全体の累積天井は範囲外 — 確定**（査読賛成）。永続化と時計が
  要り、因果単位の天井だけで「1 トリガーあたりの燃焼」は抑えられる。
  予定の多重登録による累積は Spec 07 の登録数が人の手にあるので人に残す
- **D4 残額の可視化は範囲外（v1）**: 進行中の残額表示は毎秒変わる数字の
  IPC/描画を増やす。v1 は「尽きたときに System 行」だけ。要望が実測されたら
  作業状況ペインへの投影を検討
- **D5 警告線（80% など）は入れない — 確定**（査読賛成)。警告を見て人が
  止めるなら Spec 10 が既にある。自動の天井に前振りは要らない
- **D6 hop 上限との関係 — 直交で確定**。既存の hop 上限・
  max_tool_iterations は残す。予算は「どれだけ深く/長く」ではなく
  「いくら使ったか」を縛る直交の歯止めで、どれかが最初に効けばよい。
  同時成立の分類は不変条件 9 の優先順位が決める
