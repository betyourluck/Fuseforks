**ID**: 10
**Date**: 2026-08-01
**Status**: **rev2 査読承認**（2026-08-01 LGTM）→ **Phase 0〜1 完了**（2026-08-01）。

Phase 1 = ターン局所の純機構 — `TurnHandle { seq, token }`・周回境界の検査・

子の Reply send 失敗は正常）。残は Phase 2（波への伝播）〜 Phase 4
**Branch**: なし（main へ Phase 単位で直接コミット — Spec 01〜09 と同じプロセス）

- **矛盾 4 件の解消** — 不変条件 1 の射程拡張（周回境界 + ターン開始直後）/
  不変条件 2 の 3 分割（飛行中・未着手・no-op で出口が違う）/

  `Reply { Interrupted }` 必須（drop で `NoAnswer` に化けるのは実装バグ）

- **未定義 3 件を機構で解消** — 親のキャンセルは `child_token` で自ターンへ

  出口の行は**切られたターン自身が検知時に 1 回書く**（二重割り込みが
  構造的に重複しない）

  `TurnInterrupted { agent_id, turn_seq }`

- 検証の述語を「飛行中の中断」と「未着手の畳み」で分離（後者は round 行 0 本が
  常態なので不在は証拠にならない）
- 計測を 1 つ追加: 割り込み要求から周回境界での検知までの elapsed を
  System 行へ載せる（LLM 呼び出し中の切断を別 Spec で入れるかの判断材料）

## Goal

**飛行中のターンを、ターンの完了を待たずに人が切れるようにする。**

CLAUDE.md「次の作業」の 2 番（2026-07-31 合意）。1（同一失敗の検出 =
`RepeatGuard`、完了）が病を直す側だったのに対し、これは症状（トークン燃焼）を
人の判断で止める側。機構が誤発火しても人が見ていれば止まる、という最後の網になる。

今は止める手段が **`stop_agent` しかない**。`stop_agent` は飛行中ターンの完了を
最大 30 秒待ち、待ちきれなければ受信箱だけ外して放置する（タスクは次のループ
まで自走を続ける）。つまり:

- **ターンの中身は 1 周も切れない。** ツールループは最大 `max_tool_iterations`
  周まで回り、1 周ごとに LLM 呼び出しが入る。周回の途中で介入する点が無い
- **plan の波は最悪 `ask_timeout`（既定 180 秒）まで待つ。** 進行役を
  `stop_agent` しても波の JoinSet は待ち続け、ワーカーは依頼を処理し続ける
- **止めたいのは大抵「今の仕事」であって「エージェント」ではない。**
  `stop_agent` は稼働ごと降ろすので、切ったあと使うには再起動が要り、
  Spec 03 の通り**会話が新規に始まる**（履歴ごと捨てる代償が付く）

### 立場の宣言

**打ち切りは協調的（cooperative）に限る。** `JoinHandle::abort` による強制中断は
採らない。理由は `stop_agent` が既に同じ判断をしているのと同じ —
ターンの途中には「呼び出しと結果を対で積む」（failures.md #29）や
`push_exchange`（#45）のような**壊してはいけない不変条件**があり、任意の await
点で切るとこれらが半端な状態で残る。切ってよい場所を機構の側が指定する。

**打ち切りには必ず出口を書く**（failures.md #44 の一般化 3 = 歯止めは
行き止まりを塞がない）。ただし rev1 の「出口 3 点セットを全経路で」は
**経路ごとに出すべきものが違う**という査読指摘（矛盾 C2）を受けて、
不変条件 2a〜2c に分割した。欠けてよい出口と欠けてはならない出口を
経路ごとに名指しする。

## 現状の構造（接地・2026-08-01 起票時）

- **ターンの実行単位は `handle_message`**（`orchestrator.rs`）。中のツールループは
  `for iteration in 0..max_tool_iterations` で、1 周 = LLM 呼び出し 1 回 +
  ツール実行 0〜N 本。周回の境界に介入点は無い
- **進行役は `run_plan` の JoinSet を join で待つ間、ツールループの外に居る**
  （rev2 で追記 — 周回境界の検査だけでは波の待ちを切れない。U2）
- **停止の既存機構は 2 つ**。`agent_loop` の `watch::Receiver<bool>`（`biased` で
  受信より優先。ただし見るのは**ターンとターンの間**だけ）と、`stop_agent` の
  受信箱除去 + 30 秒 join 待ち
- **`agent_loop` は mpsc を順次処理する = 1 エージェントに飛行中ターンは
  常に高々 1 つ**。`interrupt_turn(agent_id)` が引数 `agent_id` でターンを
  一意に特定できるのはこの性質が根拠（不変条件 7 として凍結する）
- **`deliver_and_wait` の解決分類は `PlanTaskState`**（`data_contract.yaml` で
  凍結済み: Running / Answered / HandedOff / Undeliverable / NoAnswer / TimedOut）。
  oneshot が dropped なら NoAnswer、時間切れなら TimedOut
- **失敗ターンの記録は `record_failed_turn`**。attributed だけを履歴へ積む
  （#45 の「残す穴」— 文脈を再構成できないため。キャッシュが 1 回リセットされる）
- **受信箱は `mpsc`**。積まれた封筒を後から抜く手段は無い
- **依存**: `CancellationToken` は tokio 本体に無い（確認 2 経路 —
  ローカル registry の tokio-1.52.3 `src/sync/` に不在 / docs.rs latest でも
  `tokio::sync` に該当なし）。実体は `tokio_util::sync::CancellationToken`
  （tokio-util 0.7.19。docs.rs で `child_token` の意味論も確認 —
  親の cancel は全ての子へ伝播する / 子の cancel は親へ遡らない /
  **cancel 済みの親から作った子は cancel 済みで生まれる**。3 点目は
  未着手封筒の畳み（不変条件 2b）がターン開始時の検査だけで成立する根拠）。
  **既に間接依存として Cargo.lock に居る** — 直接依存への昇格は
  新しいコンパイル対象を 1 つも増やさない

## Stories

### P1: ターンの割り込み（人 → 1 体）

> 利用者として、長いターンを回しているエージェントの「今の仕事」を
> 止められる。エージェントは稼働したまま残り、会話も履歴も消えない。

- 新 API **`interrupt_turn(agent_id)`**（rev2 確定）。切るのはターンであって
  エージェントではない、という本 Spec の核心を名前が運ぶ。引数が `agent_id` なのは
  今の構造で飛行中ターンを一意に指す手段がそれしか無いため（不変条件 7）。
  将来 `TurnId` が生まれたら引数だけ差し替わる。新 API なので互換の別名は作らない
- **飛行中のターンだけ**を切る。ターンが飛んでいなければ何もしない（エラーにも
  しない — 「今の仕事を止めて」に仕事が無いのは成功であって失敗ではない）
- 検査点は**ツールループの周回境界**（次の LLM 呼び出しを組み立てる前）。
  ここなら呼び出しと結果の対（#29）が必ず揃っており、`push_exchange` の
  不変条件（#45）も壊れない
- 飛行中の LLM 呼び出し・実行中のツールは**完走させる**（rev1 の判断を維持。
  Notes 2 に代替案と、入れるかを決めるための計測）
- 打ち切られたターンの終わり方（不変条件 2a）:
  - 会話ログへ **System の 1 行**。割り込み要求から検知までの elapsed を含める
    （例:「ユーザーの指示でこのターンを打ち切りました（要求から 12.3 秒）」）。
    この数字が Notes 2（LLM 呼び出し中の切断）を起票するかの判断材料になる
  - 履歴へは **`record_interrupted_turn`**（新設。`record_failed_turn` の文言を
    使い回さない — 失敗の文言だと次のターンの自分が「エラーが起きた」と誤読する。
    書くのは「ユーザーの指示で打ち切られた・依頼は未処理」だけ）
  - `CoreEvent::TurnInterrupted { agent_id, turn_seq }` を発行
  - まとめの LLM 呼び出しは**しない**（打ち切りの直後にもう 1 回課金しない。
    RepeatGuard の打ち切りと同じ判断）
- **出口の行は切られたターン自身が検知時に書く**。割り込んだ側は書かない。
  これにより二重割り込み・`interrupt_all` との重複・親トークン経由との重複が
  **構造的に** 1 行に収まる（U3。テストでも固定する）
- エージェントの状態は **Running のまま**。次の封筒は普通に処理する

### P2: plan の波への伝播（設計の主戦場）

> 利用者として、波を撒いた進行役を止めたら、その波のためだけに働いている
> ワーカーの仕事も止まると期待する。

**伝播の単位は「エージェント」ではなく「ターンの因果」**。進行役を切ったとき
止めてよいのは**この波が生んだ仕事だけ**で、ワーカーが並行して受けている
別の依頼（ユーザー直や他エージェントから）を巻き添えにしてはならない。

- 封筒（`Envelope`）に **`CancellationToken`** を載せる。進行役のターンが持つ
  トークンから `child_token` で子を導出して波の各封筒へ入れる。
  ワーカーのターンは**受け取った封筒のトークンからさらに自分の子を作り、
  それを自ターンのトークンとする** — 親のキャンセルも自分への直接の
  `interrupt_turn` も同じ 1 つのトークンに畳み込まれるので、
  **周回境界の検査は 1 トークンで足りる**（U1 の構造的解消。
  「自分宛」と「親由来」の 2 本を別々に見る設計は採らない — 片方を見忘れる
  未来のバグの席になる）
- **進行役の `run_plan` の join 待ちも select 化する**（U2）。自ターンの
  トークンで抜けられなければ、周回境界へ戻る前の最大 `ask_timeout` が
  割り込み不能のまま残る。抜けたら子トークンを cancel し、束ねは作らず
  （部分的な束ねを履歴へ積むと、次のターンの進行役が「全員から答えが揃った」と
  誤読する）、未解決タスクは `finish_wave` が **Interrupted に倒して**波を閉じる
  （Spec 08 の「永遠の Running を残さない」を維持。倒し先が NoAnswer でないのは、
  答えなかったのではなく止めさせたから）。
  **親が先に Interrupted で確定した後、子の `Reply { Interrupted }` の send は
  receiver drop で失敗するが、これは正常**（承認時追記 — 「drop は実装バグ」の
  射程は**ワーカーが送らないこと**であって、確定済みの親が受け取らないことでは
  ない。子は send の失敗を無視してよい。結果はどちらの経路でも Interrupted で
  一致しており、race の勝敗が分類を変えない）
- **まだ受信箱の中の封筒**（ワーカーが別の仕事で塞がっていて未着手）は、
  ワーカーがターン開始直後にキャンセル済みを検知して **LLM を 1 回も呼ばずに
  畳む**。mpsc から封筒を抜く機構は作らない（抜けない構造は変えず、着手時に見る）。
  畳みの出口は不変条件 2b（飛行中とは出すものが違う）
- 進行役自身は P1 の規則で終わる

### P3: 解決分類への追加

> 波ペインを見る利用者として、「答えなかった」と「途中で止めさせた」を
> 区別できる。

- `PlanTaskState` へ **`Interrupted`** を追加する（契約変更）。完了条件:
  - `data_contract.yaml` の enum へ追加 + 遷移の注記
  - `PlanTaskState` で全台帳・全実装を grep し、UI の色・波ペインの凡例・
    集計の全ヒットを改修
  - **加算的変更であることのテスト**を Phase 4 に置く — 旧レコードの
    マイグレーションは不要で、既存の `finish_wave` により旧 `Running` が
    永遠に残ることもない、を回帰で固定
- 文言での区別は採らない — Spec 08 で「分類は文言 parse でなく型で運ぶ」と
  決めた線をここでも守る
- 依頼主（進行役）が読む本文は事実だけを書く:
  「この依頼はユーザーの指示で打ち切られました。答えはありません」

### P4: 全体停止（人 → 村）

> 利用者として、村全体の仕事を 1 操作で止められる。

- `interrupt_all()`。全エージェントへ P1 を適用するだけの薄い皮。
  新しい機構は持たない（P1 の for 文であること自体が仕様）
- **冪等**（rev2 で確定）: 飛行中ターンが 1 つも無くても全体として成功。
  進行役とワーカーが親子で二重に切られても、出口の行は各ターンが検知時に
  1 回書くだけなので重複しない（P1 の構造保証に乗る。独自の重複排除は持たない）

### P5: `stop_agent` の高速化（副産物）

> 利用者として、停止ボタンが 30 秒黙る場面が減る。

- `stop_agent` は最初に飛行中ターンへ割り込みを立ててから join を待つ。
  30 秒の上限はそのまま残す（割り込みが効かない異常系の網として）
- この経路の打ち切りは不変条件 4 の但し書き側 — ステータスは Running に
  戻らず、`stop_agent` 本来の Stopping → Idle へ進む

## 機構の要点（Phase 0 で凍結する不変条件）

1. **検査点は 2 箇所のみ** — `handle_message` のツールループ周回境界
   （+ `run_plan` の join 待ちの select。これは周回境界の待ち時間内の検査点で、
   検査するトークンは同じ）と、**ターン開始直後**（未着手封筒の畳み）。
   どちらの点でも呼び出しと結果の対（#29）・送信と保存の一致（#45）は
   構造的に壊れない（rev1 の「周回境界だけ」は P2 の畳みと矛盾していた — C1）
2. **出口は経路ごとに定める**（rev1 の一律 3 点セットは経路間で矛盾した — C2）:
   - **2a. 飛行中に中断されたターン**: (a) 会話ログへ System の 1 行
     （elapsed 含む） (b) 履歴へ `record_interrupted_turn` の注記
     (c) 依頼主が居れば `Reply { kind: Interrupted }`。3 点とも必須
   - **2b. 未着手で畳まれた封筒**: (c) 依頼主への `Reply { kind: Interrupted }`
     **だけが必須**。会話ログへは出さず、履歴にも積まない（そのターンは
     始まっていないので「ターンの記録」が存在しない。依頼が消えたように
     見える問題は、依頼主側のセルが Interrupted で確定することで解決する）。
     debug ログへ 1 行（`turn folded:` — 会話に出さない事実の記録先は
     Spec 07 rev2 の「猶予超過は debug ログへ」と同じ判断）。
     **Reply を送らず drop すると親が `NoAnswer` に誤分類する。drop は
     実装バグと定義する**（C4）。
     **`CoreEvent::TurnInterrupted` はこの経路では出さない**（承認時追記 —
     ターンは中断されていない。始まらなかっただけ。出すと U3 の
     「1 中断 = 1 イベント」の数えが壊れる）
   - **2c. no-op**（飛行中ターンの無い `interrupt_turn`）: 何も出さない。成功
3. **伝播はターンの因果を辿る**。エージェント単位で殺さない。
   波の子タスクの巻き添え範囲 = その波が配送した封筒 + そこから派生した委譲のみ。
   親のキャンセルは `child_token` の連鎖で末端まで届く
4. **打ち切りは失敗ではない**。`AgentFailed` を出さない・`last_error` に書かない・
   ステータスは Running のまま。**ただし `stop_agent` 経由はこの限りではない**
   （Stopping → Idle へ進む。ここを但し書きしないと `stop_agent` が
   エージェントを止められなくなる — C3）
5. **自動では発火しない**。割り込みの起点は人の操作だけ（CLAUDE.md の
   「止める側の作業が終わるまで、自動で仕事を増やす機構は入れない」と対。
   自動判断で仕事を切る機構も同様に入れない — 誤発火の被害が「勝手に増える」
   から「勝手に消える」に変わるだけで、予測できない点は同じ）
6. **割り込みの有効範囲はターン seq に束縛する**。`TurnHandle { seq, token }` を
   ターン開始時に発行し（seq は単調増加）、検査は「自分の seq のトークン」しか
   見ない。エージェントに紐づくフラグを置かない — 置くと「ターン A への
   割り込みが直後に始まったターン B に漏れる」事故と、P2 の巻き添え禁止の
   両方が壊れる（rev1 Note 7 を不変条件へ昇格）
7. **1 エージェント 1 飛行中ターン**。`agent_loop` の mpsc 順次処理が根拠。
   `interrupt_turn(agent_id)` の API はこの前提の上に立つ — 並行ターンを
   導入する変更はこの Spec の API を壊す、と契約に明記する

## 検証の設計（実装の前に決める）

#45 の一般化 3（容疑を潰したと言えるのは、その容疑を検出できる計装が
あるときだけ）をここに適用する。「止まった」と「止まったように見える」は
画面上で区別が付かない。**述語は経路ごとに分ける**（rev2 — 未着手の畳みは
round 行が元々 0 本なので「増えない」は証拠にならない。C 細部 3）:

- **飛行中の中断**: `note_cache_diag` の round 行が割り込み後に増えないこと
  （実機）。結合テストではモックバックエンドの呼び出し回数が割り込み後に
  増えないことを述語にする — 「ターンが終わった」を述語にすると完走した場合でも
  通ってしまう（#45 の一般化 4）
- **未着手の畳み**: モックバックエンドが**その封筒について 1 回も呼ばれない**こと
  + 依頼主側の `PlanTaskState` が `Interrupted` で確定すること + debug ログの
  `turn folded:` 行。round 行の不在は使わない
- **結合テスト（rev2 で 2 本追加）**:
  1. **巻き添え禁止**: ワーカーがユーザー直の依頼 A と波の依頼 B を持つ状態で
     進行役を切る。B は `Interrupted`、A は完走して `Answered` になること
  2. **二重割り込み**: 割り込み済みのターンへもう一度 `interrupt_turn` しても
     System 行が 2 本にならないこと（`interrupt_all` と親トークンの重複も同型）

## Notes（rev2 時点の未決と、決めた事の残置理由）

1. **（解決済み）API 名** — `interrupt_turn(agent_id)`。査読の判断:
   「伝播単位はエージェントではない」が Spec の核心なので、API 名で嘘をつくと
   後の実装者がまたエージェント単位で考える
2. **LLM 呼び出し中の打ち切り** — rev1 の判断を維持し**入れない**。
   `select!` で HTTP ごと切る案は、(a) `reqwest` の drop がストリーミングの
   途中でどう始末されるか (b) プロバイダ側の課金がどの時点で確定するか、の
   2 点を確かめてからでないと入れられない。**判断材料は 2a の elapsed 計測**で
   取る — 周回境界だけの検知遅延が 1 秒未満に収まっているなら困っていない。
   分単位が頻発するなら別 Spec で起票する
3. **ツール実行中の打ち切り** — rev1 と同じく入れない。同梱ツールは短時間で
   終わる。長いのは MCP の外部ツールだが、子プロセスの中断は別の主題
   （プロセス管理）を持ち込むので、必要が実測で出てから起票する
4. **（解決済み）未着手封筒の畳み方** — 不変条件 2b へ。rev1 の
   「System 1 行だけ残す」は撤回（畳んだ側の会話ログには何も出さない。
   依頼の可視性は依頼主側の Interrupted セルが担う）
5. **（解決済み）`record_failed_turn` との関係** — `record_interrupted_turn` を
   新設。P1 に記載
6. **キャッシュへの影響 — Phase 1 実装で rev2 の想定より良い事実が確定した。**
   rev2 は「失敗ターンと同じく attributed だけを積む = リセット 1 回」と
   書いたが、**打ち切りの検知点では組み立てが済んでいる**ので、失敗経路と
   違って送った形（`sent_user_turn`）が手元にある。縮める理由が無いので
   そのまま積む — 受信側の前方一致は切れず、**キャッシュのリセットは
   起きない**（切られたターンの位置までのプレフィックスは次のターンでも
   一致する）。attributed へ縮めるのは `record_failed_turn`（組み立て前に
   落ちうる経路）だけになった。固定は
   an_interrupt_cuts_the_turn_at_the_round_boundary の履歴検証
7. **（不変条件 6 へ昇格）割り込みの競合** — seq 束縛として凍結
8. **拡張か収縮か**（起票時の自問）: 拡張。ただし「止める」方向の拡張で、
   自動で仕事を増やす機構は含まない。収縮側の代替（既存の `stop_agent` だけで
   済ませる）は Goal に書いた 3 点（周回を切れない・波を待つ・稼働ごと落ちて
   会話が消える）により棄却
