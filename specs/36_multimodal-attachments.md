## Goal

入力欄の添付を画像（Spec 23）から**音声・動画・PDF**へ広げる。

起点は利用者裁定の順番（2026-08-09 の v0.2.0 三分 → 2026-08-12 の
「英語化 → 多モーダル」）。Thinking 3 部作（Spec 32〜34）と英語化（Spec 35）が
Done になり、順番がここへ来た。

**Goal の形は Spec 23 と同じ 2 本 + 新しい 1 本**:

- **使わない村の固定費はゼロ** — ツールを 1 本も増やさない。モデルへ提示する
  スキーマもシステムプロンプトも 1 字も伸びない。**添付が無い発話の
  シリアライズ結果は今日とバイト等価**（Spec 23 P2 の golden がそのまま網になる）
- **払うのは添付した人だけ、その 1 ターンだけ**（D1 据え置き）。音声・動画は
  画像より**桁が上がる**ので、この規律は緩むのではなく**強く**効く
- **送れない場所へ黙って落とさない**（新設。[Spec 34](34_openai-responses.md) D8 が
  本 Spec へ明示的に渡した宿題）— 現状、Responses ワイヤの個体へ画像を貼ると
  **黙って落ちる**（Gemini / xAI / OpenAI の 3 例目まで確認済み。Spec 34 検収 7）。
  多モーダルで種別が 4 つに増えると、この「黙って落ちる」の組み合わせは
  放置すれば掛け算で増える。**「どのワイヤがどの種別を運ぶか」を述語にするのが
  本 Spec の構造の本体**

**読み方 2 点**:

- **動画を受けるのは Gemini ネイティブだけ**（予測）。動画を scope に入れるなら
  Spec 23 D8（Gemini ネイティブに添付を実装しない）を**覆すしかない**（D8）
- **音声は「ワイヤが受ける」と「モデルが受ける」が別**（OpenAI は音声対応モデル
  限定）。述語で守れるのは前者だけで、後者は 400 を画面へ出す（設計の核の 2 層）

### P0 実測結果（2026-08-12。probe 18 セル。**全 20 マス確定**）

判定は全て**内容の照合**（WebP = 左赤・右青の矩形 / WAV = TTS の合言葉
「ガーネット」7.6 秒 / MP4 = 赤 2 秒 → 青 2 秒の 320×240 / PDF = 本文に
`GARNET-77`）。素材は使い捨てを生成（ffmpeg + System.Speech + 手書き PDF 671B）。

|---|---|---|---|---|

| `Anthropic` | ✓（Spec 23 P0） | **✗**（列挙に無い） | **✗**（同） | **◎**（`document` で `GARNET-77`。input 1,633 tok / 頁 = 公式の 1,500〜3,000 帯内） |
| `Gemini` | **◎**（左赤・右青） | **◎**（「ガーネット」） | **◎**（「赤、青」） | **◎**（`GARNET-77`） |

**予測と観測の差分（外れは 2 つ + 未知の確定 3 つ）**:

1. **xAI Responses の PDF は通る**（予測 ✗ → 観測 ◎。input 1,496 tokens）。
   xAI の「文書は画像のみ」が実装と食い違う **2 例目**（1 例目は Spec 23 の WebP。
   本走行で WebP も 3 度目の通過）。**文書を根拠に ✗ を凍結しなくてよかった** —
   rev2 査読 8（省略条件の厳密化）が実測で正当化された形
2. **Gemini 互換口は音声が通る**（? → ✓。「ガーネット」まで返った）。
   PDF は `Invalid content part type: file` で ✗（? → ✗）。**同じ互換口でも
   part の種類ごとに受理が割れる** — 「互換だから同じ」はここでも成立しない
3. OpenAI Responses の音声は**型が存在しない**（? → ✗）。400 の列挙が
   `input_text / input_image / output_text / refusal / input_file /
   computer_screenshot / summary_text / encrypted_content` — `input_audio` 不在

**設計の 2 層が実物で観測できた**（oai_compat/audio の 1 発）— 互換口の列挙は
`text / image_url / input_audio / refusal / audio / file` で **`input_audio` は
ワイヤに実在する**（= carries ✓）のに、gpt-5.6-luna は「text か image_url だけ」と
断った（= **モデルの受理は別の層**。この 400 が画面へ出るべきもの）。

**受理集合の列挙という手筋（Spec 34）には適用範囲があった** — OpenAI は
誤った型 1 つで全列挙を返すが、**xAI は untagged enum のデシリアライズ失敗
（422）で、何も列挙しない**。列挙で受理集合を確定できるのは OpenAI 系の
実装様式だけ。xAI の ✗ は「どの variant にも一致しない」からの構造的判定。

**トークンの実測（Notes 1 の予測を部分的に置き換える）**:

| 観測 | 値 | 予測との差 |
|---|---|---|
| Gemini 音声 7.6 秒 | AUDIO 228 tok ≈ **30/秒** | 公称 32/秒どおり |
| Gemini 動画 4 秒（320×240） | VIDEO 252 tok ≈ **63/秒** | **公称 260〜300 の 1/4** — 解像度依存と読める。長辺の大きい実写では公称側を見込む |
| Gemini PDF 1 頁 | IMAGE **520** tok | 予測 258/頁の **2 倍** — 頁の描画解像度依存 |
| Gemini WebP 320×240 | IMAGE 1,064 tok | 画像は小さくても高い |
| OpenAI Responses 画像 | input 計 130 | Gemini の 1/8 — 社ごとに桁が違う |

**Anthropic の 3 マスは probe 2 発で閉じた**（同日。鍵は env へ利用者が配置）。
PDF は `GARNET-77` を内容照合まで返し、誤った型 1 発の 400 が受理集合を列挙
（`document / image / text / search_result / container_upload / …` —
**音声・動画の variant が無い**）。**Anthropic は OpenAI 系の列挙様式**で、
1 発で 2 マスが構造確定した（xAI の untagged 422 と対照的）。

### 公式文書との突き合わせ（2026-08-12 利用者査読。**観測 20 マスすべて公式仕様と整合**）

- **Gemini**: `inlineData` の mime 許容リストに 4 種別すべてが並ぶ（音声 8.4h /
  動画 1h までの定義つき）。**63 tok/秒の機序も公式にあった** —
  `mediaResolution` の LOW/MEDIUM/HIGH で、低解像度はトークンが 1/4 になる。
  公称 260〜300 は HIGH 時の値。**S6 の注記は HIGH 側の桁で書く**
- **OpenAI Responses**: Overview が「text and image inputs」と明言 —
  音声 ✗ は文書とも一致。PDF は File inputs ガイドの正規例
- **OpenAI 互換**: `input_audio` は `gpt-4o-audio-preview` 系向けの正規形 =
  「形は実在・モデル依存」の観測どおり。**PDF は 1 ファイル 50MB まで**
- **xAI**: 公式は Image understanding のみ（jpg/png・20MiB）。**PDF の記述は
  一切無いのに通った** = 文書と実装の乖離 2 例目で確定
- **Anthropic**: PDF は `document` で 32MB / URL・base64・file_id の 3 経路が公式
- **D4 の「最狭 = Gemini 20MB」が確定** — PDF の各社上限は OpenAI 50MB /
  Anthropic 32MB / **Gemini 20MB（インライン要求全体）**。種別 1 門の基準は動かない

## 設計の核

**種別を閉じた列挙で増やし、「どのワイヤがどの種別を運べるか」を 1 実装の述語で
持つ。構造の可否は送信の入口で断り、モデルの受理は 400 を画面へ出す。**

```
入力欄（貼り付け / 参照…）
  → 種別判定（magic）。画像だけ WebP へ変換（既存 worker）、他は無変換
  → send_user_message(…, attachments)
  → 【入口の検査】宛先のワイヤ × 種別を carries で判定
      ├─ 運べない → 発話ごと拒否。ここで終了 —
      │   保存しない・発話を記録しない・ターンを起こさない。
      │   出るのは IPC エラー（画面の辞書文言）と
      │   計器 `attachment kind: … outcome=rejected` の 1 行だけ
      └─ 運べる ↓
  → {workspace}/attachments/{uuid}.{ext} へ保存（バックエンドで再検証）
      ext は保存形式から決める: 画像 = 変換後 .webp 固定（Spec 23 既存のまま）、
      音声 / 動画 / PDF = magic 判定から .mp3 / .wav / .mp4 / .pdf。
      **利用者のファイル名の拡張子は信用しない**（判定は常に magic）
  → 発話の記録 → そのターンのプロンプト組み立て時だけブロックへ展開
  → 履歴（Record::Exchange.sent）へは入れない          ← D1 据え置き
```

（rev2 — 査読 1。旧図は拒否の後ろに保存が並び、拒否時に保存・記録が走るとも
読めた。**拒否時は保存もターンも無く、計器の 1 行と画面のエラーだけ**。
P6-4 はこの「rejected 行あり + turn 行なし」を**対で**読む。査読 6 の
保存 ext の規則もここへ固定した）

検査の 2 層（Spec 20 の「fail closed は提示ではなく decide が守る」と同じ分業）:

| 層 | 何を守るか | どこで | 失敗の見え方 |
|---|---|---|---|
| **述語 `carries(provider, kind)`** | ワイヤに**書ける形があるか**（構造） | 送信の入口（保存・記録より前） | 発話ごと拒否 + 辞書の文言 + `outcome=rejected` の計器 |
| **プロバイダの 400** | **そのモデルが受理するか** | 送ってみた結果 | 400 本文を画面へ（Spec 23 S5 と同じ「黙って落ちない」） |

述語を分けずに「送ってみて 400」へ全部倒さない理由 — Anthropic へ音声を送る形は
**ワイヤに存在しない**（`AnthropicRequestBlock` に音声の variant が無い）ので、
そこは 400 ではなく**こちらのシリアライズが決める**。構造的に不可能なものを
実行時エラーの層で扱うと、「たまたま拒否された」と「原理的に送れない」が
画面で区別できなくなる（`AGENT_NOT_FOUND` と `EXTERNAL_RECEPTION_UNSET` を
分けたのと同じ判断）。

## 決めること

- **D1（据え置き）添付は 1 ターン限り。履歴に残さない。** 画像で 1,736〜4,784
  だったものが、音声 1 分 ≈ 1,900・**動画 1 分 ≈ 16,000**（Gemini 予測値）になる。
  滑る窓 8 往復に残すと動画 1 本が **≈126,000 トークン**の再送に化ける。
  Spec 23 の「払う量と人の操作の 1 対 1 対応」はそのまま。
  **【添付】の 1 行（添付があった事実の印）も種別語を広げて据え置く** —
  「もう手元に無い」と言える材料を残す（Spec 23 の「実機で出た穴」の一般化）
- **D2（本 Spec の構造の本体）`carries(provider, kind)` を 1 実装で持つ。**
  読み手は 3 つ — **送信入口の拒否** / **フロントの警告表示**（D12。表は TS へ
  写すが機械で同期）/ **テスト**（表の凍結）。
  **転送（D6）は読み手ではない**（rev2 — 査読 2。D6 は宛先が運べる種別でも
  一律 Drop なので、転送の断り書きに述語は要らない。旧 rev1 は読み手に
  転送を数えており、D6 の「一律」と矛盾していた）。
  **表は 4 種別 × 5 ワイヤの全 20 マスを閉じて凍結し、P0 の実測で埋める**。
  Spec 34 D8 が「先に作るな、多モーダルの Spec が 3 件の材料で設計しろ」と
  書いた当の述語。**提示と判定の集合を分けない**（ずれると Spec 20 の形）
- **D3 変換しない。形式は閉じた列挙。** 音声 = **mp3 / wav**、動画 = **mp4**、
  PDF = **pdf**。判定は magic（`ID3`/フレーム同期・`RIFF….WAVE`・`ftyp`・`%PDF-`）。
  **JPEG フォールバックの同型は作らない** — 画像の再エンコードは worker に
  道具があったが、音声・動画の変換器を同梱するのは依存の桁が違う
  （ffmpeg 系は純 Rust で揃わない）。受け付けない形式は入口で断る。
  **フロントの変換は画像のみ現状維持**
- **D4 サイズ上限は種別ごとに 1 つ。ワイヤ別の門は作らない。**
  仮置き（P0 で確定）: **PDF 10MB / 音声 10MB / 動画 12MB**。
  基準は**その種別を運ぶ最も狭いワイヤ**（= Gemini のインライン 20MB）で、
  **余白まで数えて置く**（rev2 — 査読 3。旧 rev1 の動画 14MB は
  base64 で 18.7MB になり、プロンプトが乗ると 20MB を超えうる計算漏れ）:

  | 種別 | 上限（生） | base64 後 | 20MB までの余白 |
  |---|---|---|---|
  | 動画 12MB | 12MB | 16.0MB | 4.0MB（システム + 履歴 + JSON の枠） |
  | 音声 10MB | 10MB | 13.3MB | 6.7MB |
  | PDF 10MB | 10MB | 13.3MB | 6.7MB（Anthropic の 32MB より狭いが、Gemini も運ぶ以上ここが天井） |

  **ワイヤ別にしない理由**: 門をワイヤ別にすると**同じファイルが宛先によって
  通ったり通らなかったりする**。carries の断り（種別が構造的に送れない）は
  理由を画面で言えるが、「この宛先ではサイズ超過」は利用者から見て
  規則が読めない。1 つの門なら「このファイルは大きすぎる」で閉じる。
  代償は PDF が Anthropic 単独なら許される 32MB を使えないこと — 許容する
  （P0 実測で 20MB が本当に要求総量の天井かも確かめる）。
  `ATTACHMENT_MAX_BYTES`（2MB）の**値は触らない**が**名前は改名する**（D13）
- **D5（据え置き）1 発話 1 添付。型は `Vec` のまま、保証は入口が持つ。**
  （rev2 — 査読 5）`Option<Attachment>` へは変えない — `AgentMessage.attachments`
  は redb の `Record::Message` に既に載っており、型を変えると既存レコードと
  非互換になる（Spec 23 D1 根拠 1 と同じ形）。1 件保証は Spec 23 と同じく
  送信入口の検査（2 件目は拒否）で、**「2 件は拒否される」をテストで凍結**して
  「Vec だから複数対応」という将来の誤読を機械で止める。種別の混在も無し
- **D6（据え置き + 一般化）転送・委譲では、宛先が運べる種別でも一律渡さない。
  System 行で知らせる。**（rev2 — 査読 2 の推奨を採用）根拠は D1 と同じ因果 —
  転送で渡すと 1 回の添付が N ターンの支払いに化け、「払う量と人の操作の
  1 対 1 対応」が切れる。展開が読むのは**そのターンの受信の参照だけ**という
  D1 の構造もそのまま使える。分業を固定する: **転送は常に Drop、
  `carries` は入口だけが読む**。`note_dropped_attachment` の文言を
  「画像」から種別語へ一般化。**新しい文字列は 2 言語で書く**（Spec 35。
  `Language` の match — 既存 4 例目の逃げ道と同じ形）
- **D7（据え置き）広場ログには存在だけ**（`（音声 1 件）` 等）
- **D8 Spec 23 D8 を覆す — Gemini ネイティブに `inline_data` を生やす。**
  **覆したと明記して覆す**（#56 の規律）。当時の根拠は「ネイティブ経路が要るのは
