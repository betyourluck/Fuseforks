## 何がしたいか（利用者の言葉・2026-08-03）

入口は**タイトルバーの「条例」の次くらい**。Role は 2 役を兼ねる。

1. **サーヴァントを作るときのテンプレート**（雛形としての Role）
2. **サーヴァント自身の判断基準** —「このサーヴァントはこういう役割なんだ」を
   本人が読む。つまり**プロンプト素材**になる

## 決めるべきこと（**これが決まるまで設計に入らない**）

### 主論点: Role は「コピー」か「参照」か

Role が (1) 雛形 かつ (2) プロンプト素材なら、**作成時に本文を `Construct.md` へ
流し込むだけで両方満たせる**。`Construct.md` は既に「安定部分に入る自由テキストの
プロンプト素材」で、`ConfigFileKind::construct` として IPC も UI も存在する
（`data_contract.yaml` の `ConfigFileKind`、`types.ts:483`）。

| | コピー方式 | 参照方式（`AgentSpec.role` を毎回引く） |
|---|---|---|
| コアの変更 | **ゼロ** | `compose_system_prompt` の連結順を改訂 |
| 契約の変更 | **ゼロ** | `ordinance_contract` の連結順 + `stable_len` の再定義 |
| ワイヤ | **ゼロ** | Rust / TS / data_contract の 3 系統 |
| キャッシュ境界 | **触れない** | 動く（下の (1) を参照） |
| Role を後から直したとき | **既に居る個体には伝わらない** | 全員に効く |

**線の引き方は「後から直したとき既存のサーヴァントに反映されてほしいか」の 1 問。**

**この草案の推し = コピー方式。** 根拠は 1 つで、**条例が既に「後から直すと全員に
効く共有規則」の役を担っている**こと。参照方式は同じ性質の層を 2 つにするので、
「設定を増やさない」軸と正面から衝突する。収縮側の選択肢を先に検討する規律から、
**既定はコピー、参照が要る根拠が出たときだけ昇格**とする。

> 反証の口: 「役職の定義を直したら全員に効いてほしい」が実運用で 1 回でも出たら、
> コピー方式は間違い。**その一言が出るまでは出ていない**ので、今は安いほうを採る。

## 起票前調査の結果（2026-08-03・コードで接地済み）

### (1) 挿入点とキャッシュ境界

安定素材の連結順は 条例 → あなたについて → 作業フォルダ → 接地 → Construct → Skill。
`crates/agent-core/src/config_store.rs:383` が**その末尾で `stable_len` を確定**させ、
顔ぶれと Memory はその後ろ = **キャッシュ境界の外**。

参照方式を採る場合、自分の Role は安定側が正しい（1 ターンでは変わらない）。ただし
**上へ置くほど、Role を編集したときに割れる安定プレフィックスが長くなる**。
条例の直下ならその個体の安定部分がほぼ全部、`stable_len` の直前（Skill の後ろ）なら
割れるのは Role の分だけ。**しかし意味の序列とは逆**で、「あなたについて」の直後が
読み手の自然な位置。手順書（Skill）の後ろに人格の定義が来るのは読みにくい。

**決め方の順序を間違えないこと**: 先に **Role の編集頻度**を決め、それから位置を
決める。逆にすると根拠なしで位置が決まる。

### (2) 他人の役職を見せるか（Spec 06 の拡張）

顔ぶれは `crates/agent-core/src/orchestrator.rs:3023` で
`{id}（表示名）: 状態` として組まれ、`stable_len` の**後ろ**に置かれる
（`config_store.rs:385` に「可変部分に置くので stable_len は据え置き」と明記）。

- ゆえに**役職を足してもキャッシュ境界は動かない**
- 増えるのは**量**。毎ターン・全エージェント・素の値段で、接続 N 体ぶんの役職文字列
- **#45 の規律への抵触の仕方が違う。** #45 と論文 1 が問題にしたのは
  「毎ターン**形が変わる**ものを差し込む」こと。Role は毎ターン変わらないので、
  抵触するのは**揺れではなく量**。同じ規律で自動的に却下はできない
- **安い代案が 1 つある**: 役職を**表示名に混ぜる**（「ザリ（調査）」）。
  機構ゼロ・増分最小・Spec 06 の契約を触らない
- **実測の口がある**: 顔ぶれに役職を足した村と足さない村で、plan の宛先の
  取り違えが減るか。機構を足す前にこれを測れる

### (3) 進行役フラグにしない — コードは既にそう書いてある

`crates/agent-core/src/orchestrator.rs:5030` の `self.entries.len() >= 2` が
plan の発火条件で、5025 行の doc コメントが
**「『進行役フラグ』のような設定は足さない」**と明記済み。

**起票時にやるべきは新しい判断ではなく凍結**。`data_contract.yaml` へ
「**Role は配送・権限・ツール提示のどの分岐にも入らない**」を書く。これが無いと、
後から「進行役 Role なら plan を出す」が自然に見えてくる。ここが混ざると
AdaptOrch を採らなかった根拠（線は人が引く）ごと崩れる。

## 起票するときに書くこと

- Goal は「役割を**人が**与えられるようにする」であって「役割で**振る舞いを
  変える**」ではない。この 1 行で (3) の逸脱を最初から塞ぐ
- 収縮側の選択肢を明記する（**機構を足さずに `Construct.md` の雛形だけで足りないか**）
- 「他人の役職」は**別 Phase か別 Spec**に切る。自分の Role と相乗りさせると、
  可変注入の是非という別の論点が Goal に混ざる
- UI の入口は未定。「条例の次くらい」は利用者の感触であって決定ではない
