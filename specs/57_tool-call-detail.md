## Goal

1. **会話ペインのツール行を開くと、モデルが送った引数と、モデルへ返した本文が読める。**
   今の行は「成否のドット・実行者・ツール名・理由・時刻」の 1 行で、クリックしても
   何も開かない。`grep` が何を探したか、`run` が何を出力したかは画面のどこにも無い
2. **ターンを終えた個体の連続したツール行は 1 行へ畳まれ、押せば今と同じ行が並ぶ。**
   走っている最中の個体の行は畳まない（**既定で畳む** = 2026-09-21 利用者裁定）
3. **引数と出力は、ログにも `sessions.redb` にも書き出しにも残らない。**
   `failures.md` #71（計器がモデルの本文をログへ写し、`Authorization: Bearer …` が
   平文で残った）の線を動かさない

**やらないこと（範囲外）**: 引数・出力の永続化（アプリを再起動すると詳細は消える。
ツール行そのものが今も再起動で消えるのと同じ寿命）/ GUI の再読み込み後にツール行を
復元すること（Notes 2）/ `fuseforks.log` への引数の出力（`tool:` 行は `args_chars` /
`body_chars` の字数のまま）/ 欄ごとの「出してよい引数」の許容表（Notes 1 で退けた）/
ツール行を会話で非表示にするスイッチ（Spec 13 の候補のまま別件）/ 実行中のコマンド
出力の逐次表示（`run` は完了してから 1 回で返る）。

## Design

### D1. 開くのは行。中身は「モデルが送った引数」と「モデルへ返した本文」の 2 つ

- **入力 = `call.args`。** コアは欄を足しも除きもしない。`reason` 欄も除かない
  （行に出ている理由と重複するが、**「モデルが実際に送ったもの」と 1 文字でも違う
  ものを入力と呼ばない**）
- **出力 = モデルへ `tool_result` として返した文字列。** ツールが `Ok(text)` を
  返したときはその `text`、**`Err` を返したときはコアが
  `ツールの実行に失敗しました: {err}` へ組み直した文**（`turn.rs:2167`）。
  後者はツールの返り値そのものではなくコアの合成だが、**モデルが読んだのは
  この文字列**なので同じ欄に出す。`Ok` / `Err` の別は行のドット（`ok`）が運ぶ
- `run` の出力は既に stderr 4,000 + stdout 8,000 の固定枠で組まれており、
  その本文をそのまま出す。**コマンド出力のための別経路は作らない**

### D2. 置き場はコアの in-memory リング。イベントは `call_id` だけを足す

`crates/fuseforks-core/src/tool_calls.rs` に `ToolCallStore`（純機構）を新設し、
`Shared` に 1 欄持つ。形は `PlanWaveStore` と同じ。

- **`ToolInvoked` に足すのは `call_id: u64` の 1 欄だけ**（加算。既存 4 欄は動かさない）。
  1 始まり・単調増加・プロセス寿命。**採番は `ToolCallStore::record` の中**
  （ロックの中で振るので、並行するターンでも重複しない）。再起動で振り直すが、
  フロントは id を保存しないので食い違わない（`plan_id` と同じ性質）
- **引数と本文をイベントに載せない理由は 3 つ**（実測 6）— (a) 橋は `Lagged` を
  捨てるので、載せた本文は取りこぼすと復元できない (b) `broadcast` は購読者ごとに
  clone するので、p99 19,754 字・最大 193,264 字が読まないティッカーにも複製される
  (c) 開かれない行が大半なのに全件を WebView へ送ることになる
- **記録する点は 1 つ = `ToolInvoked` を emit する直前**（`turn.rs:2196` へ向かう
  合流点。実測 7）。**`Executed(body)` を返す箇所ではない** — `:2083` の提示外の
  返事も `Executed` だが行を出さないので、そこで記録すると開く入口の無い詳細が溜まる
- **並びは 実行 → `body` の確定 → `record`（`call_id` が返る）→ emit →
  `tool:` 行 → RepeatGuard。** 動かすのは emit の位置だけで、`tool:` 行と
  RepeatGuard は今の位置のまま。emit が `record` より先だと、行が出た瞬間に
  押した人が「詳細なし」を引く

### D3. 残さない — ログ・`sessions.redb`・書き出しのどれにも出さない

**線は「運ぶのは可、残すのは不可」。** `tool_reason_contract` は既に
「ログには字数だけ。**画面には出す** — 画面は人が見せると決めて撮るもので、
自動で残り続けるログとは性質が違う」と凍結している。本 Spec はこの 1 行を
理由（60 字）から引数と出力へ延長するだけで、新しい裁定は作らない。

- `fuseforks.log`: **変更なし**（`tool:` 行は字数のまま）
- `sessions.redb` / `export_session`: **`Record` に種別を足さない**
- 他のイベント・広場ログ・履歴: 載せない
- **`ConversationCleared` を出す 2 箇所（実測 10）でリングを空にする。**
  会話を切り替えた後に、前の会話の引数と出力をコアが持ち続けない

**開く入口の無い詳細がメモリに残る場合が 2 つあり、どちらも許容する**（査読 1-3）:

- **GUI の再読み込み** — フロントの `toolRuns` だけが消え、`ConversationCleared` は
  飛ばないのでリングは残る
- **`ToolInvoked` の取りこぼし（`Lagged`）** — 行が生えないまま詳細だけ記録される

どちらも行が無いので画面から読めず、次の `ConversationCleared`・500 件の押し出し・
アプリの終了で消える。**メモリの中だけの話で、D3 の線（残さない）は越えない。**

**D3 は P1 の機械テストで留める**（目印の文字列を引数と出力へ入れ、全イベントと
`export_session` の出力を走査して 1 件も出ないこと。`orchestrator.rs:8123` の
「理由は ToolInvoked 以外のイベントに乗らない」と同じ形）。

### D4. 上限は件数 500 と、1 件あたり引数 16,000 字・出力 16,000 字

- **件数 500 = フロントの `toolRuns` の上限と同じ数。** 数えている対象も同じ
  （`ToolInvoked` 1 本 = 1 件）なので、**通常は「行がある = 詳細がある」が成り立つ。
  保証ではない** — フロントがイベントを取りこぼすと 2 つの窓がずれ、行は残っているのに
  詳細が先に押し出されることがある。そのときは D5 の「残っていません」が出る
- **16,000 字は「同梱ツールの出力が 1 件も切れない」値**（実測の最大 13,606）。
  切れるのは MCP の長い出力だけで、8,000 字超は全体の 8.0%・p99 が 19,754
- **字数は `chars().count()`、切るのは `chars().take(16_000).collect()`。**
  `len()` で数えると日本語は 1/3 の位置で切れ、バイト位置のスライスは文字の途中で
  panic する
- **引数の字数は `serde_json::to_string(&call.args)`（詰めた形）で数える** —
  `tool:` 行の `args_chars` と同じ数え方なので、**画面の字数とログの字数が一致する**。
  フロントが字下げして表示した長さではない
- **切ったら必ず書く**（`failures.md` #44 / #58）— 保持するのは先頭 16,000 字と
  **元の字数**。画面は「先頭 16,000 字を表示（全 193,264 字）」と出す
- **最悪値**: 500 × 32,000 字 ≈ 1,600 万字（UTF-8 で約 48MB）。**実測の平均なら
  500 × 2,232 字 ≈ 112 万字（約 3MB）**。総量の上限は置かない

### D5. IPC は 1 本。開いたときに引く

`get_tool_call(call_id) -> Option<ToolCallDetail>`

```text
ToolCallDetail {
  callId:        number
  args:          JSON 値 | string   // argsTruncated で決まる（下）
  argsChars:     number             // 詰めた形で数えた元の字数
  argsTruncated: boolean
  body:          string
  bodyChars:     number             // 元の字数
  bodyTruncated: boolean
}
```

- **`args` は 2 つの形を取る。どちらかは `argsTruncated` だけで決まる** —
  偽なら `call.args` の JSON 値そのまま、真なら**詰めた形の文字列の先頭 16,000 字**
  （途中で切った JSON は parse できないので値では返せない）。
  フロントの表示は `argsTruncated ? args : JSON.stringify(args, null, 2)` の 1 箇所。
  `types.ts` は `args: unknown`（`typeof` で推測させず、旗で分岐する）
- **`None` は「押し出された / 会話を切り替えた」**で、エラーではない。画面は
  「この呼び出しの詳細はもう残っていません」と出す
- 一覧を返す IPC は作らない（Notes 2）

### D6. 合成側も MCP も分けない

`ask_*` / `plan` / `room_log` も MCP 由来も、**`ToolInvoked` を emit する合流点**を
通るので同じ形で記録される。**ツールの種類で分岐を作らない。**

- `ask_*` / `plan` の引数は発話として会話ペインに出るが、**出力（相手の答え・束ね）を
  進行役が受け取った形そのまま読める場所は今どこにも無い**。分けずに記録すると
  これが副産物として読めるようになる
- MCP は他人のスキーマなので欄の意味をこちらが知らない。**D3 の線が守りなので、
  欄を選り分ける必要が無い**

### D7. 画面 — 行を押すと開き、もう一度押すと閉じる。高さは測らない

- ツール行の左端に開閉の印を足し、**行全体が押せる**。開くと行の下に
  「入力」「出力」の 2 節（等幅・`max-h` + 縦スクロール・`whitespace-pre-wrap`）
- **開閉の状態と、引いた詳細は別に持つ** — `expanded: Set<callId>` と
  `details: Map<callId, 状態>`。1 つに畳むと「一度引いたら閉じられない」になる。
  閉じても `details` は捨てない（開き直すたびに IPC を撃たない）
- **`details` の状態は 4 つ**: 取得中 / 取得済み / 残っていない（`None`）/
  取得に失敗。取得中は「読み込み中…」を出し、**取得中の行をもう一度押しても
  2 本目の IPC を撃たない**。失敗は行の下に 1 行で出し、トーストは出さない
  （押した本人の目の前で起きているので通知を重ねない）。失敗した行は
  押し直せば取り直す
- IPC は生の `ipc` + `try/catch` で呼ぶ（投影を持たないので `orchestrator.*` の
  `mutate` を通さない。Spec 19 P3 の使い分け）
- **`state.toolRuns` が空になったら `expanded` と `details` を捨てる**
  （`conversationCleared` の帰結。部品は `state` を watch するだけでイベントを
  直接は聴かない）。`state` には詳細を入れない — 500 件ぶんの本文を投影に持たない
- **`getBoundingClientRect` / `elementFromPoint` を使わない。** 会話ペインは
  `zoom` を掛ける場所で「座標計算 0 箇所」が前提（2026-09-09 の表示倍率）。
  高さは CSS の `max-height` だけで決める
- 色はトークンのみ。ライトテーマで読めること
- 辞書 ja / en に鍵を足す（入力 / 出力 / 切り詰めの注記 / 読み込み中 /
  残っていません / 取得に失敗 / 束ねの見出し）

### D8. 束ね — ターンを終えた個体の、エラーを含まないまとまりだけ畳む

`lib/chatRows.ts` に純関数を足す（入力は時系列の項目と、**いま処理中の個体の集合** =
`state.typing`）。規則は 4 つ:

1. **同じ個体のツール行が、間に他の項目（発話・告知・別の個体の行）を挟まずに
   3 本以上続いたら 1 つのまとまり**
2. **その個体が処理中（`typing`）のあいだは畳まない。** いま何をしているかが
   見える必要がある
3. **`ok = false` の行を 1 本でも含むまとまりは畳まない。** 赤いドットを
   見出しの裏へ隠さない
4. それ以外は畳む。見出しは「{name}: ツール {n} 件」。押すと今と同じ行が並ぶ

- **rev1 の「後ろに項目が来たら畳む・末尾は畳まない」を 2 へ置き換えた**（査読 2-3）—
  波では別の個体の行が後ろに来るので、答えを出していない個体の行が途中で畳まれていた。
  **「後ろに何が来たか」ではなく「その個体のターンが終わったか」で切る**
- **見出しにエラーの本数は出さない**（rev1 から撤去。査読 2-4）。規則 3 により
  畳まれたまとまりは常に `ok = false` が 0 本なので、出す数が無い。
  **「エラー 0 件」とも書かない** — 同梱ツールは失敗を `Ok(<エラー文>)` で返すので
  （`failures.md` #41）、`ok` は「返り値が Ok か」であって「成功したか」ではない。
  畳んでいない行の緑のドットも同じ意味で、**畳みが新しく隠すのは理由の行だけ**
- **まとまりの鍵は先頭の行の `callId`。** 行は末尾にしか増えないので、まとまりが
  伸びても鍵は動かない。先頭が 500 件の押し出しで消えたときは鍵が変わり、
  そのまとまりは既定の状態へ戻る
- 1 の閾値 3 本の根拠は実測 — 中央 4 本・連続 3 本以上が全ツール行の 76.0%。

再起動後・新規チャット後の「詳細が消える」は、**行そのものが消えるので開く入口が

## 裁定（2026-09-21。未決はゼロ）

1. **束ねは既定で畳む — 利用者裁定（rev2 の本文どおり）。** 裁定の理由 3 点:
   (a) 実測で同じ個体の連続 3 本以上が全ツール行の 76.0%。既定が開いたままだと、
   利用者は会話のたびに手で畳むことになり、起点の要望（AionUi のように畳まれている）に届かない
   (b) **Spec 27 の「安心のための表示」とは時間軸で棲み分ける** — 何をしているか・なぜ呼んだかが
   最も要るのは**その個体が走っている最中**で、D8 規則 2 によりその間は畳まない。
   畳むのはターンが終わって主役が答えの発話へ移った後
   (c) 見出しの本数を撤去したので「エラー 0 件 = 正常終了」の誤読が無く、
   `ok=false` を含むまとまりは規則 3 で開いたまま残る。
   以下は裁定前の記録（査読 2 系統の意見が割れた）:
   - 査読 1: 畳む。実測が支える。本 Spec の主目的は Goal 1 で、束ねは副次的な整理
   - 査読 2: 開いたままか、エラーを含むまとまりは畳まない。Spec 27 の凍結
     「安心のための表示なので見せない既定には意味が無い」と当たり、しかも
     同梱ツールの失敗は `ok=true` なので見出しのエラー本数では拾えない
   - **rev2 の本文 = 畳む + `ok=false` を含むまとまりは畳まない + 見出しに本数を出さない。**
     査読 2 の後半（見出しが「正常に終わった」と読める）は採り、前半
     （畳むと失敗が隠れる）は採らなかった — 畳んでいない行でも同梱ツールの失敗は
     緑のドットで、**畳みが新しく隠すのは理由の行だけ**。代償はそこにある
   - 「開いたまま」へ裁定するなら、D8 の規則 4 を「畳まない。見出しを押したときだけ畳む」へ
     変え、Goal 2 を「畳める」へ弱める。機構は同じ

**rev2 で降ろした未決**: 上限 16,000 字 / 500 件（査読 1 が支持。引数を 4,000 へ下げると
`file` の write の `content` が切れる実測が決め手）/ GUI の再読み込み後の復元
（範囲外で確定。Notes 2）。

## Notes

### 1. 退けた形 — 欄ごとの「出してよい引数」の許容表

起票前の調査で私は「`grep` の `pattern` は構造、`file` の `content` は本文なので、
出す欄を閉じた許容で決める」形を推した。**契約を読み直して退けた。** 理由は 3 つ:

- `tool_reason_contract` が**画面とログを既に分けて裁定している**（D3）。私は
  `event.rs` の doc と #71 だけを読んで「画面へ出すのは #71 と正面衝突」と
  報告したが、**同じ #71 を引いた契約の行が「画面には出す」と書いていた**。
  衝突するのは保存とログであって画面ではない
- **MCP 由来が 20.8%** あり、他人のスキーマには表が作れない。表を作ると
  「同梱は選り分け、MCP は全部出す（または全部隠す）」という 2 つの規則になる
- 利用者が見たいのは `file` の `content` や `run` の argv = **表が隠す側の欄**

### 2. GUI の再読み込み後の復元（範囲外）

リングができると `list_tool_calls` 1 本でツール行を再投影できる（Spec 08 の波と
同じ形）。ただし今の行の時刻はフロントが受信時に打っており（`tsMs: Date.now()`）、
復元するならコアが時刻を持つ必要がある。入れるときは `ToolCallStore` に `ts_ms` と
`agent_id` / `tool` / `ok` / `reason` を足すだけで、置き場は変わらない。
**`ipc_contract` へ予告は書かない**（査読 1 の提案。契約に未実装の口を書くと、
実装されないまま残った行が「あるはずの IPC」として読まれる。材料はこの節が持つ）。

### 3. 起票前の報告で私が外した 2 点

- 「引数を出すのは #71 と正面衝突」— Notes 1 のとおり、契約の側が既に線を
  引いていた。**`event.rs` の doc を読んで `data_contract` を読まなかった**
- 「畳みだけ入れても無駄」— 数える前に書いた。実測は 5 本以上が 42.8%・p90 12 本で、
  畳みには単独の価値がある

### 4. 打ち切りは先頭だけを残す

コマンドの失敗は末尾に出ることが多いが、`run` は stderr を先に 4,000 字確保して
組むので、同梱ツールの範囲では先頭を残せば足りる（そもそも 16,000 字では切れない）。
切れるのは MCP の長い出力で、先頭 + 末尾の 2 片にする価値が出たら頻度を見て足す。
