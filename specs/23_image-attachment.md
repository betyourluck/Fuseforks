# Spec: 画像の添付 — 入力欄からサーヴァントへ画像を送る

**ID**: 23
**Date**: 2026-08-06
**Status**: Draft rev1（査読待ち）
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

会話ペインの入力欄に画像を添付し、宛先のサーヴァントへ送れるようにする。

起点は利用者の言葉（2026-08-06）—「**おそらく僕はコストの面で使いたくない機能だが、
無ければ『どうして無いの？』と聞かれそうな機能だ。なので機能は入れておきたい**」。

**この Goal は「画像を活用する」ではない。「目立つ欠落を埋める」ことと
「使わない人に払わせない」ことの両立が本体である。** 設計の判断はすべてここから出る:

- **使わない村の固定費はゼロ** — ツールを 1 本も増やさない。プロンプトのスキーマも
  システムプロンプトも 1 字も伸びない。画像を添付しない限り、ワイヤは今日と同じ
- **払うのは添付した人だけ**、しかも**その 1 ターンだけ**（D1）
- **既定は「使える」で OFF ではない** — `run` のような明示オプトインにしない。
  オプトインが要るのは*実行能力*が増えるからで、画像は能力ではなく入力の種類

## 現況（実測 2026-08-06）

**LLM 層に画像・base64 という語は 1 箇所も無い。** 型は 3 層とも素の文字列:

| 層 | 型 | 位置 |
|---|---|---|
| canonical | `ChatMessage.content: String` | `canonical.rs:40` |
| OpenAI 互換ワイヤ | `OaiMessage.content: Option<String>` | `wire.rs:46` |
| Anthropic ワイヤ | `AnthropicRequestBlock` = `Text` / `ToolUse` / `ToolResult` の 3 種 | `wire.rs:335` |
| 会話ログ | `AgentMessage.content: String` | `model.rs:656` |
| 永続化 | **`Record::Exchange { sent: String, replied: String }`** | `session_store.rs:115` |

**`Record::Exchange` が `String` であることが D1 を決める**（後述）。

**プロバイダ側はどれも画像を受け取れる。ネイティブ経路は要らない**（実測で
確認したのは仕様であって実機ではない — P5 の検収 1 件目がそこ）:

- Anthropic: `{"type": "image", "source": {"type": "base64", "media_type": …, "data": …}}`
- OpenAI 互換: `content` を配列にして `{"type": "image_url", "image_url": {"url": "data:…"}}`
- **Spec 05 で Gemini のネイティブ経路を作った事情は当てはまらない** — あれは
  `google_search` が互換層に `400 Invalid tool type` で拒否されたからで、
  **ツールの制約**だった。画像は `content` に乗るので互換層が知らない道具ではない
- ただし「OpenAI 互換」は名乗った時点で保証されるものではない。
  `Provider::detect` は判定できないホストを互換へ落とす設計（`client.rs:51`
  「互換を名乗るサーバのほうが圧倒的に多く、外したときの傷が浅い」）なので、
  **通るかは叩くまで分からない**

**Spec 19 の画像機構がそのまま使える**（この Spec の実装量を大きく削る）:

- **WebP 1 形式に固定済み**（`config_store.rs:49`「形式を 1 つに固定すると、
  表示側は MIME 判定なしで `image/webp` として扱える」）。3 プロバイダとも WebP 可
- **UI が WebP へ変換して送る**規約が既にある（`config_store.rs:16`）—
  縮小と再エンコードの置き場が決まっている
- `validate_icon`（WebP マジックバイト検査）/ `write_icon_at` / `read_icon_at`
- 置き場の前例: `{workspace}/user/icon.webp`（Spec 19）/ `{workspace}/exports/`（Spec 12 P3）

**入口の部品も揃っている**: `dialog:allow-open` は scope 無しで許可済み
（`capabilities/default.json`）。ファイル選択は追加の依存も権限も要らない。

## 設計の核

**`AgentMessage` へ加算的な欄を 1 つ足し、画像の実体はファイルへ置く。**
canonical と両ワイヤは**送信の瞬間だけ**ブロック列へ組み立てる。

```
入力欄（貼り付け / 参照…）
  → フロントで WebP へ変換・縮小（Spec 19 と同じ場所）
  → send_user_message(… , attachments)
  → {workspace}/attachments/{uuid}.webp へ保存
  → AgentMessage.attachments = [参照]        ← 会話ログ・再開後の表示はここ
  → そのターンのプロンプト組み立て時だけ画像ブロックへ展開
  → 履歴（Record::Exchange.sent）へは入れない  ← D1
```

- **`AgentMessage.attachments: Vec<Attachment>` は加算**（`#[serde(default,
  skip_serializing_if = "Vec::is_empty")]`）。**`grounding` と同じ形**で、
  添付が無い発話のシリアライズ結果は今日と 1 バイトも変わらない
- **本体は base64 ではなくファイル参照**。会話ログは redb に載るので、
  画像の実体を入れると再開のたびに全部読む。`{workspace}/attachments/{uuid}.webp`
  へ置いて `AgentMessage` は id と寸法だけ持つ（`exports/` と同じ「置き場を
  1 つ決める」判断）
- **canonical に画像を持たせるのは送信経路だけ。`ChatMessage.content: String` は
  変えない**（D2）。変えると `push_exchange` / `exchange_pair` / `restore_histories` /
  `session_store` の 4 箇所が同時に動き、#45 と #29 の規律を全部書き直すことになる
- **ワイヤの差は adapter が吸収する**（契約どおり）。`encode_message` が
  添付を受け取ったときだけブロック列を組む

## 決めること

- **D1（最重要）画像は 1 ターン限り。履歴に残さない。** 根拠 3 つ:
  1. **`Record::Exchange.sent` が `String`** — 残すなら永続化の形が変わる
     （redb の既存レコードと非互換）
  2. **滑る窓は 8 往復**。残すと同じ画像が最大 8 ターン再送される。
     Anthropic の高解像度は **1 枚あたり最大 4,784 トークン**なので、
     1 枚の添付が **約 38,000 トークン**に化ける
  3. Goal が「コスト面で使いたくない」— 残す設計は Goal と正面から反する

  **代償を正直に書く**: 2 ターン目に「さっきの画像の左側は？」と訊いても
  モデルには見えていない。**ただし完全に失われるわけではない** — モデルが
  1 ターン目に書いた説明は履歴に残るので、そこを足がかりにできる。
  **画面と本文の両方で「この画像は今回のみ渡ります」と明示する**
  （黙って消えると欠陥に見える。#44 の「歯止めの先に道を書く」と同じ）。
  **利用者の裁定が要る** — 残す設計（窓が自然に押し出すまで保持）も筋は通るが、
  その村では 1 枚の添付が 38K トークンになる
- **D2 `ChatMessage.content: String` は変えない**。添付は
  `ChatMessage.attachments`（加算）で運び、adapter が組み立てる。
  型を丸ごとブロック列へ変えるのは影響が 4 層に及び、Goal に対して払いすぎ
- **D3 形式は WebP のみ。変換と縮小はフロント**（Spec 19 の規約を延長）。
  長辺の上限は **1568px** を推す — 高解像度（2576px）は 1 枚 4,784 トークンで、
  Goal と釣り合わない。**縮小したことを画面に出す**（黙って劣化させない）
- **D4 入口は「貼り付け」と「参照…」の 2 つ。ドラッグ&ドロップは入れない。**
  Spec 21 P0 の実測で **Tauri v2 の `dragDropEnabled` 既定 `true` が
  ページ内の `drop` を横取りする**ことが分かっており、HTML5 のドロップは
  当てにできない。**スクリーンショットの主経路は Ctrl+V なので実害は小さい**
- **D5 上限は 1 発話あたり 1 枚・2MB**（rev1 の案）。複数枚は Goal に対して
  払いすぎで、要望が実測で出てから広げる（「頻度を見てから決める」）
- **D6 サーヴァント同士の転送では画像を渡さない。** `ask` / `plan` /
  `transfer_to_*` の経路は文字列のまま。**利用者 → サーヴァントの 1 方向だけ**に
  閉じる — 転送に載せると hop のたびに再送され、コストが人の目の届かない所で増える
- **D7 広場ログには添付の存在だけを書く**（`（画像 1 枚）`）。本文には出さない。
  抜粋は 200 字 × 12 件の固定費で、画像を混ぜると全員のプロンプトが膨らむ

## Stories

- S1 利用者が入力欄へ画像を貼り付け（または「参照…」で選び）、宛先のサーヴァントが
  その画像を見て答える
- S2 画像を添付しない村・しないターンでは、送るワイヤも払うトークンも今日と同じ
- S3 添付した画像が会話ペインに残り、再起動して開き直しても消えない
- S4 「この画像は今回のみ渡ります」が画面から読め、2 ターン目に見えないことに
  利用者が驚かない

## Tasks

- **P0 契約**: `data_contract.yaml` へ `attachment_contract`。凍結: 加算欄の形 /
  置き場（`{workspace}/attachments/{uuid}.webp`）/ **1 ターン限り（D1）** /
  WebP 固定と長辺上限 / 転送に載せない（D6）/ 広場ログは存在のみ（D7）。
  あわせて `prompt_cache` の節へ**画像は安定プレフィックスに入らない**ことを追記
- **P1 コア（純機構）**: `Attachment` 型 + 検査（WebP マジック・サイズ・寸法）+
  `{workspace}/attachments/` の読み書き（**Spec 19 の `validate_icon` /
  `write_icon_at` / `read_icon_at` を一般化して共有**。同じ規律を 2 箇所に書かない）。
  単体: 非 WebP を拒否 / 上限超を拒否 / 往復 / uuid 衝突なし
- **P2 ワイヤ**: `ChatMessage.attachments`（加算）+ 3 adapter の `encode_message`。
  **`AnthropicRequestBlock` へ `Image` variant を追加**し、`OaiMessage.content` を
  文字列と配列の両対応にする（`#[serde(untagged)]`。添付が無ければ今日と同じ
  文字列を出す = **バイト等価をテストで凍結**）。Gemini は `inline_data`。
  単体: 添付なしのエンコード結果が現行と 1 バイトも変わらない × 3 adapter
- **P3 配線**: `send_user_message` へ `attachments`（加算・省略可）+
  `AgentMessage.attachments` + 保存 + そのターンだけプロンプトへ展開 +
  **履歴へは入れない**（D1）。結合: 画像が 1 ターン目に届く / 2 ターン目の
  リクエストに画像ブロックが無い / 転送先へ渡らない（D6）
- **P4 フロント**: `ChatInput.vue` の貼り付け + 「参照…」+ WebP 変換・縮小 +
  添付チップ（×で外す）+ 「今回のみ」の注記 + `ChatPanel` の表示 + 辞書 ja/en
- **P5 台帳**: README 日英 + CLAUDE.md + ディレクトリ木（`attachments/`）
- **P6 実機確認**（画面・ログで観測できる項目だけ — #68）:
  1. **互換エンドポイントで実際に画像が通る**（`Provider::detect` が
     OpenAiCompat へ倒したテンプレートで。**通らなければ D8 を起こす** —
     rev1 は「仕様上は通る」までしか確かめていない）
  2. 貼り付けた画像をサーヴァントが説明できる
  3. 2 ターン目に画像が渡っていない（`turn:` 行の `prompt` が 1 ターン目より小さい）

## Notes

1. **「使わない人に払わせない」の実装上の意味**は、スキーマを増やさないことと、
   **添付なしのワイヤがバイト等価**であること。後者を P2 のテストで凍結する —
   ここが崩れると、画像を一度も使わない村のキャッシュが割れる（`stable_len` と
   同じ性質の事故で、**画面には何も出ない**）
2. **D1 は「画像を軽く扱う」判断ではなく「トークンの因果を人の目に見える所へ置く」判断。**
   Spec 11 が天井を依頼の因果へ掛けたのと同じ形で、**払う量が添付という
   人の操作と 1 対 1 で対応する**。履歴に残すと、1 回の操作が 8 ターンぶんの
   支払いに化けて因果が見えなくなる
3. **Spec 05 の「ネイティブ経路が要る」は今回に適用しない**。あれはツールの制約で、
   画像は content の話。**同じ「プロバイダ差」でも、道具か中身かで結論が変わる**
4. **`grounding` が先例として効いている**（`model.rs:671`）— 表示層専用の加算欄で、
   `skip_serializing_if` により無いときは何も出ない。今回の `attachments` は
   **モデルへ 1 度だけ渡る点だけが違う**
5. **ドラッグ&ドロップを外した根拠は Spec 21 P0 の実測**（`dragDropEnabled` が
   ページ内の drop を横取りする）。**別 Spec の実測が設計判断に効いた 2 例目**
   （1 例目は Spec 20 の `prune_settled` が `decide` を使い回した件）
6. **未確認**: rev1 は 3 プロバイダの画像対応を**仕様で**確かめただけで、
   実機では 1 度も叩いていない。P6 の 1 件目がそこ。**「通る」と書いた箇所を
   実測が反証したら D8 として起票し直す**
