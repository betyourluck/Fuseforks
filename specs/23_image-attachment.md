# Spec: 画像の添付 — 入力欄からサーヴァントへ画像を送る

**ID**: 23
**Date**: 2026-08-06
**Status**: Draft rev2（rev1 査読の 10 点を反映。うち 1 点は**査読の前提を一次資料で
訂正して採用**した — Notes 7）
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

会話ペインの入力欄に画像を添付し、宛先のサーヴァントへ送れるようにする。

起点は利用者の言葉（2026-08-06）—「**おそらく僕はコストの面で使いたくない機能だが、
無ければ『どうして無いの？』と聞かれそうな機能だ。なので機能は入れておきたい**」。

**この Goal は「画像を活用する」ではない。「目立つ欠落を埋める」ことと
「使わない人に払わせない」ことの両立が本体である。** 設計の判断はすべてここから出る:

- **使わない村の固定費はゼロ** — ツールを 1 本も増やさない。プロンプトのスキーマも
  システムプロンプトも 1 字も伸びない。画像を添付しない限り、ワイヤは今日と同じ
- **払うのは添付した人だけ**、しかも**その 1 ターンだけ**（D1）
- **既定は「使える」で OFF ではない** — `run` のような明示オプトインにしない。
  オプトインが要るのは*実行能力*が増えるからで、画像は能力ではなく入力の種類

## 現況（実測 2026-08-06）

**LLM 層に画像・base64 という語は 1 箇所も無い。** 型は 3 層とも素の文字列:

| 層 | 型 | 位置 |
|---|---|---|
| canonical | `ChatMessage.content: String` | `canonical.rs:40` |
| OpenAI 互換ワイヤ | `OaiMessage.content: Option<String>` | `wire.rs:46` |
| Anthropic ワイヤ | `AnthropicRequestBlock` = `Text` / `ToolUse` / `ToolResult` の 3 種 | `wire.rs:335` |
| Gemini ネイティブワイヤ | `GeminiPart` は `text` だけ | `wire.rs:508` |
| 会話ログ | `AgentMessage.content: String` | `model.rs:656` |
| 永続化 | **`Record::Exchange { sent: String, replied: String }`** | `session_store.rs:115` |

**`Record::Exchange` が `String` であることが D1 を決める**（後述）。

### プロバイダの画像仕様（Anthropic は一次資料で確認・2026-08-06）

**Anthropic の公式ドキュメント（vision.md）で確定した事実**:

- **トークンは 28×28px のパッチ数**。`⌈幅/28⌉ × ⌈高さ/28⌉` が視覚トークン数。
  **`(w*h)/750` ではない**（あれは旧版の近似。28²=784 なので値は近いが、
  契約へ書くなら現行の式で書く）
- **ティアは 2 つ** — 高解像度（Claude 4.7 以降）は長辺 2576px・**上限 4,784 トークン**、
  標準は長辺 1568px・**上限 1,568 トークン**。超える画像は自動縮小される
- 形式は **JPEG / PNG / GIF / WebP**。**アニメーションは非対応で先頭フレームだけ**
  （アニメーション WebP を弾く根拠 — D3）
- source は **base64 / url / file_id の 3 種**（Bedrock と Vertex は base64 のみ）
- 上限は **10MB/枚**（Bedrock・Vertex は 5MB）。**20 枚を超えるリクエストでは
  1 枚 2000px の制限**が別に掛かる（D5 が 1 枚なので当たらない）
- **画像はテキストより前に置くのが推奨**（P2 の組み立て順に効く）

**互換層は保証されない**（査読の指摘。**未実測** — P0 で叩く）。xAI/Grok の公式は
`jpg/jpeg` と `png` のみと明記しており、自前の OpenAI 互換サーバ（llama.cpp /
vLLM 系）も WebP を拒むことがある。`Provider::detect` は判定できないホストを
互換へ倒す設計（`client.rs:51`）なので、**rev1 が「仕様上は通る」とした所が最初に落ちる**。

**Spec 05 で Gemini のネイティブ経路を作った事情は当てはまらない** — あれは
`google_search` が互換層に `400 Invalid tool type` で拒否されたからで、
**ツールの制約**だった。画像は `content` に乗るので互換層が知らない道具ではない。

**入口の部品は揃っている**: `dialog:allow-open` は scope 無しで許可済み
（`capabilities/default.json`）。Spec 19 の画像機構（**WebP 1 形式へ固定** /
`validate_icon` / `write_icon_at` / `read_icon_at` / 「UI が WebP へ変換して送る」規約）も
そのまま延長できる。

## 設計の核

**`AgentMessage` へ加算的な欄を 1 つ足し、画像の実体はファイルへ置く。**
canonical と各ワイヤは**送信の瞬間だけ**ブロック列へ組み立てる。

```
入力欄（貼り付け / 参照…）
  → フロントで縮小・WebP へ変換（WebWorker。D3）
  → send_user_message(… , attachments)
  → {workspace}/attachments/{uuid}.webp へ保存（バックエンドで再検証）
  → AgentMessage.attachments = [参照]        ← 会話ログ・再開後の表示はここ
  → そのターンのプロンプト組み立て時だけ画像ブロックへ展開（画像はテキストより前）
  → 履歴（Record::Exchange.sent）へは入れない  ← D1
```

- **`AgentMessage.attachments: Vec<Attachment>` は加算**（`#[serde(default,
  skip_serializing_if = "Vec::is_empty")]`）。**`grounding` と同じ形**で、
  添付が無い発話のシリアライズ結果は今日と 1 バイトも変わらない
- **本体は base64 ではなくファイル参照**。`{workspace}/attachments/{uuid}.webp`
  へ置き、`AgentMessage` は id・寸法・元ファイル名だけ持つ
- **`ChatMessage.content: String` は変えない**（D2）。添付は
  `ChatMessage.attachments`（加算）で運び、adapter が組み立てる

## 決めること

- **D1（最重要）画像は 1 ターン限り。履歴に残さない。** 根拠 3 つ:
  1. **`Record::Exchange.sent` が `String`** — 残すなら永続化の形が変わる
     （redb の既存レコードと非互換）
  2. **滑る窓は 8 往復**。残すと同じ画像が最大 8 ターン再送される。
     実額は下表（rev2 で一次資料の式に基づき計算し直した）:

     | 送る画像 | 1 ターン | 8 ターン再送 |
     |---|---|---|
     | 縮小なし・高解像度ティア上限 | 4,784 | **38,272** |
     | D3 の 1568px 制限・16:9（1568×882） | 1,792 | **14,336** |
     | D3 の 1568px 制限・正方形（1568×1568） | 3,136 | 25,088 |

  3. Goal が「コスト面で使いたくない」— 残す設計は Goal と正面から反する

  **代償を正直に書く**: 2 ターン目に「さっきの画像の左側は？」と訊いても
  モデルには見えていない。**ただし完全に失われるわけではない** — モデルが
  1 ターン目に書いた説明は履歴に残るので、そこを足がかりにできる。
  **利用者の裁定が要る** — 残す設計も筋は通る（上表の 14,336〜38,272 を払う）
- **D2 `ChatMessage.content: String` は変えない**。型を丸ごとブロック列へ変えると
  `push_exchange` / `exchange_pair` / `restore_histories` / `session_store` の
  4 箇所が同時に動き、#45 と #29 の規律を全部書き直すことになる
- **D3 形式は WebP を既定とし、互換層が拒んだら JPEG へ 1 度だけ再エンコードして
  再送する**（rev2。査読 1）。フロントは常に WebP を作る。`Provider::OpenAiCompat`
  かつ画像付きで **400 が返った 1 回だけ** JPEG へ落として再試行し、それも落ちたら
  「この接続先は画像を受け付けません」と**画面へ出す**（黙って落とさない）。
  **アニメーション WebP は拒否**（先頭フレームしか渡らず、利用者の意図と食い違う）。
  **長辺の上限は 1568px** — 高解像度ティアの 2576px を使わないのは Goal のため
  （上表で 4,784 対 1,792）。**縮小したことを画面に出す**
- **D4 入口は「貼り付け」と「参照…」の 2 つ。ドラッグ&ドロップは入れない。**
  Spec 21 P0 の実測で **Tauri v2 の `dragDropEnabled` 既定 `true` が
  ページ内の `drop` を横取りする**ことが分かっている。**スクリーンショットの
  主経路は Ctrl+V なので実害は小さい**
- **D5 上限は 1 発話あたり 1 枚。元ファイル 10MB で拒否、変換後 2MB で拒否**
  （rev2: 元ファイルの門を追加。査読 6 — 20MB の HEIC がフロントへ届くと
  デコードで落ちる）
- **D6 サーヴァント同士の転送では画像を渡さない。ただし落としたことを System 行で
  必ず知らせる**（rev2。査読 8）。`ask` / `plan` / `transfer_to_*` の経路で
  添付を落とすとき、転送先の本文へ `（画像 1 枚は転送されません）` を入れる。
  **黙って落とすと、B がなぜ画像を見られないのか誰にも診断できない** —
  #44 の「歯止めの先に道を書く」と、Spec 12 P4 の「飛ばした相手が居たら
  System 行に必ず書く」の同型
- **D7 広場ログには添付の存在だけを書く**（`（画像 1 枚）`）。本文には出さない
- **D8（新設）Gemini は互換経路で通す。ネイティブ経路には画像を実装しない**
  （rev2。査読 5）。この村の Gemini ネイティブは `GeminiPart { text }`
  （`wire.rs:508`）で、画像を足すなら `inline_data` を新設することになる。
  **ネイティブ経路が要るのは Google 検索の接地だけ**（Spec 05 の凍結）なので、
  **画像と接地を同時に使う経路は作らない**。ネイティブ選択時に画像を添付したら
  D6 と同じく画面で断る
- **D9（新設）`{workspace}/attachments/` は GC する**（rev2。査読 2）。
  **起動時に 30 日より古いファイルを削除**し、合計 500MB を超えたら古い順に削る。
  **会話ログから参照が消えても実体は残る**（redb と file の 2 つの真実を
  同期させない — Spec 12 が index.json を捨てた判断と同じ）。GC で消えた画像の
  表示は「画像は保持期間を過ぎて削除されました」の枠にする

## Stories

- S1 利用者が入力欄へ画像を貼り付け（または「参照…」で選び）、宛先のサーヴァントが
  その画像を見て答える
- S2 画像を添付しない村・しないターンでは、送るワイヤも払うトークンも今日と同じ
- S3 添付した画像が会話ペインに残り、再起動して開き直しても（保持期間内なら）消えない
- S4 「この画像は今回のみモデルへ渡ります。2 ターン目以降はモデルからは見えません
  （画面には残ります）」が画面から読め、利用者が驚かない（rev2: 文言を具体化。査読 4）
- S5 画像を受け付けない接続先では、その旨が画面に出る（黙って落ちない）

## Notes

1. **「使わない人に払わせない」の実装上の意味**は、スキーマを増やさないことと、
   **添付なしのワイヤがバイト等価**であること。後者を P2 のテストで凍結する —
   ここが崩れると、画像を一度も使わない村のキャッシュが割れる（`stable_len` と
   同じ性質の事故で、**画面には何も出ない**）
2. **D1 は「画像を軽く扱う」判断ではなく「トークンの因果を人の目に見える所へ置く」判断。**
   Spec 11 が天井を依頼の因果へ掛けたのと同じ形で、**払う量が添付という
   人の操作と 1 対 1 で対応する**
3. **Files API は誘惑だが D1 の代わりにはならない**（rev2 の新発見）。Anthropic の
   vision ドキュメントは「多ターンでは base64 が毎回再送されるので `file_id` を
   使え」と明示的に勧めている。**しかしあれが小さくするのはペイロードであって
   トークンではない** — 視覚トークンは毎ターン数えられる。**「payload を減らす」と
   「トークンを減らす」を取り違えると、D1 を捨てて Files API を採る誤った判断へ
   まっすぐ進む。** ここは将来の改訂で最も踏みやすい罠なので明記しておく
4. **キャッシュヒット率は画像を添付したターンだけ下がる。これは仕様**（rev2。査読 10）。
   D1 により 2 ターン目以降はプレフィックスが伸びて率は戻る。毎ターン添付する
   使い方では毎回割れるが、それは Goal（払うのは添付した人だけ）と一致している
5. **Spec 05 の「ネイティブ経路が要る」は今回に適用しない**。あれはツールの制約で、
   画像は content の話。**同じ「プロバイダ差」でも、道具か中身かで結論が変わる**
6. **ドラッグ&ドロップを外した根拠は Spec 21 P0 の実測**。**別 Spec の実測が
   設計判断に効いた 2 例目**（1 例目は Spec 20 の `prune_settled` が `decide` を
   使い回した件）
7. **査読の 1 点を一次資料で訂正して採用した**（rev2）。査読は「`4,784` は
   OpenAI のタイル方式の数字で、Anthropic は `(w*h)/750` 方式」と指摘したが、
   Anthropic の vision ドキュメントで**両方とも誤り**と確認した —
   **4,784 は Anthropic 高解像度ティアの視覚トークン上限そのもの**であり、
   式は `(w*h)/750` ではなく **28×28px パッチの `⌈幅/28⌉ × ⌈高さ/28⌉`**
   （28²=784 なので旧式の `/750` は近似）。
   **ただし指摘の効き目は本物だった** — 数字をプロバイダと式に紐付けずに
   書いていたため、rev1 の「38,000 トークン」は*縮小しない場合*の値なのに
   D3 で 1568px へ縮小する前提と並べて書いており、**自分の 2 つの決定が
   噛み合っていなかった**。rev2 で 3 行の表にして、どの前提でいくつかを固定した。
   **一般化: 数字は出典と前提とセットでしか書けない。片方だけ書くと、
   同じ Spec の中の別の決定と矛盾しても気づけない**
8. **査読の点 7（Anthropic は base64 のみ・URL 不可）も一次資料で反証した** —
   `type: url` と `type: file` は公式に対応している（Bedrock と Vertex は
   base64 のみ）。ただし**この Spec は base64 を選ぶ** — URL は外部から到達できる
   場所に画像を置くことになり、村の画像を外へ出さない方が筋が通る
9. **未確認のまま残すもの**: 互換層（xAI / ローカル）の WebP 可否。
   **P0 の `curl` で最初に潰す** — ここが D3 の既定を決める
