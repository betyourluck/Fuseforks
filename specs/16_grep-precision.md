### 参考実装から採らなかった 4 点

査読は Rust の実装案を添えてくれたが、**そのまま写すと既存の不変条件を 4 つ破る**。
方針（マッチ集合を作ってから窓を畳んで描く）は採り、下記は既存コードに合わせる。

1. **`size_limit(10 * (1 << 20))` は `pattern` と同じではない。** 実際の
   `run_grep` は **`size_limit(1 << 20)`**（1 MiB。コメントは「regex 既定の
   10 倍未満」）。査読の値は 10 倍で、**`include` だけ緩い上限になる**。
   `pattern` と同じ 1 MiB を使う
2. **`out.len() > MAX_CHARS` はバイト数で数えている。** 既存は
   `.chars().count()` を積む `output_chars`。日本語では `len()` が約 3 倍になるので、
   **枠の 1/3 で切れる**。**同じ誤りが Spec 17 の査読でも出た**（あちらは
   `out.truncate()` で diff を切る案）— **文字数の枠をバイト長で数える形は
   2 回続けて出ている**
3. **`clip_line` が抜けている。** 1 行 240 字（`MAX_LINE_CHARS`）のクリップは
   minify 済み JS のような 1 行の塊で出力が埋まるのを防ぐ既存の不変条件。
   **文脈行にも掛ける**（掛けないと 1 本の長い行で枠が飛ぶ）
4. **窓の途中で `break` している。** 内側のループで上限に達したら抜ける形は
   **文脈ブロックを半分だけ描いて終わる**うえ、打ち切りの告知が無い。
   既存の規律（打ち切りは黙って行わず件数を書く）に合わせ、**窓の境界で止めて
   打ち切り文を出す**。**Spec 17 D3 と同じ判断** — 切ってよいのは一覧であって
   ブロックの中身ではない

**あわせて、査読のコードは `looks_binary` と `MAX_FILE_BYTES` の検査を落としている**
（`read_to_string(...).unwrap_or_default()`）。既存の走査はどちらも見ているので残す。

## Goal

同梱 `grep` に引数を 2 つ足し、**1 回の呼び出しで返る情報の密度**を上げる。

- **`include`** — ファイル名で走査対象を絞る。**引いた結果のノイズを減らす**
- **`context`** — 一致行の前後を返す。**引いた後の追い読みの周を消す**

起点は利用者の指示（2026-08-05）。実測の裏付けは同日の `shell.json` → `run.json`
改名作業で、**私は 16 箇所の回収に `--include` を 5 回使った** — 同じ語が `.md` と
`.rs` と `.yaml` と `.json` に散る村では、`MAX_MATCHES=100` の枠が台帳の散文で
埋まり、コードの一致が枠から落ちる。

### 立場の宣言

- **新しいツールは足さない。** 既存 `grep` の引数を 2 つ増やす。ツールを 1 本足すと
  スキーマ分のトークンが**全サーヴァントの毎ターン**に乗る（`yq` に `op` を増やして
  新ツールにしないと決めたのと同じ制約）。引数 2 つでも説明は伸びるので、
  **足す説明は各 1 文に抑える**
- **`count_only` は消さない。** 「何件あるか」と「どの行か」が別の問いであることは
  変わらない（`bundled_tools_contract` で凍結済み）
- **`file read` の行範囲は依然として足さない。** `context` は**一致行を起点に
  有界な窓を返す**もので、任意の位置から読む経路ではない。契約が
  「`read` に offset / range は持たない」を凍結した理由（「全部読む」を助長して
  入力トークンを増やす側に効く）とは向きが逆 — `context` は
  **`file read` を呼ばずに済ませる**側に効く

## Stories

### S1: ファイル名で走査対象を絞る

> エージェントとして、`run.json` がコードのどこで参照されているかだけを知りたい。
> 台帳の散文に一致 100 件の枠を食われたくない。

**引数**: `include`（String、省略可）。**ファイル名（パスの最後の要素）に対する
正規表現**。省略時は全ファイル。

```
grep(pattern: "run\\.json", include: "\\.rs$")
```

- **一致対象は名前だけ。** 相対パス全体には掛けない。`bundled_tools_contract` の
  `fd` の規律（「一致対象は名前だけ。相対パス全体に掛けると一致フォルダの配下が
  道連れでヒットし一覧がノイズで埋まる」）をそのまま適用する
- **`path` と役割が重ならない。** `path` は**場所**（どのフォルダ）、`include` は
  **種類**（どの名前）。両方指定できる
- **大文字小文字は `case_insensitive` に従う**（`pattern` と同じ扱い。`fd` の
  「名前検索は既定で無視」とは揃えない — 1 つの呼び出しの中で 2 つのパターンが
  別の既定を持つと、どちらに掛かった設定なのかが読めなくなる）。
  **`fd` と挙動が違うことを契約に 1 行で書く**（査読 [C6]。どちらも「名前に対する
  正規表現」なのに既定が逆なので、書かないと将来「片方が壊れている」と読まれる）
- **`size_limit` は `pattern` と同じ 1 MiB**（`1 << 20`）。片方だけ緩めない

#### D1: 構文は glob ではなく正規表現（**査読で最も見てほしい点**）

**`*.rs` ではなく `\.rs$` と書く。**

glob を採らない理由は `bundled_tools_contract` の凍結行
「**grep / fd / sd のパターンは Rust regex 構文**」。ここで `include` だけ glob に
すると、**1 つのツールの中に 2 つのパターン言語が同居する** — `pattern` は regex、
`include` は glob という形は、書く側が必ず取り違える。

**採らなかった代償を正面から書く**: モデルは習慣で `*.rs` と書く。**これは黙って
空振りしない** — `*.rs` は Rust regex として**コンパイルに失敗する**
（`repetition operator missing expression`）。ゆえに:

- **glob 形の誤りを名指しで返す。** `include` のコンパイルが失敗し、かつ文字列が
  `*` で始まるか `*.` を含むなら、専用の文面を返す:
  「`include` は glob ではなく正規表現です。`*.rs` ではなく `\.rs$` と書いてください」
- **これは「検査があるから安全」ではなく「予測できる誤りを大きな音で返す」処方。**
  空振り（一致ゼロ）で返すと、モデルは**パターンのほうを疑って再検索する**ので
  周が増える（`failures.md` #44 と同型 — 次に何をするかが書かれていない打ち切りは
  同じ呼び出しの反復を生む）

### S2: 一致行の前後を返す

> エージェントとして、一致した行が何をしているのかを、
> `file read` でファイルを丸ごと読み直さずに判断したい。

**引数**: `context`（整数、省略可、**0〜3、既定 0**）。一致行の前後 N 行を添える。

```
2 件が一致:
crates/agent-core/src/tools/run.rs:80- impl RunTool {
crates/agent-core/src/tools/run.rs:82: /// `agents/{id}/run.json` を読む。
crates/agent-core/src/tools/run.rs:83-     async fn load(&self, id: &AgentId) -> CommandPolicy {
--
crates/agent-core/src/tools/run.rs:249-      利用者への要求として記録しました。
crates/agent-core/src/tools/run.rs:250: 利用者が `agents/{}/run.json` の `allow` へ追加すると、
crates/agent-core/src/tools/run.rs:251-      次から実行できます。
```

#### D2: 一致行と文脈行は**書式で区別する**（`#55` の再演を防ぐ要）

- **一致行**: `パス:行番号: 内容`（**コロン**。現行のまま 1 字も変えない）
- **文脈行**: `パス:行番号- 内容`（**ハイフン**。GNU grep と同じ）
- **ブロックの区切り**: `--` の行

**区別が付かない出力は、文脈行を一致行として報告させる。** `failures.md` #55 は
5 体が同じ見出しの行番号を別々に報告した事故で、真因は「表示件数を総数として
返した」こと＝**読み手が数を誤る形で出した**ことだった。文脈行を一致行と同じ書式で
混ぜると、**同じ形の誤りが「どの行が一致したか」で起きる**。

**書式の意味は description に書く。** 出力を見れば分かる、では足りない —
`:` と `-` の差は 1 文字で、モデルは書式の規則を知らずに読む。

#### D3: 上限 3 の根拠

`diff` が unified diff の context 3 行で固定されている（同契約）。**同じ村の中で
「前後」の既定値が 2 つあると、どちらが効いたのかが読めない。**

上限を大きくしないのは、`context: 20` が実質「その関数を全部読む」になり、
**`file read` の行範囲を却下した理由（全部読むを助長する）へ裏口から戻る**ため。
足りなければ `file read` を呼べばよく、**そのときは呼んだと分かる。**

#### D4: 数えるのは一致行だけ。文脈行は表示枠だけを食う

- `MAX_MATCHES=100` は**一致行**に掛ける（文脈行は数えない）
- `MAX_OUTPUT_CHARS=12,000` は**出力全体**に掛ける（文脈行も食う）
- ゆえに `context` を上げると**表示できる一致件数が減る**。これは正しい挙動だが、
  **打ち切り文にそう書く**（下記 D6）

契約の「**上限は表示に掛け、数えには掛けない**」はそのまま生きる — `total_matches`
は `context` の値に関係なく同じ数になる。

#### D5: 重なった窓は畳む

一致行が隣接して文脈が重なったら 1 ブロックにする。畳まないと同じ行が複数回出て、
**12,000 字の枠を重複で食う**。GNU grep と同じ挙動。

#### D7: 範囲外の `context` は**エラー。clamp しない**（査読 [C3]）

`context: 4` や `context: -1` は「`context` は 0〜3 で指定してください」で返す。

**黙って 3 に丸めない。** 丸めると**指定した値と効いた値が食い違ったまま出力が返り**、
モデルは「4 行分の文脈を見た」と思って読む。`failures.md` #44 と同じ形
（何が起きたかが伝わらない縮退）。

#### D8: 窓の畳みは**同じファイル内だけ**。`--` の出し分けも同じ（査読 [C4][C5]）

- **畳みはファイルごと。** ファイルをまたいで窓を結合しない（行番号の意味が変わる）
- **`--` は `context > 0` のときだけ出す。** `context: 0` で出すと、
  **既存の出力を読んでいる側の形が変わる**
- **`--` は同じファイル内で離れた窓の間だけ。** ファイルが変わるところでは出さない
  （**パスが行頭に付いているので既に区切れている**。ここで出すと「同じファイルの
  別ブロック」と「別のファイル」が同じ記号で区切られ、区別が消える）

### S3: `count_only` との組み合わせ

`count_only: true` と `context: N` が同時に来たら、**`context` を無視し、
無視したことを結果に 1 行書く**。

**黙って無視しない。** `bundled_tools_contract` の「打ち切りは黙って行わず件数を
結果に書く（silent truncation は『全部見た』と誤読される）」と同じ理由で、
**指定した引数が効かなかったことは、指定した側に伝わらないと次の手が選べない。**

拒否（エラー）にしないのは、**その周で答えが返らなくなる**ため。件数は正しく
返せるのだから返す。

### Phase 2: 打ち切り文と description の更新

#### D6: 打ち切り文は**種別ごとに分ける**（rev2 で改訂。査読 [C2]）

**`include` をどの打ち切り文にも足す、では嘘になる。** grep の打ち切りは 2 種類あり、
**`include` が効くのは片方だけ**:

| 打ち切り | 次の手として書くもの |
|---|---|
| **`MAX_MATCHES` / `MAX_OUTPUT_CHARS`**（表示の打ち切り） | `include` / `path` / パターンの具体化 / `count_only: true`。`context > 0` なら「**`context` を下げると表示できる一致が増えます**」も |
| **`MAX_FILES`**（走査の打ち切り、20,000 ファイル） | **`path` で場所を絞る**。**「`include` では直りません」を明記** |

**`MAX_FILES` の文面に `include` を出すと、直らない方法を案内することになる** —
モデルは `include` を付けて再実行し、同じ打ち切りに当たり、また `include` を
変える。`failures.md` #44 が記録した「次の手が無い打ち切りは同じ呼び出しの反復を
生む」の変種で、**こちらは次の手が「あるが効かない」形**なので、反復が
もっともらしく見えるぶん質が悪い。

**新機能を打ち切り文に書くこと自体は必須。** モデルが引数を知る経路は description と
打ち切り文の 2 つで、**打ち切りに直面した瞬間が「絞る」を最も必要としている瞬間**。

#### 説明文の追加は各 1 文

```
`include` でファイル名を正規表現で絞れる（例: `\.rs$`。glob ではない）。
`context: 1〜3` で一致行の前後も返る（一致行は `:`、前後は `-`）。
```

## Notes

1. **`include` は木の走査を減らさない**（rev2 で表現を確定。査読 [C1]）。
   順序は **`walk`（`MAX_FILES` 20,000 がここに掛かる）→ `include` で絞る →
   内容を read**。**read は減るが walk は減らない。**
   ゆえに **`MAX_FILES` の打ち切りには `include` は効かない** — 直すのは `path`。
   doc と打ち切り文の両方に書く（D6）。
   rev1 は「名前で弾くのは読んだ後ではなく前」と「`collect_files` の後にフィルタ」を
   別々の場所に書いており、**読むと矛盾して見えた**

2. **`context` は RepeatGuard に影響しない。** 判定は結果本文の完全一致で、
   同じ引数なら同じ出力が返る。`context` の値が違えば引数が違うので別の呼び出しとして
   数えられる — これは正しい（違う問いだから）

3. **2 つのパターン言語の同居は D1 で退けたが、`pattern` と `include` が
   どちらも regex であることは説明しないと伝わらない。** 「`include` も正規表現」を
   description に明示する。書かないと glob だと仮定される

4. **査読で見てほしい点**: D1（glob を採らない判断）が最重要。
   凍結行「パターンは Rust regex 構文」を守る側に倒したが、
   **実機でモデルが `*.rs` を書き続けて毎回 1 周無駄にするなら、判断は逆になりうる。**
   その場合は「凍結行のほうを改訂して `include` だけ glob にする」ことになり、
   **本 Spec ではなく契約の改訂**として起票し直す（同梱ツール全体の話になるため）
