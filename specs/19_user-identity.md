## P1 実装記録（2026-08-05）

`world.rs` に `USER_NAME_MAX_CHARS` / `normalize_user_name` / `PersistedWorld.user_name` /
`World.user_name()` / `set_user_name()`、`error.rs` に `InvalidUserName { reason }`
（code `INVALID_USER_NAME`）、`orchestrator.rs` に `DEFAULT_USER_LABEL` と
`user_name()` / `set_user_name()`、`attribute_sender` の `Endpoint::User` 分岐。
単体 5 本（world 366 本全緑）+ 結合 2 本（112 本全緑）。workspace 全緑・clippy 新規警告ゼロ。

**実装で決めた 5 点**:

- **`normalize_user_name` は保存経路と読み込み経路の両方が通る。** 入口
  （`set_user_name`）だけを塞ぐと、**塞ぐ前に手で書かれた値がそのまま封筒へ流れる** —
  `api_key_env` の処方 (2)「読み込み時に不正値を落とす」の写し
- **処方 (3)「起動時に正規化したら即ファイルへ書き戻す」はやらない。**
  `api_key_env` が書き戻しを要したのは**残るのが秘密だった**から。呼び名は秘密では
  ないので、ディスクに残る害は「起動のたびに WARN が出る」だけで、**むしろ手で
  直す手掛かりになる**。次に何かを保存した時点で `to_persisted` が消す。
  **同じ事故の処方でも、3 点すべてが常に要るわけではない — 要否は「残るものが
  秘密か」で決まる**
- **`】` は拒否し `【` は通す。** 開き括弧は封筒を閉じないので境界を壊さない
  （`【送り手: あ【い】` は 1 つの封筒として読める）。P0 が `】` だけを凍結したのは
  正しかった、を実装で確かめた
- **`stable_len` 不変の証明を「system に呼び名が 1 文字も現れない」で書いた。**
  Spec 14 の役職テストは「安定プレフィックスの一致」で書いたが、**呼び名は system に
  そもそも入らないので、入らないこと自体がより強い主張**になる。加えて入退室通知の
  揺らぎに影響されない（プレフィックスの一致は、通知が窓から押し出されると崩れうる）
- **`PromptProbeBackend` は再利用できなかった** — system ブロックしか控えないので、
  封筒（user ロール）を見るこの検査には使えない。`FullProbeBackend` を
  テスト内に置いた

**字数の検査はコードポイントで数え、テストがバイト長への退行を捕まえる。**
`a_user_name_is_measured_in_chars_not_bytes` は境界値を**日本語で**踏んだうえ、
`at_limit.len() > USER_NAME_MAX_CHARS`（バイト長は上限を超えている）を
**先に主張してから** `is_ok()` を見る。この 1 行が無いと、実装を `len()` へ
戻してもテストが緑のままになる。`MAX_*_CHARS` を `len()` と突き合わせる誤りは
この村の査読で 2 回続けて出ており、**どちらも ASCII だけのテストを通っていた**。

**実装で決めた 4 点**:

- **`mutate` は例外を飲んで `false` を返す。** 最初 `saveLanguage`（生の `ipc` +
  try/catch）と同じ形で書きかけたが、`orchestrator.setUserName` は `mutate` を

  作法でもう片方を書くと、**テストではなく実機でしか出ない**（コアは正しく拒否し、
  画面だけが保存済みと表示する）
- **`orchestrator` 経由で呼ぶ**（生の `ipc` ではなく）。会話ペインの投影
  `state.userName` を同時に更新する必要があるため。言語が生の `ipc` でよいのは、
  反映先が `setLocale`（グローバルな i18n）で投影を持たないから
- **書式の検査をフロントに置かない。** 天井の 0 を入力段で弾いているのとは
  事情が違う — あちらは「保存したのに黙って別の値になる」正規化を打ち消すためで、
  こちらは拒否がそのまま返ってくる。先回りすると同じ規律が 2 箇所に生える
- **呼び名は明示保存、アイコンは即保存。** 入力中の 1 文字ごとに封筒が変われば、
  途中の名前でサーヴァントに呼ばれる周ができる。アイコンは封筒に入らない

**コンポーネントテストの土台がこのリポジトリに無い**（`@vue/test-utils` も
jsdom / happy-dom も未導入で、テストは純関数と composable に閉じている）。
`label()` の 1 行のために testing 層を足すのは割に合わないので、
**投影が壊れる経路**を composable のテストで留めた（`useOrchestrator.user.test.ts`）—
保存で投影が変わる / **拒否されたら変わらない** / 既定へ戻る / アイコンの
object URL が入れ替わる / アイコンの失敗で変わらない。**「拒否されたのに
画面だけ変わる」はコアのテストでは出ない**（コアは正しく拒否している）。

**IPC を足すと 4 つのテストのモックが落ちる。** `getUserName` / `getUserIcon` を
`init()` に足した時点で、`vi.hoisted` のモックにそれが無い 4 ファイルが
`ready === false` で落ちた。**手で足りない口を教えてくれる形なので、これは
壊れ方として正しい** — モックが自動で穴埋めされると、初期化の増加が誰にも
見えないまま通る。

## Goal

**サーヴァントが利用者を呼ぶ名前**と、**会話ペインに出る利用者のアイコン**を、
システム設定から変えられるようにする。入口は「全般」カテゴリの**一番上**に
「ユーザー」ページを新設する（言語の上）。

現在はどちらも画面から触る方法が無い。Spec 13 の起票理由（「天井は
`world.json` に存在するのに、手編集以外に触る方法が無い」）と違い、**こちらは
値そのものが存在しない** — コードに固定文字列で書かれている。

## 現況（実測 2026-08-05）

| 何 | 実装の場所 | 今の値 | 言語に追従するか |
|---|---|---|---|
| サーヴァントが読む封筒 | `orchestrator.rs:2628` `Endpoint::User => "ユーザー".to_owned()` | `【送り手: ユーザー】` | **しない**（日本語固定） |

**利用者の呼び名は 1 つではなく 2 つあり、片方は言語に追従してもう片方はしない。**
利用者の要望「"あなた" や "You" ではなく」は表示名を、「サーヴァントから
呼ばれる呼び名」は封筒を指している。**この Spec は 2 つを 1 つの設定へ畳む。**

## Stories

- **S1**: サーヴァントが、私が設定した名前で私を呼ぶ。`【送り手: ユーザー】` では
  なく `【送り手: <設定名>】` が届く
- **S2**: 会話ペインで、私の発話の行に私のアイコンと私の名前が出る
- **S3**: 何が設定できるかが左メニューの目録に見える（Spec 13 の Goal を継ぐ）
- **S4**: 何も設定しなくても今までどおり動く。既存の村を開いて挙動が変わらない

## 決定

### D1: 呼び名の置き場は `world.json` の `userName`

`PersistedWorld` へ `#[serde(default, skip_serializing_if = "Option::is_none")]
pub user_name: Option<String>`（ファイル上は `userName`）。`World` は
`user_name: Option<String>` を持ち、`user_name()` / `set_user_name()` で読み書きする。
**`language` の隣**に置く。

**`localStorage` の `fuseforks.settings.v1` には置かない。** `settings_contract` が
凍結した境界は「村に保存＝配ると付いて回る / 端末に保存」で、判定材料は
**会話ログへ焼き付くかどうか**。呼び名は `attribute_sender` が組む封筒として
`AgentRecord.history` と `session_store` の両方へ**文字列そのもの**が入る（#45 の
規律 = 送った文字列をそのまま履歴へ積む）。言語を `localStorage` から
`world.json` へ移した理由がそのまま当てはまる。

**保存先で分類しない**（Spec 14 P3 / `failures.md` #52）。`world.json` に住むから
「村のカテゴリ」ではない — 呼び名は**アプリがどう振る舞うか**なのでシステム設定の
「全般」に置く。条例・役職が「この村がどういう村か」であるのと対になる。

### D2: アイコンの置き場は `{workspace}/user/icon.webp`

`agents/{id}/icon.webp` と**同じ規則**（`ICON_FILE` 定数を共有し、親フォルダだけ
違う）。`ConfigStore` へ `read_user_icon` / `write_user_icon` / `delete_user_icon` の
3 本を足す。既存の `read_icon` / `write_icon` / `delete_icon` は `AgentId` を取るので
**別関数にする** — `AgentId` に「利用者」を表す特別な値を作ると、その値が
`world.agents` の検索や `Endpoint::Agent` の照合へ漏れる。

**WebP への変換と 256px 角への中央切り出しは UI 側**、**コアはマジック番号と
512 KB の上限を検証する** — `icon_contract` が既に凍結済みで、利用者のアイコンも
同じ規律に従う（P0 で実測。起票時の Notes 3「既存に上限があるか確かめる」への答え）。

**検証は 1 実装を共有する。** 現状の `write_icon` は WebP マジック番号と
`ICON_MAX_BYTES` の検査を**関数の中にべた書き**しており（`config_store.rs:173-189`）、
`write_user_icon` を素直に足すと**同じ規律が 2 箇所に生える**。検証を述語へ
切り出し、両方がそこを通る形にする。**分かれてよいのは親フォルダだけ。**

### D3: 未設定のときは現状を 1 文字も変えない

`user_name` が `None` のとき:

- 封筒は `"ユーザー"`（今と同じ。**言語に追従させない**）
- 画面は `t("chat.you")`（今と同じ。ja「あなた」/ en「You」）
- アイコンは頭文字の円（今と同じ）

**未設定時に封筒を言語追従させるのは、この Spec の射程外。** 追従させると
既存の村で **en の利用者だけ封筒が `ユーザー` → `You` に変わり**、履歴の途中で
送り手名が切り替わる。S4（設定しなければ挙動が変わらない）を破る。

### D4: 設定したら封筒と画面は**同じ文字列**になる

`user_name = Some("たかはし")` なら、封筒は `【送り手: たかはし】`、画面の
表示名も「たかはし」。**言語を切り替えても変わらない。**

理由は `attribute_sender` の doc コメントが既に書いている —
「プロンプトと画面で同じ送り手が違う名前になると、利用者とエージェントの会話が
噛み合わない」（`Endpoint::System` を UI と同じ「Fuseforks」にした根拠）。
利用者にも同じ規律を適用する。

### D5: 呼び名は書式検査で拒否する。注意書きでは足りない

保存時に以下を**拒否**し、`CoreError` の新しい変種で返す:

- 空文字・空白のみ
- **`】` を含む**（封筒 `【送り手: {name}】` の閉じ括弧。含めると 1 つの発話の中に
  封筒が 2 つあるように読め、送り手を偽装できる）
- **改行・制御文字を含む**（封筒は 1 行目に入る。改行を通すと本文と封筒の境界が消える）
- **32 字を超える**（封筒は**毎ターン・全宛先**に乗る。長い名前は全ターンの
  固定費になる）

**注意書きを画面に置くだけにしない。** `api_key_env` は UI ラベル・注意文・
README・`data_contract` の 4 箇所に「実値を入れるな」と書いてあったが、型は素の
`String` で、実キーが平文で保存された（`failures.md` の該当項）。**自由入力欄に
壊れた値が入りうるなら、必ず入る前提で機械的な検査を置く。**

**拒否エラーに入力値を載せない**（同じ事故の処方の写し）。

### D6: 顔ぶれには載せない

`compose_presence` は `spec.connected_agents` から組む「**誰に何を頼めるか**」の
一覧で、利用者はサーヴァントの `ask` / `plan` の宛先ではない。載せると
「利用者へ委譲できる」と読める行がプロンプトへ入る。

**呼び名がプロンプトへ入るのは封筒だけ。** 顔ぶれ・条例・`Construct.md` の
どこにも入らない。

### D7: キャッシュの安定境界は動かない

封筒は**毎ターンの user ロール本文**に入る（`stable_len` の外）。system ブロックの
安定プレフィックスに呼び名は 1 文字も現れない。**呼び名を変えても全員の
プロンプトキャッシュは割れない。**

Spec 14 が役職について証明した `stable_len` 不変を、**同じ形の結合テストで留める**
（呼び名を設定しても安定プレフィックスが 1 字も動かない）。

### D8: 村を配ると呼び名とアイコンも付いて回る

`world.json` と `{workspace}/user/icon.webp` はどちらも workspace の中なので、
村を配れば受け取った人は**前の持ち主の名前で呼ばれる**。

**これを機構で防がない。** 受け取った人は設定画面で直せる（S3 の入口がある）。
Spec 14 が `work_dir` を役職の雛形から外した理由は「**端末ごとに違う絶対パスで、
存在しないパスを指す**」ことであって、名前は端末に依存しない — **同型ではない**。

**README へは 1 行書く**（配ると付いて回ること）。

## P5 実施記録（2026-08-05・利用者）

**5 件とも実機で確認、すべて OK。Spec 19 は Done。**

**ただし検収項目 4 は書き方が誤っていた。** 利用者の指摘 —「サーヴァントの絆に
影響する？ 会話ペインには影響するのは分かるが」。コードで裏を取った結果、
**絆の地図に利用者のアイコンが出る経路は 1 本も無い**:

- `TopologyMap.vue:53` のノードは `[...state.agents]` から生える（利用者は
  ノードとして存在しない）
- 描くアイコンは `state.icons[data.agent.id]`（エージェント分のキャッシュのみ）
- `userIcon` / `userName` の参照は**ゼロ件**

**利用者のアイコンが出るのは会話ペインだけ**（`AgentList.vue` も
`state.icons[agent.id]` なのでサーヴァント専用）。

**この誤りの質は「範囲が広すぎた」ことではなく、「絶対に失敗しない項目を置いた」
こと。** 見に行った側は、絆の地図で何も変わらないのを見ても
**「変わらないのが正解なのか、壊れているのか」を判断できない**。合格条件が
書かれていない検収項目は、注意を消費して疑いだけを残す。

**一般化**: **検収項目を書く前に、その画面がその値を引いているか数える。**
「関係しそうな画面」を並べるのは、実装を読まずに書ける分だけ安く見えるが、
**確かめられない項目は無いほうがまし**。Spec 14 D5（未決を立てる前に、その形が
実際にそうなっているかを見る）と Spec 17 P1（規則を凍結する前に、その差が
観測できるかを確かめる）の**検収版**で、同じ規律の三例目。

### D9: 絆の地図に利用者のノードを出さない（利用者裁定 2026-08-05）

上の訂正から出た「では出すべきか」に、利用者がその場で答えた —
**「みんなに話せるので意味ない。ユーザーはサーヴァントみんなと繋がっている」。**

実測で裏を取った: `send_user_message` は接続を**一切検査しない**
（`connected_agents` はサーヴァント同士の委譲にしか効かない）。UI 側の門も
「稼働中か」だけ。**利用者の辺は構造上かならず全結線**になる。

**地図の情報量は「繋がっていない組み合わせがある」ことから来る。** 全員と繋がる
ノードを足すと、辺が N 本増えて情報は 0 しか増えない。利用者の到達範囲は
そもそも線で描かれていない = **トポロジーの模型の外に居る**（「線は人が引く」の裏返し）。

**凍結 5（顔ぶれに載せない）と結論は同じだが根拠が違う。** 顔ぶれは
*誤読を誘発する*（載せると「利用者へ委譲できる」と読める）。地図は*無情報*
（誤読ではなく、足しても何も分からない）。**同じ結論に別々の根拠があるときは
両方書く** — 片方が将来変わっても、もう片方が残る。
`data_contract` の `user_identity_contract` 凍結 9 として凍結した。

## Notes

1. **`】` の拒否は利用者を疑っているのではない。** 封筒の書式が壊れると、
   モデルが 1 つの発話を 2 つの発話として読む。同じ理由で改行も落とす。
   **利用者自身が送り手を偽装しても損をするのは利用者だけ**だが、事故として
   起きたときに原因が画面から読めない種類の壊れ方になる。

2. **32 字の根拠は封筒の位置。** 毎ターン・全宛先に乗るので、100 字の名前は
   1 ターン 100 字 ×（宛先の数）の固定費になる。役職の説明を「自分の分は全文・
   他人の分は名前だけ」に分けた判断（値段と価値の非対称）と同じ考え方。

3. **アイコンの上限は既にあった**（P0 で決着）。`icon_contract` が WebP 固定・
   512 KB・256px 中央切り出しは UI 層、を 2026-07-28 に凍結済み。**起票時に
   「Phase 2 で確かめる」と書いたが、契約を読めば起票の時点で消えていた未決**
   — Spec 14 の D5 と同じ形（未決を立てる前に、その形が実際にそうなっているかを見る）。
   **同時に、契約を読んだからこそ検証のべた書きが見つかった** — 未決を早く潰す
   価値は答えそのものではなく、隣の実装を読む口実になること。

4. **`chat.you` の辞書キーは残す。** 未設定時のフォールバックとして使い続けるので
   消さない — 消すと未設定の村で表示名が空になる。

5. **セッションを跨いだ改名に何も作らない。** 呼び名を変えても過去の履歴と
   会話ログの `【送り手: 旧名】` はそのまま残る。Spec 14 が役職の改名について
   出した結論（「system プロンプトは毎ターン組み直されるので現在の役職が必ず勝つ。
   残るのは履歴の残り香だけ」）と同じで、**残り香を消す機構は作らない**。
