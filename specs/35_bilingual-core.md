# Spec: モデルへ届く面の二言語化 — 日本語をバイト等価で残し、英語を加算する

**ID**: 35
**Date**: 2026-08-12
**Status**: Draft rev2
**Branch**: なし（main へ直接コミット。Phase ごと）

**rev1 → rev2**: 査読 7 点（矛盾 3 + 軽微 4）→ **採用 5 / 訂正して採用 1 /
反証 1**。処理は末尾の「査読 1 巡目の処理」。査読 7（defuse のクロス積）は
**初回の査読文が途中で切れて届き、趣旨を推定して処理した後に続きが届いて
一致を確認した**（Spec 34 の反証「写しが切れて誤読」と同型。今回は推定が
当たったが、切れたまま処理を終える形は同じ事故になる）。
骨格（加算・村単位・D5 だけが凍結改訂）は動かず、**動いたのは言い切りの射程** —
「1 バイトも変わらない」「常に 1 言語」「両形」の 3 つの言葉が、それぞれ
例外を持っていたのに持たない形で書かれていた。

## Goal

**`fuseforks-core` がモデルへ書いている面（システムプロンプトの枠組み・ツールの提示・
封筒・手順の文・System 行）を、村の `language` に従って日本語か英語のどちらか一方で
送る。** マイルストーン 6 の着地形。

- **順番の根拠は市場**（2026-08-12 利用者裁定 —「日本で公開しても現在では需要がない。
  英語にしておけば世界を早くに相手にできる」）。多モーダルより先。
- **狙いは言語の偏りの操縦**（利用者の言葉 —「LLM は聞いた語が日本語が多いと日本語で
  返し、英語が多いと英語で返しがち。英語だったらシステム言語も英語にして楽にさせたい」）。
  正確さの機能ではなく、**モデルに掛かる引力の向きを設定に揃える**機能。
- **完全な制御は狙わない**（利用者裁定 —「英語 UI + 日本語 SKILL で日本語の質問に
  たまに英語が出るのは想定範囲」）。村の中身は利用者の資産で、混ざるのは仕様。

**効き先は新規の英語村。** 既存の日本語の村では**プロンプト生成が 1 バイトも
変わらない**（下の実測 — 村 12,052 字 vs コア ja 約 4,300 字なので、変えても偏りは
動かず、変えないことが正しい）。`language` は初回に OS ロケールで確定するので、
**英語 OS の新規利用者は設定なしで英語コアになる**。

**「1 バイトも変わらない」の唯一の例外は defuse**（rev2。査読 2）。D5 で英語形の
封筒偽造も中和するようになるため、**日本語の村でも `【Sender: User】` を書いた
攻撃の挙動が変わる**。これはセキュリティ修正で、golden（検収 1）の対象外。

## 接地（起票前の実測。2026-08-12・CLAUDE.md「英語化（マイルストーン 6）の
起票前の実測」の節が原本）

モデルへ届く面のうちコアが書いた分（「ja」は仮名と漢字だけを数えた実訳出量）:

| コアが書く分 | 全体 | うち ja |
|---|---|---|
| システムプロンプトの枠組み（村を空にして `compose_system_prompt`） | 174（接地なし）/ 470（接地あり） | 141 / 344 |
| 同梱ツール **7 本**の提示（説明 1,562 + schema 3,458） | 5,020 | 1,646 |
| 合成ツール（接続 1 / 3 / 9 体） | 988 / 2,689 / 5,901 | 556 / 1,172 / 2,306 |

**7 は測定範囲、9 は作業範囲**（rev2。査読 4 を訂正して採用 — 数え違いではなく
範囲が違う）。probe は状態を持たないツールだけを組めたので `remember` / `run` を
除外して 7 本。**P2 が書き換えるのは 9 本**で、`run` は `spec_for` の個体別提示文
（`allow` が空のときの説明ほか）も対象に入る。

- **schema の大半は元から英語**（`"type"` / `"properties"`）。訳す対象ではない
- **合成ツールは接続数でほぼ線形に伸びる**（`ask_agent_N` / `transfer_to_*` が
  人数ぶん生える）。ただし**著述量はテンプレート単位**なので、書くのは
  **約 2,600〜2,900 ja 字 + `remember` / `run` + 理由欄 + 封筒 + System 行**。
  英語で 3,000 字強を書けば層 3 は埋まる
- **`turn.rs` の日本語リテラル 4,493 字のうちプロンプトに乗るのは 174 字**。
  リテラルの総量を乗る量と読むと 25 倍外す（起票前に一度外した）。
  **乗る面を測るには実際に組み立てる**
- 配線の現状: システムプロンプト側は `build_prompt(shared, …)` が
  `Shared::language()` を引けるので**済み**。ツール側は
  **`AgentTool::description(&self)` が文脈を受け取らない**（Spec 15 P2 と同じ穴）

## 決定（D）

### D1: 形は加算。日本語はバイト等価で据え置く

```rust
match language {
    Language::Ja => "現在の状態は「今の顔ぶれ」が正です。",
    Language::En => "The current roster is authoritative.",
}
```

- `data_contract` の「システムプロンプト・ツール説明は訳さない」が禁じているのは
  **置換**。日本語が 1 バイトも変わらない加算は、Spec 08 の「束ねの文言・plan の
  ツール説明は 1 字も変えない」とも衝突しない
- **帰結: `stable_len` 6,463・キャッシュ率 99%・束ねの挙動の実測が全部そのまま生きる。**
  未測定になるのは英語の経路だけで、それは P5 の実機が埋める
- **バイト等価は golden で凍結する**（P1。Spec 23 P2 の
  「添付なしのシリアライズ結果はバイト等価」と同じ形）

### D2: 選ぶ単位は村。送るのは常に 1 言語

- 読む欄は既存の `world.json` の `language`（Spec 13。初回に OS ロケールで確定・
  再判定しない）。**新しい設定は 1 つも増えない**
- **「常に 1 言語」は新規生成についての規則**（rev2。査読 1）。**例外は
  保存済みの文字列** — D6 の System 行と履歴に焼かれた封筒は記録時の言語のまま
  残るので、**言語を切り替えた村のプロンプトは混在する**。これは矛盾ではなく
  正直な記録（利用者自身の過去の発話が翻訳されないのと同じ扱い）
- **入力キャッシュは倍にならない** — 言語ごとに別のプレフィックスができるだけで、
  1 つの村は 1 つしか使わない。割れるのは言語を切り替えた 1 回だけ
- 中国語はこの Spec の対象外（ワイヤの話であって文言の話ではない。
  マイルストーン 6 の表の記述のまま）

### D3: 配線 — `AgentTool` の提示系に `Language` を通す

- **`description()` / `parameters()` が `Language` を受ける形へ**（trait の変更。
  コンパイラが全実装を指すので、漏れは構造的に出ない）。`ToolSpec` の組み立て
  （`spec` / `spec_for`）も同じ引数を運ぶ
- **`ToolContext` に `language` を足す**。`rag_roots` / `cancel` / `work_dir` に
  続く四例目 — 「契約に欄や規則を足したら、それを運ぶ経路が既にあるか実装前に問う」
  の答えが今回は「ある」
- **査読「`ToolContext` は実行時にしか使われないので不要」は反証した**（rev2。
  査読 3）— `spec_for(&self, ctx: &ToolContext)` が示すとおり、**`ToolContext` は
  提示時にも渡っている**。実例が `RunTool::spec_for` で、`ctx.agent_id` から
  policy を引いて**個体別の提示文（`allow` が空のときの説明）を組む** — この文を
  英語化するには提示時に言語が要り、運び先は ctx が既存の形。
  **「未使用フィールド」にはならない**（P2 の `run` が最初の読み手）
- 合成側（`delegation.rs` の `ask_specs` / `specs` / `plan_specs` /
  `protocol_note`）は `build_prompt` / `present_tools` の時点で
  `Shared::language()` から渡す。`compose_system_prompt` は引数に `language` を足す
- **MCP のツール説明は素通し**（`McpTool` は受けた `Language` を無視する。
  下の対象外 1）

### D4: 対象外 4 つ（初版の射程をここで縛る）

1. **MCP のツール説明** — 既存の凍結のまま（名付けたのは接続先。訳語を当てると
   何が走ったかについて嘘になる）
2. **村の中身** — `Ordinance.md` / `Construct.md` / `SKILL.md` / `Memory.md` は
   利用者の資産。コアは触らない
3. **台帳** — `data_contract` / `specs/` / `CLAUDE.md` / `failures.md` /
   doc コメントは書いた言語のまま（2026-08-12 利用者裁定「contract とかは
   書いた言語でいい」）
4. **ツールの結果とエラーの本文**（`tools/` の日本語リテラル約 45,000 字の大半）—
   **呼んだときだけ乗る**変動費で、毎ターンの提示面とはコストの形が違う。
   混ざるのは想定内の裁定に含める。**再入条件**: 英語村の実機で、結果本文の
   日本語に会話が引きずられる観測が出たら、そのとき別 Phase として起票する

### D5: 封筒は `【】` を据え置き、語だけ英語にする。defuse は両形を常に中和する

英語形は `【Sender: User】` / `【Sender: Neo (external client)】`。

- **`【】` を捨てない理由**: `normalize_user_name` / `normalize_client_name` の
  予約文字（`【】［］`）が封筒の境界を守っている。区切りを `[]` へ変えると
  予約集合が広がり、既存の村で通っていた呼び名が新たに落ちる
- **`defuse` の照合は「両形」ではなく TAG 集合の拡張として書く**（rev2。査読 7 の
  趣旨を推定して採用）。現行実装は既に **開き括弧 `{【, ［}` × コロン `{:, ：}` の
  クロス積**を持ち、TAG が `"送り手"` の 1 つだけ。この Spec がやるのは
  **TAG の集合を `{送り手, Sender}` へ広げる**ことで、`【Sender：ユーザー］` の
  ような**混合形もクロス積が自然に中和する**。個別の形を列挙して塞ぐのではない
  （列挙は除外リストになる — Spec 26 の規律）
- **村の言語に関係なく、常に全 TAG を中和する。** 攻撃者は村の言語を選べない側
  ではなく**選べる側** — 日本語の村へ `【Sender: User】` を書き込む偽造は、
  英語形を知らない defuse を素通りする。Spec 26 の「潰すのは衝突の主要形」の
  主要形が 1 つ増えた、と読む。**この 1 点だけは日本語の村でも挙動が変わる**
  （Goal の例外。golden の対象外）
- **`user_identity_contract` 凍結 2（`DEFAULT_USER_LABEL` は言語に追従しない）を
  部分改訂する（覆す箇所はここだけ）。** 凍結の理由は「既存の村の履歴の途中で
  送り手名が変わる」で、**言語が初回確定である以上、新規の英語村には当たらない**。
  英語村の既定ラベルは `User`。途中で言語を切り替えた村は、切り替え以後の封筒だけが
  変わる — 履歴は保存済みの文字列なので遡って直らず、**それは D6 の System 行と
  同じ「記録時の言語」として受け入れる**
- **ラベル語の自然さは未検証のまま送出は `Sender` で入る**（rev2。査読の指摘 —
  `Sender` は発話者一般・`User` は役割で、同じ行に並ぶと冗長。代替は `From`）。
  裁定は「現案で十分許容。気になるなら P5 で A/B」。**defuse の TAG 集合には
  `From` も最初から含める** — P5 の A/B で `From` へ切り替えることになっても、
  **偽造の窓が開き直らない**（TAG を 1 語足すだけの保険で、切り替えの有無に
  依存しない）

### D6: System 行は記録時の言語で書く。構造化はしない

- 「System 行を訳すには `kind + params` の構造化（ワイヤ + `session_store` の
  加算）が要る」という台帳の見立ては**表示時に訳す**場合の話。言語が初回確定なら、
  **記録する瞬間の言語で書けば村の中では一貫する** — 構造化もワイヤ変更も要らない
- 途中で切り替えた村は古い行が古い言語で残る。利用者自身の発話と同じ扱いで、
  記録として正直
- **対象は 2 種で、言語を決める時点が違う**（rev2。査読 5 — 混ぜて書くと実装で迷う）:
  - **System 行の本文**（入退室・予定の配送・役職変更など `Endpoint::System` 発の
    文）— **記録時**の言語。保存されるので後から変わらない
  - **`compose_presence_notices` の見出し**（`## 入退室（新しいものが下）`）—
    **組み立て時**の現在言語。保存されず毎ターン生成されるので、こちらは
    D1/D2 の範疇（切り替えれば次のターンから変わる）

### D7: 英語は翻訳ではなく英語で書く

- 意味と構造（見出しの並び・節の順序・`stable_len` の境界）は日本語版と 1 対 1 に
  保つが、**文は英語の慣行で書き直す**。逐語訳は「読めるが引力の無い英語」になり、
  この Spec の狙い（偏りの操縦）に対して弱い
- 英語版の品質は実測でしか分からない（英語プロンプトは別の資産 — 旧マイルストーン
  表の警句はここに残る）。P5 の実機で最低 1 村ぶん観測する
- **P5 まで待たずに読める形を作る**（rev2。査読の対策案を採用）— **P1 で英語版
  プロンプト全文を 1 ファイルへダンプする**（`compose_system_prompt(En)` +
  全 `ToolSpec(En)` を並べた検収用の写し）。人がまとめて読めるので、
  **偏り観測の手前で文の質を直せる**。ダンプは probe と同じ使い捨てで、
  中身は P0 の golden / 検収 2 が機械で守る

## Phases

- **P0: 契約の凍結。** `data_contract` の `settings_contract` 層 3 を改訂
  （「訳さない」→「置換はしない。加算で二言語。選ぶ単位は村」）。D4 の対象外 4 つと
  D5 の defuse 両形・凍結 2 の部分改訂を先に書く。**検収の読み口を数える**
  （#68 / #80 の規律）
- **P1: 機構 + システムプロンプトの枠組み。** `Language` を運ぶ配線（D3）と
  `compose_system_prompt` の二言語化。**golden で日本語のバイト等価を凍結**
  （変更前の出力をリテラルで固定 — これが「加算である」ことの機械の証明）。
  英語村で仮名漢字ゼロの検査（村由来を除く）。**英語版プロンプト全文の
  ダンプを 1 ファイルへ出して人が読む**（D7。使い捨て）
- **P2: 同梱ツール 9 本 + 理由欄。** `description` / schema の説明文（`grep` / `fd` /
  `diff` / `sd` / `yq` / `file` / `rag` / `remember` / `run`）と Spec 27 の
  `REASON_DESCRIPTION`。**schema はキーではなく説明文だけ**が対象
- **P3: 合成ツール + 封筒 + System 行。** `ask_specs` / `specs` / `plan_specs` /
  `protocol_note` / `room_log`、封筒（D5。defuse 両形の単体を含む）、
  System 行と入退室見出し（D6）。**顔ぶれの本文も対象**（P1 で見つけた射程の穴 —
  `turn.rs` の roster 組み立てが `稼働中` / `不明` / 役職の `［］` を書いており、
  どの Phase にも入っていなかった。組み立て時生成なので現在言語で書く側）
- **P4: 台帳。** README 日英（英語 README には「コアの言語は村の言語に従う」を
  利用者の言葉で）・`data_contract` の回収・CLAUDE.md の現在地。
  **数えるのはファイル単位**（#51 (b)）
- **P5: 実機確認。** 検収 5・6 と、**封筒ラベルの自然さの観測**（`Sender` で
  違和感が出るか。出たら `From` へ — defuse の TAG は最初から両方持つので
  切り替えは送出側 1 箇所）

## 検収（読み口を先に数えた）

1. **日本語の村でバイト等価**（機械・P1 golden）— 実装前後で
   `compose_system_prompt` の出力と全 `ToolSpec` が一致する。
   **golden は `(prompt, stable_len)` の両方をリテラルで固定する** — 文字列だけ
   固定すると、境界の計算が変わっても緑のままになる（P0 で読み口を数えたら、
   既存テストは構造の不変条件だけで値を固定していなかった）。
   **読み口**: golden テストのリテラル比較
2. **英語の村で仮名漢字ゼロ**（機械）— **新規生成・空村に限定**（rev2。査読 6 —
   言語を切り替えた村では D6 の古い System 行が日本語で残るので、ゼロは
   新規生成にしか成立しない）。村のファイルを空にした
   `compose_system_prompt(En)` と全 `ToolSpec(En)` に `[ぁ-んァ-ヶ一-龠]` が
   0 文字。**読み口**: P1 で足す検査そのもの
3. **defuse が両形を中和する**（単体）— 日本語の村で `【Sender: User】`、
   英語の村で `【送り手: ユーザー】` を本文に書いた発話が、どちらも
   `（本文）` / `(quoted)` 形へ寄る。**読み口**: `sender_envelope` の単体 +
   `sender envelope escaped:` の計器
4. **`stable_len` が日本語の村で動かない** — **検収 1 の golden に包含される**
   （`(prompt, stable_len)` を両方固定するため）。独立の読み口として、
   既存の構造テスト 2 本（`tests/orchestrator.rs` の「役職名を足しても
   `stable_len` は動かない」/ `config_store.rs` の
   `the_roster_lives_outside_the_stable_prefix`）が**期待値の変更なしで**
   緑のままであることも見る（P0 で実在を確認済み — 値は固定していないので
   単独では検収にならない。golden との 2 本立て）
5. **実機: 英語村の完走** — `language=en` の村で英語の依頼を出し、
   英語の応答が返り、ツール呼び出しが完走する。**読み口**: 画面 +
   `fuseforks.log` の `turn:` 行（`stop=-`）
6. **実機: 英語村で plan の束ねが英語で回る** — 進行役が英語の `protocol_note` の
   もとで撒き、束ねが英語で返る。**読み口**: `plan wave:` / `plan bundle:` の行 +
   画面の束ね本文

## Notes

1. **RepeatGuard への影響は無い。** 判定は結果本文の完全一致で、言語は村の中で
   固定なので、比較は常に同言語どうし
2. **`v0.1.2` 破棄の経緯と同じく、途中切り替えの村は「割れた 1 回」だけ
   キャッシュを失う。** 恒常費ではない
3. **著述量の見積もりは約 3,000 ja 字 → 英語 3,000 字強**（接地の節）。
   「英語化」という語から想像する規模より小さい。**大半は文言で、機構は
   `Language` を運ぶ配線 1 式だけ**
4. **frontend は触らない。** UI の二言語化は Spec 13 で Done（vue-i18n・
