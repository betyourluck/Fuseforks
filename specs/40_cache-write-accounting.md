# Spec: キャッシュ書き込みを数える — `cache_creation_input_tokens` が `prompt` へ畳まれている

**ID**: 40
**Date**: 2026-08-18
**Status**: **起票（rev1・査読前）**
**Branch**: P0（契約）は rev 承認後に main 直コミット。P1 以降は `YYYYMMDD_cachewrite` へ積む

## Goal

**Anthropic のキャッシュ書き込みトークンを、読み取りと別に数えられるようにする。**

起点は利用者（2026-08-18）—「API のトークン単価のサイトを作り、そこから JSON で
だいたいの使用料を算出させようかなと思っている」。**算出の入力になる数字に、
倍率が 2 倍違う 2 つの量が同じ欄へ畳まれている。**

**この Spec は「数えられるようにする」までを扱う。** 通貨への換算は扱わない
（Spec 39 D5 の凍結。倍率は外部の価格表が持つ）。

**これは拡張か収縮か**: 拡張（canonical の `Usage` に欄が 1 つ増え、6 ワイヤの
decode を数え直し、記録と画面へ伸びる）。**収縮側の選択肢は D0 に置く。**

## 現況（実測 2026-08-18。参照は行番号ではなく関数名と定数名）

**`anthropic.rs` の `usage` の写しが、3 つの量を 2 つの欄へ落としている**:

```rust
prompt:     u.input_tokens + u.cache_read_input_tokens + u.cache_creation_input_tokens,
cache_read: u.cache_read_input_tokens,
```

- **`cache_creation_input_tokens` は読まれているのに、独立した行き先が無い。**
  ワイヤ型 `AnthropicUsage` には欄があり、doc も「キャッシュ書き込みに要した
  トークン数」と正しく書いてある。**捨てているのではなく、畳んでいる**
- 下流が「未キャッシュ」として扱う量は `prompt − cache_read` で、これは
  **`input_tokens`（本当に新しい入力）と `cache_creation`（書き込み）の和**。
  **前者は 1.0×、後者は 2.0× で課金される**
- **倍率が 2.0× なのは、この村が `CACHE_TTL = "1h"` を送っているため**
  （`anthropic.rs` の定数。5 分なら 1.25×）。**同じ表に読み取り 0.1× も書いてある**
- **どのログ行にも、どのレコードにも出ていない** — `cache:` 行が出すのは
  `prompt` と `cached`（= `cache_read`）だけ。`turn:` 行も `Record::Turn` も同じ。
  **だから既存のログを遡っても大きさが測れない**（これが Phase 構成を決めた）

**書き込みは最初のターンだけではない。** `place_message_breakpoint` が
**毎ターン、最後の発話の最後のブロックへ境界を打つ**（`failures.md` #42 の処方）。
つまり各ターンは前回の境界までを読み、**そのターンで増えた分を新しく書く**。
`cache_creation` はターンごとに立つ量であって、初回限定の固定費ではない。

**6 ワイヤのうち、書き込みの概念を持つのは Anthropic だけ**（decode を全部読んだ）:

| ワイヤ | 読み取り | 書き込み |
|---|---|---|
| **Anthropic** | `cache_read_input_tokens` | **`cache_creation_input_tokens`** |
| OpenAI 互換 | `prompt_tokens_details.cached_tokens` | 欄が無い |
| Gemini | `cachedContentTokenCount` | 欄が無い（**この村は cache を作っていない** — 暗黙のみ） |
| xAI Responses | `cached_tokens` | 欄が無い |
| OpenAI Responses | `cached_tokens` | 欄が無い |
| Meta Responses | `input_tokens_details.cached_tokens` | 欄が無い |

**「欄が無い」と「0 だった」は、ここでは同じ扱いでよい** — 書き込みに課金しない
プロバイダでは、書き込みトークンは費用の計算に現れない量だから（`reasoning` を
`Option` にしなかったのと同じ判断。`canonical.rs` の doc が理由を書いている）。

## この見落としの機序（#62 / Spec 32 P0 と同型）

**Spec 32 は「捨てている `decode` の行」で数えたので、思考を `completion` へ
足し込んでいた Gemini が網の外に落ちた。今回はその裏返し** —
`cache_creation` は**捨てられておらず `prompt` へ足し込まれている**ので、
「捨てている行」を探す走査にも、`dropped` の計器にも、1 件も出ない。

**一般化: 数え落としは「捨てている場所」ではなく「畳んでいる場所」に住む。**
畳みは情報を消すが、消したことを何も記録しないので、**捨てた回数を数える計器
（#72 の処方）を置いても捕まらない。** 見つけるには「この式の右辺に、
左辺の名前と違う概念が混ざっていないか」を型ではなく単位で問う必要がある。

## 設計の核

**`Usage` に `cache_write` を足し、`prompt` の内数として持つ。** `cache_read` と
同じ規律（`prompt` は 3 つの和のまま。**既存の下流はバイト等価で動く**）。

```text
prompt = input + cache_read + cache_write    ← 不変条件（Anthropic のみ 3 項）
未キャッシュ = prompt − cache_read − cache_write
```

**倍率はここに焼かない。** 記録するのは生のトークン数だけで、2.0× / 0.1× を
掛けるのは外部の価格表の仕事（Spec 39 D5 と同じ線）。**例外は予算の実効トークン**で、
あちらは内部の重みなので D3 で別に裁定する。

## 決めること

### D0. そもそも足すか（収縮側の選択肢）

**足さない案**: 価格表の側で「未キャッシュのうち一定割合は書き込み」と仮定して
掛ける。**却下を推す** — 割合はターンの形（ツールの周回数・履歴の伸び）で動くので、
仮定した瞬間に**検証できない数字を検証できるかのような見た目で配る**ことになる
（Spec 05 が `sources` 空のときに縮小した判断と同じ）。**ただし裁定は利用者。**

### D1. `Usage.cache_write` は `prompt` の内数か外数か

**内数**（`cache_read` と同じ）。外数にすると `prompt` の意味が Anthropic だけ
別になり、**`turn:` 行の `prompt=` が他ワイヤと比較できなくなる**。

### D2. 他 5 ワイヤは 0 固定か `Option` か

**0 固定。`Option` にしない** — `reasoning` の前例（`canonical.rs` の doc）。
「取れない」と「0 だった」を型で分けると表示側が 2 状態を扱う。

### D3. 予算（`budget.rs`）の重みを変えるか — **本 Spec で最も重い決定**

実効トークン = 未キャッシュ ×1 + キャッシュ済み ×0.1 + 出力 ×4（Spec 11 で凍結）。
書き込みを 2.0× で数えると**同じ天井がより早く尽きる**。

- **変える利点**: 天井が実際の支払いに近づく
- **変える代償**: **既存の村の `tokenBudget` の意味が黙って変わる**。1,000,000 と
  書いた人は「今までと同じ量」を期待するのに、実効が増えて波が早く欠ける
  （Spec 38 の代償がより早く出る）。**破壊的変更**で、Spec 11 の凍結に触れる
- **私の推し: 本 Spec では変えない。** 記録と表示だけ先に入れ、**測ってから
  別 Spec**（重みは「実際の値段」ではなく「歯止めの単位」で、目的が違う）。
  ただし**契約に「実効トークンは書き込みを 1.0× で数えている」と明記する** —
  書かないと、記録が正しくなったあとに実効だけが古い前提のまま残る

### D4. 統計画面に出すか

**`Slice` に `cacheWrite` を足す。列は増やさない** — 既存の「キャッシュ率」の
`title`（ホバー）へ内訳を出す。**8 列ある表に 9 列目を足すと横スクロールが常態化**
する（`stats-table` は既に `overflow-x-auto`）。

### D5. `cache:` 行へ `cache_write=` を足す

**足す。末尾へ 1 つ**（`observability_rule` の「接頭辞と既存欄の並びは変えない」）。
**P1 の目的そのもの** — これが無いと大きさを測れない。

### D6. 5 分 / 1 時間の内訳を取るか

**取らない（rev1）。** この村は `CACHE_TTL = "1h"` 固定なので倍率は 2.0× で一意。
**未測定**: 新しい API は `cache_creation: { ephemeral_5m_input_tokens,
ephemeral_1h_input_tokens }` を返すとされるが、**この村のワイヤ型は平坦な
`cache_creation_input_tokens` しか持たず、実際に何が返るか撃っていない**。
TTL を可変にするときに測る（Notes 2）。

## Stories

- **S1**: 価格表 JSON を持つ利用者が、`turn` レコードから **Anthropic の請求額を
  倍率どおりに**再現できる（書き込み 2.0× / 読み取り 0.1× / 未キャッシュ 1.0×）
- **S2**: `cache:` 行を grep すると、そのターンで**何トークン書いたか**が読める
- **S3**: Anthropic 以外の個体では `cache_write=0` が出て、**書き込みの概念が
  無いことと 0 だったことが同じ形**で並ぶ（対照が組める）

## 検収（**書く前に、その値がどこから引けるかを数えた** — #68）

1. `cache:` 行に `cache_write=` が出る。**Anthropic の個体で 0 でない値**が出る
   （0 しか出ないなら P1 の配線が死んでいる。**肯定の対照を先に取る**）
2. 同じ走行で、**Anthropic 以外の個体の行は `cache_write=0`**（S3 の対照）
3. **`prompt` は `input + cache_read + cache_write` に一致**する。1 ターンの
   `cache:` 行の 3 値で検算できる（**この等式が破れたら畳み方を間違えている**）
4. P1 の前後で、**`turn:` 行の既存欄が 1 文字も変わらない**
5. P2: 未キャッシュに占める書き込みの割合が出る。**予測を観測の前に書く**（#80）

## Notes

1. **`prompt` を変えない理由。** `prompt` から書き込みを外すと `turn:` 行の
   `prompt=` が縮み、**8 日ぶんのコスト実測（CLAUDE.md「コストの実測」の節）と
   比較できなくなる**。あの数字は今後この領域を触るときの基準なので、
   **単位を動かすほうが高くつく**
2. **未測定 2 件**: (a) D6 の 5m / 1h の内訳が実際に返るか (b) **`cache_creation`
   に課金されたトークンが `input_tokens` にも重複して現れないか** — Anthropic の
   3 値が排他だという前提は doc の読みで、**この村では撃っていない**。検収 3 の
   等式がそのまま検定になる（**破れたら前提が誤り**）
3. **Gemini の明示キャッシュは対象外。** あちらは事前に cache を作る API 呼び出しが
   要り、この村は呼んでいない（CLAUDE.md「Gemini Context Caching は Anthropic と
   形が違う」）。**呼ぶようになったら作成コストが別に立つ**ので、そのときに戻る
4. **価格表の鍵は `model` 単独では足りない可能性がある** — レコードは `model` と
   `backend`（ワイヤ名）を持つが `base_url` を持たず、**OpenAI 互換の口は複数の
   ベンダーが共有する**。本 Spec の射程外だが、表を作る側で先に決めること
