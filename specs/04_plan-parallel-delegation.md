## Goal

進行役のエージェントに `plan` ツールを渡す。進行役が**工程の 1 波**
（どのワーカーへ何を頼むか、の並列集合）を出すと、コアが並列配送・
合流（join）・タイムアウト・集約を**コード側で保証**し、束ねた結果を
進行役へツール結果として返す。

### 立場の宣言（この製品の答え）

オーケストレーションの工程を**誰が作るか**には 3 流派ある:
人間が静的に書く（Airflow 型）/ 高位モデルが動的に作る / 創発（計画なし）。
Concordia は「設定が少なくて分かりやすい」がコンセプトであり、
**人間に DAG を書かせる道は採らない**。採るのは:

- **計画はモデルが作る**（進行役 = 高位モデルが毎回その場で）
- **実行の保証はコードが持つ**（並列・合流・タイムアウト・集約・燃料）

計画の逐次即興はエラーが複利で膨らむ — だからモデルには「1 波を宣言する」
ことだけをさせ、波の実行は決定論で回す。波の結果を見て次の波を出すのは
再びモデルの仕事（plan → 結果 → plan の往復が、多段 DAG の動的な代替になる）。

### 何が新しくなるか

現状の道具立てには「並列に撒いて、全部待って、束ねる」だけが無い:

| 経路 | 並列性 | 答えの行き先 |
|---|---|---|
| `ask_*`（委譲） | **直列**（1 体ずつ待つ） | 依頼主へ戻る |
| `transfer_to_*` fan-out | 並列 | **ユーザーへ散る**（合流しない） |
| `plan`（本 Spec） | **並列** | **束ねて依頼主へ戻る** |

ワーカー 3 体へ独立サブタスクを撒く場面で、直列 ask は壁時計が人数倍になる。
また、ワーカー間の調整会話が構造（join）に置き換わるため、
**トークン思想的にも節約側**である。

なお、凍結中の「ユーザーからの同報」（failures.md #25）の戻し条件 1
「進行役だけに調整ツールを渡す（構造で縛る）」は、本 Spec がその実装である。
**ユーザー側の同報 UI は凍結のまま** — 並列の入口は進行役への依頼に一本化する。

## Stories

### P1: plan ツール

> 進行役として、複数のワーカーへ独立した作業を並列に頼み、全員の答えを
> 束ねて受け取る。なぜなら直列の委譲は人数分遅く、ワーカー同士に調整させる
> と反響とトークンで支払うことになるから。

**ツール定義**

- name: `plan`
- **提示条件: 接続先が 2 体以上のエージェントだけ**（設定は増やさない。
  トポロジーがそのまま「進行役かどうか」を決める。1 体なら `ask_*` で足りる）
- 引数（`to` は**閉じた列挙**。自由文字列にしない — rev2 指摘 1）:
  ```json
  {
    "tasks": [
      { "to": "agent_2", "message": "依頼内容" },
      ...
    ]
  }
  ```
  ```jsonc
  // tasks[] のスキーマ。to は接続先の AgentId をそのまま enum に並べる
  {
    "type": "object",
    "properties": {
      "to": { "type": "string", "enum": ["agent_2", "agent_3"],
              "description": "依頼先。agent_2 = ザリ・ロブステル / agent_3 = ジェミー" },
      "message": { "type": "string", "description": "その相手への依頼内容" }
    },
    "required": ["to", "message"],
    "additionalProperties": false
  }
  ```
  `message` は **`string` かつ必須**（`ask_*` の `message` と同じ形。
  欠けた場合の本文フォールバックは持たない — `transfer_to_*` は宛先が
  1 つなので本文で代替できるが、plan は宛先ごとに内容が違うのが前提で、
  同じ本文を全員へ配ると「相手ごとに依頼を変えられる」という説明が嘘になる）
**失敗の 3 分類（rev3）**

処方が分かれる根拠は「**その値がいつ確定するか**」の 1 点だけ。

| 分類 | 例 | 処方 |
|---|---|---|
| **静的な不正** — 波の中で不変、事前に確かめられる | 宛先が接続先集合に無い／同一宛先の重複／`tasks` が空 | **何も配送せず差し戻す** |
| **波全体で一様に決まる制約** — 波の中で不変、全タスクが同じ値を共有 | `hop` の上限到達 | **何も配送せず 1 つの結果文字列**（N 個の同じ文字列を返さない） |
| **動的な失敗** — 確かめた瞬間と配送の瞬間で違いうる | 停止中／受信箱飽和／無応答／タイムアウト／ワーカーが転送した | **そのタスクの結果文字列**（道連れなし） |

**3 分類はいずれも `Ok(String)` の 1 ツール結果として返る。** 差し戻しも
エラーチャネルを使わない — 「ツールの失敗で会話を止めない」既存規律
（`ask_agent` が停止中・タイムアウトを全部 `Ok(String)` で返しているのと同じ）に
従う。`Err` を返すと実行ループが `ツールの実行に失敗しました: {err}` で包み、
モデルが読むべき「なぜ配送されなかったか」が一段深い所へ埋まる。
**分類は文言の違いであって、経路の違いではない。**

`hop` を動的に入れないのは、**1 回の plan の中で `hop` が変わらない**から。
全タスクが同じ `incoming.hop` を共有するので、波の開始時点で全員一様に決まる。
「確かめても配送時には別の値」という動的の定義に当てはまらない。

- 動作（コアの保証）:
  1. 静的な不正を**全件**検証する（上表 1 行目）。1 件でも不正なら
     **何も配送せず**読める文言で差し戻す（部分実行は「どこまで走ったか」の
     追跡を利用者に強いる）。**稼働状態はここで見ない**
  2. `hop` を 1 回だけ確かめる（上表 2 行目）。上限なら何も配送しない。
     判定式は **`incoming.hop + 1 >= max_hops`** — `ask_agent` と**同一**にする
     （`saturating_add(1)` を含めて。片方だけ境界がずれると、同じ配置で
     ask は通り plan は止まる、という説明できない差になる）
  3. 検証後、全タスクを **ask と同じ封筒（返信路つき）で並列配送**
  4. `ask_timeout` を**波全体ではなくタスクごと**に適用し、join で全員を待つ。
     **並列なのは配送で、壁時計はキュー待ちを含む最遅 1 体分**
     （各ワーカーの受信箱は 1 本でターンは直列に処理される。Notes 8）
  5. 動的な失敗は**そのタスクの結果文字列**になる（上表 3 行目）
  6. 結果を **`agent_id（表示名）` の見出し**で束ね、**入力順**で連結して
     1 つのツール結果として進行役へ返す。表示名だけの見出しにしないのは、
     **表示名の一意性が保証されていない**から（Notes 6 と同じ根拠。
     同名が 2 体いると束ねた結果が判別不能になる）
- hop: 各配送で +1（ask と同じ燃料。ネストした plan は hop が深さを縛る）
- `tasks` の件数: **下限 1**（空は静的な不正）。**上限は設けない** —
  同一宛先禁止 × 接続先限定で有界。**1 件の波は許容する** — 進行役が 2 波目で
  1 体にだけ追加調査を頼むのは正当で、そこでツールを持ち替えさせる理由が無い
  （「1 体なら `ask_*` で足りる」は**ツールの提示条件**の話で、波の大きさの
  話ではない）
- 提示条件はツール構築時のトポロジー、**検証は実行時のトポロジーで取り直す**。
  この 2 点はターンの中で時刻が違う。`set_connections` は稼働中に呼べて
  `TopologyChanged` を撒くので、**繋ぎ替えは今すでに起こりうる**（将来の話ではない）
- ワーカー側から見た形は **ask と完全に同じ**（送り手封筒つきの依頼が
  届き、答えを返すと自分の仕事は終わり）。ワーカーに新しい概念は増えない

**ワーカーが答えずに転送したとき（rev3 指摘 4 — `ask` の既存バグでもある）**

ワーカーが依頼に対して `transfer_to_<別のエージェント>` を呼ぶと `Outcome::Handoff`
になる。現状のコードでは **`reply_to` は `Finish` 分岐でしか使われない**ため、
Sender は送られないまま `handle_message` の終わりで drop され、依頼主は
`Ok(Err(_))` を受けて **「相手から答えが返りませんでした。」**を読む。

**この文言は嘘である。** 答えは返っている — 宛先が違うだけで、会話は第三者へ
渡って最終的にユーザーへ流れる。join を迂回する経路がここにある。

- **抑制しない。** 転送はワーカーの正当な選択で、黙って握り潰すと
  「呼んだのに何も起きない」穴に変わる（Notes 9 と同じ形）
- 代わりに、**Handoff 分岐で `reply_to` に事実を送る**:
  「〇〇へ会話を渡したため、答えは返りません」。依頼主はそれを結果文字列として
  読み、次の波を決められる
- **`plan` 固有の修正ではない。** `ask` が同じ経路を通るので同時に直る。
  plan は宛先が N 体ぶんあるぶん、同じ穴を N 倍踏みやすくするだけ

**Acceptance**

- Given 接続 2 体の進行役、When plan で 2 タスク、Then 2 体へ並列に届き、
  束ねた結果が進行役へ返る。見出しは **`agent_id（表示名）`**、順序は**入力順**。
  **答えはユーザーへ散らない**
- Given ワーカー 2 体、When 並列 plan、Then **同時に処理中のワーカー数の
  最大値が 2 に達する**。壁時計では測らない（rev2 指摘 2）— 固定時間に
  依存するテストは遅いマシンで壊れ、速いマシンで無駄に待つ。
  この repo は `drain_until_quiet` で同じ問題を既に避けている
- Given 1 体が停止中を含む plan、Then 生きている側の答えは束ねに入り、
  停止側はその旨の文字列になる（道連れなし）
- Given 接続外の宛先を含む plan、Then 何も配送されず差し戻される
- Given 同一宛先へ 2 タスク、Then 配送されず差し戻される
- Given `tasks` が空、Then 何も配送されず差し戻される
- Given `tasks` が 1 件、Then **通常どおり実行される**（許容する）
- Given `hop` が上限、Then 何も配送されず、**1 つの**結果文字列が返る
  （タスク数ぶん同じ文字列を並べない）
- Given 接続 1 体以下のエージェント、Then plan は提示されない
- Given ワーカーが答えず転送した、Then そのタスクは
  「〇〇へ会話を渡したため答えは返らない」旨の文字列になり、
  **「答えが返りませんでした」にはならない**（`ask` 単独でも同じ）
- Given plan の連鎖（波 → 結果 → 次の波）、Then hop が燃料として効く

## Notes（査読論点）

1. **命名 `plan`**: 「計画を宣言すると実行される」ツール。`ask_all`
   （内容が宛先ごとに違うので不正確）、`delegate_parallel`（正確だが冗長）
   との比較で選んだ。モデルへの説明文は「複数の相手へ**並列に**頼んで
   全員の答えを束ねて受け取る。相手ごとに依頼内容を変えられる」とする
2. **多段 DAG をスキーマに持たない**: `stages: [[...], [...]]` のような
   波の直列宣言は入れない。波間で結果を見て次を決めるのはモデルの強みで、
   先に全段を宣言させると「2 波目が 1 波目の結果に依存する」場合に
   破綻する（計画の逐次即興のエラー複利を、スキーマの中で再発明するだけ）。
   **実機の続報（2026-07-30）**: 最初の実戦がこの判断を実証した。波 2 の
   依頼文（「範囲を半分に」「ツール 4 回以内に」「gemini のツール定義だけ
   追加で」）は、**波 1 で誰が溶けてどこまで進んだかを読まなければ書けない**
   内容だった。先に宣言させていたら波 2 は宣言できずに破綻していた。
   **再訪のトリガー（これが観測されるまで動かない）**:
   - `depends_on` の検討 → 「前の波の結果を読まずに書ける 2 波目」
     （完了にだけ依存し内容に依存しない機械的な直列）が実機で反復したら。
     現時点の観測はゼロ回
   - 束ね要約の機構化 → `[concordia] plan bundle:` の実測が波を重ねて
     実際に膨らんだら（今はプロンプト規律のみ）
   - `plan_id`（Notes 12）→ 波の因果を追えなくて困った実例が出たら
3. **提示条件 = 接続 2 体以上**: 「進行役フラグ」のような設定は足さない。
   設定が少ないというコンセプトに従い、トポロジーから導出する
4. **1 波あたりのタスク数**: **上限は設けない**（同一宛先禁止 × 接続先限定で
   有界。接続先数が自然な上限になる）。**下限は 1**（空配列は静的な不正。
   通すと何も配送されない空の束ねが返り、hop だけ消えてモデルが混乱する）。
   **1 件の波は許容する** — 「1 体なら `ask_*` で足りる」は**ツールの提示条件**の
   話であって、波の大きさの話ではない。進行役が 2 波目で 1 体にだけ追加調査を
   頼むのは正当で、そこでツールを持ち替えさせる理由が無い（rev3 指摘 6）
5. **ユーザー同報は凍結のまま**: 本 Spec は戻し条件 1 の実装だが、
   ユーザー向け UI として復活させるかは別判断（進行役への依頼で足りる
   間は、入口を増やさない）

6. **`to` を enum にする理由（rev2 指摘 1）**: `HandoffTools::build` は
   「**ツール名は ID、説明は表示名**」という組み合わせを意図的に選んでいる。
   関数名に使えるのは `[a-zA-Z0-9_-]` だけで日本語の表示名は潰れ、一方で
   会話は表示名で流れるのでモデルが「ザリ・ロブステル」と `agent_2` を
   結び付けられなくなる（実際に宛先の取り違えが起きた）。`to` を自由文字列に
   すると、その解決をもう一度モデルの文字列生成へ差し戻すことになる。
   しかも**表示名の一意性はどこも保証していない** — `World::register_agent` が
   拒否するのは ID の重複（`DuplicateAgent`）だけで、同名のエージェントは
   今すぐ作れる。enum なら存在しない宛先は**原理的に書けない**。
   Gemini の OpenAPI 部分集合でも `enum` は受理される（Spec 05 P3 が
   `const → enum` へ写しているのがその証拠）
7. **束ねた結果の肥大は未解決のまま残す**: plan は N 体分の回答全文を
   1 つのツール結果にして進行役の**履歴へ積む**。ask の N 倍で、しかも
   進行役は次の波でも同じ履歴を運ぶ。上限を設けるか要約するかは、
   **実測で膨らむのを見てから決める**。確かめる前に席を作らない
   （Spec 05 Notes 4 と同じ流儀）
8. **並列なのは「配送」で、「実行」は各ワーカーの空き具合に依存する**:
   各エージェントの受信箱は 1 本で、ターンは直列に処理される。ワーカーが
   別の仕事で塞がっていれば、その分だけ待つ。壁時計の主張は「最遅 1 体分」
   ではなく「最遅 1 体の**待ち時間を含む**」が正確
9. **実装で必ず踏む穴**: `decide()` は転送ツール名でしか handoff を判定
   しないので `plan` が誤って転送扱いされることはない。だが `plan` は
   `executable`（同梱・MCP ツール）にも `resolve_ask` にも該当しないため、
   実行ループの `calls` フィルタへ**明示的に足さないと黙って無視される**。
   `calls` が空 = 最終出力、と読まれ、モデルが plan を呼んだのに何も起きず
   本文だけが返る。エラーにならないので気づきにくい
10. **ワーカーの転送で `ask` が嘘をついていた（rev3 指摘 4）**: `reply_to` は
    `Outcome::Finish` 分岐でしか使われず、`Handoff` では送られないまま drop
    される。依頼主が読むのは「相手から答えが返りませんでした。」だが、
    **答えは返っている — 宛先が違うだけ**。plan 固有ではなく `ask` の既存バグで、
    plan は宛先が N 体ぶんあるぶん踏みやすくするだけ。転送を抑制せず、
    `Handoff` 分岐で `reply_to` へ事実を送る（抑制すると「呼んだのに何も
    起きない」穴に変わる — Notes 9 と同じ形）
11. **提示条件と検証は時刻が違う（rev3 指摘 9）**: ツールを組むのはターンの
    開始時、検証するのは実行時。`set_connections` は稼働中に呼べて
    `TopologyChanged` を撒くので、**繋ぎ替えは今すでに起こりうる**（将来の
    拡張の話ではない）。検証は実行時のトポロジーで取り直す
12. **既知の限界（実機確認後の査読で確認。いずれも意図的に入れない）**:
    - **早期アボート無し**: 1 タスクが致命的に失敗しても join は最遅 1 体まで
      待つ。「道連れ無し」を優先した帰結で、キャンセル機構は複雑さに見合わない
    - **`max_parallel` 無し**: 接続 20 体の進行役は 20 並列の LLM 呼び出しを
      張れる。自然上限（同一宛先禁止 × 接続先数）のみ。波サイズの明示上限は
      Notes 7 と同じく**実測してから決める**
