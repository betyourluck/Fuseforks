# Spec: コマンド承認の画面 — `run.json` の `pending` を押して消す

**ID**: 20
**Date**: 2026-08-05
**Status**: **rev2 承認（2026-08-05）→ P0 完了**。次は P1（コアの純機構と API）
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

サーヴァントが呼んで拒否されたコマンド（`run.json` の `pending`）を**一覧で見て、
承認か却下のボタンで消せる**ようにする。今は `run.json` をエディタで開き、
`pending` の項目を手で `allow` か `deny` へ書き写している。

起点は利用者の言葉（2026-08-05）—「今は手で写すのだが、これは pending に
上がっているものをリスト化して、承認か却下ボタンを押して消していきたい」。

**Spec 15 D10 の「初回の手間は欠点ではなく仕様」は取り下げない。** 取り除くのは
**手で JSON を書き写す手間**であって、**人が 1 件ずつ許容を決める手間ではない**。
後者は閉じた許容の本体なので残す（D1 / D6）。

## 現況（実測 2026-08-05）

| 何 | 実装 |
|---|---|
| `run.json` の構造化 IPC | **無い**。GUI が持つのは `readAgentConfig` / `writeAgentConfig` の**テキスト読み書きだけ** |
| `CommandPolicy` を触る場所 | `tools/run.rs` の `RunTool` **のみ**（`load` / `note_pending`） |
| 書き戻しの作法 | 読み直して `pending` だけ差分適用 → 3 回 retry → 駄目なら WARN 1 行（`run.rs:105`） |
| `pending` の上限 | `MAX_PENDING = 20`（1 体あたり）。超過は `first_requested_at_ms` の古い順に捨てる |
| `merge_pending_into` | **本番の呼び出し元ゼロ**。生かしているのは自分のテスト 1 本だけ（`command.rs:213` / テストは `:437`） |

**承認画面はコアの API から新規に要る。** 既存のテキスト読み書きで組むと、
GUI が JSON を組み立てて全文上書きすることになり、`command_tool_contract` の
「**人と機械の両方が書く唯一のファイルなので全文上書きにしない**」を破る。

## Stories

- **S1**: `pending` に上がったものを一覧で見て、ボタン 1 つで消せる。JSON を開かない
- **S2**: 承認するとき、**何を許すのかを自分で選べる**（この呼び出しだけか、
  この先頭に続く任意の引数までか）
- **S3**: **村全体を 1 画面で**見られる。個体ごとに開いて回らない
- **S4**: 承認している最中にサーヴァントが別の要求を積んでも、**承認した項目が
  復活せず、積まれた要求も消えない**

## 決定

### D1: 許容の粒度は機械が決めない。承認時に 2 択を出す

**文字列化はコアの 1 関数に閉じる**（rev2。GUI は粒度を `bool` で渡すだけ）:

```rust
impl PendingCommand {
    /// 承認・却下で `allow` / `deny` へ入れるパターン。
    ///
    /// `open == false` … この呼び出しだけ（完全一致）
    /// `open == true`  … 先頭 1 語ぶんを固定して、以降の引数を任意にする
    pub fn pattern(&self, open: bool) -> String {
        if !open {
            // 引数なしなら command のみ。`ruff` は引数なしにしか一致しない。
            return std::iter::once(self.command.as_str())
                .chain(self.args.iter().map(String::as_str))
                .collect::<Vec<_>>()
                .join(" ");
        }
        match self.args.first() {
            // 引数なしの pending を開くと `ruff *`（Spec 15 の例そのもの）。
            None => format!("{} *", self.command),
            // 引数ありなら**第 1 引数までを固定**して開く。
            Some(first) => format!("{} {first} *", self.command),
        }
    }
}
```

| `pending` | `open == false` | `open == true` |
|---|---|---|
| `ruff` | `ruff` | `ruff *` |
| `git log --oneline -5` | `git log --oneline -5` | `git log *` |
| `cargo test -- --nocapture` | `cargo test -- --nocapture` | `cargo test *` |
| `ls -la /tmp` | `ls -la /tmp` | `ls -la *` |

**末尾 `*` は 0 個以上の引数に一致する**（rev2 追記。査読の推奨。**実測で確認** —
`allow: ["ruff *"]` に対し `ruff`（引数なし）は `Allowed`）。**この性質が
2 択の前提**で、`*` が 1 個以上だと**広いほうが狭いほうのスーパーセットでなくなり**、
「`ruff *` を承認したのに `ruff` 自体が通らない」が起きる。`command.rs` の
コメントとテスト `a_trailing_star_matches_zero_or_more_args` で固定した。

**この確認の副産物として、`*` 単独のパターンで panic するのを見つけて直した**
（`failures.md` #69。`&parts[1..parts.len()-1]` が要素 1 個で `&parts[1..0]` に
なる）。承認経路が作るパターンは必ずコマンド名で始まるので**この Spec は
その入力を生まない**が、人が `run.json` へ手で書ける以上、先に潰した。

**既定は完全一致（狭いほう）。** 広いほうを既定にすると、押し慣れた指が
毎回広い許容を作る。

根拠は Spec 15 の凍結 —「登録要求から作る下書きは**名前だけ**。何を固定引数に
して何を任意引数へ回すかは**利用者の判断**で、機械が決めると閉じた許容の粒度が
勝手に決まる」。**承認ボタンが 1 つしか無いと、その規律を UI が破る。**

**「第 1 引数までを固定」は当てずっぽうであることを認める。** 実際の pending の
多くは `git log` / `cargo test` / `docker run` のようにサブコマンドが第 1 引数に
来るので大半は当たるが、**`ls -la /tmp` では旗を固定してしまう**（`ls *` の
ほうが自然な場面がある）。**当てずっぽうを隠さないための処方が 2 つ**:

- **画面には、選んだ結果の文字列そのものを出す**（`git log *` と書いて見せる）。
  ラジオのラベルが結果の literal になるので、外れていれば押す前に分かる
- **細かい粒度が要る人は `run.json` を直接編集する**（編集経路は残す）

**末尾 `*` の位置を選ばせない**のは、先頭何語まで固定するかを選ばせると
選択肢が引数の数だけ増えるため。**2 択に畳む代わりに、結果を見せて逃げ道を残す。**

### D2: 却下は `deny` へ入れる。`pending` から消すだけにしない

`Decision::Denied` は「実行せず、**承認要求も積まない**」。単に `pending` から
消すと、**次に同じコマンドが呼ばれたらまた積まれる** — 同じものを何度も却下する
ことになり、一覧がノイズで埋まる（`Denied` の doc が既に書いている理由そのもの）。

却下のパターン粒度も D1 と同じ 2 択。

### D3: 入口はタイトルバー。システム設定ではない

**「どのサーヴァントに何を許すか」は村の内容物**であって、アプリの振る舞いの
設定ではない。Spec 14 P3 で確定した境界（`failures.md` #52）—
**「村の内容物か、アプリの設定か」。保存先は分類の根拠にならない**。条例・役職と
同じ棚に置く。

**`AgentSettingsDialog` の中にも置かない。** `run.json` は `agents/{id}/` に住むが、
そこに置くと S3（村全体を 1 画面で）が成立せず、**個体ごとに開いて回る手間が残る** —
それは今の「手で写す」と同じ形の手間。

**件数を入口に出す。数え方は村の合計**（rev2 で定義）:

```
badge = command_policies().iter().map(|(_, p)| p.pending.len()).sum()
```

**個体ごとの最大値ではなく合計。** S3 が「村全体を 1 画面で」なので、入口の数も
村全体の判断待ち件数を指すのが素直。`MAX_PENDING` は 1 体 20 件なので、
10 体の村では最大 200 になりうる — **それは「溜まりすぎ」が数で見えるという
ことなので、丸めない。**

**0 件でも入口は残す**（非活性にもしない）。消えると「機能が無い」と読める。
バッジだけを出さない。開かないと気づけない一覧は、`run.json` を開かないと
気づけない今と変わらない。

### D4: 書き込みは「読み直して差分適用 + 3 回 retry」。`RunTool` と同じ作法

承認は `run.json` を**全文上書きしない**。人の操作を
**「この `(command, args)` を `pending` から消し、このパターンを `allow`（または
`deny`）へ足す」という差分**として表し、読み直した最新へ適用する。

これで S4 が成立する — 承認処理の最中にサーヴァントが積んだ**別の**要求は残り、
承認した項目は復活しない。

**`merge_pending_into` は流用できない。方向が逆。** あれは「機械が持っている
`pending` を、人が編集したファイルへ勝たせる」関数で、承認では**人が消した
`pending` が勝たなければならない**。

### D5: `merge_pending_into` を撤去する

**本番の呼び出し元がゼロ**で、生かしているのは自分のテスト 1 本
（`merging_keeps_the_human_edits_and_only_moves_pending`）。`RunTool` は使わず、
読み直した最新へ直接 `note_pending` している（そちらが正しい作法）。

**#62 と同型** — 「呼び出し元が自分のテストしか無い関数を、テストが覆っている
ように見せる」形。D4 で流用もできないと確定したので、**残す理由が無い**。

拡張と収縮を等価に評価する規律に従い、**この Spec は 1 つ足して 1 つ減らす**。

### D6: 承認は 1 件ずつ。「全部承認」は作らない

D1 の裏返し。まとめて承認は**粒度の決定を飛ばす**ので、閉じた許容の本体が消える。
一覧が長いなら、それは「そのサーヴァントに何をさせたいか」を決めていない状態で、
ボタン 1 つで片付けてよい種類の長さではない。

### D7: 承認した瞬間に `run` が提示され始めることを画面に書く

提示は 2 段ゲートで、2 段目は `offers_anything()`（`allow` が空でない）。
**`allow` の 1 件目を承認した瞬間、次のターンから `run` がそのサーヴァントへ
提示される。** これは D10 の fail closed が解ける瞬間なので、画面で告げる。

### D8: `Malformed` は承認できない（rev2 で**理由を訂正**して採用）

`command` にパス区切りを含む呼び出しは**照合前に拒否**され `pending` へ積まれない
（`run.rs:232` の `Decision::Malformed` は早期 return で `note_pending` に到達
しない）ので、機械が積む経路では一覧に現れない。

**`approve` / `reject` はコアで `normalize_command` を通し、`None` なら拒否する。**
人が `run.json` を手編集して `pending` へパス区切り入りの項目を置いた場合に、
承認画面がそれを `allow` へ移すのを止める。

**ただし査読の「Malformed 経路を迂回できる」は成立しない。訂正して採用する。**
`pattern_matches` は**パターン側の先頭も `normalize_command` に通す**
（`command.rs:264`）ので、パス区切りを含むパターンが `allow` に入っても
`None` を返して**何にも一致しない**。つまり通っても**死んだ行が 1 本増えるだけ**で、
実行可能な範囲は 1 ミリも広がらない。

**それでも検査を入れる理由は衛生**: `allow` に「効かない行」が並ぶと、
利用者は許可したつもりで許可できておらず、**なぜ動かないかが画面から読めない**
（`allow` に書いてあるのに `Unknown` で拒否され続ける）。**防御ではなく、
嘘の設定を作らせないための検査。**

### D9: `pending` に無いものは承認も却下もしない（rev2 で追加）

**rev1 は矛盾していた。** D4 は「`pending` から消し、`allow` へ足す」という差分と
書き、Phase 1 のテスト要件は「存在しない要求の承認は何も変えない」と書いていた。
**`MAX_PENDING` の押し出しや、承認中にサーヴァントが積み替えた場合に、
この 2 つは違う結果になる。**

**倒す先は「何もしない」。** `pending` に該当の `(command, args)` が無ければ
`allow` / `deny` へも足さない。理由は**任意の許容を注入する口を作らないこと** —
承認画面は「**実際に要求されたものだけ**を許容へ変える」装置であり、
そこが緩むと閉じた許容が「GUI から任意に書ける許容」へ変わる。

**ただし黙って何もしない、にはしない。** `approve` / `reject` は
`ApprovalOutcome { Applied, NotFound }` を返し、IPC を通して画面まで運ぶ。
`NotFound` のとき画面は一覧を引き直し、「この要求はもう一覧にありません
（新しい要求に押し出されました）」と出す。**押したのに何も起きない画面は、
壊れているのか成功したのかを利用者が区別できない**（`failures.md` #44 の
「歯止めの先に道が無い」と同型）。

## Notes

1. **`pending` の上限（20 件）に触らない。** 承認画面ができても上限は要る —
   捨てるのは「頼まれたが判断されていない要求」で、画面があっても人が見ない
   期間は存在する。

2. **一覧の並びは要検討（P2 で決める）。** `first_requested_at_ms` の古い順が
   素直だが、`count` の多い順のほうが「本当に要るもの」が上に来る。**実機を見て
   から決める** — どちらが良いかは pending の溜まり方に依存し、いま決めても
   根拠が無い（Spec 14 D5 の規律）。

3. **却下したものを後から取り消す経路はこの Spec で作らない。** `deny` から
   消すのは `run.json` の編集で足りる（編集経路は残っている）。画面に
   「却下の取り消し」を足すと、`deny` の一覧を画面に出すことになり、
   **「禁止の一覧を見せない」（モデルへは見せない）とは別の話とはいえ、
   画面の目的が「判断待ちを消す」から「許容の全体を編集する」へ広がる**。
   広げるなら別 Spec。

**軽微 3 だけ理由を訂正した。** `pattern_matches` は**パターン側の先頭も
`normalize_command` に通す**（`command.rs:264`）ので、パス区切りを含むパターンが
`allow` に入っても `None` を返して**何にも一致しない**。実行可能な範囲は 1 ミリも
広がらず、**死んだ行が 1 本増えるだけ**。検査を入れる理由は防御ではなく**衛生** —
`allow` に書いてあるのに拒否され続ける設定を作らせない。

**指摘 1 と 2 は、どちらも「rev1 の本文どうしが食い違っていた」形。** 1 は
D1 の例と関数名だけがあって規則が無く、2 は D4 とテスト要件が違う結論を書いていた。
**Spec 14 rev1 の「実装したら落ちる矛盾 10 件」と同じ種類**で、実装まで行けば
必ず落ちるが、**査読で落ちるほうが安い**。
