# Spec: 委譲の輪の検出と待ち時間 — `ask_timeout` を保険へ格下げする

- 起票: 2026-08-24
- 状態: **rev1（査読待ち）**
- 起点: 実機（ルナの委譲でイクスの調査が 180 秒で時間切れ →「時間内に応答が
  なかったため確定集約から除外」）と利用者裁定 —「調節できたほうがいい。
  たぶんほとんどの深い依頼が 180 秒だとタイムアウトが来て無駄になる。
  せっかくの調査が無駄になる。ただ本当のデッドロックは回避しなければいけない」
  →「起票しましょう。**たぶんこれはかなり重大な欠陥だ。ちょっと重たい作業は
  まったくできない**」

## Goal

**1 本の時計（`ask_timeout` = 180 秒固定）に載っている逆向きの 2 つの仕事を分ける。**

| 仕事 | 望む向き | 本 Spec での行き先 |
|---|---|---|
| 深い委譲をどこまで待つか | **長く**（調査は分単位 — 実測） | 時計に残す。既定を上げ、設定に出す |
| 相互委譲の輪をいつ解くか | **短く**（#106 — 輪は 180 秒 × 深さぶん居座る） | **構造へ移す**（配送時の即時拒否） |

輪が構造で締め出されれば、時計に残る仕事は「本当に遅い・固まったワーカーの
保険」だけになり、気兼ねなく長くできる。**現状の実害は二重** — 調査は
タイムアウトで捨てられ、しかも相手のターンは止まらないので**答えは作られ、
課金され、届かずに捨てられる**（`reply_to` 送信失敗は無視する設計）。

## 起票時の実測（2026-08-24）

- `ask_timeout` は `OrchestratorConfig::default()` の **180 秒コード定数**
  （`orchestrator/mod.rs:171`）。GUI は `default()` をそのまま使う
  （`state.rs:111`）= 全村・全委譲で一律。**設定に出ていない**
  （Spec 13 の「`OrchestratorConfig` の 12 個は出さない」の中）
- 待ちの実装点は `deliver_and_wait` の
  `tokio::time::timeout(shared.config.ask_timeout, rx)`（`delegation.rs:150`）。
  `ask_*` と `plan` の各タスクが共有する 1 実装
- **デッドロックの形（#106）**: 輪は「回る」のではなく**受信箱で詰まる** —
  A は自分のターンの中で B の返事を待ってブロックしており、その間 A は
  自分の受信箱を読まない。B が A へ委譲すると封筒は A の受信箱で永遠に待つ
- **転送（`transfer_to_*`）は直接の依頼主の待ちを解く** — B が転送すると
  `Reply { kind: HandedOff }` が A へ返り、A のブロックはそこで終わる
  （`delegation.rs:150` の match と `PlanTaskState::HandedOff` の doc）。
  **輪の検出はこの解除を数えないと偽陽性が恒久化する**（下の D2）
- 封筒への相乗りの前例が 3 つ既にある — `cancel`（Spec 10）/ `budget`
  （Spec 11）/ `participants`（Spec 28 D7）。**待ち手の集合は 4 つ目**で、
  形は同じ（加算的・in-memory・因果に沿って運ぶ）
- 検索の重い委譲は分単位（xAI probe の実測。1 検索ターン平均 $1.27）。
  camel（eigent の土台）の同種の値は `task_timeout_seconds = 3600`

## Stories

- S1. 進行役が調査をワーカーへ委譲し、**5 分かかる調査が捨てられずに戻る**
- S2. A と B が誤って相互に委譲し合う配置でも、**待たずに即座に**
  「循環する委譲」と typed で拒否され、モデルは同じ周で進路を変えられる
- S3. 利用者がシステム設定で委譲の待ち時間を変えられ、**次の委譲から**効く
- S4. B が転送で会話を C へ渡した後、C が元の依頼主 A へ委譲する —
  A の待ちは転送で解けているので、**これは拒否されない**（偽陽性の対照）

## 決めること

### D1. 輪の検出 — `Envelope` に「待ち手の連鎖」を 1 欄

`Envelope` へ `waiting: Vec<AgentId>`（**順序つきの連鎖**・末尾が直近の依頼主）
を足す。運び方は 3 経路で違い、**それぞれの理由が形を決める**:

| 経路 | waiting の値 | 理由 |
|---|---|---|
| `ask_*` / `plan` の配送 | **incoming の連鎖 + 自分を末尾に追加** | 自分は今からブロックする |
| 転送（`transfer_to_*`） | **incoming の連鎖から末尾を除く** | 転送は直近の依頼主の待ちを解く（`HandedOff` が返る）。それより上流（依頼主の依頼主…）はまだブロック中なので残す |
| 利用者発話 / 予定の発火 / Spec 43 の dispatch / 束ねの配送 | **空** | 新しい因果の根。誰もブロックしていない（dispatch の進行役は提案でターンを終えており待っていない） |

**判定は `deliver_and_wait` の入口 1 箇所**: 宛先が連鎖に居たら、受信箱へ
**積まずに** typed の結果で即拒否する（停止中の `Undeliverable` と同じ
即答の形 — 呼んだモデルは同じ周で読んで進路を変えられる）。文面は
「宛先はこの依頼の因果の中で答えを待っています（循環する委譲）。
**依頼主への返信で直接答えてください**」— 禁止だけでなく次の手を書く（#44）。

### D2. 偽陽性の扱い — 恒久と競合を分ける

- **恒久の偽陽性は転送の減算（D1 の 2 行目）が消す**。これが無いと
  「A→ask→B、B が C へ転送、C→ask→A」という正当な形が永久に拒否される
- **競合の偽陽性は許容する** — 連鎖は配送時点のスナップショットなので、
  「B の委譲が拒否された直後に A の待ちが解けていた」瞬間はありうる。
  代償は拒否文 1 通で、モデルは次の周で頼み直せる。**輪が時計の長さ ×
  深さぶん居座る現状より安い**。契約に「保証するのは輪の不成立であって、
  拒否の最小性ではない」と明記する

### D3. plan のセル分類は `Undeliverable` を再利用（新しい enum 値を足さない）

循環の拒否は「配送できなかった」の動的失敗そのもの（parallel_delegation の
3 分類 3）。`PlanTaskState` へ値を足すと wire・TS union・辞書・セル色の
4 面が動くが、セルの色で「循環」と「停止中」を見分ける必要は薄い —
**区別は計器が持つ**（D5）。ask の結果文は循環専用なのでモデル側の区別は付く。

### D4. 時計 — 既定 600 秒 + `world.json` の欄 + システム設定

- **既定を 180 → 600 秒へ上げる**。輪が構造で消えた後の時計は保険なので
  長くできる。600 は「検索の重い委譲は分単位」の実測から（camel の 3600 は
  過剰 — 保険が 10 分を超えると「固まった」の発見が遅すぎる）
- **置き場は `world.json` の `askTimeoutSecs: Option<u64>`**（`None` = 既定
  600）。`tokenBudget` と同じ棚 — 待ちの長さは村の運用の性質で、村を配ると
  付いて回るのが正しい。`deliver_and_wait` が呼び出しごとに `World` から
  読む（`new_root_budget` と同じ「保存すれば次から効く・再起動不要」の形）
- **UI はシステム設定 > コスト管理**へ 1 欄（「委譲の待ち時間（秒）」）。
  タイムアウトは「払ったのに捨てる」の防波堤なのでコストの棚が正しい。
  **Spec 13 の「`OrchestratorConfig` は出さない」をこの 1 点だけ名指しで
  覆す** — あの裁定の理由は「増やさない」で、これは利用者が実害を報告した
  最初の 1 個。残り 11 個の凍結は不変
- 下限 30 / 上限 3600 を保存時に検査（0 や負を許すと全委譲が即死する村が
  作れる — `INVALID_TOKEN_BUDGET` と同じ形の拒否）

### D5. 計器

`ask refused: agent={呼び手} to={宛先} reason=circular chain=[{連鎖}]` を
1 行（拒否のたび）。既存の `turn:` / `tool:` では**輪の拒否と停止中の拒否が
同じ文字数の結果にしか見えない** — #72 の規律（握り潰した事実を数える）。
タイムアウト側は既存の `TimedOut` 分類 + 結果文で読めるので新設しない。

### D6. `MAX` 系との相互作用（変えないことの明記）

- `max_hops` は不変 — 深さの燃料であって輪の対策ではない（輪は hop が
  尽きる前に受信箱で詰まる — #106）
- MCP 外部の扉の D7（同時 1 本・自己呼び出しは busy）は不変 — あちらは
  プロセスの外から来る輪、こちらは村の中の輪で、機構は別のまま
- Spec 43 の凍結 8（ターン外の実行形は 2 つまで）に触れない — 検出は
  配送時の検査で、実行形を増やさない

## 凍結（P0 で `data_contract` へ）

1. 輪の不成立を構造で保証する（時計に依存しない）。保証するのは不成立で
   あって拒否の最小性ではない（競合の偽陽性は拒否文 1 通で許容）
2. 連鎖は順序つき・末尾が直近の依頼主。ask / plan は追加、転送は末尾の除去、
   新しい因果の根は空
3. 判定は `deliver_and_wait` の入口 1 実装。受信箱へ積まずに即答
4. `askTimeoutSecs` は `world.json`（村と配られる）。`None` = 既定 600 秒。
   30..=3600 の外は保存時に拒否
5. Spec 13 の「`OrchestratorConfig` は出さない」を `ask_timeout` の 1 点だけ
   名指しで覆す（残り 11 個は不変）
6. タイムアウトしても相手のターンは止めない（既存挙動の凍結 — 止めると
   「遅いが健全な調査」を殺す側に倒れる。届かない答えの払いは
   `turn:` 行と統計に今までどおり残る）

## 検収（実機）

1. S2 — A⇄B の相互委譲で `ask refused: reason=circular` が**即座に**出て、
   180 秒（旧）も 600 秒（新）も待たない。両者のターンは正常に続く
2. S1 — 5 分級の調査委譲（検索の重い問い）が捨てられずに束ねへ入る
3. S3 — 設定で 60 秒へ下げ、遅いワーカーへの委譲が 60 秒で `TimedOut` になる
   （時計が動いている証拠。**上げる側だけの検収では「読んでいない」と
   区別が付かない**）
4. S4 — A→ask→B、B が C へ転送、C→ask→A が**拒否されずに**答えを返す
5. 旧い村（`askTimeoutSecs` 無し）を開いて WARN が出ず、既定 600 で動く

## Notes

1. **`specs/tla/` の候補**（凍結ではない）: 輪の不成立は SAFE / BUG の対で
   書ける形（BUG = 連鎖の追加を外した版で、TLC がデッドロックを見つける）。
   #105 / #106 と同族の主張なので、P1 と別に足す価値がある
2. **既定 600 の根拠は薄い**ことを正直に書く — 実測にあるのは「分単位」まで
   で、600 と 900 を分ける観測は無い。設定に出すので、外れていても利用者が
   直せる（定数のままなら根拠がもっと要った）
3. eigent / camel の対応物: `ask_human` は無限待ち（人が離席すると
   固まる — 反面教師）、`task_timeout_seconds = 3600`。輪の構造的検出は
   camel に無い（`_validate_dependencies` の DFS は人が組む PIPELINE 専用）
