## Goal

村の会話を再起動をまたいで保つ。複数の会話を名前付きで持ち、切り替えて再開できる。
長く続いた会話は要約して続けられる。

起点は利用者の判断（2026-08-02）: **「再起動して前回の続きから始められないと、
道具として使えない」**。現状は会話ログもエージェントの履歴も in-memory で、
アプリを閉じた瞬間に消える。

### 立場の宣言

- **保存するのは「会話」であって「実行状態」ではない。** plan の波・トークン予算・
  MCP 接続・飛行中ターンは作業の寿命で、プロセスと共に消えてよい（Spec 08 が
  波を in-memory と凍結したのと同じ線）
- **要約は自動で走らせない（v1）。** 要約は LLM 呼び出し = トークンで、
  Spec 11 の天井と競合する。「自動で仕事を増やす機構は入れない」（Replan 不採用と
  同じ規律）に従い、**人が押したときだけ**要約する
- **索引は作らない（v1）。** 実測で 20,000 レコードの全走査が 11 ms。
  索引が要るのはその 1 桁上からで、いま作ると「効いているか分からない機構」が増える
- **人が読める出口を必ず持つ。** redb はバイナリなので、`export_session` で
  JSONL へ書き出せることを **P1 の完了条件**にする。この企画の診断は
  grep に依存しており（failures.md #47 は `concordia.log` の grep で解けた）、
  読めない保存先を作るなら出口は機構の一部
- **秘密は書かれうる前提で置き場を決める。** 会話ログをディスクへ書くのは
  この Spec が初めて

## 現状の構造（接地・2026-08-02 起票時）

**履歴は 2 層ある。これが他ツール（Claude Code / Copilot / Cursor）と決定的に違う。**

| | 何を持つか | 形 | 上限 | 誰が読むか |
|---|---|---|---|---|
| `Shared.log` | 村の会話ログ | `Vec<AgentMessage>` | リング 5,000 件 | 会話ペイン・広場ログ・トークン集計 |
| `AgentRecord.history` | エージェント個別のプロンプト履歴 | `Vec<ChatMessage>` | 滑る窓 8 往復 | **LLM へ送るリクエスト本体** |

- 単一エージェントの道具では「会話ログ = モデルの文脈」なので、ログを保存すれば
  再開できる。**Concordia では一致しない**
- **`log` から `history` は復元できない** — `push_exchange` は #45 の規律で
  「**送った文字列をそのまま**」積む。そこには畳んだ可変文脈（入退室通知・
  広場ログ・顔ぶれ・送り手名）が含まれ、`log` のどこにも無い
- **`history` から `log` も復元できない** — `log` には System 行・他人宛の発話・
  どの history にも入らない発話がある

→ **会話ログだけ保存して再開すると、画面は正しく見えるのに全エージェントが
健忘症で始まる。しかも画面上その 2 つは区別が付かない。**

その他の接地:

- `reset_conversation`（Spec 03 の「新規チャット」）は log と全 history を
  **捨てる**。契約で処理順まで凍結済み（log → history → `conversationCleared`）
- `ChatMessage` / `AgentMessage` はどちらも serde 可能
- `PersistedWorld` は履歴を**意図的に持たない**
- 依存は現在 17 個で、それぞれ `Cargo.toml` に理由が書いてある

## Stories

### S1: 閉じて開いたら続きから

村を使い、アプリを閉じ、開き直す。会話ペインには前回の会話がそのまま出ている。
**そのまま次の依頼を出すと、エージェントは再開前の話を踏まえて答える**
（S1 の本丸はここ — 画面ではなく履歴）。

### S2: 会話を複数持てる

「Spec 11 の実装」の会話と「黒板の運用」の会話を別々に持ち、一覧から選んで
切り替える。切り替えても、もう一方は消えない。

### S3: 新規チャットは捨てるのではなく閉じる

「新規チャット」は今の会話を**捨てる**のではなく、**閉じて新しい会話を始める**。
前の会話は一覧に残り、いつでも戻れる（Spec 03 の意味を変更する）。

### S4: 枝分かれ

ある地点までは同じで、そこから別の頼み方を試したい。**fork** で
`at_seq` までを複製し、元は不変のまま残す。

### S5: 長い会話を要約して続ける

会話が長引いたとき、人が「要約して続ける」を押す。要約はエージェントごとに作られ、
以後のプロンプトへ注入される。**元のレコードは消さない**（要約の品質が悪かった
ときに戻れる）。

### S6: 中身を人が読める

`export_session(id)` で JSONL へ書き出せる。デバッグ・移行・他ツール
（Claude Code 形式）との突き合わせに使う。**redb を選んだ以上、これは必須機能**。

## 機構の要点（Phase 0 で凍結する不変条件）

1. **セッションの単位は村**（エージェント別ではない）。1 セッション =
   「村の会話ログ + 全エージェントの履歴 + 要約」。エージェント別に切ると、
   同じ波に参加した 2 体が別々の会話に属することになり、束ねの因果が切れる
2. **保存先は `{workspace}/sessions.redb` の 1 ファイル**。`world.json` へ
   入れない理由は `schedules.json` と同じ — エージェントの定義ではない。
   **`index.json` は作らない**（真実を 2 つにしない）
3. **テーブルは 2 つ**:
   ```
   sessions: TableDefinition<&str, &[u8]>          // key = session_id, value = SessionMeta(JSON)
   records:  TableDefinition<(&str, u64), &[u8]>   // key = (session_id, seq), value = Record(JSON)
   ```
   `seq` はセッション内で単調増加。**タプルキーの範囲走査**が「後ろから N 件」を
   O(log n + k) で返すことを実測済み（16 件で 0.03 ms / 20,000 件のテーブル）
4. **`Record` は 3 種別で閉じる**（`kind` の閉じた列挙）:
   - `message` — 会話ログ 1 件（`AgentMessage` 丸ごと。`grounding` /
     `co_recipients` も含む — 再開後の表示に要る）
   - `exchange` — 履歴 1 往復（`agentId` / `sent` / `replied`）。
     `sent` は**実際に送った文字列そのもの**（#45 の規律を保存側へ延長）
   - `summary` — 要約 1 本（`agentId` / `text` / `coversUpToSeq`）
   **2 種別ではない**（rev1 の記述矛盾を解消）
5. **1 トランザクション = 1 つの原子的な変更**。メタデータ更新とレコード追加は
   同じトランザクションで行う。temp+rename は使わない（redb が保証する）
6. **書き込みトランザクションを `await` を跨いで持たない。** redb は同期 API で
   書き込みは 1 本に直列化される。トランザクションを持ったまま LLM 呼び出しや
   ファイル I/O を待つと村全体が固まる。**書くのは決まった 2 点だけ**
   （`record` の中 / `push_exchange` と同じ点）で、どちらも短いトランザクションで閉じる
7. **滑る窓はロード時に再適用する。** `records` には全 `exchange` が残り、
   復元時に `history_turns` の窓で切る。窓の値を変えたら次回の復元から効く
   （保存時に切ると、設定を広げても過去は戻らない）
8. **復元しないもの**: plan の波（Spec 08 が in-memory と凍結）/ `BudgetPool`
   （因果ごと・Spec 11）/ MCP 接続 / `TurnHandle` / 稼働状態
   （bootstrap は自動起動しない、既存契約）/ 累積統計（プロセス寿命）
9. **`Shared.log` の 5,000 件はメモリ上の上限であって、保存の上限ではない。**
   ファイルには全量が残り、起動時に読むのは末尾 5,000 件（リングと同じ形で
   画面へ復元する）
10. **半端なターンを許容する。** ユーザー発話の `message` は投入時に、
    `exchange` はターン完了時に書かれるので、飛行中にアプリが落ちると
    「`message` はあるが `exchange` が無い」状態が残る。これは**正しい記録**
    （発話は起きた事実）として扱い、**画面には出すが履歴には入れない**。
    再開後は「頼んだが答えが返らなかった」ように見える
11. **セッションの切り替えは飛行中ターンが無いときだけ**（`interrupt_all` の
    後か、全員 idle のとき）。飛行中に切り替えると、答えが別のセッションへ着地する
12. **新規チャットは破棄しない**（Spec 03 の改訂）。今のセッションを閉じ、
    新しい `session_id` を開く。イベントは**加算**:
    `conversationCleared` は「会話ペインを空にせよ」の意味で残し、
    `sessionSwitched { sessionId }` を足す（旧イベントの意味を変えると
    既存 UI が誤動作する）
13. **`session_id` は時刻順にソートできる形**にする: `{epoch_ms}-{短い乱数}`。
    「最新」を辞書順に依存させない — 判定は `SessionMeta.updatedAt` で行い、
    ID の順序は**人が一覧を読むときの都合**に留める
14. **上限**（R3 で確定）:
    - セッション数: 無制限。**200 を超えたら起動時に WARN 1 行**（削除はしない）
    - 1 セッションのレコード数: 無制限。**50,000 を超えたら WARN**（要約を促す）
    - ファイルは**自動で縮まない**（redb は copy-on-write）。`compact()` は
      持つが v1 では呼ばない — 呼ぶなら明示操作
15. **`sessions.redb` の権限**: unix では `0o600`（親ディレクトリ `0o700`）。
    **Windows では設定しない** — `%APPDATA%` は既にユーザー私有の ACL 下にあり、
    POSIX 権限の API は無い。`.gitignore` へ `sessions.redb` を保険として足す
    （`{workspace}` は既定で `%APPDATA%` 配下なのでリポジトリには入らないが、
    workspace をリポジトリ内へ置く運用を将来する場合の備え）

### 要約の設計（査読指摘 7 — #45 との衝突を解く）

**`coversUpToSeq` は「レコードの seq 境界」であって件数ではない。**

- 復元時、あるエージェントの履歴は
  「**最新の `summary`** ＋ `coversUpToSeq` より後の `exchange`（滑る窓を適用）」で組む
- **注入は既存の可変文脈の畳みに相乗りさせる。** #45 の規律は
  「可変文脈は最終 user 発話へ畳み、**送った文字列をそのまま履歴へ積む**」。
  要約も同じ経路に乗せれば、送信と保存が食い違わない —
  つまり **`history` の中に summary 専用の席を作らない**。次のターンの
  `context`（入退室通知・広場ログと同じ場所）へ要約を差し、
  その結果できた `sent_user_turn` がそのまま `exchange` として保存される
- **要約の要約は許す。** 新しい `summary` は前の `summary` の本文を入力に取れる。
  `coversUpToSeq` は単調増加するので、参照が循環しない（査読が指摘した
  無限ループはこの単調性で塞ぐ）
- **注入されるのは最新の 1 本だけ。** 古い `summary` はレコードとして残るが、
  復元には使わない（痕跡であって現役ではない）

## 検証の設計（実装の前に決める）

- **本丸**: 再起動後の最初のターンで、エージェントが再開前の文脈を参照できること。
  「画面に出ている」だけでは通さない — **LLM へ渡ったリクエストの `messages` に
  復元した履歴が入っていること**を結合テストで見る
- 送った文字列と保存された文字列が一致すること（#45 の回帰の保存側版）
- 飛行中に落ちた形（`message` だけ・`exchange` 無し）を読んでも、
  画面に出て履歴に入らないこと
- 新規チャットで前のセッションが消えないこと / `fork(at_seq)` で元が不変であること
- 要約の後、履歴が「最新 summary + それ以降の exchange」で組まれること /
  要約を 2 回しても循環しないこと
- `export_session` の JSONL を読んで、同じ会話が再構成できること
- 上限（200 セッション / 50,000 レコード）で WARN が 1 回出ること
- 実機: アプリを閉じて開き、前の会話が出て、続きの依頼が文脈込みで通ること

  **移行が必要になったときの手当ては `export_session` → 新形式で取り込み**で
  足りるか。v1 はこれで進めるが、実際に更新が来たときに検証が要る

## 実測（2026-08-02、この機械で計測）

**候補の比較**:

| 候補 | 依存数 | ビルド | C 依存 | 日本語検索 |
|---|---:|---:|---|---|
| **redb 4.1.0** | **2** | 10 秒 | なし | 全走査（索引なし） |
| tantivy 0.26（既定） | 189 | 1分21秒 | **zstd-sys** | 別途トークナイザ |
| tantivy + lindera | **451** | — | zstd-sys | 形態素解析 |
| rusqlite（bundled） | 10 | 29 秒 | SQLite 同梱 | FTS5 trigram |

**SQLite FTS5 の日本語**（rusqlite 経由・SQLite 3.53.2）:
`unicode61`（既定）は「周回境界」「予算切れ」「ロブステル」すべて **0 件**、
`tokenize='trigram'` は全ヒット。**日本語検索に形態素解析は要らない**
（この事実が lindera の 451 依存を外す根拠になった）。

**redb で凍結する形の実測**（40,000 レコード・1 件約 600 バイト）:

| 操作 | 所要 |
|---|---:|
| 書き込み 40,000 件（1 トランザクション） | 271 ms |
| **後ろから 16 件**（滑る窓の復元） | **0.03 ms** |
| 1 セッション 20,000 件の全走査（v1 の検索） | 11 ms |
| `fork`（10,000 件のコピー・1 トランザクション） | 55 ms |
| ファイルサイズ | 64.3 MB |

ファイルサイズは実データの約 2 倍（copy-on-write の頁が残るため）。
自動では縮まないので、気になる規模になったら `compact()` を明示操作で出す。

**全走査の比較対象**（JSONL 案で測った値）: 25.9 MB で 30 ms（暖まった状態）、
415 MB で 732 ms。redb でも桁は同じで、**索引の要否は保存先の選択に依存しない**。

## 参考（外部調査・2026-08-02 利用者提供）

収束点は 4 つ — 追記型永続化・プロジェクト紐付け・continue / resume / fork の
再開モデル・フルログ温存 + 要約レイヤ。

- **Claude Code**: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`。
  continue / resume / fork の 3 プリミティブ。**会話は永続化するが
  ファイルシステムは永続化しない**という分離 — 本 Spec の不変条件 8 の下敷き
- **Copilot CLI/SDK**: 索引 DB と本体ファイルの二層。`disconnect()`（メモリ解放）と
  `deleteSession()`（削除）の区別
- **Cursor**: workspace DB と global DB の二重 SQLite。ワークスペースのハッシュ
  紐付けが切れると「履歴が消えた」ように見える — **紐付けをパスのハッシュに
  依存させない**理由になる（本 Spec は workspace 直下に置く）
- **VS Code Copilot**: 自動要約はトークン 95%、手動 `/compact` は**要約の焦点を
  指示できる**。D4 で自動化を検討する際の型
- **LangGraph**: checkpointer を `thread_id` 単位で抽象化。本 Spec は村 1 つなので
  抽象化しない
- **CrewAI Flows**: `kickoff(inputs={"id"})` = resume、
  `kickoff(restore_from_state_id=)` = fork
- **Turso**（旧 Limbo、2026-08 時点で beta）: SQLite を純 Rust で書き直した実装。
  ファイル形式に互換がある。**SQLite を選んでも C への永久の賭けにはならない**
  ことの根拠だが、beta で FTS5 の対応も未確認のため v1 では採らない
