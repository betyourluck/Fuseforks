# Spec: 会話の永続化とセッション管理（再起動で消えない・複数持てる・再開できる）

**ID**: 12
**Date**: 2026-08-02
**Status**: **Draft rev1**（査読待ち）
**Branch**: なし（main へ Phase 単位で直接コミット — Spec 01〜11 と同じプロセス）

## Goal

村の会話を再起動をまたいで保つ。複数の会話を名前付きで持ち、切り替えて再開できる。
長く続いた会話は要約して続けられる。

起点は利用者の判断（2026-08-02）: **「再起動して前回の続きから始められないと、
道具として使えない」**。現状は会話ログもエージェントの履歴も in-memory で、
アプリを閉じた瞬間に消える。

### 立場の宣言

- **保存するのは「会話」であって「実行状態」ではない。** plan の波・トークン予算・
  MCP 接続・飛行中ターンは作業の寿命で、プロセスと共に消えてよい（Spec 08 が
  波を in-memory と凍結したのと同じ線）。復元するのは「何を話したか」だけ
- **要約は自動で走らせない（v1）。** 要約は LLM 呼び出し = トークンで、
  Spec 11 の天井と競合する。「自動で仕事を増やす機構は入れない」（Replan 不採用と
  同じ規律）に従い、**人が押したときだけ**要約する。頻度が実測できてから自動化を検討
- **SQLite を入れない（v1）。** 索引 DB が要るのは「複数プロジェクト × 数万
  セッション」の規模で、村 1 つの会話はその手前にある。依存を 1 つ増やす前に
  JSONL + 一覧ファイルで足りるかを確かめる（「機構を足す前に既存の機構で書けるか」）
- **秘密は書かれうる前提で置き場を決める。** 会話ログをディスクへ書くのは
  この Spec が初めて。利用者がチャットへ API キーを貼る経路は実在する
  （failures.md #28 の world.json 事故と同型）

## 現状の構造（接地・2026-08-02 起票時）

**履歴は 2 層ある。これが他ツール（Claude Code / Copilot / Cursor）と決定的に違う。**

| | 何を持つか | 形 | 上限 | 誰が読むか |
|---|---|---|---|---|
| `Shared.log` | 村の会話ログ | `Vec<AgentMessage>` | リング 5,000 件 | 会話ペイン・広場ログ・トークン集計 |
| `AgentRecord.history` | エージェント個別のプロンプト履歴 | `Vec<ChatMessage>` | 滑る窓 8 往復 | **LLM へ送るリクエスト本体** |

- 単一エージェントの道具では「会話ログ = モデルの文脈」なので、ログを保存すれば
  再開できる。**Concordia では一致しない**
- **`log` から `history` は復元できない** — `push_exchange` は #45 の規律で
  「**送った文字列をそのまま**」積む。そこには畳んだ可変文脈（入退室通知・
  広場ログ・顔ぶれ・送り手名）が含まれ、`log` のどこにも無い
- **`history` から `log` も復元できない** — `log` には System 行・他人宛の発話・
  どの history にも入らない発話がある

→ **会話ログだけ保存して再開すると、画面は正しく見えるのに全エージェントが
健忘症で始まる。しかも画面上その 2 つは区別が付かない。**（この企画が
繰り返し踏んでいる形 — #33 の「表示は実装していても、データの通り道が
偶然にしか通らないなら出ないのと同じ」の裏返し）

その他の接地:

- 書き込みの作法は既にある: `world.json` / `schedules.json` は一時ファイル +
  rename で原子的に書く。`{workspace}/` 直下にファイルを増やす前例も両者
- `reset_conversation`（Spec 03 の「新規チャット」）は log と全 history を
  **捨てる**。契約で処理順まで凍結済み（log → history → イベント）
- `ChatMessage` / `AgentMessage` はどちらも serde 可能（そのまま JSON へ書ける）
- `PersistedWorld` は履歴を**意図的に持たない**（保存対象は定義とテンプレートのみ）

## Stories

### S1: 閉じて開いたら続きから

村を使い、アプリを閉じ、開き直す。会話ペインには前回の会話がそのまま出ている。
**そのまま次の依頼を出すと、エージェントは再開前の話を踏まえて答える**
（S1 の本丸はここ — 画面ではなく履歴）。

### S2: 会話を複数持てる

「Spec 11 の実装」の会話と「黒板の運用」の会話を別々に持ち、一覧から選んで
切り替える。切り替えても、もう一方は消えない。

### S3: 新規チャットは捨てるのではなく閉じる

「新規チャット」は今の会話を**捨てる**のではなく、**閉じて新しい会話を始める**。
前の会話は一覧に残り、いつでも戻れる（Spec 03 の意味を変更する）。

### S4: 枝分かれ

ある地点までは同じで、そこから別の頼み方を試したい。**fork** で複製を作り、
元は不変のまま残す。

### S5: 長い会話を要約して続ける

会話が長引いたとき、人が「要約して続ける」を押す。要約はエージェントごとに作られ、
以後のプロンプトは `system + 要約 + 直近 N 往復` で組まれる。**フルログは残る**
（要約の品質が悪かったときに戻れる — Cursor の data contamination の教訓）。

## 機構の要点（Phase 0 で凍結する不変条件の候補）

1. **セッションの単位は村**（エージェント別ではない）。1 セッション =
   「村の会話ログ + 全エージェントの履歴」。エージェント別に切ると、
   同じ波に参加した 2 体が別々の会話に属することになり、束ねの因果が切れる
2. **保存先は `{workspace}/sessions/`**。`<session-id>.jsonl` が本体、
   `index.json` が一覧。`world.json` へ入れない理由は `schedules.json` と同じ —
   **エージェントの定義ではない**
3. **本体は追記型 JSONL、1 行 1 レコード、2 種別**:
   - `{"kind":"message", ...AgentMessage}` — 会話ログ 1 件（`record` の中で追記）
   - `{"kind":"exchange","agentId":…,"sent":…,"replied":…}` — 履歴 1 往復
     （`push_exchange` と同じ点で追記）
   **2 種別を分けるのが設計の核** — 上の「片方から他方を復元できない」の帰結。
   `sent` は**実際に送った文字列そのもの**（#45 の規律をそのまま保存側へ延長）
4. **滑る窓はロード時に再適用する。** ファイルには全 `exchange` が残り、
   復元時に `history_turns` の窓で切る。窓の値を変えたら次回の復元から効く
   （保存時に切ると、設定を広げても過去は戻らない）
5. **書き込みは 1 行ずつ flush、rename は使わない。** 追記は「途中で落ちても
   最後の 1 行が欠けるだけ」で、全損しない。`world.json` の temp+rename は
   全体を書き換えるファイルの作法で、追記ログには要らない
6. **復元しないもの**: plan の波（Spec 08 が in-memory と凍結）/ `BudgetPool`
   （因果ごと・Spec 11）/ MCP 接続 / `TurnHandle` / 稼働状態
   （bootstrap は自動起動しない、既存契約）/ 累積統計（プロセス寿命）
7. **要約は別レイヤ**。`{"kind":"summary","agentId":…,"text":…,"covers":N}` として
   同じ JSONL へ追記し、**元の exchange は消さない**。復元時は
   「最後の summary + それ以降の exchange」で history を組む
8. **セッションの切り替えは飛行中ターンが無いときだけ**（`interrupt_all` の
   後か、全員 idle のとき）。飛行中に切り替えると、答えが別のセッションへ
   着地する
9. **新規チャットは破棄しない**（Spec 03 の改訂）。今のセッションを閉じ、
   新しい `session-id` を開く。旧セッションはファイルに残る

## 検証の設計（実装の前に決める）

- **本丸**: 再起動後の最初のターンで、エージェントが再開前の文脈を参照できること。
  「画面に出ている」だけでは通さない — LLM へ渡ったリクエストの `messages` に
  復元した履歴が入っていることを結合テストで見る
- 送った文字列と保存された文字列が一致すること（#45 の回帰の保存側版）
- 壊れた 1 行を含む JSONL を読んでも、その行だけ落として残りを開くこと
  （`schedules.json` の 1 件ずつ検証と同じ規律）
- 新規チャットで前のセッションが消えないこと / fork で元が不変であること
- 上限（セッション数・1 ファイルのサイズ）に達したときの振る舞い
- 実機: アプリを閉じて開き、前の会話が出て、続きの依頼が文脈込みで通ること

## Phases（案 — 査読で確定）

- **P0 契約凍結**: data_contract へ `session_store` ブロック（レイアウト・
  レコード 3 種別・滑る窓の再適用・復元しないものの列挙・上限）
- **P1 純機構**: JSONL の読み書き（追記・復元・壊れた行の切り捨て）・

- **P2 配線**: `record` / `push_exchange` の追記点、bootstrap での復元、
  `reset_conversation` の意味変更（Spec 03 改訂）、セッション API
  （`resume` / `continue_latest` / `fork` / `list` / `delete`）
- **P3 投影**: 会話ペインのセッション一覧・切り替え・fork・削除の UI、IPC
- **P4 要約**: 手動のみ。エージェントごとに要約し `summary` レコードを追記
- **P5 台帳と実機確認**: README 日英・CLAUDE.md・Spec 03 の改訂

## Notes（rev1 時点の未決 — 査読で決めたい）

- **D1 起動時の既定**: 最新セッションを自動で開く（Claude Code の `--continue`
  相当）か、毎回新規で始めるか。rev1 は**最新を開く**を推す — 「閉じて開いたら
  続き」が Goal そのもので、新規は 1 クリックで作れる
- **D2 保存の粒度**: 不変条件 3 の 2 種別追記でよいか。代案は履歴を丸ごと
  スナップショット（temp+rename）だが、追記型のほうが壊れにくく Claude Code と同型
- **D3 セッションの単位**: 村全体（不変条件 1）でよいか。エージェント別
  セッションは作らない、で確定してよいか
- **D4 要約は手動のみで始めてよいか**: 自動（トークン 95% 等）は Spec 11 の
  天井と競合する。rev1 は手動のみ
- **D5 上限**: セッション数の上限、1 ファイルのサイズ上限、超えたときの扱い
  （古いものを畳む / 警告のみ / 何もしない）。現状の log リング 5,000 件は
  どう扱うか（ファイルには全部残し、メモリだけリングにする、が rev1 案）
- **D6 SQLite を入れない判断**: 全文検索が欲しくなったら？ rev1 は
  「一覧と本文の grep で足りる」に賭ける。実測で遅ければ Spec を改訂
- **D7 保存するフィールド**: `AgentMessage` を丸ごと保存してよいか
  （`grounding` / `co_recipients` は表示層専用だが、再開後の表示に要る）
- **D8 秘密の扱い（要判断）**: 会話ログをディスクへ書くのは本 Spec が初めて。
  利用者がチャットへ API キーを貼れば `{workspace}/sessions/*.jsonl` に平文で
  残る（failures.md #28 の world.json 事故と同型の面）。選択肢:
  (a) 何もしない（利用者自身の機械の中で、他の台帳と同じ扱い）
  (b) 保存時に既知の形（`sk-ant-…` 等）を検出して警告を 1 行
  (c) 検出して伏せ字で保存
  rev1 は **(a) + README への明記**を推す — (c) は会話の再現性を壊し、
  (b) は誤検出が続くと無視される。ただし「書いてあることを知らせる」責任は残る
- **D9 Spec 03 の改訂範囲**: 「新規チャット」の確認ダイアログは、捨てなく
  なったら不要では。文言も変わる（「破棄しますか」→「新しい会話を始めますか」）

## 参考（外部調査・2026-08-02 利用者提供）

収束点は 4 つ — JSONL / SQLite の追記型永続化・プロジェクト紐付け・
continue / resume / fork の再開モデル・フルログ温存 + 要約レイヤ。

- **Claude Code**: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`。
  continue / resume / fork の 3 プリミティブ。**会話は永続化するが
  ファイルシステムは永続化しない**という分離 — 本 Spec の不変条件 6 の下敷き
- **Copilot CLI/SDK**: `session-store.db`（索引）+ `session-state/{id}/`
  （チェックポイント・成果物）の二層。`disconnect()`（メモリ解放）と
  `deleteSession()`（削除）の区別
- **Cursor**: workspace DB（一覧）と global DB（本文）の二重 SQLite。
  ワークスペースのハッシュ紐付けが切れると「履歴が消えた」ように見える —
  **紐付けをパスのハッシュに依存させない**理由になる（本 Spec は workspace 直下
  に置くので、村ごと移動しても付いて回る）
- **VS Code Copilot**: 自動要約はトークン 95% で透過的、設定で無効化可能、
  手動 `/compact` は**要約の焦点を指示できる**。D4 で自動化を検討する際の型
- **LangGraph**: checkpointer を `thread_id` 単位で抽象化。バックエンド差し替え
  （InMemory / SQLite / Postgres）。本 Spec は村 1 つなので抽象化しない
- **CrewAI Flows**: `kickoff(inputs={"id"})` = resume、
  `kickoff(restore_from_state_id=)` = fork。Claude Code と概念的に一致
