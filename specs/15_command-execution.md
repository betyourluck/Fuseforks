## Goal

同梱ツールへ `run` を 1 本追加し、**利用者が事前に登録したコマンドだけ**を
エージェントに実行させる。登録は名前・実行ファイルの絶対パス・引数・
引数の自由度・タイムアウトの 5 つ。

起点は利用者の要望（2026-08-04）: 「エージェントに python とか Lint、curl を
使わせたい」。現状の同梱ツールは読む（`grep` / `fd` / `diff` / `file read`）と
書く（`sd` / `yq` / `file write`）で閉じており、**書いたものを走らせて確かめる
経路が無い**。

利用者の言葉「許可されたコマンドは JSON でリスト化して次は承認無しで使える」は
**そのまま登録制で満たせる** — 一度登録すれば以後は承認なしで通る。

### 立場の宣言

- **閉じた許容**（2026-07-31 の判断を維持）。登録したものだけが走る。
  除外リストは作らない
- **シェルを介さない。** 実行ファイルと引数配列で起動し、`cmd /c` / `sh -c` を
  経由しない（S1）
- **登録は絶対パスを解決して記録する。** `PATH` の時々の内容に実行対象を委ねない
- **`run` は安全機構を増やさない。囲いは登録ただ 1 つ。** 環境変数の遮断も
  作業フォルダも**境界ではない**。この点を契約に明記する（S4）

## Stories

### S1: `run` ツール

> エージェントとして、利用者が登録したコマンドを実行したい。
> なぜなら書いたコードが動くかは、走らせるまで分からないから。

**ツール定義**

- name: `run`
- 引数:

  | 引数 | 型 | 意味 |
  |---|---|---|
  | `name` | String | 登録名。登録簿に無ければ実行しない |
  | `extraArgs` | String[] | **登録の `args` の後ろへ足す引数**。登録が `allowExtraArgs: false` なら**渡すと拒否** |

**引数の名前を `args` から `extraArgs` へ変えた**（査読の指摘）。登録簿の欄も
`args` なので、同じ名前だと「登録の `args` を置き換えるのか、足すのか」が
本文からも登録要求の記録からも読めない。**実際に走るのは
`registered.args ++ extraArgs`** で、置き換えは起こらない。

**`allowExtraArgs: false` への追加引数は「未登録」とは別の拒否**（同じく査読の指摘）。
文面を分け、**登録要求には積まない**（登録は既にある。要求を積むと利用者の画面に
「登録済みのものを登録しろ」が並ぶ）:

```
`test` は登録されていますが、`allowExtraArgs: false` のため追加引数を受け付けません。
引数なしで呼び直すか、追加引数が必要なら利用者に登録の変更を頼んでください。
```

**文面を分けるのは、モデルが自己修正できる余地を残すため。** 未登録と同じ文面だと
「登録されていない」と読んで登録を待ち続けるが、実際は**引数を外せばその周で通る**。
RepeatGuard が止めるのは 3 回目なので、2 回目までに直せる形にしておく

- **エージェントは実行ファイル名を書けない。** 書けるのは登録名だけ。
  これが閉じた許容の実装であり、rev1 の PATH 問題と Windows の
  コマンド名正規化問題（`python` / `python.exe` / `PATHEXT` / 大文字小文字）が
  まとめて消える理由
- モデルへの提示: 登録簿の `name` と `description` を**ツールの説明文に列挙する**

**提示の判定は「実行可能な登録」を単位にする**（査読の指摘で書き直した。
rev3 以前は「登録件数」と「`cwd` が決まるか」を別の列にしており、
**1 件でも `cwd` が決まればゲートが開き、決まらない登録まで列挙されていた** —
提示で防ぐはずのものが実行時の拒否に落ちる）。

**実行可能な登録** = `cwd` が決まる登録（登録の `cwd` か個体の `work_dir` の
どちらかがある）。

| `enabledTools` に `run` | 実行可能な登録 | 提示 |
|---|---|---|
| 含まない（既定） | — | **しない** |
| 含む | 0 件 | **しない** |
| 含む | 1 件以上 | **する（実行可能なものだけ列挙）** |

- **1 段目は「利用者がこの個体に許したか」**（`enabledTools`。既定 OFF）
- **2 段目は「今それが使えるか」**（実行可能な登録が 1 件以上あるか）
- **列挙するのは実行可能な登録だけ。** 実行できない登録の `name` を見せると、
  モデルはそれを呼び、拒否され、他に手が無ければ同じ呼び出しを繰り返す
- **実行不能な登録が k 件あれば、末尾に 1 行だけ添える** —
  「他に k 件の登録がありますが、作業フォルダが未設定のため使えません
  （利用者に設定を頼んでください）」。件数と次の手だけで、`name` は出さない
  （#44 の規律を満たしつつ、使えないものにスキーマ分のトークンを払わない）

意図は「使えないツールにスキーマ分のトークンを毎ターン払わない」で、
`WORK_DIR_TOOL_NAMES` の考え方と同じ。**ただし `run` はあの集合には入れない**
（Notes 7）。二重ゲートなので、**設定でオンにしたのに出てこない**状態が起こりうる —
`AgentSettingsDialog` は `run` の行に理由を出す（登録 0 件／作業フォルダ未設定）。
`file` 系の `noWorkDirWarn` と同じ形
- 戻り: 終了コード + stdout + stderr。**非ゼロ終了は `Err` にしない**
  （`tool.rs` の「実行の境界」と、RepeatGuard が結果本文で数える規律
  ＝ `failures.md` #41 の一般化 3）

**シェルを介さない理由**

シェルへ 1 本の文字列を渡すと、登録との照合は文字列のパースでしか効かなくなる。
`registered && rm -rf ..` から実行対象の集合を取り出すには shell の文法を実装する
ことになり、**パースで守る境界は必ず抜けられる**。
`resolve_in_work_dir` が「パス文字列の検査」ではなく「canonicalize 後の前方一致」を
採ったのと同じ判断。

代償はパイプ・リダイレクト・変数展開が使えないこと。主用途（検索・絞り込み・差分）は
同梱の `grep` / `fd` / `diff` が埋めている。

**前例が無い道であることの自覚**（査読の指摘を受けて明記）: Claude Code / Cursor /
Aider はいずれもシェル経由で、引数配列のみの汎用エージェントの実例は確認できていない。
**採るのは、この村が閉じた許容を先に選んでいるから** — シェルを入れると
その選択が成立しない。実測で行き詰まったら D1 を再裁定する。

### S2: 登録簿

> 利用者として、走らせてよいコマンドを自分で決めたい。
> 一度決めたものは次から黙って通ってほしい。

**置き場**: `{workspace}/commands.json`。

```json
{
  "version": 1,
  "commands": [
    {
      "name": "test",
      "description": "pytest を走らせる",
      "program": "C:\\Python313\\python.exe",
      "args": ["-m", "pytest", "-q"],
      "allowExtraArgs": true,
      "timeoutSecs": 300,
      "cwd": null
    }
  ]
}
```

- **`program` は絶対パス。** 登録時に `which` 相当で解決し、`canonicalize` して
  記録する。実行時に `PATH` を引き直さない
- **検証の粒度は「実在するファイルか」まで**（`Path::is_file()`）。**実行可能かは
  見ない** — 判定の意味が OS で違い（Windows は拡張子と ACL、Unix は mode と
  実効 uid）、確実に知る方法は実行してみることしかない。**確かめられないことを
  確かめたふりの検査で覆わない**（`api_key_env` の教訓の同型 — 検査があると
  通ったものは安全だと読まれる）
- **検証に失敗した登録は「無効化」であって「削除」ではない**（査読の指摘で用語統一）。
  **ファイルは書き換えない** — メモリ上で無効印を付け、WARN を 1 行出し、
  提示の列挙から外す（上の「実行可能な登録」の判定にも掛ける）。
  ファイルを書き換えると、**別の端末で開いただけで登録が消える**（配布した村を
  一度開いて閉じると、元の端末へ戻しても登録が失われている）。
  利用者がパスを直せば次の起動で復活する
- **登録後に実行ファイルが消えた場合**は実行時に気づく。文言は S3 と同じ形で
  「登録されていますが実行ファイルが見つかりません（`{program}`）。
  利用者が登録し直すと使えます」+ 次の手。**起動時検証と実行時検査の両方が要る** —
  起動時だけだと、アプリを開いたまま環境を入れ替えたときに素通りする
- **`allowExtraArgs`**: `false` なら `args` 固定。`true` ならエージェントが末尾へ
  足せる（`ruff check <path>` のような形）。**汎用インタプリタ（`python` / `node` /
  `sh` 等）で `true` にすると任意コード実行になる** ので、UI が登録時に警告を出す。
  止めはしない — 利用者の判断を機構で否定しない
- **`cwd`**: `null` なら呼び出したエージェントの `work_dir`。未設定なら実行しない
- **`timeoutSecs`**: 既定 60、上限 3600。**登録ごとに持つ**（rev1 の 60 秒固定は
  `cargo build` / `pytest` を最初から締め出し、Goal と矛盾していた）

**配布との関係**（査読の指摘で書き直した）

rev1 は「村に入れない＝端末側に置く」と書いたが、`world.json` も
`{workspace}` 直下（`config_store.rs` の `root()`）なので**分離になっていなかった**。

正しい機構は置き場ではなく **`program` の絶対パス**にある。別の端末へ workspace を
丸ごと配っても、記録された絶対パスはその端末に存在しないので**起動時の検証で
無効化される**。**fail closed が構造で成立する。**
`{workspace}/commands.json` に置くのは、他の設定と同じ棚に置くためであって、
配布から隠すためではない。

**ただし fail closed が成立するのは `program` 自体の存在についてだけ**（査読の指摘）。
子プロセスには S4 のとおり `PATH` を渡すので、`python -m pytest` が呼ぶ
`pytest` 本体は**実行時に `PATH` で引き直される**。別の端末に
`C:\Python313\python.exe` が同じパスで在っても、その中の `pytest` が違えば
挙動は違う。**閉じているのは 1 段目の実行ファイルまでで、推移的な依存は閉じていない** —
S4 の「`run` は安全機構を増やさない」と同じ線の上にある。

### S3: 未登録コマンドの扱い

> エージェントとして、登録されていない名前を呼んだとき、何をすれば次に進めるのかを
> 知りたい。

**実行せず、待たず、その場で返す。**

```
`pytest` は登録されていないため実行しませんでした。
利用者が「システム設定 > コマンドの登録」で追加すると、次から実行できます。
利用者へ依頼するか、別の手段で進めてください。
このターンでは実行できません（登録されるまで、同じ呼び出しは何度でも失敗します）。
```

同時に、**登録要求として永続化する**（rev1 は in-memory で、非同期承認の根拠を
保存層が否定していた）。利用者はシステム設定で見て、登録するか捨てる。

**置き場は `{workspace}/command_requests.json` で、`commands.json` とは別ファイル。**
同居させると、`commands.json` が壊れた JSON になったときの「空として起動 WARN」で
**登録要求まで一緒に消える** — 無人の夜に積んだ要求が、翌朝に人が見る前に
落ちる経路を残さない（S3 の設計根拠がまた保存層に否定される形）。

```json
{
  "version": 1,
  "requests": [
    {
      "name": "pytest",
      "attemptedExtraArgs": ["-q", "tests/"],
      "agentId": "agent_3",
      "firstRequestedAtMs": 1785800000000,
      "count": 4
    }
  ]
}
```

- **欄名は `attemptedExtraArgs`**（査読の指摘）。**エージェントが渡そうとした
  追加引数だけ**を記録する。`args` にすると、利用者が登録画面で見たときに
  「これを登録の `args` に入れるのか、`allowExtraArgs: true` にして
  追加で渡させるのか」が決められない
- **重複は `(name, attemptedExtraArgs)` の完全一致で畳む** — `count` を増やし
  `firstRequestedAtMs` は最初のまま。`name` だけで畳むと、利用者が
  「何を登録すればよいか」を決める材料（実際に呼ばれた引数）が消える
- **上限 50 件。超えたら `firstRequestedAtMs` が最も古いものから捨てる**
  （査読の指摘で規則を単純化した。当初案の「`count` の少ない古いものから」は
  2 つの軸を混ぜており、どちらが効いたかを利用者が読めない）。歯止めが効かない
  エージェント（Notes 5 のとおり `run` では RepeatGuard の効きが落ちる）が
  ファイルを無限に太らせる経路を作らない。捨てたことは WARN に書く
- **壊れた JSON は空として起動 WARN。`commands.json` には影響しない**
  （2 ファイルの非対称を埋める。査読の指摘）。ただしこれは
  **「無人の夜に積んだ要求が消える」経路を残す**ので、対策は読み側ではなく
  書き側に置く — **書き込みは temp + rename の原子的な差し替え**にして、
  途中で落ちても壊れた内容が残らないようにする（`save_world` の既存パターン）。
  **壊れたものをどう読むかより、壊れないように書くほうが効く**
- **時刻は引数で受け取る。** 内部で `Local::now()` を呼ばない
  （`schedule.rs:5` と `lib/clock.ts` と同じ規律 — 内部で壁時計を読むと、
  テストが特定の時刻でだけ落ちるものになる）

**待たない理由**: 予定発火（Spec 07）は人が居ないところで走る。同期承認だと
無人ターンが承認待ちで席を占める。

**「初回は必ず失敗する」ことを認める**（査読の指摘）。再試行の設計は次のとおり:

- **自動リトライはしない。** 失敗したターンは失敗のまま終わる
- **予定発火は次回発火で通る。** 登録が済んでいれば、次の周期で同じ依頼が成功する。
  これが無人タスクの再試行機構であり、別に作らない
- **人が出した依頼は人が出し直す。** 登録画面に「エージェントが要求したコマンド」が
  残っているので、何を頼み直せばよいかは画面から読める

打ち切り文は `bundled_tools_contract` の規律どおり「何が起きたか」と
「次に何をするか」を書き、**続きを取る経路が無い**ことまで書く（`file read` が
「続きを読む方法はありません」と書くのと同じ扱い）。

### S4: 境界の明示（`run` は安全機構を増やさない）

> 利用者として、`run` を有効にすると何が失われるのかを知りたい。

**契約と UI の両方に、次の 3 つを書く。**

1. **作業フォルダ境界は `run` には効かない。** `cwd` を `work_dir` にしても、
   子プロセスは絶対パスで外を読める。`file` / `grep` の
   「canonicalize 後の前方一致」は**同梱ツールの境界であって、プロセスの境界ではない**
2. **`file remove` のごみ箱限定も `run` の前では意味を失う。** 登録したコマンドが
   `rm` を含むなら完全削除が走る。これは矛盾ではなく境界の位置の違い
   （同梱＝Concordia が提供する操作は安全側／`run` ＝利用者が明示的に登録した外部の能力）
3. **環境変数の遮断は境界ではない。** `env_clear` は環境変数経路だけを閉じる。
   `~/.aws/credentials` や `~/.config/gh/config.yml` は**ファイル経路で読める**ので、
   `allowExtraArgs: true` の汎用インタプリタを登録した時点で秘密は読める。
   **`env_clear` を残すのは事故の確率を下げるためで、秘密保護の境界ではない**
   （査読の指摘 CRITICAL 2 を受けて位置づけを訂正。rev1 の
   「渡さないことでしか塞げない」は、塞げる範囲を過大に見せていた）

**環境変数の実装**: `env_clear()` してから、親プロセスの環境から**名前を指定して
値をコピー**する。初期集合は `PATH` / `SYSTEMROOT` / `TEMP` / `TMP` / `HOME` /
`USERPROFILE` / `LANG`。`PATH` を渡す以上、子プロセスは端末上の任意の実行ファイルへ
届く — これは**可用性のための選択**であって安全のためではない（D5 の裁定を反映）。

## Notes（査読論点）

1. **`allowExtraArgs` が閉じた許容の穴になりうる**。`python` を `allowExtraArgs: true`
   で登録すれば任意コード実行になり、rev1 が批判された状態と実質同じになる。
   **これを機構で止めない理由**: 止めると `ruff check <path>` のような正当な用途まで
   消える。処方は UI の警告と契約の明文化のみ。**査読で最も反論が来る点**で、
   「`allowExtraArgs` を汎用インタプリタに立てられなくする」案は
   *汎用インタプリタの一覧*という除外リストを作ることになり、閉じた許容の設計と衝突する
2. **パイプを持たない代償**: 主用途は同梱ツールが埋めている。残るのは
   `pytest | tail` のような整形で、出力の有界化が代替する。**rev1 が「`stdin` を
   足せば 2 呼び出しで書ける」と書いたのは撤回** — `stdin` に任意文字列を渡せると
   `sh -c` 相当のインジェクションが可能になる（査読の指摘）。`stdin` は持たない
3. **出力の分配**（rev1 は「合算 12,000 字」としか書かず、分離方法が未定義だった）:
   `MAX_OUTPUT_CHARS`（`tools/fs.rs:48` の `pub(crate) const MAX_OUTPUT_CHARS:
   usize = 12_000`。`file.rs` / `edit.rs` と共有）を上限とし、
   **stderr 4,000 字・stdout 8,000 字の固定枠**に分ける。

   **融通しない。** stderr が 3,000 字なら stdout は 8,000 字のままで、
   9,000 字にはしない。理由は RepeatGuard が結果本文の**完全一致**で数えること —
   融通すると「stderr の長さで stdout の打ち切り位置が変わる」ので、
   同じコマンドの 2 回目が 1 文字でも違う stderr を出した瞬間に
   **stdout 側の打ち切り位置ごと変わり、一致が壊れる**。総量が可変になる設計は
   歯止めを壊す側に効く。

   stderr を先に確保するのは、非ゼロ終了時の診断がそこにあるため。
   どちらも打ち切ったら **#55 の規律で総量を書く**（「全 N 字のうち先頭 K 字」）+
   `bundled_tools_contract` の規律で**続きを取る経路が無いこと**まで書く
   （`file read` の「続きを読む方法はありません」と同じ扱い。
   再実行しても同じ出力とは限らないので、なおさら明示が要る）
4. **プロセス木ごとの kill**: `tokio::process::Child::kill` は対象 PID にしか効かず
   **孫が残る**（査読の指摘。rev1 の実機確認 (5) は実装方針では達成不能だった）。
   Windows は Job Object の `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`、Unix は
   `setsid` + `kill(-pgid)`。**依存を 1 本足す**（`command-group`）。
   `trash` を足したときと同じ判断 — 安全側の挙動を自前の unsafe で書かない
5. **RepeatGuard の効きが落ちる**: 判定は（ツール名 + 引数 + 結果本文）の一致だが、
   コマンドは同じ引数で違う出力を返すものが多い（`git log` / `curl` /
   時刻を含む出力）。**病理は「同じコマンドを叩き続ける」形で現れうるのに歯止めは
   効かない。** 機構は足さない（何が異常かを決められない）。実測で出たら Spec を切る
6. **`run` の既定 OFF は破壊的変更**（査読の指摘）。`enabledTools: null` の意味が
   変わる。**Phase 0 で契約として記録し、Phase 3 で `DEFAULT_ENABLED_TOOLS` を
   新設する**（rev1 は Notes にだけ書き、Tasks にも検収項目にも無かった）
7. **`WORK_DIR_TOOL_NAMES` に `run` を入れない**（査読の指摘）。あの集合は
   「作業フォルダがあるときだけ提示し、かつその中しか触らない」ツールの集合で、
   境界を破る `run` を入れると集合の不変条件が壊れる。`run` の提示条件は
   「登録が 1 件以上あり、かつ `cwd` が決まる（登録の `cwd` か個体の `work_dir`）」で
   別に書く
8. **タイムアウトは登録ごと**（rev1 の 60 秒固定を撤回）。`cargo build` /
   `pytest` が超えると Goal「書いたものを走らせて確かめる」が果たせない。
   既定 60 / 上限 3600
9. **Phase 0 で既存の追従漏れを 2 件回収した**（2026-08-04）。契約を書く前に
   隣の記述を読んだので見つかった:
   - `data_contract.yaml` の `tool_extension_point` が同梱ツールを
     **「4 本」**のままにしていた（Spec 01 の `sd` / `yq` と Spec 09 の `file` が
     入っていない）。**同じファイルの `enabled_tools_invariant` は 7 本**と
     書いており、**1 つの契約ファイルの中で本数が 2 つあった**
   - `specs/02` に Spec 09 の続報が入っていなかった。Spec 09 Phase 4 は
     「Spec 02・07 の本数記述へ続報を追記」と書いたが、**実際に入ったのは
     Spec 07 だけ**（07 には「2026-07-31 の続報: Spec 09 で file が加わり
     同梱は 7 本になった」がある）
   - **一般化**: **数の記述は、増えた名前で grep しても引っかからない。**
     `file` で全台帳を引いても「4 本」「6 本」は出てこない。`failures.md` #51 の
     grep 規律は**名前**を対象にしており、**名前の個数を述べた文**は網の外。
     機構・enum・フィールドを足したら、**その集合の要素数を述べている文**を
     別に探す（`\d 本` / `\d 個` / `seven` のような数量表現で引く）

## P1 実装記録（2026-08-04）

`crates/agent-core/src/command.rs` に型と純機構、`config_store.rs` に I/O 4 本
（`load_commands` / `save_commands` / `load_command_requests` /
`save_command_requests`）。`schedule.rs`（型 + 純機構）と `config_store.rs`（I/O）の
分業をそのまま踏襲。単体 15 本 + store 8 本。workspace 443 → 456 本全緑、
clippy 新規警告ゼロ。

**実装で決めた 7 点**:

1. **`load_commands` は `Err` を返さない。空 + `dropped` で返す。**
   `load_schedules` は `Err` を返して呼び出し側に書き戻しを止めさせるが、
   コマンドは**閉じた許容なので「空 = 何も実行できない」が安全側**。
   読めない登録簿で起動を止める理由が無い（直せば次の起動で戻る）
2. **1 件ずつの読み取り失敗は、その 1 件だけを落とす。** ファイル全体が JSON として
   壊れているときだけ空にする。予定と同じ扱いで、**壊れた 1 件が他を人質にしない**
3. **`Unavailable` は 2 値**（`ProgramNotAbsolute` / `ProgramMissing`）。
   1 つに畳むと「登録し直してください」と「別の端末の村を開いた可能性があります」が
   同じ文面になる。**理由ごとに次の手が違う**（#44）
4. **`mark_availability` は実在判定の述語を受け取り、自分では `fs` を触らない**
   （`AgentRoleDefaults::apply_to` の `template_exists` と同じ形）。テストが
   実ファイルを置かずに書ける。**無効印は毎回付け直す**ので、パスを直せば復活する
5. **`get` は無効な登録も返す。** 「登録が無い」と「登録はあるが使えない」は
   別の答えで、モデルへ返す文面が違う。フィルタするのは `runnable` の側
6. **タイムアウトの範囲外は登録を落とさず丸めて WARN。** 落とすのは罰が重い
   （`timeoutSecs` の書き間違いでコマンドごと消える）。ただし黙って丸めない
7. **同名は最初の 1 件を採り、後を落とす。** 後勝ちにすると、どちらが効いているかを
   利用者がファイルから読めない

**併せて `write_atomic` を切り出した。** temp + rename は `save_world` /
`save_schedules` が個別に書いており、今回の 2 本を足すと**同じ 8 行が 4 箇所**に
なるところだった。既存 2 本も同じ経路へ寄せた（`world_save_is_atomic_and_leaves_no_temp_file`
が回帰を留めている）。

## P2 実装記録（2026-08-04）

`crates/agent-core/src/tools/run.rs`。単体 7 本、workspace 456 → 463 本全緑、
clippy 新規警告ゼロ。依存に `command-group 5.0.1` を追加。

**契約が実装を見ずに書けていなかった点が 2 つ出た。** どちらも P0 の凍結時には
見えず、実装して初めて分かった形。

1. **`description()` は個体を知らない。** 契約は「**列挙するのも実行可能な登録
   だけ**」と凍結したが、`AgentTool::description(&self) -> String` は
   `ToolContext` を受け取らないので、**その個体の `work_dir` に依存する列挙が
   書けない**。`enabled_tools` と `WORK_DIR_TOOL_NAMES` による除外は
   オーケストレーター側で**名前の集合**として実装されているが、
   「登録が 1 件も実行可能でない」は**中身を見ないと決まらない除外**で、
   名前の集合では書けない。
   処方: **`AgentTool::spec_for(&self, ctx) -> Option<ToolSpec>` を追加**
   （既定は `spec()`。`None` で非提示）。加算的で、他の 7 本は 1 行も変わらない。
   **これは Spec 14 P1 の「`AgentSnapshot` にも `role_id` が要る」と同型** —
   契約に欄や規則を足したら「**それを運ぶ経路が既にあるか**」を実装前に問う
2. **Spec 10 の不変条件 1 と衝突しかけた。** 「検査点は周回境界だけ」を守ると、
   打ち切りを押しても走っているコマンドは**最長 `timeoutSecs`（上限 1 時間）
   走り続ける** — 実機で観測した「要求から 0.0 秒」がそこだけ破れる。
   処方: **`ToolContext.cancel: Option<CancellationToken>` を追加**し、
   **`run` だけが見る**。判断は「**葉で 1 箇所だけ見るのは、周回境界の検査を
   増やすことではない**」— ターンループの構造は変わらず、止められない待ちを
   1 つ潰すだけ。不変条件 1 の趣旨（検査を散らさない）は保たれている

**そのほか実装で決めた 4 点**:

- **出力の枠は融通しない**（`STDERR_CHARS = 4_000` / `STDOUT_CHARS = 8_000`）。
  stderr が短くても stdout の枠は広がらない。融通すると stderr の長さで
  stdout の打ち切り位置が変わり、**RepeatGuard の完全一致が壊れる**
- **打ち切り文に「続きを読む方法はありません」を書く。** `run` は
  `file read` 以上に続きが取れない（**再実行しても同じ出力とは限らない**）ので、
  #58 の規律をそのまま適用した
- **`now_ms()` は `command.rs` に 1 つだけ置く。** `CommandRequestLog::record` が
  時刻を引数で受ける規律（`schedule.rs`）は保ち、**壁時計を読む縁を 1 箇所に集める**
- **`resolve_program`（`which` 相当）は登録時にだけ使う。** 実行時は絶対パスを
  そのまま起動する。Windows の `PATHEXT` 展開はここに閉じ込めた

**P3 へ送る宿題が 1 つ**: `execute_tool` の `ToolContext` は今 `cancel: None` で、
**打ち切りはタイムアウトまで効かない**。ターンのトークン（`TurnHandle.token`）を
渡すのは P3 の配線。実機確認 (6)「Spec 10 の打ち切りで子プロセスが残らない」は
それまで検証できない。
