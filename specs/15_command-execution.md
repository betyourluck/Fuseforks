# Spec: run — コマンド実行の同梱ツールと許可リスト

**ID**: 15
**Date**: 2026-08-04
**Status**: **Draft rev1**（査読待ち）
**Branch**: なし（main へ Phase 単位で直接コミット。Phase 0 は査読承認を前提条件とする）

---

## Goal

同梱ツールへ `run` を 1 本追加し、エージェントに外部コマンドの実行を渡す。
どのコマンドを実行してよいかは JSON の許可リストで決め、**一度許可したものは
次から承認なしで通る**。

起点は利用者の要望（2026-08-04）: 「エージェントに python とか Lint、curl を
使わせたい」。現状の同梱ツールは読む（`grep` / `fd` / `diff` / `file read`）と
書く（`sd` / `yq` / `file write`）で閉じており、**書いたものを走らせて確かめる
経路が無い**。エージェントがコードを直しても、テストが通るかを自分で確かめられない。

### 立場の宣言

- **シェルを介さない。** 実行ファイル名と引数配列を受け取り、`cmd /c` や `sh -c`
  を経由しない。理由は許可リストの成立条件（下記 S1）
- **許可リストは村に入れない。端末側に置く。** 村を配ったら実行許可も付いてくる、
  という形にしない（下記 S2）
- **許可リストは安全機構ではない。承認の手間を減らす機構である。** `python` を
  許可した時点で任意コード実行を許可している。この事実を契約と UI の両方に書く
- **環境変数は既定で渡さない。** `api_key_env` の事故（世界に平文の API キーが
  保存された件）と同じ形を、今度は子プロセス経由で作らない

## Stories

### S1: `run` ツール

> エージェントとして、作業フォルダでコマンドを実行したい。
> なぜなら書いたコードが動くかは、走らせるまで分からないから。

**ツール定義**

- name: `run`
- 提示条件: `WORK_DIR_TOOL_NAMES` に入れる（作業フォルダ未設定なら提示しない）。
  `enabledTools` のフィルタにも従う。**既定は OFF**（下記 S3）
- 引数:

  | 引数 | 型 | 意味 |
  |---|---|---|
  | `command` | String | 実行ファイル名。パス区切りを含めない（`python`、`ruff`、`curl`） |
  | `args` | String[] | 引数。省略時は空 |

- 戻り: 終了コード + 標準出力 + 標準エラー。**非ゼロ終了は `Err` にしない** —
  ツールの失敗で会話を止めない既存の規律（`tool.rs` の「実行の境界」）と、
  RepeatGuard が結果本文で数える規律（failures.md #41 の一般化 3）の両方から

**シェルを介さない理由（本 Spec の中核）**

シェルへ 1 本の文字列を渡すと、許可リストは文字列のパースでしか効かなくなる。
`echo ok && rm -rf ..` は 1 つの文字列で、そこから「実行されるコマンドの集合」を
取り出すには shell の文法を実装することになる。**パースで守る境界は必ず抜けられる。**

引数配列で受ければ、許可の判定対象は `command` ただ 1 つで、**構造的に**決まる。
これは `resolve_in_work_dir` が「パス文字列の検査」ではなく「canonicalize 後の
前方一致」で境界を敷いたのと同じ判断（`bundled_tools_contract` の不変条件）。

**代償**: パイプ・リダイレクト・シェル変数展開が使えない。`grep` / `fd` / `diff` は
同梱で持っており、パイプの主用途は既に埋まっている。埋まらない用途が実測で出たら、
そのときに考える（Notes 2）。

**環境変数**

`std::process::Command::env_clear()` で全消しし、明示した分だけ足す。
初期集合は `PATH` / `SYSTEMROOT`（Windows で多くの実行ファイルが要求する）/
`TEMP` / `TMP` / `HOME` / `USERPROFILE` / `LANG`。

理由は 1 つ。`echo $ANTHROPIC_API_KEY` は「`echo` を許可した」だけで通る。
許可リストはコマンド名しか見ないので、**秘密の読み出しは許可リストの外側の問題**。
親の環境を丸ごと渡さないことでしか塞げない。

**有界化**

- 出力は stdout + stderr の合算で `MAX_OUTPUT_CHARS`（12,000 字）。
  打ち切りは #55 の規律 —「全 N 字のうち先頭 K 字」と総量を書く
- タイムアウト 60 秒。超えたら kill して「時間切れ」を返す
- Spec 10 の打ち切りで子プロセスも kill する（`tokio::process` + `CancellationToken`）

### S2: 許可リスト

> 利用者として、一度許可したコマンドは次から黙って通ってほしい。
> なぜなら毎回同じものを承認するのは、承認を形骸化させるから。

**置き場**: `{workspace}/allowed_commands.json`。**`world.json` には入れない。**

理由が 2 つある。

1. **村を配ると実行許可も付いてくる形にしない。** `world.json` は配布物
   （Spec 14 が「`work_dir` は端末ごとに違う絶対パスで、村を配ると壊れた参照を
   配ることになる」として雛形から外したのと同じ筋）。実行許可はそれより重い —
   受け取った側は、開いた村でどのコマンドが許可済みかを知らないまま起動する
2. **`python` が在るかどうかは端末で決まる。** 村の性質ではない

**形式**:

```json
{
  "version": 1,
  "allowed": ["python", "ruff", "curl"]
}
```

コマンド名だけ。**引数パターンは持たない**（Notes 1）。

**判定**: `command` が `allowed` に完全一致するか。パス区切り（`/` `\`）を含む
`command` は一致以前に拒否する — `./python` と `python` を別物として数えると、
許可リストが指す対象が曖昧になる。解決は OS の `PATH` に任せる。

### S3: 未許可コマンドの扱い

> エージェントとして、許可されていないコマンドを呼んだとき、何をすれば
> 次に進めるのかを知りたい。

**実行せず、待たず、その場で返す。**

```
`pytest` は許可されていないため実行しませんでした。
利用者が「システム設定 > コマンドの許可」で追加すると、次から実行できます。
利用者へ依頼するか、別の手段で進めてください。
```

同時に、UI 側へ**承認待ちとして積む**（システム設定のコマンド許可ページに
「エージェントが要求したコマンド」として並ぶ）。利用者が押せば次から通る。
これで「次は承認無しで使える」は成立する。

**待たない理由**: 予定発火（Spec 07）は人が居ないところで走る。同期承認だと
無人ターンが承認待ちで止まり、Spec 10 の打ち切りか天井（Spec 11）が来るまで
席を占める。**線は人が引くが、人が居ない時間に線を引かせない。**

文面が「次に何をするか」を書くのは failures.md #44 の規律。作業フォルダ未設定の
`work_dir_missing()` と同じ形で、モデルが読んで利用者に頼める。

## Notes（査読論点）

1. **引数パターンを持たない根拠**: `python scripts/*.py` のような粒度は、
   安全性を上げるように見えて上げない。`python` を許可した時点で任意コードが
   走るので、引数を絞っても `python -c "..."` が残る。粒度を上げると
   「許可リストで守られている」という**誤った安心**だけが増える。
   rev1 はコマンド名だけにし、契約と UI へ「許可 = そのコマンドができること
   全部の許可」と書く。**この判断は査読で最も反論が来る点**
2. **パイプを持たない代償の見積もり**: 主用途（検索・絞り込み・差分）は同梱ツールが
   埋めている。残るのは `python -m pytest | tail` のような整形で、これは出力の
   有界化が代替する。実測で足りないと分かったら、`run` に `stdin` 引数を足す
   （パイプ 1 段は 2 呼び出しで書ける）— シェルを入れるより射程が小さい
3. **`run` の既定を OFF にする**: 既存 7 本は既定 ON（`enabledTools: null` =
   全提示）。`run` を同じ扱いにすると、**アプリを更新した瞬間に全個体が
   コマンド実行能力を得る**。`batch_start_invariant` が「開いただけで課金が
   始まる作りにしない」と言うのと同じ形で、**更新しただけで実行能力が増える
   作りにしない**。実装は `enabled_tools: None` の解釈を「既定集合」に変え、
   既定集合から `run` を外す（`BUNDLED_TOOL_NAMES` とは別の定数）
4. **Spec 09 の境界は `run` を許可した個体には適用されない。** `file` / `grep` の
   作業フォルダ境界は canonicalize の前方一致で担保しているが、子プロセスは
   その外を読める（cwd を work_dir にしても、絶対パスで外へ出られる）。
   **契約へ明記する** — 「`run` を有効にした個体では、同梱ツールの作業フォルダ
   境界は実効的に無くなる。境界を担うのは許可リストだけになる」。
   書かないと、README の「作業フォルダの外は構造的に読めない」が嘘になる
5. **RepeatGuard の効きが落ちる**: 判定は（ツール名 + 引数 + 結果本文）の一致だが、
   コマンドは同じ引数で違う出力を返すものが多い（`date` / `git log` /
   ネットワーク越しの `curl`）。**病理は「同じコマンドを叩き続ける」形で
   現れうるのに、歯止めは効かない**。機構は足さない（何が異常かを決められない）
   が、Notes として残し、実測で出たら Spec を切る
6. **タイムアウト 60 秒の根拠は薄い**。`pytest` や `cargo build` は超える。
   ただし長時間のコマンドは天井（Spec 11）と打ち切り（Spec 10）の射程外で
   席を占め続けるので、rev1 は短く固定して実測を待つ。設定で伸ばせるように
   するかは D4
7. **`file` の `remove` と `run` の非対称**: `file remove` はごみ箱のみで完全削除の
   経路を作らなかったが、`run` を許可すれば `rm` も `del` も走る。
   **これは矛盾ではなく境界の位置の違い** — 同梱ツールは「Concordia が提供する
   操作」なので安全側に倒し、`run` は「利用者が明示的に許可した外部の能力」。
   ただし README の削除に関する記述は、`run` の存在を前提に読み直す必要がある（P5）

## 未決（査読で裁定がほしい）

- **D1**: シェルを介さない（パイプ不可）で通すか。利用者が `python -m pytest |
  tail -20` のような書き方を期待している場合、rev1 の形は体験を損なう
- **D2**: 許可リストを端末側（`{workspace}/allowed_commands.json`）に置く判断。
  村の共有物にしたい理由があれば聞きたい
- **D3**: 承認を非同期だけにするか。利用者の言葉「次は承認無しで使える」は
  **初回に承認がある**ことを含意しており、S3 は初回を「拒否 + 承認待ちへ積む」に
  読み替えている。会話を止めて待つ同期承認も要るなら、無人ターン（Spec 07 の
  予定発火）の分岐を設計に足す必要がある
- **D4**: タイムアウトを設定可能にするか（Spec 13 の器へ 1 項目足すか、固定か）
- **D5**: 環境変数の初期 allowlist に何を入れるか。`PATH` は必須だが、
  `PATH` 経由で利用者の環境の任意の実行ファイルに届く。絞る案（Concordia が
  管理する専用 PATH）は、`python` を見つけられなくなるので採らない方向で書いた
