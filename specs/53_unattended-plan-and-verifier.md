## Goal

1. **予定から始まった作業は、計画の確認（Spec 43）で止まらずに配られる**（予定ごとのオプトイン）
2. **ステータスバーのスイッチで、計画の確認をまとめて飛ばせる**（1 プロセス 1 村なので村全体）
3. **束ねの検証を仕組みにする** — 既定の検証役を 1 体（または「なし」）指定でき、計画の確認の
   パネルでは波ごとに選び直せる（既定を初期選択・「なし」可）

**既存の村は 1 ミリも変わらない。** 予定の欄の既定は偽・スイッチの既定は OFF・既定の検証役の
既定は「なし」で、3 つとも既定なら今日の挙動とバイト等価（検収 7 と P0 の凍結で担保）。

**やらないこと（範囲外）**: 窓に時間切れを付ける（承認待ちを N 分で自動実行する）/ 検証の結論で
自動的に聞き直す（Replan は 2026-08-02 に ×8.5 の実測で退けた）/ 検証役を複数にする /
波ペインに検証役の列を出す（計器で読む）/ 条例の書き換え（利用者の資産 — Notes 3）。

## Design

### D1. 予定起点の印 — `Envelope.auto_approve_plans: bool`

- **真を立てられるのはコードの 2 箇所だけ**: `deliver_scheduled` で `task.auto_approve_plans` が
  真のとき / その予定の検収の再依頼 `redeliver_for_acceptance`（`AcceptancePending` に
  `auto_approve_plans: bool` を足し、発火時に写し、再配送の封筒へ積む）。**封筒はコアの内部型で、
  モデルや外部クライアントが組む経路は無い** — 他の配送はすべて受信封筒の値を**写すだけ**
- **引き継ぐ**: `ask` / `plan` / 転送の配送は、受信封筒の値をそのまま積む（予算と同じ経路。
  委譲先のワーカーが進行役で、さらに `plan` を撒く場合も止まらない）
- **新しい根は偽**: 利用者の発話 / `dispatch_plan_wave` / 束ねの配送 / MCP の外部依頼
- **予定の欄**: `ScheduledTask.autoApprovePlans: bool`（`serde(default)`・偽なら省略）。
  `ScheduleOptions` / `ScheduleView` / `scheduleDraft.ts` の往復 / `update_schedule` で保つ
- **運ぶ引数の数**: `run_turn` / `CallRunner` / `run_plan` / `execute_wave` / `deliver_and_wait` に
  `bool` が 1 本ずつ増える。因果の欄（予算・参加者・待ちの連鎖・この印）を 1 つの構造体へ畳むのは
  **本 Spec ではやらない**（差分が移動と混ざる — 巨大ファイル分割の 6 箇条の 3）

### D2. 窓の判定を 1 箇所で拡張する

```rust
spec.plan_review
    && !self.awaiting_reply          // 凍結 10
    && !self.auto_approve_plans      // D1（予定の欄）
    && !shared.plan_review_bypass()  // D3（ステータスバーのスイッチ）
```

- 利用者の裁定「予定で自動で通すになっているとスイッチが OFF でも飛ばす」は、この OR で成立する
- **飛ばしたことを計器に出す**: `plan review skipped: agent=… reason=schedule|bypass`
  （**設定がオンの個体で窓が開かなかったときだけ**。`awaiting_reply` の飛ばしは既存どおり出さない）。
  出さないと「計画の確認をオンにしたのに止まらなかった」がログから読めない
- **両方が真なら `reason=schedule`**（予定の印を優先）。スイッチを戻しても同じ予定は飛ばし続けるので、
  持続する側の理由を出すほうが、後から読んだ人の次の手（予定を直す）に繋がる

### D3. ステータスバーのスイッチ — プロセス寿命で保存しない

- 状態は `Shared` のメモリだけ（`AtomicBool`）。**起動時は必ず OFF。** 1 プロセス 1 村なので、
  スコープは「プロセス全体 = その村」。IPC 2 本（`get_plan_review_bypass` /
  `set_plan_review_bypass`、村の識別子は持たない）と、変更を画面へ伝える
  `CoreEvent::PlanReviewBypassChanged`
- **保存しない理由**: スイッチは人の確認をまとめて外す操作で、**付けっぱなしのまま再起動すると、
  確認が要る村で黙って確認が消え続ける**（MCP の扉を「誰もいないのにつけっぱなしにしない」ために
  ステータスバーへ出したのと同じ懸念）。**再起動をまたいで無人で回したいものは、予定の欄（D1）が担う**
- ステータスバーでは統計アイコンの左に置き、オンの間は発光させる（統計と同じ作法）。
  **ステータスバーの doc の「この帯で唯一の操作」を覆す** — 2 つ目の操作になる

### D4. 検証役の決まり方

| 経路 | 使う検証役 | 解決する時点 |
|---|---|---|
| ターンの中で撒く `plan`（窓なし・窓を飛ばした場合を含む） | 村の既定（`world.json` の `defaultVerifier`） | `run_plan` が撒く時点で `World` から読む（「検証は今」の規律） |
| 計画の確認で承認した波 | **パネルで選んだもの**（初期選択は村の既定。「なし」を選べる） | `dispatch_plan_wave` の引数 |

- `World.default_verifier: Option<AgentId>`（`None` = なし）。保存は既存の `set_ask_timeout` と
  同じ形（IPC 2 本・`world.json` へ書き戻し・次の波から効く）。指定した個体が削除されたら
  読むときに `None` 扱い（`reception` と同じく掃除はしない — 設定し直すのと初めて設定するのとで
  次の手が同じなので、ここは画面で「（削除済み）」と出す）
- `dispatch_plan_wave(planId, tasks, verifier?)` — **凍結 4 の IPC の形を覆す**（3 つ目の引数）。
  **3 つ目は省略可で、省略は `None`（なし）と解釈する**（Tauri のコマンド引数の `Option` の既定）。
  TS 側は `verifier?: AgentId | null`。提示時の値は持たず、押したときの値が真実（凍結 4 と同じ規律）
- `execute_wave` に `verifier: Option<AgentId>` を足す。`run_plan` は村の既定を、
  `run_dispatched_wave` は承認時の引数を渡す（**`execute_wave` の中では解決しない** — 解決の場所が
  2 つあると、窓を通った波と通らない波で既定の読み方がずれる）
- 検証役として選べるのは登録済みのサーヴァント。**絆（接続）は要らない** — 人が明示に選んだ宛先で、
  予定の `to` と同じ扱い。これは「線は人が引く」の例外として `plan_verifier_contract` に明記する
  （**選ぶのが人である**ことで原則の意図は保つ）
- **設定の置き場は作業状況タブの見出し**（「検証役: [選択]」）。検証役は村の内容物で
  （#52 の境界 — 保存先ではなく「村の内容物か、アプリの設定か」）、計画を見る場所の隣にある

### D5. 検証の機構 — 束ねの後・返す前に、システムが検証役へ頼む

**検証役が `None` なら何もしない** — 検証の処理に入らず、束ねには見出しも理由も一切足さない
（既存とバイト等価。検収 7）。以下は検証役が指定されているときだけ:

1. **システムが検証役へ `deliver_and_wait` で頼む**（`execute_wave` の `Some(bundle)` の手前）。
   本文 = 各タスクの依頼文 + 束ね + 見る 4 点（条例と同じ: 空の答え / 依頼の取り違え /
   答え同士の矛盾 / 欠けている論点）+ 結論の 3 択（このまま使える / この相手にだけ聞き直す /
   依頼元に確認する）
2. **検証役の答えを束ねの末尾に付ける**: `## 検証: agent_x（表示名）` の見出しで 1 節
3. **検証役が指定されているのに検証しなかった場合は、理由を束ねに 1 行書く**（黙って飛ばさない — #44）:
   検証役が波の宛先に含まれる（自己採点しない）/ 検証役が進行役自身 / 停止中 /
   待ちの輪（Spec 44 の拒否）/ 時間切れ / 予算切れ。**どれも束ねは返す**（検証の失敗で仕事の
   結果を捨てない）
4. **波が打ち切られた場合は検証しない**（束ねを作らない既存の経路のまま）

- **財布**: 検証役の配送は、その波を配った財布を使う。ターンの中の `run_plan` = 進行役の因果の財布、
  承認後の波 = 承認時に切った根の財布（`mod.rs:1164`）。**波のワーカーで尽きていたら 3 の
  「予算切れ」**（`deliver_and_wait` の事前検査がそのまま返す）
- **待ちの連鎖**: ターンの中では進行役を積む（検証役が進行役へ `ask` し返すと Spec 44 で拒否される）。
  承認後の波は根なので空から始まる
- **本文の区切り**: 依頼文と各答えは既存の束ねと同じ `## agent_id（表示名）` の見出しで分け、
  `---` は使わない（答えは Markdown で `---` が普通に現れる。Spec 17 で diff の見出しと衝突した前例）。
  答えの中に封筒構文があれば、配送の `wrap` が既存どおり無害化する（Spec 26）
- **LLM に「検証するか」を選ばせない**（凍結 1 以来の規律 — 選べる形にすると #84 で飛ばされる）
- **計器**: `plan verify: agent=… plan_id=… verifier=… outcome=ok|skipped:<理由> chars=… elapsed_ms=…`
  （検証役が `None` の波では出さない）

## 検収

1. 「自動で通す」予定から始まった作業で、進行役（計画の確認オン）が止まらず撒く。
   `plan review skipped: … reason=schedule` が出て、`plan pending:` が出ない
2. 同じ進行役に利用者が頼むと、今までどおり止まる（負の対照）
3. スイッチをオンにすると利用者の依頼でも止まらない（`reason=bypass`）。アプリを再起動すると OFF に戻る
4. 既定の検証役を指定した村で、束ねの末尾に `## 検証:` の節が付き、`plan verify: outcome=ok` が出る
5. 計画の確認パネルで「なし」を選んで実行すると、検証の節も理由の行も付かない
6. 検証役を波の宛先に含めると、束ねに「検証役が束ねに参加したため検証していません」が出る
7. 3 つの設定を既定のままにした村で、`plan` の束ねの本文と計器が変わらない
