## Goal

サーヴァントが処理している間に「新規チャット」を押すと、その処理の答えは**新しい会話**に書き込まれる。
依頼は元の会話に、答えは新しい会話に分かれる。利用者の観察（2026-11-12）—「Fuseforks のセッションは、
一般の AI チャットアプリとは違う概念になっている」。

一般のチャットアプリでは、スレッドが仕事の単位で、依頼と答えは同じスレッドに属する。別のスレッドを開いても、
答えは依頼したスレッドへ書かれる。Fuseforks の会話（セッション）は「いま開いている会話」が村に 1 つあるだけで、
すべての書き込みは**書き込んだ瞬間に開いている会話**へ行く。

本 Spec は、会話を**依頼の根（因果）の属性**にする。根を作った時点の会話を封筒に載せて運び、その因果の
書き込みはその会話へ行く。画面とメモリ上の状態（広場ログ・履歴・要約）は、いま開いている会話の写しのままにする。
結果として次の 3 つが成り立つ:

1. 処理中に新規チャットを押しても、答え・1 往復の記録・ターンの統計は元の会話に残る
2. 新しい会話は、その前から走っていた処理の答えも、それを知る個体も持たずに始まる
3. 処理中でも既存の会話を開ける・分岐できる（拒否する理由が消える）

**変えないもの**: 個体はプロセスのまま（受信箱は 1 本で、ターンは個体ごとに直列）。前の会話の処理で
忙しい個体は、新しい会話での返事が遅れる。これは一般のチャットアプリとの差として残る（範囲の外）。

## 接地（起票前の実測。2026-11-12・コードの読み。rev2 で査読を受けて訂正）

### 書き込み先は書き込んだ瞬間の会話

- `Shared::persist`（`orchestrator/mod.rs:951`）は、保存の瞬間に `current_session()` を読む。
  ターンを始めたときの会話はどこにも持っていない
- `persist` を通る記録は 5 種類 — 発話 `message`（`Shared::record` = `mod.rs:649`）/ 1 往復 `exchange`
  （`push_exchange` = `mod.rs:975`）/ ターン `turn`（`settle_turn` = `turn.rs:350`）/ 要約 `summary`
  （`summarize_agents` = `mod.rs:811`）/ 下書き補助 `assist`（`assist.rs:345`）
- `Shared::record` の呼び出しは **18 か所**（rev1 の「17」は数え間違い。ツール呼び出しの詳細の `record` 2 件は別物）。
  - **因果の中の書き込み**（12）: 利用者の発話 `runtime.rs:471` / 依頼の発話 `delegation.rs:191` / 束ねの配送と、
    配送できなかった束ねの破棄 `delegation.rs:1165, 1188` / 止まったターンの System 行 `turn.rs:477, 618, 742` /
    返信 `turn.rs:3331, 3432` / 予定の配送と検収の再依頼 `schedules.rs:381, 788` / 承認後の続行 `settings.rs:638`
  - **対象を持つ人の操作**（2）: 計画の破棄 `mod.rs:1382`（波に属する）/ 要約の知らせ `mod.rs:878`（人が押した要約と、
    予定の完了後要約 `schedules.rs:629, 817` の両方がここを通る）
  - **村全体の知らせ**（4）: 入退室 `mod.rs:1073` / 役職 `lifecycle.rs:224` / 判断役の無効化 `judging.rs:580`

- 失敗したターンの記録 `record_failed_turn`（`turn.rs:44`）は、`agent_loop`（`mod.rs:1616`）が封筒から
  `incoming` だけを写して呼ぶ

### メモリ上の状態は、いま開いている会話の写し

- 会話を開く `open_session`（`mod.rs:902`）は、広場ログの輪・全員の履歴・要約・ツール呼び出しの詳細・
  **承認待ちの印**（Spec 72）を消し、開いた会話の分を保存先から読み直す
- プロンプトはこの写しから組む — 履歴 `turn.rs:3030` / 要約 `turn.rs:3060` / 広場ログと入退室
  `context.rs:34, 222, 310`。`room_log` の pull（`read_room_log`、ターン中にツールの呼び出しごと）も `Shared.log` を読む
- `Shared` の `world` / `log` / `summaries` は tokio の `RwLock`、開いている会話の ID は `std::sync::RwLock<String>`
  （`mod.rs:416`）。`Shared::record` は `log` の write lock を外してから `persist` する

### 新規チャットは処理中でも通り、他の切り替えは拒む

- 新規チャット（`create_session`、`sessions.rs:71`）は飛行中のターンがあっても通る。Spec 03 の案 A
  （飛行中ターンの完了書き込みは許容）を Spec 12 でも残した。理由は「着地先は新しい空の会話なので、
  既存の記録を汚さない」（`data_contract.yaml` の `session_store` / `reset_rule`）
- 既存の会話を開く・分岐・最新を開く・**開いている**会話を消すは、`ensure_idle_for_switch`（`sessions.rs:302`）が
  `Shared.turns` の件数で拒む（`SESSION_SWITCH_BLOCKED`、文面は「飛行中のターンがあるため会話を切り替えられません」）。
  **開いていない会話の削除は処理中でも通る**
- テスト `resuming_is_refused_mid_turn_but_a_new_chat_is_not`（`tests/session_persistence.rs:510`）が両方を固定している

### その結果、処理中に新規チャットを押すと

1. 依頼は元の会話に、答えは新しい会話に残る。新しい会話の最初に問いの無い答えが並ぶ
2. 新規チャットは全員の履歴を消し、その後で飛行中のターンが「依頼と答え」の 1 往復を積む。
   その個体だけが新しい会話でも前の依頼を覚えていて、他の個体は白紙から始まる
3. 元の会話を開き直しても、その答えと 1 往復は無い（新しい会話へ移っている）
4. 委譲の続き（`ask` の答え・束ね・ツール行）と、ターンの統計も新しい会話に入る
5. 切り替えの後に届いた委譲（依頼元が古い会話の因果）は、新しい会話の空の履歴でプロンプトを組む
6. 承認待ちで止まった個体の印（Spec 72）は切り替えで消え、元の会話へ戻っても「続けさせる」が出ない

**Spec 03 の「既存の記録を汚さない」は古い会話の側から見た理屈で、新しい会話の側から見ると 1・2 が混ざり、
古い会話の側も 3・6 を失っている。**

### 読みで見つけた潜在的な穴（未実測）

- **要約の途中で会話を切り替えると、要約が別の会話へ書かれる。** `summarize_agents` は覆う範囲
  `coversUpToSeq` を始めた会話で取る（`mod.rs:671`）が、保存とメモリ上の要約・履歴の畳み（`mod.rs:811` 以降）は
  書いた時点の会話へ行く。要約は `Shared.turns` に入らないので、LLM を呼んでいる間は既存の会話を開く操作も
  拒まれない。予定の完了後要約（Spec 28）も同じ関数を通り、しかも材料を「いま開いている会話」の履歴から読む
- **予定の `sessionMode: fresh` は村全体の会話を切り替える**（`schedules.rs:433` の `start_fresh_session`）。
  同じ tick に `fresh` と `continue` が混ざると、`continue` のぶんも新しい会話へ積む（`deliver_batch` の doc）
- **予定の後判定と完了後要約は、個体の `AgentTyping { active: false }` で発火する**（`schedules.rs:44`）。
  鍵は `AgentId` だけで、どの会話のターンが終わったかを見ない
- 消した会話への書き込みは `SessionStore::append` が `SessionNotFound` を返し、`persist` が WARN を 1 行出して捨てる

### 根ごとの値を運ぶ形は既にある

封筒（`Envelope`、`mod.rs:200`）は根ごとの値を 4 つ運んでいる — 予算 `budget`（Spec 11）/ 参加者 `participants`
（Spec 28）/ 待ちの連鎖 `waiting`（Spec 44）/ 計画の確認を開かない印 `auto_approve_plans`（Spec 53）。
新しい根で決め、`ask` / `plan` / 転送は受け取った封筒の値を写す。**会話はこの 5 つ目になる。**

## 決定（D）

### D1: 会話は依頼の根の属性。封筒に `SessionRef` を足す

- `Envelope` に `session: SessionRef` を足す。`SessionRef` は**会話 ID と、その会話に結び付いた処理の生存数を
  数える参照**（`Arc` の複製で数える）。誰かがこれを持っている間、その会話には処理が残っている（D11 で使う）
- **新しい根が取る会話の規則は 1 つ: 「操作の対象が会話を持っていれば、その会話。持っていなければ、
  そのとき開いている会話」**

| 新しい根 | 対象 | 取る会話 |
|---|---|---|
| 利用者の発話（`runtime.rs:471`） | なし | 送った時点で開いている会話 |
| 外部依頼（MCP の扉・`fuseforks-cli ask`。`ask_external_outcome`） | なし | 受けた時点で開いている会話 |
| 予定の発火（`deliver_scheduled`） | なし | `fresh` はその予定のために作った新しい会話・`continue` は発火の時点で開いている会話（D14） |
| 検収の再依頼（Spec 46。`redeliver_for_acceptance`） | 発火 | 元の発火の会話 |
| 承認後の続行（Spec 56・72。`settings.rs:638`） | 承認待ちの印 | 印の会話（D5） |
| 計画の確認の承認で配る波（Spec 43。`run_dispatched_wave`） | 計画の波 | 計画を提示した会話（D6） |
| 束ねを進行役へ戻す配送（Spec 43 凍結 5。`delegation.rs:1165`） | 計画の波 | 計画を提示した会話（D6） |

- **写す経路**: `ask` / `plan`（`execute_wave` の配送）/ 転送 / 判断役の配送（`run_judge` → `deliver_and_wait`）は、
  受け取った封筒の `SessionRef` を写す。上書きしない
- `deliver_and_wait` は新しい根（`ask_external_outcome`）と写す経路の両方から呼ばれるので、**会話を引数で受け取る**
  （自分では決めない）
- 封筒に載らない処理（下書き補助・要約）も、始めた時点で `SessionRef` を取り、終わるまで持つ（D2 の表・D7）

### D2: 書き込みは運んできた会話へ。いま開いている会話のときだけメモリと画面にも

- `persist(record)` を `persist(record, &SessionRef)` にする。**呼び出しはすべて会話を明示する**（暗黙の
  `current_session()` を読む `persist` は残さない）

| 記録 | 会話の出どころ |
|---|---|
| `message`（因果の中・対象を持つ操作） | 封筒の `SessionRef`、または対象の `SessionRef`（D1 の表・D6） |
| `message`（村全体の知らせ） | 書いた時点で開いている会話（D9） |
| `exchange` | ターンの封筒。失敗したターン（`record_failed_turn`）にも封筒の `SessionRef` を渡す |
| `turn` | ターンの封筒。`TurnRecorded.sessionId` も同じ |
| `summary` | 要約を始めたときに取った `SessionRef`（D7） |
| `assist` | 下書き補助を始めたときに開いていた会話の `SessionRef` |

- `Shared::record(message, &SessionRef)`
  - その会話がいま開いていれば、今と同じ — 広場ログの輪へ積み、保存し、`MessageSent` を出す
  - 開いていなければ、**保存だけ**する。輪へは積まず `MessageSent` も出さない。代わりに `SessionUpdated { sessionId }` を出す（D10）
- `push_exchange` も同じ規則 — 開いていればメモリ上の履歴へ積んで保存、開いていなければ保存だけ

### D3: 「いま開いているか」の判定と会話の切り替えを、1 本の lock で直列にする

- 開いている会話の ID（今は `std::sync::RwLock<String>`）を **tokio の `RwLock`** にし、これを
  「開いている会話の lock」とする
- **書き手**（`record` / `push_exchange` / `settle_turn` / 要約の保存と畳み）は、この lock の **read** を取ってから
  「開いているか」を判定し、メモリへの積み込みと `persist` を済ませてから外す
- **切り替え**（`open_session`）は、この lock の **write** を取り、保存先の読み直し → メモリ上の状態の差し替え →
  `set_session` を済ませてから外す。**保存先の読み直しの間、`world` の lock は持たない**（差し替えるときだけ短く取る）
- **lock の順序は「開いている会話の lock → `world` → `log` → `summaries`」で固定する。** `world` を握ったまま
  開いている会話の lock を取る経路を作らない。今の `push_exchange` は呼び出し側が `world` の write guard を握って
  呼ぶ形（5 か所）なので、呼び出し側が先に開いている会話の lock を取る形へ並べ替える
- 帰結: 書き込みが切り替えより先なら、保存済みの記録として読み直しに含まれる。後なら、開いた会話のメモリへ積まれる。
  どちらでも 1 回だけ載る。切り替えが書き手を待たせるのは、保存先の読み直しの間（Spec 12 の実測で 20,000 件の
  全走査 11 ms）だけ

### D4: 読み取りも運んできた会話から

開いていない会話に結び付いたターン（切り替えの後に届いた委譲・受信箱で待っていた発話）は、プロンプトを
**その会話の保存先から**組む。開いている会話のターンは今と同じ（メモリ上の写しを読む）。

- 保存先から読むもの: 履歴（`restore_histories` を 1 体ぶん）/ 要約 / 広場ログの抜粋と入退室の節（`tail_messages`）。
  ターンの開始で 2 回の読み
- `room_log` の pull（`read_room_log`）に会話の引数を足す。開いていない会話のターンは、呼び出しのたびに
  その会話の保存先を読む（rev1 の「読み 1 回」は誤り。pull のぶんが呼び出しごとに足される）
- 要約の材料も同じ規則で読む（D7）

### D5: 承認待ちの印は（個体, 会話）で持つ

Spec 72 の印（`Shared.approval_stopped`）は今は個体の集合で、`open_session` が全部消す。切り替えを許すと、
別の会話へ移った後に止まった個体の帯と「続けさせる」が無関係な会話に出て、押すとその会話へ「続けてください」が届く
（Spec 72 が防いだ不具合の再発）。逆に、止まった後に別の会話を見て戻ると印が消えている。

- 印を `HashSet<(AgentId, SessionId)>` にする。**`open_session` は印を消さない**
- 印を立てるのは止まったターンの封筒の会話。外すのは同じ会話の出来事だけ — その個体のその会話での次のターンの入口
  （`turn.rs:1123`。今は会話を問わず外している = 別の会話のターンで A の印が消える）/ その印の「続けさせる」
  （`settings.rs:635`）。**個体の停止と削除は会話を問わず全部外す**（停止 `runtime.rs:228`・削除 `lifecycle.rs:233` の
  今の規則のまま）
- 「続けさせる」の新しい根は印の会話（D1 の表）
- 画面: 入力欄の上の帯（Spec 72 の腕）と承認画面の「続けさせる」は、**開いている会話の印だけ**を出す。
  承認画面は、他の会話の印を「別の会話（タイトル）で止まっています。その会話を開くと続けさせられます」の 1 行で出す。
  **コマンドの判断待ち（`run.json` の `pending`）は個体の単位のままで、会話を問わず承認できる**
- 予定の後判定の見送り（`schedules.rs:58`）は、根の会話の印を見る（D8）
- 印はメモリだけで、再起動で消える（Spec 72 の利用者が負う条件のまま）

### D6: 計画の波は提示した会話を持つ

- 承認待ちの波（`Shared.plan_waves` の提示）に、提示したターンの封筒の `SessionRef` を持たせる
- 承認で配る波・束ねの配送・配送できなかった束ねの破棄の System 行（`delegation.rs:1188`）・計画の破棄の System 行
  （`mod.rs:1382`）は、すべてその会話へ書く（rev1 は計画の破棄を「村全体の知らせ」に分類していた）
- 作業状況タブは今と同じく**すべての波を出す**（村の作業の一覧）。波に会話 ID を持たせ、開いている会話以外の波には
  「別の会話」と出す。確認待ちの件数のバッジも全部を数える（人の手番であることは会話を問わない）。
  承認すると、配る先は計画を提示した会話（開いている会話ではない）
- 承認待ちの波は `SessionRef` を持つので、その会話を消す操作を拒む（D11）

### D7: 要約は始めたときの会話に結び付ける

`summarize_agents(session: SessionRef, only)` にする。

- 会話の出どころ: 人が押した要約は押した時点で開いている会話 / 予定の完了後要約（Spec 28・46）は**根の会話**
  （`pending_summaries` / `pending_acceptances` に根の `SessionRef` を持たせる。D8）
- 材料（履歴・前の要約）はその会話から読む（D4 の規則 — 開いていればメモリ、開いていなければ保存先）。
  覆う範囲 `coversUpToSeq` もその会話で取る
- 保存とその System 行（「N 体の記憶を要約しました」、`mod.rs:878`）はその会話へ。メモリ上の要約の差し替えと
  履歴の畳みは、**その会話がいま開いているときだけ**（D2・D3 の規則）
- 要約を走らせている間は `SessionRef` を持つので、その会話は消せない（D11）

### D8: 予定の後判定と完了後要約は、根の会話のターンの終わりで発火する

- `ScheduleRuntime` の `pending_acceptances` / `pending_summaries` に根の `SessionRef` を持たせる
- `AgentTyping` に `sessionId` を足し、**個体と会話の両方が一致した `active: false`** でだけ取り出す。
  同じ個体の別の会話のターンが終わっても発火しない
- 承認待ちの見送り（`schedules.rs:58`）は（個体, 根の会話）の印を見る（D5）
- `in_flight`（同じ予定の重なりを止める集合）は個体の単位のまま — 個体が忙しいことは会話を問わない
- 残る近似: 同じ個体・同じ会話で、利用者の発話のターンが予定のターンより先に終わると、今と同じく早く発火しうる
  （本 Spec では変えない。会話を足したことで、別の会話のターンによる誤発火だけが消える）

### D9: 村全体の知らせは、書いた時点で開いている会話にだけ残す

- 対象: 入退室 / 役職の変更 / 判断役の無効化 / 停止中で飛ばした予定
- これらは村の状態の**変化の記録**で、どの依頼の因果にも属さない。書いた時点で開いている会話に記録し、
  **その会話のプロンプトにだけ入る**（入退室の節は広場ログから組むため）
- 開いていない会話のターンは、その間に起きた村の変化を節としては見ない。**それで困らない理由**: 顔ぶれの節は
  会話の記録からではなく毎ターン `World` から組み、入退室の節の末尾に「現在の状態は「今の顔ぶれ」が正です」と書いてある
  （Spec 06・`context.rs:72`）。誰が稼働しているかは、どの会話のターンも今の状態で持つ
- 開いている会話のプロンプトに、いま起きた村の変化が入るのは今と同じで、汚染ではない

### D10: 画面

- 会話ペインは開いている会話の発話だけを出す（D2 で `MessageSent` が出ないので、コアの側で決まる）
- `ToolInvoked` と `AgentTyping` に `sessionId` を足す
  - **`state.typing` は個体の単位のまま**（会話を問わず「その個体が忙しい」）。黒板の持ち主の状態と `interruptAll()`
    はこれを読むので、会話で絞ると壊れる
  - 入力中のバブルと周回数（`toolRound`）は、`typing` の会話が開いている会話のときだけ出す
    （個体ごとに `typingSession` を持つ）
  - ツール行（`toolRuns`）は開いている会話の `ToolInvoked` だけ積む。カードの `lastTool` は個体の単位のまま
- **一覧のカードに「処理中」の表示は今も無い**（rev1 の「カードは会話に関係なく処理中を出す」は前提の誤り）。
  足さない
- 会話を開き直しても、処理中だったターンのツール行と周回数は戻らない。ツール行はメモリだけの投影で、開き直しで
  消えるのは今と同じ（Spec 57 の利用者が負う条件）。入力中のバブルは `typingSession` から戻る
- `SessionUpdated { sessionId, from }`（`from` は P0 で足した。トーストに送り手の名前を出すため）の受け手は 2 つ — 会話一覧（`state.sessions` を引き直して並びと更新時刻を変える）と、
  開いていない会話に答えが書かれたことの知らせ。System 行にはしない（今の会話のログとプロンプトへ
  入る = `failures.md` #89 の経路）
- **知らせはトーストと「開く」ボタン**（2026-11-12 裁定）。文言は「別の会話（{タイトル}）に {名前} の答えが届きました」。
  「開く」はその会話を開く（D11 で処理中でも開ける）。出すのは**開いていない会話にサーヴァントの発話が書かれたとき**
  だけで、利用者の発話・System 行・1 往復やターンの記録では出さない。同じ会話への知らせが続くときは 1 枚にまとめ、
  最後の送り手の名前と件数を出す（予定の波で 5 体が答えるとトーストが 5 枚並ぶため）

### D11: 切り替えは拒まない。消すのは処理の残っていない会話だけ

- **既存の会話を開く・分岐・最新を開くは、処理中でも通す。** 拒否の理由（前に保存された会話へ無関係な答えが混ざる）は
  D2 で消える。`ensure_idle_for_switch` を撤去する
- **会話を消す操作は、その会話の `SessionRef` を誰かが持っている間は拒む。開いているかどうかを問わない**
  （rev1 の「開いている会話だけ」は、新規チャットで移ってから処理中の会話を消せる非対称を残していた）
- `SessionRef` を持つもの: 封筒（受信箱で待っているものも、飛行中のものも）/ 承認待ちの波（D6）/ 予定の
  後判定と完了後要約の登録（D8）/ 走っている要約（D7）/ 走っている下書き補助
- エラーは新しい `SESSION_BUSY`（「この会話にはまだ処理が残っています。終わってから消してください」）。
  `SESSION_SWITCH_BLOCKED` は作る経路が無くなるので撤去する（文面が実態と逆になるため流用しない）
- 判定と `SessionRef` の発行は同じ lock の下で行う（消した直後にその会話の参照が新しく作られない）。
  `SessionNotFound` の WARN は網として残す

### D12: 計器

- `turn:` 行の末尾に `session=<会話 ID>` を足す
- 開いていない会話へ書いた発話は `session write: kind=message session=… open=…` を 1 行出す。
  開いている会話への書き込みでは出さない
- 消す操作を拒んだときは `session busy: session=… refs=N` を 1 行

### D13: 保存先の無い村

会話の単位が無いので今と同じ。`SessionRef` は持たず（`None`）、**「開いているか」の分岐をしない**（常に開いている扱いで、
書き込みはメモリだけ、新規チャットはメモリを白紙にする）。空の会話 ID を「全会話に共通」と読む経路を作らない。

### D14: 予定の `fresh` は画面を切り替えず、新しい会話へ書く（2026-11-12 裁定）

- `start_fresh_session`（`schedules.rs:433`）は `open_session` を呼ばない。`SessionStore::create_session` で会話を作り、
  その会話の `SessionRef` を発火の根にする。**開いている会話も画面も動かない**
- `fresh` の予定は**1 件ごとに新しい会話を 1 つ作る**。同じ tick の `continue` の予定は、発火の時点で開いている会話を
  根にする（`deliver_batch` の「`fresh` が 1 件でもあれば全部を新しい会話へ積む」をやめる。あれは会話が村に 1 つ
  だった頃の、画面を 2 回切り替えないための規則）
- 新しい会話のターンは、開いていない会話のターンとして D4 で読む（空の履歴・要約なし・空の広場ログ）。答え・
  1 往復・ターン・検収の再依頼・完了後要約はすべてその会話へ（D1・D2・D7・D8）
- 作った会話は作った時点から会話一覧に並ぶふつうの会話。答えが書かれると D10 の知らせが出る
- 保存先の無い村では会話を作れないので、今と同じく開いている会話（メモリ）へ配送する（D13）
- 代償（利用者が負う条件）: 予定の結果を見るには、知らせの「開く」か会話一覧から開く必要がある
