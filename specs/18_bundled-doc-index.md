## Goal

`D:\Github\Manuale`（MCP サーバー）の核を Concordia の**同梱ツール 1 本**として取り込み、
**Markdown の見出し階層を索引として引ける**ようにする。

**同時に、使われていない同梱 RAG（`rag.rs`）を置き換える。** 現状の `rag.rs` は
`HashEmbedder`（doc が自ら「意味を捉えないので検索品質は出ない」と書いている）+
in-memory の索引 + **取り込み導線ゼロ**で、**索引は常に空**。設定画面の
「参照 RAG」は永久に「索引済みの RAG ソースがありません。」を表示する。
村は既に MCP（`agent_3` の `mcp.json` に `manuale`）で RAG を実現しており、
**同梱 RAG は 1 度も経由されていない**（2026-08-05 実測）。

### なぜ同梱するか（MCP があるのに）

**ナレッジベースは work_dir と直交する軸だから**（利用者判断 2026-08-05）。

- **work_dir** = 「**どのプロジェクトを触っているか**」。個体ごとに違い、
  作業の寿命で入れ替わる
- **ナレッジベース** = 「**何を知っているか**」。規格書・論文・資料は
  **どの work_dir にも属さない**（`D:\ManualeRAG` がどの村の作業フォルダでも
  ないのは、そういう性質のものだから）

**オーケストレーターは「誰に何を頼めるか」を扱う道具なので、
「誰が何を知っているか」を一級の概念として持つ。** 配送の軸（線）と
作業の軸（work_dir）に続く 3 本目。

#### 採らなかった理由付け（**書いておく**）

rev1 は「**MCP を設定できない人でも動くこと**」を理由に置いていた
（`grep` / `fd` を同梱した理由の機械的な適用）。**これは持たない** —
個人の知識ベースを真面目に運用している人は Notion か Obsidian に置いていて、
**MCP でつなぐのが自然**（利用者の指摘 2026-08-05）。同梱の見出し索引は
その人たちの役に立たない。

**MCP は引き続き第一の道。** 同梱するのは「MCP の代わり」ではなく、
**この製品が知識の軸を持つと決めたから**。

### なぜベクトルではないか

起点は利用者が読んだ記事（金融系 RAG で PageIndex がベクトル DB の RAG より
精度が上がった）。**効いている変数は「引き方」ではなく「切り方」だ**と読んでいる:

| | ベクトル DB の典型 | 見出し索引 |
|---|---|---|
| **切り方** | 分割器が推測した境界（再帰的分割・固定長） | **人が置いた見出し** |
| **引き方** | 埋め込みの類似度 | 構造をたどる + キーワード |

**この読みが正しければ、見出しで切ったチャンクをベクトル DB に入れても
同じくらい上がる。** 両者は対立していない。負けているのは「ベクトルであること」
ではなく「**分割器が意味の切れ目を知らないこと**」。

**この村にとっての含意**: 梃子が切り方なら、**埋め込みは要らない**。
見出しの木を作るだけで取り分の大半が入り、**新規依存は 1 本**で済む（D5）。

### 効く条件（**先に制約として書く**）

**見出しが構造として機能している文書に限る。** 走り書き・HTML からの変換物・
自動生成（1 節 3 行）では `grep` と大差ない。

対象は `specs/NN_*.md` / `data_contract.yaml` / 仕様書のような、
**人が構造を作り込んだ資料**。**`blackboard/` の付箋は対象外**
（サーヴァントがその場で書くので見出しの規律が無い）。

**先に書くのは、実装後に「効かない」と言われたとき、機構の欠陥か対象の性質かを
切り分けられるようにするため。** 書いていないと、次に触る人は機構を疑って
作り直しにかかる。**確かめ方も手元にある** — 同じ問いを `specs/` と
`blackboard/` へ投げて差を見る（Acceptance 参照）。

## Stories

### S1: 見出しの木を見る / 引く / 節を読む

> エージェントとして、仕様書の山から「どこに書いてあるか」を先に知りたい。
> 全文を読む前に目次を見て、当たりを付けてから節だけを読みたい。

**ツールは 1 本、`op` は閉じた列挙 3 つ。**

| `op` | 返すもの | Manuale の対応 |
|---|---|---|
| `outline` | フォルダの一覧 + 各 Markdown の見出し木 | `navigate` |
| `search` | 一致行 + **その行が属する見出しの経路** | `search` |
| `read` | **見出し名で指定した節の本文**（+ breadcrumb） | `read` |

#### D1: ツールは 1 本（`op` 列挙）。3 本に分けない

**ツールを 1 本足すとスキーマ分のトークンが全サーヴァントの毎ターンに乗る。**
`file` が read / write / mkdir / move / copy / remove を 1 本に畳んだのと同じ判断
（`file_tool_contract`）。`yq` に `op: "check"` を足す案が新ツールにならなかったのも同じ。

#### D2: ツール名は `rag`。**実装ファイルと契約名も `rag` へ揃える**（**rev3 で拡張**）

候補は `rag` / `docs` / `manual` / `toc`。**`rag` を採る**:

- **既存の `AgentSpec.rag_sources` というフィールド名と永続化がそのまま生きる**
  （**rev3 で縮めた** — rev2 は「設定画面の『参照 RAG』がそのまま生きる」と書いたが
  **過大**。画面はチェックボックスからフォルダ一覧へ**作り替える**（Phase 3）。
  生き残るのは名前と `world.json` の形だけ）
- **弁解の doc コメントを必要としない** — RAG は Retrieval-Augmented Generation で、
  **取得の方法は語に含まれていない**。「vectorless RAG」は Manuale 自身が
  名乗っている通り成立する呼び方（`run.json` の改名で降ろした `shell` は、
  「実行はシェルを介さない」という弁解が型の直上に要る名前だった。ここは違う）

`manual` は英語で「手動」と衝突し、`toc` は `search` / `read` を覆えない。

##### 3 つの名前を揃える（**rev3 で修正**）

rev2 はツール名だけ `rag` に決め、**実装を `tools/doc.rs`、契約を `doc_index_contract`
のまま残していた**（rev1 の名残）。同じものに 3 つの名前が付いている状態で、
`shell.json` → `run.json` の改名で採った規則（**設定する対象の名前をそのまま採る**）に反する。

| 層 | 名前 | 既存の前例 |
|---|---|---|
| ツール | `rag` | — |
| 実装 | **`crates/agent-core/src/tools/rag.rs`** | `tools/run.rs` = `run` / `tools/file.rs` = `file` |
| 契約 | **`rag_tool_contract`** | `file_tool_contract` / `command_tool_contract` |
| **純機構** | **`crates/agent-core/src/doc_index.rs`（このまま）** | `command.rs`（型 + 純機構）と `tools/run.rs`（ツール）の分業 |

**純機構だけ `doc_index` の名前を残すのは、層が違うから。** あそこに入るのは
「Markdown の見出しを木にする」純関数で、**`rag` という取得の概念とは独立**
（見出しの木は RAG でなくても使える）。`schedule.rs` / `command.rs` / `budget.rs` が
ツール名ではなく**扱う対象の名前**を持っているのと同じ。

**`tools/fs.rs` が `grep` / `fd` / `diff` の 3 本を抱えているのは反例に見えるが違う** —
あれは**ファイル 1 つにツールの族**を置いた形で、`rag` は族ではなく 1 本。

### S2: 索引の範囲（**本 Spec で最も重い決定**）

#### D3: `rag_sources` を「**見出し索引を張るフォルダ**」へ再定義し、**work_dir の外を許す（読み取り専用）**

現在の `rag_sources: Vec<String>` は「索引済みソース名」（実体は空）。
これを**フォルダの絶対パスの列**へ変える。**生き残るのはフィールド名と永続化
（`world.json`）の形だけで、設定画面は作り替える**（**rev3 で訂正** — rev2 は
ここでも「設定画面の複数選択がそのまま生きる」と書いていた。**査読は D2 の
同じ表現だけを指していたが、同じ文が D3 にも残っていた** = Notes 4 の実例）。

**これはアンケートで唯一裁定が落ちていた要望への回答でもある** —
ジェミーの「`D:\ManualeRAG` 外の**読み取り専用**マウント」（`grep 'マウント' CLAUDE.md`
が 0 件）。**資料は work_dir の外にあるのが普通**（`D:\ManualeRAG` は
どの村の work_dir でもない）ので、外を許さないと機能そのものが成立しない。

**囲いは `run.json` と同じ形にする**:

| | 誰が決めるか |
|---|---|
| **どのフォルダを見てよいか** | **人**（`rag_sources` に書く） |
| **今この問いに何を引くか** | **モデル**（`op` と引数） |

- **読み取り専用。** 書き込みの経路を作らない（`file` / `sd` / `yq` は
  引き続き work_dir の中だけ）
- **work_dir の内側でも宣言してよい**（**rev3 で明記**）。「外を許す」であって
  「外に限る」ではない。**禁じると本 Spec 自身の検収が通らない** — Acceptance の
  実機 1 は `specs/` を、実機 2 は `specs/` と `blackboard/` の比較を要求しており、
  **どちらも work_dir の内側**。詳細は下記「境界は領域ではなく宣言」
- **`resolve_in_work_dir` は使わない。** あれは work_dir 起点の関数。
  **宣言された各ルートを起点に、同じ規律（canonicalize + 前方一致・symlink 不追従）**
  で新しい解決関数を書く
- **`rag_sources` が空なら提示しない**（`run` と同じ 2 段ゲート。
  `enabledTools` に入っていても、宣言が無ければツールは出ない = **既定で無効**）
- **`WORK_DIR_TOOL_NAMES` には入れない。** あの集合は「work_dir の中しか触らない」
  ツールの集合で、**別の境界を持つものを入れると不変条件が壊れる**
  （`run` を入れなかったのと同じ理由）

**S4 の境界の明示（下記）を契約と UI の両方に書く。**

##### 囲いを 2 つ持つことの是非（**査読の裁定: 持ってよい**）

`run` が既に前例を作っている。`run.json` の `allow` は work_dir と無関係な境界で、
しかも `run` は work_dir の外を読むどころか**任意のプロセスを起動できる**。
**囲いは既に 2 つあり、D3 は 3 つ目ではなく `run` と同じ棚の 2 つ目。**

**非対称が効いている** — `run` は**書ける**、`rag` は**読むだけ**。
`run` を通した村で `rag` を止める根拠が無い。

##### 境界は領域ではなく**宣言**（**rev3 で新設。Notes 3 の書き直し**）

rev2 の Notes 3 は `grep` と `rag` の差を「**work_dir の中か、資料フォルダか**」＝
**領域の違い**として書いていた。**これは誤り** — `rag_sources` に work_dir 内の
フォルダを入れた瞬間に領域が重なり、その記述は嘘になる。

**正しい差は、誰がその範囲を決めたか**:

| | 範囲の決まり方 | 対象 |
|---|---|---|
| `grep` | **work_dir に自動で従う。** 宣言は要らない | 任意のテキスト |
| `rag` | **人が `rag_sources` に書いた分だけ。** 自動では 1 つも増えない | Markdown の見出し |

**重なりは想定内で、害も無い。** どちらも読み取り専用で、`grep` が既に読める場所を
`rag` が見出し付きで読むだけ。**重なりを消すために work_dir 内を禁じると、
「この村の `specs/` に索引を張る」という最も素直な使い方ができなくなる。**

`run.json` の `allow` と同じ形 — あれも「work_dir の外だけ許す」ではなく、
**人が書いた分だけ許す**。囲いの単位は領域ではなく宣言。

#### D10: `rag_sources` を `AgentRoleDefaults` から外す（**rev2 で新設**）

`AgentRoleDefaults` には `rag_sources` が入っている
（`crates/agent-core/src/model.rs:286`。`role_contract` 凍結 2 の「入れる 4 欄」の 1 つ）。
その 20 行上、`model.rs:261` に**入れなかった欄の理由**がこう書いてある:

> `work_dir` — 絶対パスで端末ごとに違う。村を配ると存在しないパスを指す

**D3 で `rag_sources` を絶対パスの列にした瞬間、この欄は「入れない」側の性質になる。**
役職の雛形が端末依存の絶対パスを運び、村を配ると壊れた参照を配ることになる —
**Spec 14 が名指しで退けた形が、別の欄から入ってくる。**

処方は**役職の雛形から外す**こと。分類の根拠が「端末依存の絶対パスは雛形に入れない」
である以上、意味を変えた `rag_sources` はその側へ移るだけで、**機構は 1 つも増えない**。

- `role_contract` 凍結 2 の内訳を **`11 = 対象外 2 + 入れる 3 + 入れない 6`** へ改訂
- `AgentRoleDefaults` から `rag_sources` を削除し、`apply_to` の代入も落とす
  （**触るのは 3 欄**へ。doc コメントの「4 欄」も同時に直す）
- `ipc_contract.rs` の `RoleDefaults` フィールド集合（`tests/ipc_contract.rs:119`）から
  `ragSources` を外す。**凍結されたワイヤ形なので契約改訂として書く**
- **移行は不要。** 既存の役職の `defaults.ragSources` は空配列しか入っていない
  （索引に入れる経路が存在しなかったので、選べるソースが 1 つも無かった）。
  `#[serde(default)]` が付いているので、欄を消しても旧い `world.json` は読める

**この指摘の一般化**: **欄の意味を変えるときは、その欄が他のどの型に写っているかを
先に数える。** `AgentSpec` だけを見て意味を決めると、同じ名前で写っている
`AgentRoleDefaults` / `AgentSnapshot` の分類根拠が黙って壊れる。
Spec 14 P1 の「`AgentSpec` に欄を足したら『投影にも要るか』を必ず問う」の**逆向き**で、
足すときだけでなく**意味を変えるときも同じ問いが要る**。

#### D11: 宣言されたルートは実在検査を掛ける。**無効化であって削除ではない**（**rev2 で新設**）

`model.rs:281` は「**存在検査は掛けない。そのまま写す**」を凍結しており、理由は
「`RagIndex` は断片を索引した瞬間にキーが生える実行時の器で、宣言された登録簿が無い。
作成時点では索引がほぼ必ず空」だった。

**D3 で意味を変えるとこの理由は消える。** フォルダは宣言する時点で既に存在しており、
「あとで資料を食わせる」という順序が無い。ゆえに `run.json` の `program` と同じく
検査を掛ける（Spec 15 rev3 の (5)(6) と同じ規律）:

- **起動時と呼び出し時の両方で見る。** 起動時だけだと、開いたまま外付けドライブを
  外した村が素通りする
- **検査に落ちたルートは無効印を付けるだけで、ファイルからは消さない。**
  消すと**配布した村を別の端末で一度開いて閉じただけで宣言が消える**
- **無効印は毎回付け直す**ので、パスを直せばその場で復活する
  （`mark_availability` と同じ形）
- **1 本でも生きていれば提示する。** 全滅したときだけ提示しない（2 段ゲート）
- **実在まで見る。読めるかどうかは見ない** — 権限の意味は OS で違い、確実に知る
  方法は読んでみるしかない。**確かめられないことを確かめたふりの検査で覆わない**

`model.rs:281` の doc コメントは Phase 3 の追従対象。

### S3: 出力の有界化

読み取り系の作法をそのまま適用する（`bundled_tools_contract`）:

- 走査は `MAX_FILES` = 20,000

#### D4: 切るのは**一覧**であって節の本文ではない

- `outline` / `search` は**打ち切ってよい**（一覧なので途中で止められる）
- **`read` は節を途中で切らない。** 1 節が上限を超えたら**その節は返さず**、
  行数・文字数と「`search` で位置を絞るか、節を分けてください」を返す

##### 打ち切りの単位（**rev3 で追加。新しい定数は作らない**）

rev2 は「件数で打ち切る」と書いて**数を書いていなかった**。ただし**固定の件数は
決めない** — `grep` が既に**文字数**で打ち切っており（`tools/fs.rs:607` / `:644` が
`MAX_OUTPUT_CHARS` を見る）、そこに件数の上限を別に足すと**上限が 2 つになって
どちらで止まったかが読めなくなる**。

**`MAX_OUTPUT_CHARS`（12,000）だけで打ち切り、決めるのは「どこで止めるか」**:

| `op` | 止める位置 | 理由 |
|---|---|---|
| `outline` | **ファイルの境界** | 見出し木が途中で終わると、無い節を「無い」と読まれる |
| `search` | **一致行の境界** | `grep` と同じ（1 行を半分だけ返さない） |
| `read` | **止めない**（超過は拒否） | 節は構造の単位（上記） |

**Spec 17 D3（切るのはファイル境界でだけ止める）をそのまま適用する。**
打ち切ったら残り件数と「範囲を絞ってください」を必ず書く（`failures.md` #44）。

**Spec 17 D3（切るのは一覧であって diff ではない）と Spec 16 D4（窓の境界で止める）と
同じ判断。** 途中で切れた本文は「ここまでが節の内容」と読まれる。

##### `file read` とは逆の作法になる（**rev2 で追記**）

**隣接するのは Spec 17 / 16 ではなく `file read` で、そちらは切り詰める** —
`crates/agent-core/src/tools/file.rs:183` が先頭 `MAX_OUTPUT_CHARS` 字 +
「残り N 字は省略しました」を返す。**同じ `read` という語で作法が 2 つ並ぶ**ので、
差の理由を書いておかないと次に触る人が `file read` に合わせて切り詰めへ倒す。

**理由: 節は構造の単位で、途中で切れると「ここまでが節の内容」と読まれる。
ファイルは構造の単位ではないので、先頭 N 字は「先頭 N 字」としてしか読まれない。**

### S4: 境界の明示（`rag` は安全機構ではない）

契約と UI の両方に書く 4 点:

1. **`rag_sources` に書いたフォルダは、そのエージェントから丸ごと読める。**
   プロンプトインジェクションを受けたとき、**そこが漏洩しうる範囲になる**
2. **漏洩先は「そのエージェント」ではない**（**rev2 で追記**）。読んだ本文は
   `ask` / `plan` でそのまま他のエージェントへ渡せるので、**実際の範囲は
   そのエージェントから到達可能な全員 + 各自のモデル提供元**になる。
   work_dir にも同じ性質はあるが、**work_dir は作業対象なので共有が前提**。
   資料フォルダは違う — 「読ませるつもりで宣言したフォルダ」が
   「村の全員とその提供元へ出うるフォルダ」になる
3. **work_dir の囲いはここには効かない。** 別の境界であり、宣言した人が範囲を決める
4. **機密を含むフォルダを指定しない。** work_dir 欄と同じ注意書きを添える

## Notes

1. **`rag_sources` の意味を変えるが、フィールド名と型は変えない。**
   `Vec<String>` のまま「ソース名」→「フォルダの絶対パス」。**既存の村の
   `world.json` には空配列しか入っていない**（索引が常に空だったので、
   選べるソースが 1 つも無かった）ため、**移行は不要**。
   これは実測に基づく — 索引に入れる経路が存在しなかった。
   **`AgentRoleDefaults` 側も同じ理由で移行不要**（D10）。

2. **`search` は `grep` と役割が重なる。重なりは想定内。**（**rev3 で書き直し**）
   rev2 はここで「`grep` は work_dir の中、`rag` は資料フォルダ。**境界も対象も違う**」と
   書いていたが、**領域で分けたのが誤り** — `rag_sources` に work_dir 内のフォルダを
   入れれば領域は重なる。**差は「誰が範囲を決めたか」**（D3 の「境界は領域ではなく宣言」）。
   `grep` は work_dir に自動で従い、`rag` は人が書いた分だけ。
   **どちらも読み取り専用なので、重なっても失うものが無い。**

3. **査読は 2 巡・1 方法。**（**rev3 で更新**）2 巡とも「実装を一次資料にして仕様を
   突き合わせる」方法で、**走らせた検証はゼロ**（ビルドもテストも回していない）。
   `failures.md` #57 のとおり独立性は人ではなく方法で数えるので、**巡を重ねても
   1 票のまま**。2 巡目で反証が 2 件出た（`P4` は実在する略記 / 8→9 は矛盾ではない）
   ことがその証拠で、**同じ方法を繰り返すと誤りも一緒に持ち越される**。
   **別の方法（実際にビルドする / 別の読み手）で 1 度当てる価値が残っている** —
   特に D3 の是非は設計判断で、コードを読んでも決まらない。

4. **2 巡の査読で、最も重い指摘はどちらも「指名していなかった箇所」から出た。**
   rev1 が「見てほしい」と挙げたのは D3 と D2 で、どちらも**そのまま承認**された。

   写っていた）、2 巡目が Notes 3 と D2 の名前の不一致 — **いずれも「既に書いた文の
   隣」で、書いた本人には見えていない場所。**
   **Spec 14 P5 の「機能を足したときに腐るのは、その機能の節ではなく隣の節」の
   2 例目と 3 例目。** 査読の指名は「自分が不安な箇所」を指すが、
   **事故は自分が安心している箇所で起きる。**
