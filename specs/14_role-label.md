### D1 は実機で差し戻した — 入口はタイトルバーの「条例」の右

初版はシステム設定の左メニューへ「サーヴァント > 役職」として入れた。
**実機で見た利用者が差し戻した**（2026-08-04）: 役職はシステム設定の

**私の理由付けが誤っていた。** 起票時は「`world.json` に住む＝村の共有設定の
棚だからトークン制限・言語と同じ」と書いたが、それは**保存先で分類した**

**正しい境界は「村の内容物か、アプリの設定か」。** 条例と役職は「この村が
どういう村か」を決めるもので、言語やトークン制限のような「アプリがどう振る舞うか」
ではない。`world.json` に住むのは条例も言語も同じで、**保存先は分類の根拠に
ならない**。

**一般化**: **保存先で分類したくなったら、それは分類ではなく実装の都合。**
同じ器に入っているものが同じ種類とは限らない。分類は「利用者にとって何の話か」で
切る（`failures.md` #52）。

`RoleDialog.vue` はタイトルバーから開くモーダル（条例・MCP・予定と同じ形）。
**CRUD を独立したファイルに置く判断は変えていない** — 置き場が変わっただけ。

作成経路の配線。`Orchestrator::create_agent` の拡張 + `list_roles` /
`upsert_role` / `remove_role`、IPC 3 本（`list_roles` / `upsert_role` /
`delete_role`）、`ipc.ts` の 3 本、`useOrchestrator` の投影 `state.roles`。
**結合 7 本**。

**実装で決めた 3 点。**

- **役職が引けなくても作成は通す。** `role_id` は残したまま流し込みを飛ばす。

- **`Construct.md` の書き込み失敗で登録を巻き戻さない。** 個体は既に村に居り、
  本文は設定ダイアログから書き直せる。巻き戻すほうが状態が読みにくい

**CoreEvent は増やさなかった。** モデルテンプレートも同じで、変更後は UI が

### P3 へ送る判断（D5・新規）

**`create_agent` は役職の意見で spec を上書きする。** これは
「役職を選ぶと設定が入る」の実装として正しいが、**P3 の作成フォームが
役職を選ばせたうえで各欄も編集させる形にすると、編集した値がコアで
黙って上書きされる**。

処方は 2 つ。**P3 で決める。**

1. **フォームを役職の値で前埋めする**（見えているものがそのまま入る）。
   前埋めした値と役職の値が一致するので、コア側の上書きは実質何もしない
2. **役職を選んだら関係する欄を伏せる**（編集させない）

**1 を推す** — 2 は「役職を選ぶと編集できなくなる」という新しい驚きを作る。
ただし 1 は前埋めの実装がフロントに要り、そこで**入れない 5 欄を触らない**規律を
もう一度書くことになる。**前埋めもコアの `apply_to` を通す**（IPC を 1 本足すか、
`create_agent` の結果を見せる）のが安全で、規律を 2 箇所に書かずに済む。

### 実装で見つけた副作用

`fetchAndAssign` の `Promise.all` へ 1 本足すと、**`ipc` をモックしている
フロントのテスト 6 本が全部落ちる**（`listRoles` が未定義で `Promise.all` ごと
reject する）。落ちたのは 4 本で、残り 2 本はその経路を通っていなかった。
モックを揃えて解消。**この形は「起動時に引くものを増やすと、モックの数だけ
追従が要る」というコスト**で、増やすときは毎回付いて回る。

## P1 の実装記録（2026-08-04）

`AgentRole` / `AgentRoleId` / `AgentRoleDefaults`、`World` の 6 つ目、
`AgentSpec.role_id`、CRUD と流し込みの純関数。**単体 14 本**（`model::` 7 +
`world::` 7）、workspace 全緑（298 + 92 + 12 …）、clippy 新規警告ゼロ、
vue-tsc / vitest 77 本も緑。

**実装で決めた 4 点。**

- **型名は `Role` ではなく `AgentRole`。** `llm::Role`（メッセージの
  System / User / Assistant）が既にあり、同一クレートに 2 つの `Role` が並ぶと
  rustc の補完候補が**両方**出る（実際に「`use crate::llm::Role` を試せ」と

  10 ファイル**でワイヤ層（anthropic / gemini / openai_compat）に届き、
  新しい側の改名は 0 箇所。**ドメインの語は「役職 / Role」のまま**で、
  Rust の型名だけ接頭辞で分ける（`AgentId` と表示名の分離と同じ形）
- **`RoleApplication` は作らなかった。** 当初は `{ construct, dropped }` を
  返す型を置いたが、`construct` は `defaults.construct` を読めば済むので
  **真実が 2 つになる**。戻りは落とした欄の `Vec<String>` だけにして
  `#[must_use]` を付けた（捨てると「入れたはずの設定が入っていない」が消える）
- **`rag_sources` には存在検査を掛けない**（P0 の契約を訂正。下記）
- **`AgentSnapshot` にも `role_id` を載せた**（下記）

### 契約の訂正 1: 参照の存在検査は `model_template_id` だけ

P0 は「参照の欠落は種類で分けず 1 規則」と凍結したが、**`rag_sources` には
検査する相手が居なかった**。`RagIndex.by_source` は**断片を索引した瞬間に
キーが生える実行時の器**（`rag.rs:80-89`）で、宣言された登録簿が存在しない。
しかも GUI からの投入口は未実装なので、**作成時点の索引はほぼ必ず空**。
契約どおり検査すると、あらゆる `rag_sources` が落ち、
「調査役を作る → あとで資料を食わせる」という正しい順序を壊す。

対して `model_template_id` は `world.json` に**宣言された**登録簿で、
`remove_template` が参照中の削除を拒む＝安定した集合として扱う設計。
検査が成立するのはこちらだけ。

**境界は「宣言された登録簿か、実行時に育つ器か」。** 同じ「id で外部を指す欄」
でも、**参照先の寿命が違えば検査の可否が変わる**。`data_contract.yaml` の
凍結 2 を訂正済み。

### 契約の訂正 2: `AgentSnapshot` にも `role_id` が要る

**型検査が 3 箇所で捕まえた。** `AgentSettingsDialog.seed()` と
`useOrchestrator.setBatchStart()` は、**投影（`AgentSnapshot`）から
`AgentSpec` を組み直して保存する**作りになっている。`AgentSpec` にだけ
`role_id` を足すと、**設定を保存するかスタンバイを切り替えるたびに役職が外れる**。

さらに **S2（バッジはカードに出る）が原理的に成立しない** — カードが描くのは
投影なので、そこに無い欄は画面に出しようがない。

`AgentSettingsDialog` には**まったく同じ罠の注記が既にあった**
（`batchStart` に「写さないと保存で既定へ戻る」）。**同型の三例目**で、
これは `AgentSpec` に欄を足すときの定型として扱うべき —
**欄を足したら「投影にも要るか」を必ず問う**。

### ワイヤ形の凍結を 2 つ追加

`ipc_contract.rs` の `wire_field_sets_are_frozen` へ `Role` と `RoleDefaults`
を追加した。**`RoleDefaults` を凍結する理由が本体** — ここに欄が増えると
「役職を選んだら何が入るか」が変わり、**入れてはいけない 5 欄が紛れ込む経路**に
なる。assert のメッセージにその 5 欄を名指しで書いてある。

- **数が合わない**（指摘 4）。箇条書き 4 本を「4 欄」と数えたが実体は 6 フィールド。

- **コピーの発火点が未列挙**（指摘 5）。厳密には機構 3 と衝突していない

- **除外理由の誤り**（指摘 6）。査読は「片方だけ入れるな」と言ったが、**実際は
  除外理由そのものが不成立**だった。Role は `world.json` に住むので `rag_sources` も
  `model_template_id` も**同一村内の参照**で、村を配れば一緒に付いて回る。

## Goal

**役職を選ぶだけでサーヴァントが作れて、誰がどの役かが場に見えるようにする。**

役職は 2 つのものを兼ねる。**兼ねさせるが、混ぜない** — 片方は作るときだけ効き、
もう片方は動いている間ずっと効く。この 2 つを同じ機構で扱おうとすると、
「役職を直したら既存の個体はどうなるか」に答えが 1 つしか作れなくなる。

1. **雛形**（作るとき）— 役職を選ぶと設定が入る
2. **ラベル**（動いている間）— バッジで、人にもサーヴァント同士にも役が見える

**Goal に含まないこと**: 役職で**振る舞いを変える**こと。役職は人格・語彙の設計で
あって、配送・権限・ツール提示の機構ではない（**機構 6「配送に入らない」**で凍結）。

## Stories

- **S1**: サーヴァントを作るとき、役職を選ぶと**設定が入った状態**で始まる。
  毎回 Construct を書き起こさなくてよい
- **S2**: カードと地図に**役職バッジ**が出る。**どの雛形から作られたか**が一目で分かる
- **S3**: サーヴァント同士も、相手の役職名を見て**誰に何を頼めるか**の当たりを付けられる
- **S4**: 役職に**説明**を書ける。次にサーヴァントを作る人（または半年後の自分）が、
  どの雛形を選べばよいか判断できる

## 機構の要点（Phase 0 で凍結する）

### 1. 置き場は `world.json`。`ModelTemplate` と同じ棚

役職は**村の共有物**。配ると付いて回る（サーヴァントの定義が付いて回るのと同じ）。
`World` に `roles: BTreeMap<RoleId, Role>` を 6 つ目として足す。

```
Role {
  id: RoleId,          // 安定した識別子。改名しても変わらない
  name: String,        // 表示名。バッジに出る
  description: String, // 人が読む説明。**プロンプトには入らない**
                       // （機構 5「説明はモデルに見せない」）
  defaults: RoleDefaults,
}
```

### 2. 雛形が持つ欄は `AgentSpec` の全欄から**明示的に選ぶ**。線と場所は詰めない

**数え落としを防ぐため、`AgentSpec` の 11 欄を 1 つ残らず分類する**（rev1 は
箇条書き 4 本を「4 欄」と数えており、実体の 6 フィールドと合っていなかった）。
`construct` は `AgentSpec` の欄ではなくファイルなので、別枠で 1 つ足す。

**検算は 2 本立てる**（片方だけだと、今度は表と算式がズレる）。

- **`AgentSpec` の 11 欄** = 対象外 2 + 入れる 4 + 入れない 5
- **下の表は 12 行** = その 11 欄 + `construct`（**ファイルであって `AgentSpec` の
  欄ではない**）。ゆえに表の「入れる」は 5 行 = **`RoleDefaults` の 5 欄**

| 欄 | 分類 | 理由 |
|---|---|---|
| `id` | **対象外** | 個体固有。雛形が決めるものではない |
| `name` | **対象外** | 同上（表示名は作成時に人が付ける） |
| `construct`（ファイル） | **入れる** | 役職の本体。作成時に `Construct.md` へ書き込む |
| `model_template_id` | **入れる** | 役職ごとに向くモデルが違う（調査は速い安価な個体、査読は重い個体） |
| `rag_sources` | **入れる** | 役職 = 読む索引、が対応する（調査役は同じ索引を見る） |
| `enabled_tools` | **入れる** | 役職 = 使う道具の集合、がいちばん自然に対応する |
| `max_tool_iterations` | **入れる** | 調査役はツール往復が多い。既定のままだと途中で切れる |
| `connected_agents` | **入れない** | 入れると**役職を選んだ瞬間に線が引かれる**。「**線は人が引く**」（AdaptOrch を採らなかった根拠）が崩れる |
| `work_dir` | **入れない** | 絶対パスで**端末ごとに違う**。村を配ると存在しないパスを指し、その事故が新規作成のたびに増える |
| `order` | **入れない** | 左ペインの並び順。役職の性質ではない |
| `batch_start` | **入れない** | 一括起動の対象。運用の選択であって役職ではない |
| `hears_room_log` | **入れない** | コスト設定（Spec 03）。役職ではなく村の懐事情で決まる |

**参照の欠落は 1 つの規則で扱う（rev2 で修正）。**

rev1 は `rag_sources` を「索引の名前は村ごとに違う。雛形が壊れた参照を配る」と
書いて除外していたが、**この理由は成立しない**。役職は `world.json` に住むので、
`rag_sources` も `model_template_id` も**同一村内の参照**であり、村を配れば
索引もモデルテンプレートも役職も一緒に付いて回る。片方だけ入れたのが誤りでは
なく、**両方に付けた理由が嘘だった**。

ゆえに両方入れ、**参照先の欠落は種類で分けずに 1 つの規則で扱う**:

> **流し込みの時点で参照先が `World` に無ければ、その欄だけ落として WARN を出す。**
> 作成そのものは通す（役職 1 つが壊れていることで、サーヴァントを作れなくしない）。
> 落とした欄は System 行でなく起動ログと同じ WARN 経路へ出す — 人が直す対象は
> 役職の定義であって、会話ではない。

これは `World::from_persisted` の既存の作法と同じ形（未登録先への接続は黙って
落とす。開けなくなるほうが害が大きい、`world.rs:242`）。**ただし黙って落とさない**
点だけ違う — あちらは復元、こちらは人が今まさに操作している最中なので、
黙ると「入れたはずの設定が入っていない」が見えない。

### 3. **中身はコピー、名前は参照**（草案の主論点の決着）

草案は「コピーか参照か」を二択で立てたが、**性質の違う 2 つを 1 つの問いにして
いた**。分けると両方が素直に決まる。

| | 扱い | 役職の定義を**直した**とき |
|---|---|---|
| **`RoleDefaults` の 5 欄** | **コピー** | 既存の個体は**変わらない** |
| **役職の名前**（表示） | **参照**（`role_id` → `name`） | 表示は**全部追従する** |

**`name` は `RoleDefaults` の外**（機構 1 の型を参照）。「中身」と書いたら
`RoleDefaults` の 5 欄のことで、`name` と `description` は含まない。

- 作成時に `RoleDefaults` を `AgentSpec` の各欄と `Construct.md` へ**流し込む**。
  以後はただの個体設定で、役職とは切れている
- `AgentSpec.role_id: Option<RoleId>` だけは**残す**。表示名は毎回ここから引く

**コピーの発火点は「新規作成」ただ 1 つ**（rev2 で凍結。rev1 の D3 を昇格）。

`RoleDefaults` が `AgentSpec` と `Construct.md` へ書き込まれるのは、
**サーヴァントを新規作成するときだけ**。これ以外に流し込む経路を作らない。

- **既存のサーヴァントに後から役職を付けられる。ただし `role_id` だけ**
  （ラベルの付け替え）。**設定は 1 欄も上書きしない**
- 理由: 上書きは**取り消せない**。既に書いた `Construct.md` を役職の雛形で
  潰すと、その個体の履歴に残っている人格と、これから読む人格が食い違う。
  雛形が欲しいなら新しく作るほうが安全で、失うものが無い
- **役職を外す**（`role_id = None`）も設定を触らない。ラベルが消えるだけ

発火点を 1 つに凍結すると、「既存の個体は変わらない」が
**役職を直したときだけでなく、あらゆる操作について**成立する。**契約はこの形で
凍結できる** — rev1 は発火点を 1 つも書いておらず、D3 を未決に残したまま
P0 で「コピー/参照の分割」を凍結すると宣言していた（凍結できない）。

**なぜ中身をコピーにするか**: 参照にすると「後から直すと全員に効く共有規則」の層が
**条例と役職の 2 つ**になる。条例が既にその役を担っているので、同じ性質の層を
増やすのは「設定を増やさない」軸と正面から衝突する。

**なぜ名前を参照にするか**: 表示名は**変わりやすい層**で、そこを指すと改名で
記述が腐る（`failures.md` #51 の一般化 2）。この村には既に同じ形の判断がある —
型は `AgentId` で固定し、表示名だけ差し替え可能にしてある。**役職も同じ形にする。**

**表示の解決規則は 1 つだけ**（rev2 で追加。指摘 7）。

`role_id` から表示名を引くのは、**カードのバッジ・地図のバッジ・顔ぶれの行**の
3 箇所。**同じ 1 つの関数で解決し、引けなかったときの扱いも 1 つに揃える。**

> **`role_id` が `World.roles` に無ければ、役職の表示を丸ごと省く。**
> バッジは描かない。顔ぶれの行は `[...]` ごと落として
> `agent_2（ザリ・ロブステル）: 稼働中` に戻る。
> **`[不明]` とは書かない** — 存在しない役を出しても判断材料にならず、
> 顔ぶれでは毎ターンぶんのトークンを払うだけになる。

3 箇所で規則が分かれると、**画面のバッジは消えたのにプロンプトには `[不明]` が
残る**のような食い違いが生まれる。解決を 1 実装に寄せるのは、
`world::exchange_pair` を 1 つにした判断（Spec 12 P1）と同じ形。

**役職を削除しても、サーヴァントの動作は 1 ミリも変わらない。** 設定の中身は
既にコピー済みだから。これがコピー方式の効き所で、**参照方式なら削除が
全個体の人格を消す**ことになる。

### 4. プロンプトに入るのは**顔ぶれの行の役職名だけ**

利用者の懸念「System Prompt に入れるなら全部入りになっちゃう」は、
**役職の目録をプロンプトに入れようとしたときにだけ**起きる。入れない。

- **役職の目録（全 Role + 説明）はプロンプトに一切入らない。**
  目録の読み手は**人**で、作成時にどの雛形を選ぶかの判断材料。モデルは
  自分が作られたあとに雛形を選び直さない
- **顔ぶれの行に役職名を足すだけ**にする。
  `agent_2（ザリ・ロブステル）[調査役]: 稼働中`
- 顔ぶれは**既に `connected_agents` のぶんだけ**に絞られていて、
  **既に `stable_len` の外**（可変部）。**キャッシュの安定境界は動かない**

**稼働していない個体を顔ぶれから外すことはしない。** 「居るが止まっている」を
知らせるのが Spec 06 の目的で、外すと停止中の相手へ投げる事故が戻る
（実機で確認済み — ザリは状態が見えたから稼働中 3 体だけへ撒いた）。
利用者の「稼働していない役職を見せるのは無駄」は**目録の話**として機構 4 の
前半で解いてあり、顔ぶれの状態表示とは別問題。

### 5. **説明はモデルに見せない**（利用者から任された判断）

理由は 3 つ。

1. **読み手が人だから。** 説明は「どの雛形を選ぶか」の判断材料で、
   その判断をするのは作成画面の前に居る人だけ
2. **値段が合わないから。** 顔ぶれは毎ターン・全エージェント・素の値段。
   役職**名**は 3〜5 トークン、**説明**は 50〜200 トークン。接続 N 体ぶんが
   全ターンに乗り続ける固定費になる（Spec 12 P4 で観測した「要約は落ちないので
   膨らみが固定費になる」と同じ形）
3. **自分の役職の説明は既に全文届いているから。** コピー方式で `Construct.md` に
   入っており、そこは**安定部**なのでキャッシュが効く。
   **自分は全文・他人は名前だけ**という非対称は、値段と価値が一致している

> 反証の口: 実機で「相手の役職名だけでは何を頼めるか分からない」が出たら、
> 説明ではなく**役職名の付け方**を先に疑う。「調査役」で足りないなら
> 「コード調査役」にすればよく、それは 3 トークンで済む。

**実測の口（草案から引き継ぎ）**: 顔ぶれに役職名を**足した村と足さない村**で、
**plan の宛先の取り違えが減るか**を比べられる。S3 は「当たりを付けられる」までしか
約束していないので（機構 8）、効いたかどうかは実測でしか言えない。
Spec 06 の実機確認が「状態が見えたから稼働中 3 体だけへ撒いた」を観測できたのと
同じ形で、**P5 の実機確認で見る候補**として置いておく。機構は足さない。

### 6. 役職は**配送・権限・ツール提示のどの分岐にも入らない**（凍結）

`plan` の発火条件は `entries.len() >= 2` のまま。役職を見て分岐する箇所を
**1 つも作らない**。ここが混ざると「進行役 Role なら plan を出す」が自然に見え、
**線は人が引く**（AdaptOrch を採らなかった根拠）ごと崩れる。

**`enabled_tools` を雛形が持つことは、この凍結の例外ではない**（rev2 で語を修正。
rev1 は直前に「例外はない」と書いており、例外の説明が続く形で自己矛盾に読めた）。

**判定は「いつ役職を見るか」の 1 点。** 雛形が `enabled_tools` を持つのは
**作成時に初期値を入れる**ためで、流し込んだ後は普通の `AgentSpec` の値になる。
実行経路に `role_id` を読む分岐は 1 つも無い。

**実装者への含意**: この節を根拠に `RoleDefaults` から `enabled_tools` を
削ってはいけない。凍結しているのは**実行時に役職を見ないこと**であって、
雛形が道具の初期値を持たないことではない。

### 7. セッションと役職の食い違いには、**何も作らない**

- **現在の役職が必ず勝つ。** セッションは system プロンプトを保存せず、
  毎ターン組み直される（現状の接地を参照）。古い会話を開き直しても、
  入るのは今の役職
- **残るのは履歴の残り香だけ** — 復元された `ChatMessage` に、旧役職として
  振る舞った過去の発言が残る。**既知の残りとして受け入れる**
- **その個体の役職表示が変わったら System 行を 1 本書く。**
  `compose_presence_notices`（`orchestrator.rs:4498`）が広場ログの直近窓から
  System 発を拾って可変文脈へ注入するので、次のターンでモデルに届く。
  **新しい機構はゼロ**。**発火は次の 3 つ**（rev2 で削除を追加。指摘 8）:
  - **付与**（`role_id` が付いた）
  - **変更**（別の `role_id` に差し替わった / 役職が改名された）
  - **削除**（役職が消えた、または `role_id` が外れた）

  **判定は「表示名が変わったか」の 1 点**にする。役職の改名も、役職の削除も、
  他のサーヴァントから見れば「あの個体の役職表示が変わった」で同じ事象。
  発火条件を操作の種類で分けると、**改名だけ通知が出ない**のような穴が空く
- **ただしこれは保証ではない。** 広場ログをオプトアウトした個体には届かず
  （`room_log_window == 0` で即 return）、窓から押し出されれば消える。
  **「自己申告する」を仕様の約束にしない** — 届いたら気づける、程度に留める

### 8. **バッジは由来であって、現在の中身を保証しない**（rev2 で新設。指摘 9）

コピー方式の**必然の帰結**として、**バッジは合法的に嘘をつける**。

作成時に「調査役」の雛形を流し込んだ後、`Construct.md` も `enabled_tools` も
手で書き換えられる。`role_id` は残るので、**バッジは「調査役」のまま、中身は
まったく別のサーヴァント**という個体が正当な操作だけで生まれる。

**これは仕様であって、直すべきバグではない。** ただし**書かないと嘘になる**ので、
言葉のほうを実態に合わせる。

> **バッジの意味は「この役職を雛形にして作られた」。**
> 「今この役職として振る舞っている」ではない。

- **S2 / S3 の約束をこの範囲へ縮めた**（rev2 で Stories を修正）。
  S2 は「どの雛形から作られたか」、S3 は「**当たりを付けられる**」であって
  保証ではない
- **UI にも同じ言葉を出す**（バッジの `title` 属性）。画面の言葉と仕様の言葉を
  分けない
- **ドリフト検出の機構は作らない。** 検出するには「今の `AgentSpec` と役職の
  現在の `RoleDefaults` の差」を見ることになるが、差が出た理由が
  **個体を直したから**か**役職を直したから**か区別できない。区別できない警告は
  読み手が対処できず、無視される計器になる（#47 の一族）
- **役職名を長くするほうが安い。** 実運用でバッジが嘘をつくのが問題になったら、
  機構ではなく**運用**（役職を変えたら付け替える）と**命名**で対処する

**この村は既に人が保つラベルで動いている。** 表示名が「ザリ・ロブステル」の
サーヴァントの `Construct.md` が詩人でも、機構は何も言わない。役職バッジも
同じ層のもので、**新しい種類の嘘を持ち込んではいない**。持ち込んでいないことを
**仕様に書いておく**のが、この節の役目。

## 検証の設計（実装の前に決める）

**「中身」は `RoleDefaults` の 5 欄を指す**（`name` / `description` を含まない）。
rev1 はここを限定していなかったため、結合 2 と結合 3 が同時に真になれなかった。

- **純関数の単体**: 流し込み（`RoleDefaults` → `AgentSpec` + Construct 本文）。
  **`connected_agents` / `work_dir` / `order` / `batch_start` / `hears_room_log`
  の 5 欄が流し込み後も既定のままであること**を名指しで押さえる
  （rev1 の「線と場所が入らないこと」は対象が曖昧でテストに落とせなかった）
- **純関数の単体**: 参照の欠落 — 存在しない `model_template_id` /
  `rag_sources` を持つ役職を流し込むと、**その欄だけ落ちて他は入る**
- **結合 1**: 役職を選んで作成 → `AgentSpec` に値が入り、`Construct.md` が書かれ、
  `role_id` が残る
- **結合 2**: **役職の `RoleDefaults` を直しても既存の個体が変わらない**
  （コピーの証明。**`name` は対象外** — それは結合 3 が見る）
- **結合 3**: **役職を改名すると表示名が 3 箇所とも追従する**（参照の証明）
- **結合 4**: **既存の個体に役職を付けても設定が 1 欄も変わらない**
  （発火点は新規作成だけ、の証明）
- **結合 5**: **役職を削除しても個体の動作が変わらない**。バッジも顔ぶれの
  `[...]` も**消える**（`[不明]` にならない）
- **結合 6**: **役職名を足しても `stable_len` が変わらない**
  （`PromptProbeBackend` で system ブロックの安定部を比較。Spec 13 P3a と同型）
- **結合 7**: 役職表示が変わると System 行が 1 本出る。**付与・変更（改名含む）・
  削除の 3 経路とも**
- **フロント**: バッジの投影、役職ダイアログの CRUD
