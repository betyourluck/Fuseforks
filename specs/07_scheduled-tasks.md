## Goal

**時刻で発火する依頼**を登録できるようにする。宛先は自分でもワーカーでもよい。

起点は利用者の要望（2026-07-31）:

> 毎週木曜の 17 時に音声ファイルの鐘を鳴らして／定期的にサイトの状態を監視する

現状、エージェントが動き出す契機は**ユーザーの発話しかない**。人が居ないと村は
一切動かないので、「決まった時刻にやっておく」種類の仕事が表現できない。

### 立場の宣言（限界は現時点のもので、行き先ではない）

**今のところ、アプリが起動していない間は予定が動かない。**

Concordia は現状デスクトップアプリで、常駐サービスではない。cron / Airflow の
スケジューラは OS やサーバーが起きている前提で成立するが、**今のこちらには
その前提が無い**。この事実を機能の中に書く（P2）。書かずに「毎週木曜 17 時」と
名乗るのは、Spec 05 で潰したのと同じ形の嘘 — できないことをできると
教えると、利用者は動いていない予定を動いていると思って計画を立てる。

**ただしこれは製品の行き先ではない。** 利用者の宣言（2026-07-31）:

> 最終的には Concordia はタスクトレイ常駐でサーバー的な動きをするようになる。
> 管理ツールだからね。

トレイ常駐が入れば、この限界は**大部分が消える**。だから本 Spec の設計は
「常駐しない」ことを前提に**作り込まない** — 逆に、常駐したときに嘘になる
決定を避ける。具体的には:

| 決定 | 常駐後も正しいか |
|---|---|
| 壁時計の予定は取りこぼしを追いかけない | **正しいまま**（稀な再起動で効くだけになる） |
| 間隔の予定は再開時に 1 回だけ | **正しいまま** |
| P2 の限界の告知（文言） | **書き換えが要る**（機構ではなく文章なので安い） |
| 多重起動の排他（P0） | **常駐後こそ必須**（トレイに 2 つ居ると二重発火する） |

常駐して初めて重くなる論点は末尾の「トレイ常駐後に重くなる論点」（11〜13）へ
分けて置いた。**先に作らない**（確かめる前に席を作らない）が、
どこが効いてくるかは記録しておく。

### OS とアプリの境界線（2026-07-31 に確定）

検討して**棄却した代替**を先に書く。「**OS のスケジューラに時刻を任せ、
アプリはチャネルの口（通知の出し先）だけを担う**」案があった。
利用者の判断は「やはりスケジュールもアプリで管理したい」で、これを採る。

引く線はこうなる:

| 層 | 担い手 |
|---|---|
| 常駐プロセスを**起こす** | **OS でよい**（自動起動。Windows のタスクスケジューラ / launchd / systemd。OpenClaw も同じ） |
| 予定を**保持し・発火させ・見せる** | **アプリ**（本 Spec） |

アプリ側に置く理由は 3 つあり、どれも要望と既存の台帳から出ている。

1. **一覧と削除が要望に入っている。** 予定が OS 側にあると、UI は
   **自分が所有していない外部状態の投影**になる。しかも Windows /
   macOS / Linux で 3 実装。投影の同期は既に何度も踏んでいる罠で
   （failures.md #5 の「判断を機構に置き換える」・#19 の世代ガード）、
   **アプリの外から書き換えられる投影**はその中でも最も悪い形
2. **予定の中身がアプリ内の概念。** 宛先は `AgentId` で、OS に「agent_3」は
   存在しない。OS へ登録できるのは `concordia fire --task-id X` のような
   コマンドだけで、**時刻は OS・宛先と本文はアプリ**に分かれる。
   1 つのものに真実が 2 箇所できる — 鍵は鍵として扱う（#7）の逆をやることになる
3. **発火規則が製品固有。** 「壁時計の予定は取りこぼしを追いかけない／
   間隔の予定は再開時に 1 回だけ」は本 Spec が慎重に決めた判断だが、
   OS のスケジューラは自前のポリシーを持つ（Windows には
   「開始時刻を過ぎた場合はできるだけ早く実行する」というチェックがある）。
   **委ねると、決めた規則が OS の設定で上書きされうる**

逆に**常駐の起動は OS に任せてよい**。ここは OpenClaw が Windows で
Scheduled Task を使っているのと同じ層で、rev2 で「OS スケジューラ案は不要」と
一括に書いたのは層の混同だった（Notes 8 で訂正済み）。

## 現状の構造（接地）

- **定期タスクの下地はある**。`spawn_stats_ticker` が
  `tokio::time::interval` + `Weak<Shared>` で 1 秒ごとに回っており、
  スケジューラは同じ形で足せる（`Weak` なのでアプリ終了で自然に止まる）
- **発話の投入口は `send_user_message` / `deliver_envelope`**。ターンを
  発火させるのは受信箱への配送だけで、`record`（ログのみ）とは別経路
- **`Endpoint::System` は Spec 06 で送出経路を得たが、宛先は User だけ**
  （入退室の通知）。**System → Agent の配送はまだ 1 件も無い**
- **`hop` はユーザー発話が 0 から始まる**。予定発火も新しい起点なので 0
- **時刻を扱う道具が無い**。`now_ms()` は `SystemTime` の epoch ミリ秒だけで、
  ワークスペースの依存に `chrono` / `time` は**入っていない**。
  「次の木曜 17 時（現地時刻）」は epoch 演算だけでは出せない（曜日・DST）
- **音を鳴らす手段が無い**。同梱ツールは `remember` / `grep` / `fd` /
  `diff` / `sd` / `yq` の 6 本で、コマンド実行も通知も音声も持たない。
  Tauri 側のプラグインも `plugin-opener` だけ（起票時。Phase 1 で
  `plugin-single-instance` が加わったが、こちらは音とは無関係）。
  **要望の「鐘を鳴らす」は、本 Spec だけでは実行できない**（Notes 9）

## Stories（P0 が新規・rev2 で追加）

### P0: 多重起動の排他（**予定を入れる前提条件**）

> 利用者として、Concordia を 2 つ起動しても予定が二重に走らないと知っている。

**これは今すぐ効く正しさの問題で、トレイ常駐の話ではない。**
**以下は起票時（Phase 1 着手前）の観測。Phase 1 で解消済み。**
当時 `tauri-plugin-single-instance` は入っておらず（依存は
`tauri-plugin-opener` だけ）、ウィンドウを閉じる操作も横取りしていない。
つまり**同じワークスペースを掴んだプロセスが 2 つ並べる**。

今日までは「`world.json` の書き込みが後勝ちになる」程度の不便で済んでいた。
だが予定が入ると次が起きる:

- 同じ予定が**両方のプロセスで発火**する（配送も課金も 2 倍）
- `lastConsumedDueMs` を同じファイルへ**競って書く**ため、消化の記録が壊れる。
  片方が「消化済み」と書き、もう片方が古い値を書き戻す

**仕様**

- `tauri-plugin-single-instance` を入れ、2 つ目の起動は**既存ウィンドウを
  前面に出して終了**する（起動しなかったことが利用者に伝わる形にする）
- コア側には何も足さない。プロセスの一意性は OS/フレームワークの層の仕事で、
  ここでロックファイルを自作するとロックの残留（強制終了後）を自分で
  面倒みることになる

**Acceptance**

- Given 起動中に 2 つ目を起動、Then 2 つ目は終了し、既存ウィンドウが前面に出る
- Given 予定 1 件、Then 発火は 1 回だけ（プロセスは常に 1 つなので構造的に保証）

### P1: 予定を登録して発火させる

> 利用者として、決まった時刻に決まった依頼が飛ぶようにする。なぜなら
> 「毎週木曜 17 時に」を人が覚えて手で送るのは、機械がやるべき仕事だから。

**型**

```yaml
ScheduledTask:
  id: String            # UUID v4
  to: AgentId           # 宛先。自分宛でもワーカー宛でもよい（区別しない）
  message: String       # 届ける依頼の本文
  recurrence: Recurrence
  createdAtMs: u64      # 作成時刻。interval の起点（rev2 指摘 2）
  lastConsumedDueMs: u64 | null   # 直近に「消化した」予定時刻（発火時刻ではない）
  enabled: bool         # 既定 true。偽なら発火も消化もしない（rev2 で採用）

Recurrence:  # tag つき判別共用体
  interval: { everyMinutes: u32 }              # n 分ごと（1 以上）
  daily:    { hour: u8, minute: u8 }           # 毎日 hh:mm（現地時刻）
  weekly:   { weekday: Weekday, hour, minute } # 毎週 X 曜 hh:mm（現地時刻）
```

**`createdAtMs` が要る理由（rev2 指摘 2）**: `lastConsumedDueMs` が `null` のとき、
`interval` の起点をどこから取るかが決まらない。rev1 は本文で「作成時刻」と
書いておきながら**保持する場所を型に持っていなかった** — 再起動後に計算不能に
なる欠落だった。`enabled` は要望を 1 項目超えるが、週次の予定を旅行中だけ
止めたいときに削除 + 再作成しか手が無いのは不便で、`mcp.json` の `enabled`
（「設定を消さずに一時停止する欄」）に前例がある。

**cron 式は採らない。** `0 17 * * 4` は表現力が高い代わりに、読めない人には
一切読めず、UI も自由入力欄にしかならない。この製品は「設定が少なくて
分かりやすい」を差別化軸に置いている（README）ので、**要望の 2 例
（毎週 X 曜 hh:mm / 定期的に）が言い切れる最小の構造**を採る。
後から cron 式を足すことはできるが、外すことはできない。

**発火の規則（純関数として持つ。rev2 で修正）**

各 tick で「**今以前にある直近の予定時刻**」= `due` を求め、判定する。

```rust
// 壁時計系（daily / weekly）: カレンダーから逆算する
fn due_wall_clock(rec, now: DateTime<Local>) -> Option<DateTime<Local>>
// 間隔系（interval）: 起点から刻んで now 以前の最後の点を取る
fn due_interval(anchor: DateTime<Local>, every: Duration, now) -> Option<...> {
    let elapsed = now - anchor;
    if elapsed < every { return None; }
    let k = elapsed.num_minutes() / every.num_minutes();  // floor
    Some(anchor + every * k)   // now に最も近い過去の予定時刻
}
// anchor = lastFired ?? createdAt
```

| 条件 | 処方 |
|---|---|
| `enabled == false` | 何もしない（消化もしない） |
| `due` が無い（まだ 1 度も来ていない） | 何もしない |
| `lastConsumedDueMs >= due` | 既に消化済み。何もしない |
| **壁時計系**で `now - due` が猶予（5 分）超 | **発火せず消化済みにする** |
| それ以外 | **発火**し、`lastConsumedDueMs = due` |

**猶予は壁時計系にだけ適用する（rev2 の修正点）。**
rev1 は猶予を全種別に掛けており、`interval` の意図（再開時に 1 回だけ）と
**矛盾していた** — 2 日止まった 10 分ごとの予定は `now - due` が 2 日超になり、
猶予の外として毎 tick 消化されるだけで、288 tick かけて追いつくまで
一度も発火しない。査読の指摘どおりバグである。

処方は 2 つ揃って初めて成立する:

1. `due_interval` を「起点から刻んだ、`now` 以前の**最後の**点」にする
   （査読提案。これで再開直後の `due` が `now` の近傍に来る）
2. **`interval` に猶予を適用しない**（本 Spec の追加）。1 だけでは
   `everyMinutes > 猶予` の予定が依然 skip される — 例: 60 分ごとで
   2900 分停止すると `k=48`、`due = anchor+2880`、`now - due = 20 分 > 5 分`。
   そもそも**間隔の予定に「間違った時刻」は存在しない**ので、猶予を掛ける
   理由が無い。猶予は「17 時の鐘を 23 時に鳴らさない」ための道具であり、
   時刻に意味がある予定にだけ効かせる

発火後に `lastConsumedDueMs = due`（`now` ではない）とすることで**刻みの位相が
保たれる**。かつ `now - due < every` が構成上保証されるので、次の tick では
`elapsed < every` となり連続発火しない。

**壁時計系は取りこぼしを追いかけない。** 17 時の鐘を 23 時に鳴らすのは
「鳴らなかった」より悪い。猶予を過ぎた予定は**発火せずに消化済みへ倒す** —
消化しないと、猶予の外に居続ける予定が tick ごとに判定され続ける。

**現地時刻が存在しない/曖昧な瞬間を `unwrap` しない（査読の実装注意）。**
`Local.from_local_datetime(&naive)` は DST の飛ぶ時刻（春の 2:30）で `None`、
戻る時刻で `Ambiguous` を返す。**どちらもその回は発火しない**（`None` 扱い）
として扱う。日本には DST が無いが、**panic する経路を他のタイムゾーンの
利用者に残さない**。契約に「`unwrap` しない」を明記する。

**配送**

- `from: Endpoint::System`（表示は「Concordia」）、`to: Endpoint::Agent`、
  **`hop: 0`**。予定発火はユーザー発話と同格の新しい起点で、そこから先の
  転送・委譲に満額の燃料を渡す
- **`Endpoint::System` → Agent の最初の利用者**。Spec 06 は System → User
  （通知）だけを使った。同じ席の別の使い道になる
- **宛先が稼働中でなければ撒かない**（`Running` 以外は消化済みにして飛ばす）。
  停止中へ投げると `NotRunning` の失敗が毎 tick 積まれるだけで、利用者に
  読ませる価値のある情報にならない。**代わりに 1 行ログへ残す**（P2）。
  消化するので**ログも 1 回だけ**になる（毎 tick 出さない）
- **本文の先頭に発火の由来を書く（rev2 指摘 7）**:
  `【定期実行: 毎週 木曜 17:00】\n{message}`。封筒（`【送り手: Concordia】`）
  だけでは、モデルは**人が今喋ったのと区別できない**。区別できると
  「これは定期実行なので、報告の口調で答える」といった調整が効く。
  `AgentMessage` に欄を足さず本文へ書くのは、(a) 契約を変えずに済み、
  (b) 会話ペインにもそのまま出るので**利用者も定期発火だと分かる**から
- 応答の行き先は既存の規則どおり。`reply_to` が無いので最終出力は
  `Endpoint::User` へ返る — **結果は会話ペインに出る**。これが
  「自律エージェント」の観測点になる
- **二重発火の軽い護り（rev2 指摘 5・査読案を採用）**: スケジューラ層に
  `HashSet<AgentId>` を持ち、配送時に入れ、`CoreEvent::AgentTyping { active: false }`
  で外す。**コアに新しい状態を持たせない**（`Shared` に処理中フラグを足すと
  Spec 04 の進行役の状態管理と結合して複雑度が跳ねる）。
  対象を task 単位ではなく**エージェント単位**にするのは、抑えたいのが
  「まだ働いている相手に積み増さない」ことであり、購読できる信号
  （`AgentTyping`）もエージェント単位だから。
  **イベントの取りこぼし時は fail open**（`Lagged` を受けたら集合を空にする）—
  塞がったままにすると予定が二度と発火しない静かな停止になり、
  それは稀な二重発火より悪い

**保存**

- `{workspace}/schedules.json`。`world.json` に入れないのは、予定が
  **エージェントの定義ではない**から（同じ理由で `Ordinance.md` /
  `mcp.json` も別ファイルになっている）
- **書き込みは tmp + rename**（査読の指摘）。これは新しい規律ではなく
  `save_world` が既にやっていることへの追従 — 電源断で壊れると全予定が消える
- **読み込み時、宛先が存在しない予定は落とす**。`World::from_persisted` が
  宙に浮いた接続を落とすのと同じ規律（参照の回収まで含めて 1 操作）
- **エージェント削除時、その宛先の予定も消す**。`remove_agent` が
  他エージェントからの参照を外すのと同じ
- **不正な値は読み込みでも弾く**（査読の指摘。UI と二重化）:
  `hour > 23` / `minute > 59` / `everyMinutes == 0`。UI だけで防ぐと
  `schedules.json` の直接編集で入る — Spec 05 で `world.json` の直接編集が
  作った穴（`grounding_active()`）と同じ形。**壊れた 1 件は落として残りを開く**
  （mcp.json とは逆の判断: あちらは「壊れた JSON を空として扱うと全ツールが
  黙って消える」ので全体をエラーにしたが、予定は 1 件ずつ独立していて
  他の予定を人質にする理由が無い）

**Acceptance**

- Given `weekly { thu 17:00 }` の予定、When 木曜 17:00 を跨いで tick、Then
  宛先へ 1 通だけ配送され、`hop` は 0
- Given 同じ予定、When 同じ週の tick が何度も回る、Then 配送は 1 回だけ
- Given `daily { 09:00 }` で 6 時間後に起動、Then **発火しない**が消化済みになり、
  以後その日の tick で再判定されない
- Given `interval { 10 分 }` で 2 日止まっていた、Then 再開後に**1 回だけ発火**
  （288 回でも 0 回でもない — rev1 の規則では 0 回だった）
- Given `interval { 60 分 }` で 2900 分止まっていた、Then **1 回発火する**
  （猶予を間隔系へ掛けないことの検証。掛けると skip される）
- Given `enabled == false`、Then 発火せず、**消化もしない**
  （再開したときに直近の予定から拾える）
- Given 宛先が停止中、Then 配送されず、消化済みになり、失敗が積まれない
- Given 宛先を削除、Then その予定も消える
- Given `hour: 99` の予定が `schedules.json` に手で書かれていた、Then
  その 1 件だけ落ち、他の予定は読める
- Given 予定の発火で始まったターンの最終出力、Then `Endpoint::User` へ返る
- Given 配送された本文、Then 先頭に `【定期実行: …】` が付いている
- **時刻はすべて引数で渡す。** 壁時計に依存するテストを書かない
  （Spec 04 rev2 指摘 2 と同じ規律）

### P1.5: 一覧・削除（UI）

> 利用者として、登録した予定を一覧で見て、要らなくなったら消す。

**仕様**

- **モーダル**で出す。ヘッダのボタンから開く（条例・MCP・モデルテンプレートと
  同じ扱い）。常駐ペインに置かないのは「たまに開くものが、いつも見るものの
  面積を奪う」ため（README）
- 1 行の表示: 宛先（`agent_id（表示名）`）／再現規則の**日本語**表記
  （「毎週 木曜 17:00」「10 分ごと」）／依頼本文の冒頭／
  **次回の発火予定時刻**／削除ボタン
- 追加フォームは同じモーダル内。宛先はエージェントの選択、再現規則は
  種別のラジオ + 時刻入力（自由入力の cron 式にしない）
- 削除は確認つき（会話ログのリセットと同じ流儀。復元できない）

**Acceptance**

- Given 予定 3 件、Then 一覧に 3 行出て、それぞれ次回の発火時刻が読める
- Given 削除、Then 確認の後に消え、以後発火しない
- Given 予定 0 件、Then 空であることと作り方が書かれている
- Given エージェントが 0 体、Then 追加フォームは宛先を選べないことを言う

### P2: 動かない時間があることを画面に書く

> 利用者として、アプリを閉じている間は予定が動かないと知っている。

**仕様**

- 一覧モーダルに 1 行:
  「**アプリを起動していない間、予定は動きません。** 過ぎた予定は
  さかのぼって実行されません（間隔の予定は再開後に 1 回だけ走ります）」
- 宛先が停止中で飛ばした予定は、**会話ログへ 1 行**残す
  （`Endpoint::System` 発・User 宛。Spec 06 の入退室通知と同じ形）。
  「〜への予定を飛ばしました（停止中）」。黙って飛ばすと、
  動くはずのものが動かない理由が画面のどこにも無い（#4 の一般化）
- **猶予超過で飛ばした予定は会話ログへ出さない**（debug ログに留める。査読の指摘）。
  停止中とは飛ばす理由が違う — 停止中は**利用者が直せる状態**（起動すれば動く）
  だから画面に要るが、猶予超過は「アプリを閉じていた」の事後報告でしかなく、
  直す手が無い。P2 の告知（起動していない間は動かない）を読んでいれば
  既知の帰結で、毎朝 9 時の予定が数日分まとめて会話ログへ流れると
  **本物の通知が埋まる**

**Acceptance**

- Given 一覧モーダル、Then 起動していない間は動かない旨が書かれている
- Given 停止中の宛先で予定時刻を跨いだ、Then 会話ログに飛ばした旨が 1 行入る
- Given `daily { 09:00 }` を 3 日閉じていた、Then 会話ログには**何も入らない**
  （猶予超過の消化は debug ログのみ。本物の通知を埋めない）

### P3（本 Spec に入れない）: エージェント自身が予定を作る

要望の「自律エージェントにもなる」は、**利用者が登録する予定でも成立する**
（発火 → エージェントが判断して動く、が自律の実体）。

エージェントに `schedule` ツールを渡す案は**採らない**。

- **繰り返す副作用を自分で増やせる**ようになる。暴走の形が「1 ターン燃える」
  ではなく「毎時燃え続ける」に変わり、`max_hops` も `max_tool_iterations` も
  この暴走を縛れない（どちらもターン内の安全網）
- 必要な護りは別物（総数上限・最短間隔・利用者の承認）で、それ自体が Spec 1 本
- **順序として、まず人が作る予定で機構を実機確認するべき**

### P4（別 Spec 候補）: 鐘を鳴らす手段

**要望の例そのものは、本 Spec だけでは実行できない。** 予定は「鐘を鳴らして」
という依頼を届けるが、届いた先に音を出す道具が無い（同梱 6 本にコマンド実行も
音声も無く、Tauri 側も `plugin-opener` だけ）。選択肢は 3 つで、**どれも
本 Spec の外**:

1. **MCP サーバーを繋ぐ**（利用者が既に持っている資産を使える。追加実装ゼロ）
2. **狭い同梱ツールを 1 本足す** — 「デスクトップ通知を出す」「同梱の音を鳴らす」。
   引数を持たない/持たせない設計なら安全側に置ける
3. **汎用のコマンド実行ツール** — **採らない**。プロンプトインジェクションを
   受ける個体に任意コマンドを渡すのは、作業フォルダで慎重に絞ってきた
   境界（`canonicalize` + 前方一致）を無意味にする

**利用者の判断（2026-07-30）**: タスクトレイのマーク表示とチップス通知
（デスクトップ通知）で足りる。ただし**それらの UI はまとめて別に作る**ので、
**Phase 4 では手を付けない**。Phase 4 の範囲は一覧・追加・削除・`enabled`
トグルのモーダルと限界の告知までで、トレイと通知はそこへ混ぜない。

## Notes（査読論点）

1. **新規依存 `chrono` を入れる判断**。「次の木曜 17 時（現地時刻）」は
   epoch ミリ秒の演算では出せない（曜日・DST・月末）。自前で書くのは
   カレンダー計算の再発明で、必ずどこかで間に合わせになる。
   `chrono`（`clock` feature）はこの用途のデファクトで、他に候補は `time` のみ。
   **代替案として棄却したもの**: 次回発火時刻をフロント（JS は完全な
   タイムゾーン演算を持つ）で計算してコアへ渡す案 — 発火のたびに次回を
   計算し直す必要があり、**コアが UI に依存する**形になる
   （「コア層は GUI 層に一切依存しない」の破壊）
2. **`lastConsumedDueMs` は「消化した予定時刻」で、発火時刻ではない**。この区別が
   規則の全体を支える — 飛ばした予定も消化済みにするので、同じ欄で
   「発火した」と「発火せず飛ばした」の両方を表せる。逆に発火時刻を持つと、
   飛ばしたことを覚える場所が別に要る。
   **rev2 まで `lastFiredMs` だった名前を査読で改名した** — 「fired」は
   飛ばした予定を書く欄として嘘になる。契約凍結前なので改名は無料で、
   凍結後は `schedules.json` の互換の話になっていた
3. **猶予 5 分の根拠は薄い**。tick 間隔（30 秒を想定）より十分長く、
   「うっかり閉じていた」を拾わない程度に短いという以外の根拠が無い。
   実測してから決める余地（Spec 04 Notes 7 と同じ流儀）
4. **tick 間隔をどうするか**。30 秒なら「17:00 の予定が 17:00:29 に飛ぶ」。
   分単位の予定に対しては十分だが、`stats_interval`（1 秒）と別に持つか
   共用するかは設計判断。**秒の予定は持たない**ので 30 秒で足りる想定
5. **二重発火（rev2 で決着）**。査読案どおり、スケジューラ層の
   `HashSet<AgentId>` + `AgentTyping{active:false}` で外す軽量ガードを入れ、
   コアには状態を足さない。**完全には防げないことを既知の制限として書く**
   （イベント取りこぼし時は fail open にするため）。受信箱の容量 64 が
   最後の背圧で、その手前で無駄に燃える可能性は残る。
   **査読は集合を `HashSet<TaskId>` にする案を出したが採らない** — 集合から
   外す契機に使える信号は `AgentTyping { active: false }` しか無く、これは
   **エージェント単位でしか来ない**。同じエージェント宛の予定が 2 件あると
   どちらの `TaskId` を外すか決められず、集合が塞がったまま残る
   （＝その相手への予定が二度と発火しない静かな停止）。
   粒度は好みではなく、**購読できる信号の粒度に強制されている**
6. **`enabled`（rev2 で採用）**。要望を 1 項目超えるが、査読で
   「削除 + 再作成は `message` の再入力コストが高く、利用者に
   『消すのが怖い』を強いる」と評価されたので入れる。既定 true、
   `mcp.json` の `enabled` と同じ位置づけ
7. **由来の明示（rev2 で採用）**。本文の先頭に `【定期実行: …】` を書く。
   封筒（`【送り手: Concordia】`）だけではモデルが人の発話と区別できず、
   区別できれば口調や報告の粒度を調整できる。実装は 1 行、
   会話ペインにも出るので**利用者側の可読性も上がる**
8. **OS のタスクスケジューラの扱い（rev2 → 実物確認で訂正）**。
   棄却するのは「**予定 1 件ずつを OS へ登録して発火させる**」案で、
   これは今も棄却で正しい（OS ごとの別実装・予定だけ実行して終了する
   動作モード・意図しない起動）。
   一方「**常駐プロセスを OS に起こさせる**」のは別の層の話で、
   OpenClaw が Windows で Scheduled Task を使っているのがまさにそれ。
   こちらはトレイ常駐の**手段として生きている**。
   rev2 で「OS スケジューラ案は不要」と一括で書いたのは雑だった —
   層が違うものを同じ名前で棄却していた（末尾の参照実装の節を見よ）
9. **P4（鐘）の扱い**。要望の例が本 Spec で完結しないことは、起票の時点で
   表に出しておく。順序としては「予定で依頼が届く」を先に確かめ、
   何を鳴らすかは MCP か狭いツールで別に決めるのが妥当
10. **Spec 04（plan）との関係**。予定の宛先を進行役にすれば、
    「毎朝ワーカー 3 体へ手分けさせて要約を出す」が自動で回る。
    予定 → plan → 束ね → ユーザーへ、が既存の経路だけで繋がる。
    本 Spec は新しい**起点**を足すだけで、その先は 04 が持っている

### トレイ常駐後に重くなる論点（rev2。**今は作らない**）

利用者の宣言「最終的にはタスクトレイ常駐でサーバー的に動く」を受けて、
**その時に効いてくる**が今は着手しないものを分けて記録する。先に作ると
「効いているか分からない機構」が増えるだけだが、どこが割れるかは残しておく。

11. **無人運用は P4（鐘・通知）を「例」から「構造的要件」へ変える**。
    今の設計では予定の結果は会話ペインへ出る。人が画面を見ている前提なら
    それで足りるが、**トレイ常駐は「見ていない」ことが前提**の運用形態で、
    誰も読まないログへ書くだけでは自律の意味が半分死ぬ。
    要望の「鐘」は装飾ではなく**無人運用における唯一の出力チャネル**になる。
    P4 の優先度は、トレイ常駐が視野に入った時点で上がる
12. **無人 + 定期 + LLM = 見張りのないコスト**。今日までの課金は必ず人の
    操作が起点だったが、常駐後は**誰も居ない時間に燃え続ける**形が初めて
    可能になる。既存の護りはどれもターン内（`max_hops` /
    `max_tool_iterations`）で、時間軸の総量を縛るものが 1 つも無い。
    観測は既に `[concordia] turn:` のログが取っているので、
    **まず実測 → 必要なら日次/月次の上限**（Spec 04 Notes 7 と同じ順序）
13. **「ウィンドウを閉じる」が「終了」でなくなる**。トレイ常駐では ✕ は
    最小化であるべきだが、今は素の終了で、**利用者は今の癖のままサーバーを
    殺す**ことになる。逆に、常駐だと気づかずに閉じたつもりで動き続けるのも
    同じ事故の裏側。どちらも「閉じたときに何が起きたか」を画面に出す設計が要る。
    P0（多重起動の排他）はこの話と同じ層にあり、**先に入れておくと後で効く**

### 参照実装: OpenClaw（2026-07-31 に実物を確認）

利用者の指す行き先は [OpenClaw](https://github.com/openclaw/openclaw)。
推測で書かないために取得して確かめた事実だけを置く（**取れなかったことも
書く** — cron の記法そのものは公開ページから確認できていない）。

| 観点 | OpenClaw | Concordia（現状 / 行き先） |
|---|---|---|
| 常駐 | **Gateway が daemon** として動く（launchd / systemd / **Windows Scheduled Task**） | 現状は前面のみ。行き先はトレイ常駐 |
| 制御面 | 「single control plane for sessions, channels, tools, and events」+ Control UI | 3 ペインの GUI が制御面そのもの |
| スケジュール | **「Cron jobs」**（Automation の一部）。Webhooks / Gmail Pub/Sub も持つ | 本 Spec が最初 |
| 到達手段 | **25 以上のメッセージチャネル**（WhatsApp / Telegram / Slack / Signal / iMessage / SMS …）+ companion アプリ | 会話ペインのみ |
| 多エージェント | **inbound を隔離エージェントへ振り分ける**（workspaces + per-agent sessions） | **エージェント同士が繋がる**（トポロジー / plan / 広場ログ） |
| コマンド実行 | main 以外のセッションを **Docker / SSH でサンドボックス**する | 同梱ツールを作業フォルダに限定（コマンド実行は持たない） |
| 実装 | Node.js / TypeScript / pnpm | Rust（コア）+ Tauri / Vue |

**確認して分かった最も重要な差は、多エージェントの向きである。** OpenClaw は
**外から来る会話を隔離したエージェントへ振り分ける**（チャネル → エージェント）。
Concordia は**エージェント同士を繋ぐ**（エージェント → エージェント）。
どちらも「多エージェント」と呼ぶが、前者は**隔離**が価値で、後者は
**接続**が価値だ。本 Spec が足すのは後者に新しい起点を 1 つ増やすことなので、
OpenClaw の Automation をそのまま写す設計にはならない。

**rev2 の判断のうち、実物に照らして変わらなかったもの**

- **構造化した再現規則（cron 式を採らない）**: OpenClaw も「Cron jobs」を
  持つが、記法は確認できていない。いずれにせよ rev2 の立場
  （「後から足せるが外せない」）は変わらない。**判断を変える条件**は
  「OpenClaw と設定ファイル互換や取り込みをやりたい」と決まったとき
- **トレイ常駐が上位の解**: OpenClaw も OS の service manager に常駐を
  任せており、**予定の発火そのものを OS へ出していない**。この形は一致

**rev2 の書き方が不正確だったもの（Notes 8 を訂正）**

「OS のタスクスケジューラ案は不要になった」と書いたが、これは雑だった。
OpenClaw は Windows で **Scheduled Task を使っている** — ただし
**常駐の起動**にであって、**個々の予定の発火**にではない。私が棄却したのは
後者（予定 1 件ずつを OS へ登録する案）で、それは今も棄却で正しい。
前者はトレイ常駐を実現する**手段の候補として生きている**（自動起動）。
**層が違うものを同じ名前で棄却していた。**

**Notes 11 の格上げ（推測 → 実物で裏が取れた）**

「無人運用では出力チャネルが要る」は思考実験ではなかった。OpenClaw の答えは
**25 以上のメッセージチャネル**で、これは「誰も画面を見ていない時間に
どうやって人へ届けるか」への構造的な回答である。
つまり要望の「鐘」は装飾ではなく、**その問題の最小の実例**だった。
Concordia が取るべき順序は、安い側から:

1. **デスクトップ通知**（Tauri のプラグイン 1 つ。今日の延長線）
2. **1 チャネルだけ**（例えば Discord か Slack。既存の MCP で足りる可能性）
3. 25 チャネル相当の抽象 — **やらない**。それは別の製品の形

**P4 の選択肢 3（汎用コマンド実行）についても示唆があった。** OpenClaw は
コマンド実行を禁止せず **Docker / SSH のサンドボックスで隔離**している。
つまり「必要な能力だが、隔離が要る」という扱い。本 Spec で汎用実行を
採らない判断は変わらないが、**将来どうしても要るなら、禁止を解くのではなく
隔離を用意する**のが先例に沿った道になる（作業フォルダの
`canonicalize` + 前方一致は、その最も安価な版だと言える）。
