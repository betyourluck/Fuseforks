## Goal

**OpenAI の `/v1/responses` を 5 本目のワイヤ `Provider::OpenAiResponses` として入れる。**
`/v1/chat/completions` では原理的に取れない 3 つを、同じ 1 本で回収する:

1. **思考の要約本文** — Spec 33 が「OpenAI 互換だけは数しか取れない」として
   ここへ引き渡した項（`33_thinking-summary.md` D1）
2. **web 検索** — 一般の gpt-5 系の `web_search` は Responses 専用。
   `/v1/chat/completions` で検索するには専用モデル（`gpt-5-search-api`）が要り、
   旧 `gpt-4o-search-preview` 系は 2026-07-23 に停止済み（一次資料で確認済み。
   CLAUDE.md「OpenAI 互換のパラメータ差の吸収」の節）
3. **`failures.md` #77 の代償の解消** — いま **gpt-5 系はツールを持つ限り
   思考を殺されている**（`reasoning_effort(model, effort, sends_function_tools)` が
   `"none"` を強制する）。推論モデルの推論を殺したまま使っており、
   **400 の本文自身が逃げ道として `/v1/responses` を名指ししている**

**「Thinking の受け取り」の名前で見積もると必ず外れる**（Spec 32 の引き渡し文）。
実質は `Provider::OpenAiResponses` の新設で、**規模は Spec 31 P1 と同等以上**。

**この Spec が v0.2.0 の最後のワイヤ作業**になる。残るは多モーダルと公表。

### **未測定 — ここがこの Spec の最大のリスク**

**この村から OpenAI の `/v1/responses` へ 1 発も投げていない。**
以下は私（実装者）の手元の理解であって、**観測ではない**。しかも
**この村が使っているモデル ID（`gpt-5.6-sol` / `terra` / `luna`）は
すべて私の知識のカットオフより後**なので、当てにならない度合いが高い。

1. リクエストは `model` / `input` / `tools` / `include` / `max_output_tokens` /
   `temperature` / `reasoning: {effort, summary}` / `store`
2. **`store` の既定が真** — 応答がサーバー側に保持される
3. **要約は `reasoning.summary` を要求して初めて返る**。値は `"auto"` / `"detailed"`。
   **組織の本人確認が要るモデルがある**という記述を見た覚えがある
4. output item は `message` / `reasoning` / `function_call` / `web_search_call`
5. `usage` は xAI と同形（`input_tokens` / `output_tokens` /
   `input_tokens_details.cached_tokens` / `output_tokens_details.reasoning_tokens`）—
   **xAI がクローンした側**なので同形なのは当然だが、**その後どちらかが動いた可能性**がある

**Spec 31 は起票時の理解（Live Search はリクエスト・パラメータ）が
最初の probe の HTTP 410 で死んでいる。** 同じ形の誤りをここで踏みうるので、
**P0 は実装ではなく probe から始める**（D10）。

**この 5 点を確かめるまで P1 に入らない。** 特に 3 が偽（要約が返らない / 本人確認が
要る）なら、Goal の 3 本柱のうち 1 本が消えて Spec の採算が変わる。

## 決定（D）

### D1: 5 本目のワイヤ `Provider::OpenAiResponses`

`POST {base_url}/responses`。認証は `Authorization: Bearer`（互換・xAI と同じ）。
既定 base URL は **`https://api.openai.com/v1`** — **互換と同じ文字列**（D7）。

`Provider` は 4 → 5 値。**網羅 match はコンパイラが指す**が、
**ワイヤカード match は黙って吸う**（Spec 25 rev3 で数えた「指す 4 / 指さない 6」）。
P0 で `_ =>` の箇所を数え直して契約へ表で凍結する。

### D2: 共有の単位は**応答の型**であって encode/decode ではない

**最重要の査読点。** xAI の `/v1/responses` は OpenAI のクローンなので、
`wire::Xai*` 型をそのまま使える可能性が高い。一方 **encode は確実に分かれる**
（`store` / `reasoning` / `include` の値 / 検索ツールの名前が違う）。

**採る形**:

| 層 | 扱い |
|---|---|
| **応答の型 10 個**（`XaiResponse` / `XaiOutputItem` / `XaiContentPart` / `XaiAnnotation` / `XaiSummaryPart` / `XaiSearchAction` / `XaiIncompleteDetails` / `XaiUsage` / `XaiInputTokensDetails` / `XaiOutputTokensDetails`） | **共有**。`wire::Responses*` へ改名 |
| **要求の型 3 個**（`XaiRequest` / `XaiInputItem` / `XaiTool`） | ~~**共有 + 加算**~~ → **rev6 で訂正**（下記） |

#### rev6 の訂正: **要求のトップレベル構造体は共有できない**（2026-08-11。P1 の着手時）

**P0b の凍結が自分の中で割れていた** — `data_contract.yaml` の `Provider.paths` には
**「応答の型だけを共有する」**と書いたのに、この表は**要求の型 3 個も共有**と
書いていた。**P0b の同じコミットで矛盾を 2 箇所へ置いた**（Spec 20 D10 と同じ形 —
1 つの契約の中で両立しないことが並ぶ）。

**実装しようとして、共有できない理由が実在すると分かった**:

| 欄 | xAI | OpenAI |
|---|---|---|
| `include` | **`["no_inline_citations"]` を常送**（Spec 31 D1/D5 の骨格） | **送らない**（T1 — stateless では `encrypted_content` が既定で来る） |
| `reasoning` | 送らない（要約は既定で来る） | **4 欄を常送** |
| `temperature` | 送る | **送ると 400**（D11） |

**共有すると `include` で必ず割れる。** `XaiRequest.include` は
`Vec<&'static str>` で `skip_serializing_if` を持たないので、OpenAI へは
**`"include":[]` が飛ぶ**（未測定）。付ければ**xAI 側の golden が動く** —
**どちらへ倒しても、片方の凍結を壊してからでないと共有できない。**

**着地**:

| 層 | 扱い |
|---|---|
| **応答の型 10 個** | **共有**（`Responses*` へ改名）。**11/11 の実測が根拠** |
| **`XaiInputItem` / `XaiTool`** | **共有**（`ResponsesInputItem` / `ResponsesTool`）。`function_call` / `function_call_output` / flat な function tool は**両社で同じ形を実測している** |
| **トップレベルの要求構造体** | **分ける**。`XaiRequest` は名前ごと据え置き、`OpenAiResponsesRequest` を新設 |

**改名の射程が縮んだのが副産物** — `XaiRequest` を触らないので、
**Spec 31 の encode golden の型名が動かない**。

**一般化: 「同じエンドポイントだから同じ型」は、送る側では成立しない。**
応答は相手が決めるので同型になりうるが、**要求は自分が決めるので、
機能の選び方の差がそのまま欄の差になる**。**共有の可否は、
測った側（応答）と決めた側（要求）で別々に判断する。**
| encode / decode 本体 | **分ける**。`llm/openai_responses.rs` を新規 |

**判定を測定へ落とす** — P0 の probe の合格条件に
**「OpenAI の実応答 JSON が `wire::XaiResponse` に serde で通る」**を入れる。
通れば共有、通らなければ**差分を欄単位で数えてから**決める
（巨大ファイル分割の 6 箇条 1「計測してから切る」の適用。設計の議論を測定へ変える）。

**改名の代償を先に数える**: `Xai` を含む識別子は wire **13 個** +
`xai_responses.rs` の参照。**台帳側は `xai search:` の観測記録の文字列に触れない**
（計器の行名は D9 で据え置く）。改名しない選択肢もあるが、
**`XaiRequest` を OpenAI が使う形は、次に読む人が「なぜ xAI の型？」で必ず止まる。**

**反対案（査読で聞きたい）**: **707 行**を丸ごと複製して独立させる。
利点は社ごとの変更が干渉しないこと、欠点は **#88 / #96 と同じ「射程だけが違う」
バグの温床**（片方だけ直す形が生まれる）。私は共有側を推すが、

### D3【P0a で確定】: `store: false` を常送する。**xAI も寄せる**

**P0a の結果**: 分岐表の 1 行目（望む形）で決着した — **`store:false` で
`summary` も関数往復も検索も壊れない**（条件 6）。さらに **xAI も `store:false` を

**非対称そのものが消える**（`PRIVACY.md` へ書き分ける必要が無くなった）。

**xAI 側の修正は本 Spec でやる**（2026-08-11 利用者裁定 —「この際だから
本 Spec でまとめてやろう」）。**触るのは Spec 31 のコード**（`wire::XaiRequest` へ
`store` 欄を足し、`xai_responses::encode` が `false` を常送する）。

- **P1 に入れる**。`encode` の golden が 1 本動くので、**Spec 31 の golden を
  更新する**（`skip_serializing_if` を付けずに常送するため。**付けると
  「送っている」ことがワイヤ形の凍結から読めなくなる** — この欄は
  プライバシーの主張を支える側なので、**出力に現れるほうが正しい**）
- **回帰で留める** — 「xAI の要求に `"store":false` が入る」を単体で凍結する。
  **親切心で `Option` へ戻すと、既定（保持する）へ黙って落ちる**
- **`PRIVACY.md` は本 Spec では触らない。** 保持しない設定で送ることは
  **`PRIVACY.md:101` の記述（各提供事業者のポリシーに従う）と矛盾しない** —
  あの文は「相手がどう扱うか」の話で、こちらが何を要求するかとは別。
  **書くとすれば P4 で「Responses 系は保持しない設定で送る」の 1 行**だが、
  **書けるのは 2 ワイヤとも寄せた後**（片方だけの状態で書くと嘘になる）

以下は rev2 の記述をそのまま残す（判断の経緯として）。

**rev1 は決定として書いていた。査読の指摘で仮決定へ降ろす** — 同じ D の中で
「常送する」と「副作用を P0 で測る」が同居しており、**測る前に決めていた**。
`Provider` を 5 値にする決定（D1）は probe が全滅しても形が変わらないが、
**`store` は probe の結果で反転しうる**ので、同じ確度で書いてはいけない。

**仮決定の中身**: `store: false` を常送し、**`include` は送らない**（T1 —
stateless では `encrypted_content` が既定で返り、`include` は互換受理にすぎない）。

- **`previous_response_id` は使わない**（これは**確定**。probe の結果で動かない）。
  使うとサーバー側に会話状態が生まれ**真実が 2 つになる** — Spec 12 rev2 が
  `JSONL + index.json` を捨てて redb 1 ファイルへ寄せたのと同型。この村の履歴の正は
  `sessions.redb` で、滑る窓 8 往復も可変文脈の畳み（#45）も送信側で組み立てている。
  **査読が引いた公式の推奨「`previous_response_id` で最短の stateful 統合を」は
  採らない** — 推奨されているのは *stateful* な統合で、この村は意図して stateless
- **分岐を先に書く**（査読の処方どおり）。P0b で次のどれかへ倒す:

| probe の結果 | 倒す先 |
|---|---|
| `store:false` で `summary` が取れる | **仮決定のまま確定**（望む形） |
| `store:false` だと `summary` が取れない | **Goal 1 と `store` が衝突**。`store:true` を許容し、**`PRIVACY.md` へ「Responses ワイヤを選んだ村は接続先に応答が保持される」を明記**して利用者の判断材料にする（黙って真にしない） |

### D3 の派生で見つけた既存の穴（**Spec 34 の外で効く**）

**`wire::XaiRequest` に `store` 欄が無い**（起票時に実測）。欄は
`model` / `input` / `tools` / `include` / `max_output_tokens` / `temperature` /
`tool_choice` の 7 つで、**`store` は 1 度も送っていない = xAI 側の既定に委ねている**。
その既定が何かは **Spec 31 で測っていない**。

**`PRIVACY.md` は破れていない** — 該当箇所は
「送信された情報の取り扱いは、各提供事業者のプライバシーポリシーに従います」
（`PRIVACY.md:101`）で、**保持しないとは書いていない**。だから査読の
「PRIVACY.md が Provider ごとに変わる」は**現状では成立しない**。

**成立するのは別の形**: OpenAI だけ `store:false` を送ると、
**同じ `/responses` の 2 本で保持の扱いが非対称になり、その差がどこにも出ない**。
処方は 2 つのどちらかで、**P0b で決める**:

- (a) **xAI も `store:false` へ寄せる**（`XaiRequest` へ加算。D2 の共有と同じ 1 手で済む）
- (b) 非対称を**残して `PRIVACY.md` に書く**（「Responses ワイヤのうち OpenAI は
  保持しない設定で送る」）

**(a) を推す** — 説明が要る非対称は、説明を書くより消すほうが安い。
ただし **xAI に `store` があるかは未測定**なので、送って 400 にならないかを
P0 の probe に足す（**xAI へ 1 発余分に投げる**）。

### D4: `reasoning` の送り方が変わり、**#77 の `none` 強制はこのワイヤへ写さない**

`/v1/chat/completions` の トップレベル `reasoning_effort: "low"` は、
Responses では **`reasoning` オブジェクト**になる。**rev1 は 2 欄と書いたが、
査読の T4 で 4 欄**（`effort` / `summary` / `mode` / `context`）:

| 欄 | 値 | rev2 の方針 |
|---|---|---|
| 欄 | 値 | **P0a 実測** | rev3 の方針 |
|---|---|---|---|
| `effort` | `none`〜`max`（モデル依存） | `low` が 200 | canonical の `Effort` を送る。**丸めはここだけに適用** |
| `summary` | `auto` / `concise` / `detailed` | **`auto` = 要約 0 字 / `detailed` = 522 字。組織検証の 400 は出ない** | **`detailed` を常送**（下記） |
| `mode` | `standard` / `pro` | **両方 200。`pro` は input +1,538 の固定費** | **固有スキルのトグル。既定 OFF・ON のとき `pro` を送る**（下記） |
| `context` | `all_turns` / `current_turn` | `current_turn` が 200 | **`current_turn` を明示送信**（下記） |

**`summary` は `detailed` を送る（未決 (b) 決着）。**
**`auto` は要約を 1 字も返さない** — 同じ問い・同じ `effort` で
`auto` が `summary_text_chars=[]`、`detailed` が `[522]`。
**`auto` を選ぶと「送っているのに何も出ない」**という、
最も診断しにくい形になる（`reasoning_tokens` は 176 出ているので払ってはいる）。

**xAI で `summary:"auto"` が効果ゼロだったのと同じ罠が、逆向きで出た** —
あちらは**既定で来るので `auto` が無意味**、こちらは**`auto` では来ないので
`detailed` が要る**。**同じ欄名・同じ値・逆の理由**。
**一般化: 隣のワイヤで効かなかった値は、次のワイヤでも効かないとは限らない。
効かなかった「理由」まで写して初めて予測になる。**

#### `mode: pro` は固有スキルのトグルにする（2026-08-11 利用者裁定。未決 (d) 決着）

**器の 3 形目は要らなかった。** rev2 は「3 値の選択肢だから器が増える」と書いたが、
**P0a で `mode` を送らない発と `mode:"standard"` の発が `input_tokens=20` で
完全に一致した** — **省略 ≡ standard**。よって
**ON で `"pro"` を送り、OFF で欄ごと省く**の 2 状態で足り、
**既存のトグルの形にそのまま乗る**（`xai_web_search` と同じ）。

- **欄名は `openai_reasoning_pro`**（ベンダー接頭辞は `openai_web_search` と同じ理由）。
  判定は **AND 述語 1 実装** `openai_reasoning_pro_active()` =
  トグル AND `effective_provider() == OpenAiResponses`（D5 と同型）
- **既定は OFF。** 効きは収穫逓減で、**Sol では +2.8 ポイント**しかない。
  「常に良い」ものではないので既定で払わせない
- **注記に 2 つの数字を書く** — **精度**（Terra 23.3 → 28.5）と
  **入力の固定費 +1,538**。**片方だけだと判断できない**。
  Spec 31 が検索のコストを画面へ書いた位置と同じ（押す判断をする場所で言う）
- **`mode` は `effort` の隣に置く**（同じ `reasoning` の欄で、独立の軸）。
  **「固有スキル」の見出しの下に置くのは、これが OpenAI にしか無い軸だから** —
  `effort` は 4 社が持つので既存の位置のまま動かさない
- **Ultra は本 Spec の範囲外**（Notes 10）

**`context` は D3 と噛み合っていない。** 既定の `all_turns` は「前ターンの思考も見る」
設定だが、この村は **`previous_response_id` を持たず**（D3）、**思考を履歴へ積まない**
（Spec 33 D2-a・型で閉じている）。**参照する先が存在しない状態で `all_turns` を
既定のまま送ることになる。**

- **明示して `current_turn` を送る**のが rev2 の方針。**送らないと既定が効く**ので、
  「送っていない = 何も要求していない」にはならない — **#77 の教訓
  （省略は「無効」ではなく「サーバ既定を採る」）がそのまま当たる 2 例目**
- **`all_turns` を活かす道は 2 つとも高い** — `previous_response_id`（真実が 2 つ
  になる。D3 で確定拒否）か、**`encrypted_content` を毎ターン全量リプレイする**
  （Spec 33 D2-a の「履歴へ積まない」を覆し、滑る窓 8 往復ぶんの固定費が乗る）。
  **どちらも本 Spec の範囲外**。`all_turns` が効かないことは**代償として明記する**
- **`mode` と `context` は「丸めだけ共有」の網の外**。rev1 は
  `openai_compat::reasoning_effort` からの分岐だけを見ており、
  **新しい欄が増える可能性を数えていなかった**

**`openai_compat::reasoning_effort` をそのまま呼ばない。** あの関数の先頭は

```rust
if model.starts_with("gpt-5") {
    return sends_function_tools.then_some("none");
}
```

で、**併用できないという `/v1/chat/completions` 固有の制約**への対処。
**このワイヤはその制約が無いことが移る理由そのもの**なので、写すと
**Goal の 3 本目を自分で潰す**（思考を殺したまま新しいワイヤへ移る）。

- **共有するのは丸め**（`xhigh` / `max` → `high` 等）**だけ**。
  制約の吸収は共有しない。**述語の境界は関数ではなく「何を不変に保っているか」**
  （Spec 23 が `validate_icon` をパラメータ化しなかったのと同じ判断）
- **負の対照をテストで留める** — `gpt-5` + tools ありの encode で

- **`summary` を要求しても返らない回がある**のは既知（Spec 33 — Anthropic の
  ツール併用回で `thinking_tokens=34` に対し要約 0 字）。**実運用の大半が後者**なので、

### D8: 画像はこのワイヤでも送らない（Spec 23 D8 据え置き）

多モーダルは次の Spec。ここで OpenAI だけ入れると

**ただし据え置きの代償を Notes ではなく本文に書く（新規の観察）** —
**`note_dropped_attachment` はワイヤの能力を見ていない。**
実装を数えると、あの関数が発火するのは `delegation.rs` の 2 箇所と
`turn.rs` の 1 箇所で、引数は**受信に添付があったか**だけ。
**「このワイヤは画像を送れない」という理由で断る経路は 1 本も無い。**

つまり **gpt-5 系の個体を Responses ワイヤへ切り替えると、画像が黙って落ちる**。
**この穴は Gemini と xAI に既にある**（Spec 05 / Spec 31 から）ので本 Spec の
退行ではないが、**OpenAI で 3 例目になると「ネイティブを選ぶと画像が消える」が
既定の体験になる**。

**rev1 はここで #47 / #72 を引いて「機構を足さない」と書いた。引用が誤りだったので
rev2 で差し替える。** 査読も同じ箇所を突いたが、**査読の読みも違っていた**ので
両方を書く:

- **査読の読み**「#47/#72 の規律は *2 回の観測で機構を足す* で、3 例目なら足すのが
  規律通り」は**規律の反転**。原文は「**2 回の観測で足すと効いているか分からない
  機構が増える**」で、主語は*足すこと*の害。処方は「**頻度を見てから決める**」
- **rev1 の引用も誤り。こちらのほうが重い。** #47（本文へ漏れた XML）と
  #72（本文の無い応答）は**稀で再現しない事象**についての規律で、
  頻度を見る意味があるのは**頻度が未知だから**。**画像が落ちるのは
  ネイティブ経路を選べば 100% 起きる構造の穴**で、**頻度は既に 1.0**。
  **頻度が確定している事象へ頻度ゲートの規律を当てたのが rev1 の誤り**

**それでも本 Spec では足さない。根拠を差し替える**:

**足す機構は「どのワイヤが画像を運ぶか」という述語**で、**その集合を書き換えるのが
多モーダルの Spec そのもの**（Spec 23 D8 を覆す）。ここで先に書くと、
**次の Spec が最初にやることがこの述語の作り直し**になる。
**Spec 24 D2 で `kind` 欄を先に作らなかったのと同じ判断** — 使う前に一般化しない。

**代わりに 2 つやる**（どちらも述語を作らずに済む）:
(a) モデル登録の画面に注記を出す（プロトコルを切り替える**その場所**で言う。
Spec 31 が検索のコスト注記を画面へ入れたのと同じ位置）
(b) **実機で 1 度踏んで `failures.md` へ起票する**（検収 7）—
**3 例目であることを記録に残す**。多モーダルの Spec は
**その 3 件を材料に述語を設計できる**。

**一般化（`failures.md` の候補）: 頻度ゲートの規律は、頻度が未知の事象にしか
当たらない。100% 起きる構造の穴へ「頻度を見てから」と書くのは、
先送りに規律の名前を借りているだけ。**

### D9: 計器の行名は engine ごとに分ける

`xai search:` は**動かさない** — Spec 31 P5 の観測記録
（`calls=15 names=custom_tool_call:15 sources=74 queries=15`）が
その文字列を指しており、統一すると**過去の観測が引けなくなる**
（改名で `concordia.log` の行を書き換えなかったのと同じ判断・Spec 30）。

新設は **`openai search: calls=N actions=search:N,open_page:N,find_in_page:N
sources=N queries=N`**（**rev1 は `actions=` を持たなかった。査読 T5 で追加**）。

- **`web_search_call.action` は 3 種ある** — `search` / `open_page` /
  `find_in_page`。**後 2 者は推論モデルで出て、検索語を持たない**。
  `xai_responses::search_query` は `action.query` と `input` の 2 形しか読まず、
  **そのまま写すと `open_page` の周で `queries` が黙って減る**
- **`queries < calls` は OpenAI では正常。ここが xAI と決定的に違う。**
  Spec 31 P5 は **`queries == calls == 15`** を「15 回の検索がすべて異なる語だった」
  と読んで合格にした。**同じ期待を写すと、ページを開いただけの周がある OpenAI は
  常に不合格に見える**。だから **`actions=` を並べて内訳で読む** —
  `queries` は `search` の回数と突き合わせる（`open_page` / `find_in_page` は
  分母に入れない）
- **一般化: 前のワイヤで合格条件にした等式は、次のワイヤでは
  「壊れている」の誤検知になりうる。** 等式を写す前に、両辺の定義が
  同じかを数える（Spec 31 の `queries` は「検索語」、OpenAI の `calls` は
  「検索**呼び出し**」で、後者は検索以外を含む）
- **ticks は足さない** — `cost_in_usd_ticks` は xAI の欄。OpenAI にあるかは未測定で、
  **無い欄を `-` で埋める計器は「測ったが無かった」と「見ていない」を畳む**
- **`dropped content blocks:` は共通のまま**（#72 の受け皿。engine を問わない）
- **検収の順序は Spec 31 に倣う** — 否定の観測（行が出ない）の前に
  肯定の対照を取る（#90）
