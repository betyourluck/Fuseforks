## Goal

広場ログの切れた抜粋の**全文へ、相手のターンを消費せずに到達できる**ようにする。
抜粋行に発話 ID を付け、ID を指定して全文を読む読み取り専用ツールを 1 本足す。

起点は利用者の方向づけ（2026-08-04）—「push で全部渡すのをやめ、pull にする。
続きが読みたいものだけエージェントが判断して読める」。起票の前提として
arXiv 2607.26637（Filesystem-Based Memory for LLM Agents）を読んだ（2026-08-06。
Notes 1）。

**品質は約束しない。** 論文の RQ2 は「どの記憶形状も正解率では常勝しない。
整理の確実なリターンは検索コストだけ」— 本 Spec の約束もコストに限る:

- **現行の全文到達経路は `ask` ただ 1 本**で、相手の 1 ターンを丸ごと消費する
  （相手のプロンプト全体の再送 + 生成。数万トークン規模）。しかも相手は
  自分の発言を要約し直すので、**返ってくるのは全文ではなく再話**
- pull は自分のツールループ 1 周で済む（LLM 呼び出しゼロ・キャッシュ 99% 下で
  再送の大半は 0.1×）。返るのは**発話そのもの**

**変えないもの・約束の範囲**:

- ユーザー発話は広場ログに載せない（凍結。pull でも読めない — D4）
- 抜粋の既定 200 字 × 12 件は本 Spec では動かさない（D6。観測してから）
- **原文性が構造で成立するのは `ROOM_LOG_READ_MAX_CHARS`（D3）まで**。
  それを超える発話は打ち切られ、フォールバックは従来どおり `ask` —
  そこでは相手のターン消費と再話に戻る。**S1 の約束は上限内に限る**
  （rev2: 査読 C2。上限超でも Goal が立つように書くと S1 が嘘になる）
- **読めるのはリング在中の発話だけ**（上限 5,000 件。D7）。`session_store` の
  永続ログからは読まない

## 現況（実測 2026-08-06）

- 抜粋の合成は `orchestrator.rs` の `compose_room_log`。**この関数は今
  3 つの責務を持つ** — 可視述語（`from_agent && !is_mine`）+ 窓切り
  （`room_log_window` = 12 件）+ 切り詰め（`room_log_excerpt_chars` = 200 字）。
  本 Spec が共有するのは**述語だけ**（rev2: 査読 C3）
- 切った行には `（全 N 字）`、切った行が 1 件でもあれば notice に
  「**全文が要るなら、その発言をした相手へ `ask`**」— **この文と、契約
  `room_log` の「広場ログは読み直す経路を持たない」が、本 Spec で嘘になる**
  （P4 で回収。data_contract:1970 とコード内コメント orchestrator.rs:4970 の 2 箇所）
- 原本は `Shared.log`（in-memory リング 5,000）。`session_store` にも永続化
  されるが、**そちらは可視述語を通す前の生ログ**で、本 Spec の読み口ではない
  （D7）。**新しい器は要らない**
- `AgentMessage` は `id: String`（UUID v4）を持つ（model.rs:650）。
  発話を指す取っ手は最初から存在する
- `ask_*` / `transfer_to_*` は `AgentTool` ではなく **orchestrator 側で合成される**
  （`Handoffs::ask_specs`）。`ToolContext` は意図的に world / shared を運ばない
  （tool.rs:39 「ツール自身に world を引かせない」）。**`Shared.log` を読む
  ツールは同じ棚に置くしかない** — `rag_sources` で踏んだ「運ぶ経路が無い」
  （三例目）を、今回は起票時に数えた
- `hears_room_log`（Spec 03 の opt-out）は `AgentSpec` の欄。false の個体は
  `compose_room_log` がスキップされ、抜粋自体が届かない
- **`RepeatGuard` はターン内でだけ数える**（orchestrator.rs:3583 のコメント
  「ターンを跨ぐ繰り返しは別の問題」+ guard はターン関数のローカル変数）。
  ターンを跨いだ同一 ID の再読は最初から止まらない（Notes 6）

## 設計の核

**新ツール `room_log`（orchestrator 合成・読み取り専用・引数は `id` 1 つ）。**

```text
抜粋行:  - [a1b2c3d4] ザリ → ジェミー: 調査の結果ですが…（全 1,824 字）
呼び出し: room_log { id: "a1b2c3d4" }
返答:    【送り手: ザリ → ジェミー】に続けて本文全文
```

- **ID は UUID 文字列の先頭 8 字**。行頭に `[a1b2c3d4]` で置く。
  **衝突は表示時に解消する**（rev2: 査読 C1、git short hash と同じ方式）—
  `compose_room_log` が、その時点の**可視集合内**で 8 字前方一致が衝突する行
  だけ 12 字 → 16 字 → 全長へ自動伸長して表示する。エージェントは
  **表示された通りに打てば一意に決まる**。ツール側の解決は前方一致のまま
- ツール側の解決は**可視述語を通した後の**リング全体への前方一致。
  一意でなければ拒否（D4）。表示時解消の後に残る曖昧は「合成後に前置が
  一致する新しい発話が到着した」場合だけで、確率は 1 発話あたり 2^-32。
  観測はする（D5 の `ambiguous`）が、機構は足さない
- **共有するのは可視述語だけ**（rev2: 査読 C3）。
  `is_visible_in_room_log(agent_id, &AgentMessage) -> bool` を
  `compose_room_log` から切り出し、抜粋の合成とツールの解決が同じ関数を呼ぶ。
  **窓切りと切り詰めは共有しない**（compose 側に残る）— 窓まで共有すると
  「窓の外でも読める」（下記）が実装で潰れる。
  「抜粋に載る条件」と「読める条件」は同じ問いの裏表 — Spec 20 の
  `prune_settled` が `decide` を使い回したのと同じ理由で、別の述語を置くと
  答えがずれる。これにより**ユーザー発話は ID を直接知っていても読めない**
  （凍結の維持が注意書きではなく述語で成立する）
- **窓の外でも読める。ただし上限はリング在中（5,000 件）**（rev2: 査読 S2 →
  D7）。窓（12 件）は抜粋の量の上限であって可視性の境界ではない
  （契約の既存文言「情報が消えるのではなく時間軸だけが落ちる」と同じ側）。
  実効的には ID を知る経路が抜粋しかないので、読めるのはほぼ窓内 +
  ツールループ中に窓から押し出された直後の発話
- **提示条件は `hears_room_log == true` だけ**（静的）。抜粋が届かない個体に
  全文読みだけ与えても ID を知る経路が無い。既存フラグに寄生することで
  **同じ意図の 2 つ目のスイッチを作らない**（Spec 18 D13 の教訓）。
  `enabledTools` の対象外側に住む（`ask_*` / `rag` と同じ棚 —
  `BUNDLED_TOOL_NAMES` にも `DEFAULT_ENABLED_TOOLS` にも入れない）。
  ログが空かどうかで提示を揺らさない（提示は静的・状態は動的）
- **原本には一切書かない**。管理エージェントも要約も再編成も置かない —
  論文の condense バグ（保存指示なしの再編成が詳細を無言で圧縮する）と
  分類契約の侵食（RQ4）は、**書く機構が存在しなければ構造的に起きない**。
  原本はハーネスが決定的に書く append-only のリングのまま

## 決めること

- **D1 ツール名 = `room_log`**。プロンプトの見出し「この場で交わされていた会話」を
  引くツールであることが名前から追える。動詞を付けない（op を持たない単機能。
  将来 `list`（遡り）が要るなら op の閉じた列挙へ改める余地はあるが、今は
  引数 `id` 1 つのフラットなスキーマが最小）
- **D2 ID を出すのは切れた行だけ**。全文が既に見えている行に取っ手は要らず、
  固定費の増分（1 行 +11 字）を切れた行に限る。「ID がある = 続きがある」が
  行の形だけで読める副産物もある。**衝突時の伸長（設計の核）も切れた行の
  集合内でだけ起きる**
- **D3 返答の上限は `ROOM_LOG_READ_MAX_CHARS`（案: 20,000 字）**。超えたら
  打ち切りの 3 点セット（何が起きたか + **母数 = 全 N 字中 M 字まで表示** +
  次の手）。**母数は打ち切り返答の必須要素として P0 で凍結する**（rev2: 査読）。
  打ち切り時の次の手は「発言した相手へ `ask`」— そこでは原文性と
  相手ターン非消費の両方が失われることを Goal の「約束の範囲」に明記済み
  （rev2: 査読 C2）
- **D4 見つからない・可視でない・曖昧、のモデル向け文面**:
  - 可視でない発話は**「見つからない」と同じ文面**で返す。存在を教えると
    「宛先外はメッセージがあったことすら知らないべき」（凍結）が
    エラーメッセージ経由で破れる
  - 曖昧（前方一致が複数）は候補を**列挙せず**、「抜粋に表示されている ID を
    そのまま使う」よう求める（rev2: 査読 C1 — 表示時解消により、表示された
    ID は合成時点で必ず一意。「桁を増やせ」は 8 字しか知らない相手に
    増やしようがないため撤回）
- **D5 計器を 1 行**: `room_log read: agent=… id=…
  outcome=ok|truncated|not_found|ambiguous chars=N`（rev2: 査読 —
  `truncated` を独立させ、D6 の観測で「上限で足りない率」を取れるようにする。
  `ambiguous` の頻度は ID 桁数の将来判断の材料）。`grep include:` /
  `run decision:` と同じ形で、呼ばれたときだけ増える。
  `concordia.log` 側では `not_found` と `not_visible` を区別してよい（人向け）。
  **本文はログへ書かない**（#71 — モデル出力を運ぶ計器は秘密の転送経路になる）
- **D6 抜粋の既定（200 字 × 12 件）は本 Spec では動かさない**。
  固定費の削減は pull の使用が実機で観測されてからの別判断（D5 の計器が材料）。
  論文の RQ2/RQ3 は「弱い検索エージェントには蒸留が要る・検索者の能力が
  正解率に直接効く」— 村は claude-opus-5 と gemini-3.5-flash-lite が混在して
  おり、**読みに行く判断を弱いモデルがどれだけ実行するか**を測らずに抜粋を
  絞ると、コスト削減と引き換えに読み落としを配ることになる
- **D7 読み口は `Shared.log` のみ。リングから溢れた発話は `not_found`**
  （rev2: 査読 S2）。`session_store` から読む経路は作らない — あちらは
  可視述語を通す前の生ログで、読み口を 2 つにすると述語の 1 実装共有が
  破れる。過去セッションへの遡りが要望として出たら別 Spec（それは
  「広場ログの続きを読む」ではなく「記録を検索する」で、射程が違う）

## Stories

- S1 サーヴァントが、広場ログの切れた抜粋の全文（`ROOM_LOG_READ_MAX_CHARS`
  以内）を、発言者に尋ねることなくその場で読める（発言者のターンとトークンを
  消費しない）
- S2 ユーザーが特定の相手にだけ話した内容は、ID を知っていても他の個体からは
  読めない（既存の凍結が pull 経路でも破れない）
- S3 `hears_room_log = false` の個体には `room_log` ツールが提示されない
  （opt-out は抜粋と読み取りの両方に効く）
- S4 利用者が `concordia.log` の 1 行から「誰が・何を・どれだけ読んだか」と
  「上限・曖昧がどれだけ起きたか」を読める（D6 と ID 桁数の判断材料が貯まる）

## Notes

1. **論文（arXiv 2607.26637）から採ったもの / 捨てたもの。**
   採った 4 点: 目的をコストに絞る（RQ2 — 整理は検索コストを概ね半減させるが、
   どのエージェントも整理を正解率向上に変換できていない）/ 原本は append-only
   （Preservation Rule — 再編成の指示は情報を落とす）/ 整理エージェントを
   置かない（RQ4 — 分類契約の遵守は最強の管理エージェント以外は成長と共に
   侵食される）/ 最小の push を残す（RQ2 スキル所見 — 弱い実行者には蒸留が勝つ。
   抜粋 = 蒸留は消さない）。
   捨てた 1 点: **ファイルシステムを器にすること**。論文がファイルを推す理由
   （inspectable / portable / 既存ツールで触れる）のうちこの村で効くのは
   「既存ツールで触れる」だけで、それは可視性の凍結と正面衝突する —
   ファイルに書けば `file read` で誰でも読め、個体別に可視範囲のファイルを
   書けば N 重書き込みになる。**置き場を決めるのは器ではなく述語**（可視性
   フィルタ）で、述語を通せる器は既にある（`Shared.log`）。機構を足す前に
   既存の機構で書けるか確かめる、の適用でもある
2. **`ask` による全文取得が「再話」になる問題は、pull でだけ解ける。**
   相手に尋ねると相手のモデルが要約し直すので、原文との一致は保証されない。
   `room_log` はリングの `content` をそのまま返すので、原文性が構造で成立する
   （**上限まで** — D3。上限超のフォールバックは `ask` なので、そこでは
   この利点ごと従来経路に戻る）
3. **コストの向き。** 固定費の増分は ID 前置のみ（切れた行 × 11 字。
   窓が全部切れても 132 字 + 衝突時の伸長ぶん）。変動費は読んだときだけ
   （全文 chars ＋ ツールループ 1 周。キャッシュ 99% 下で再送の大半は 0.1×）。
   `ask` 経由の従来コスト（相手のプロンプト全体再送 + 生成）との差が
   本 Spec の取り分
4. **課題 2（`room_log_excerpt_chars` を上げる）はこの Spec で消える。**
   上げたい動機は「全文が読めない」で、pull がその経路を安く提供する。
   固定費を増やす方向の変更は不要になる
5. **課題 3（ユーザー発話を広場ログに含める）は不採用のまま**。
   本 Spec は経路を足すが、可視述語は 1 字も変えない
6. **rev1 査読の Should Fix「RepeatGuard と S1 の衝突」は、実測で前提を
   訂正して採用した**（Spec 21 rev2 Notes 6 と同じ形）。査読は「ターンを
   跨いだ正当な再読が 3 回目で止まる」ことを懸念したが、`RepeatGuard` は
   **ターン関数のローカル変数**で、コメントに「ターン内でだけ数える —
   ターンを跨ぐ繰り返しは別の問題」と明記されている（orchestrator.rs:3583-3586）。

   以後の全周回で再送される）。**除外や限定の機構は足さない** — 既存の挙動が
   そのまま正しい
