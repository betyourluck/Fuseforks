# Spec: スケジュールの前判定と前後処理 — 変化があったときだけトークンを払う

**ID**: 28
**Date**: 2026-08-08
**Status**: **rev3 承認**（2026-08-08。`village_id` を生やす裁定を利用者が承認。
実装前に固定する細部 3 点を追記済み — 実装待ち）
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

**定期発火の LLM トークンを、変化があったときだけ払う形にする。**

起点は利用者（2026-08-08）—「最初は LLM を通さずにできることはトークン節約のため
なるべく使わないで判断してから、真だったら LLM に伝える。たとえば投稿が増えたとか、
サーバーの監視とか」。公開までのマイルストーン 2 + 4 の着地形。

現状の予定（Spec 07）は時刻が来ると**無条件に**チャットを配送する。監視の用途では
「変化が無い」が大半なのに、確かめる仕事そのものを LLM にやらせるとトークンが
毎回出る。5 分ごとの監視なら 1 日 288 回 — 変化が 1 回なら **287 回ぶんが無駄**。

足すのは 3 部品。**すべて予定ごとの設定で、どれも既定は従来どおり**:

1. **前判定（probe）** — 発火時にコマンドを実行し、stdout の合図が設定値と
   一致したときだけチャットを配送する。判定はプロセス実行のみで LLM を通さない
2. **セッション選択** — 配送を新規チャットで始めるか、いまのセッションで続けるか
3. **完了後の自動要約** — 発火した依頼の因果が終わったら、参加した個体の履歴を
   畳む（Anthropic の dreaming 相当。次の発火までの空き時間 = 完了直後）

**外部トリガー API（外から叩いて発火させる口）は本 Spec の対象外**（利用者判断
2026-08-08 —「トリガーは今回はいい。どちらかというとスケジュールでやったほうが楽」）。
経路自体は Spec 25 の `ask_concordia` で既に開通している。監視の主導権を
Concordia 側が持つ（ポーリング）形は、外部に常駐プログラムを書かせる形より導入が軽い。

## Stories

- S1 5 分ごとに監視スクリプトを走らせ、**異常のときだけ**サーヴァントに調査を
  依頼する。正常な回はトークンを 1 つも払わない。**スクリプトが異常を
  `exit 1` で表していても発火する**（監視の慣習に沿う）
- S2 「投稿が増えた」をスクリプトが検知したとき、**何が増えたか（スクリプトの
  出力）が依頼文に含まれて届く** — サーヴァントが同じ情報を取りに行く周回が消える
- S3 定期の依頼を**新規チャットで始めて**、人が進めている会話の文脈を混ぜない
- S4 同じセッションで続ける予定でも、**完了後の自動要約**で次回の送信ログが縮む
- S5 **既存の予定は 1 バイトも変わらず動く** — 読み・発火だけでなく、
  **保存もバイト等価**（probe 無し予定の直列化結果が改修前と一致。golden で固定）
- S6 **配られた村の probe は、この端末の人が承認するまで 1 回も走らない。**
  承認前に消化された due は失われ、**承認後の次の due から**走る（意図的 — D1。
  非消化のスキップにすると間隔系が毎 tick `unapproved` の行を出し続け、
  「due ごとに 1 行」の計器の性質が壊れる）

## 決定

### D1 前判定は `ScheduledTask` の欄。発火規則（`decide`）は触らない

`Recurrence` と `ScheduledTask::decide`（純関数・Spec 07 で凍結）には 1 ミリも
触れない。probe が挟まるのは `schedule_tick` の `Tick::Fire` 分岐
（`orchestrator.rs:2722`）で、**「発火する」と決まった後・配送の直前**。

**発火 1 件の判定列（上から順に評価。rev2 で表に固定）**:

| 段 | 条件 | 帰結 |
|---|---|---|
| 1 | 宛先が停止中 | **消化** + System 行（既存の挙動） |
| 2 | 宛先が飛行中（`in_flight` は**宛先個体単位** — `orchestrator.rs:2754`） | **スキップ**（消化しない・次 tick 再判定。既存の挙動） |
| 3 | **同じ予定の probe が走行中**（rev2・査読 8） | **スキップ**（消化しない・次 tick 再判定。段 2 と同じ倒し方） |
| 4 | probe があり**端末の承認が無い**（D10） | `outcome=unapproved`・**消化**（意図的 — S6）・ダイアログに承認導線 |
| 5 | probe 実行 → error / timeout | **消化**・配送しない・reason 付きログ（D8） |
| 6 | probe 実行 → 不一致 | **消化**・配送しない |
| 7 | probe 実行 → 一致（または probe 無し） | **配送候補**へ（配送の順序は D6） |

- **1 予定につき probe は同時 1 本**（査読 8）。`timeoutSecs` 上限 3600 秒 ×
  間隔 5 分の予定では probe が due をまたぎうる — 走行中の Fire は段 3 で
  消化せずスキップし、壁時計系は待つうちに猶予を超えれば `Consume` へ倒れる
  （宛先飛行中と同一の既存規則に乗る）。**プロセスが積み上がる経路を残さない**
- **消化の意味は変えない。1 つの due に判定は 1 回。** 不一致・失敗・未承認も
  `lastConsumedDueMs = due` を書く — 書かないと同じ due を毎 tick 再判定し、
  daily 17:00 の予定が一致するまで連続ポーリングに化ける
- 段の順序の帰結: **誰も起動していない村では probe のコマンドも走らない**（D5）/
  **スキップの回は probe も走らない**（実行してから捨てない + 実行回数が
  判定機会の回数と一致する）

### D2 判定は stdout の 1 行目のみ。exit code は判定に使わない

**利用者裁定**（2026-08-08）— 判定は stdout の完全一致。exit code 0 案は
「正常終了 = 発火」の重ね合わせが誤発火を生みやすいため採らない。

**rev1 の「exit 非 0 は判定不能 = 不発火」は撤回する**（査読 3）。監視の慣習は
異常を非 0 で表す（`echo CHANGED; exit 1`）ので、rev1 のままでは **S1 の主戦場で
永遠に発火しない**。「壊れたスクリプトの偶然の出力で課金しない」という動機は、
**`expect` との完全一致が既に守っている** — クラッシュ出力が合図と一字一句同じ
行になる壊れ方は、防ぐ対象として実在しない。**`allowNonZero` の欄は作らない**
（判定軸は stdout の 1 本に保つ。スイッチを増やすと「exit と stdout のどちらが
効いているか」を利用者が推理する羽目になる）。exit code は**計器にだけ載せる**
（D8 の `exit=N`）。

**裁定 2 つを重ねると分離が要る**（rev1 で導出・維持）。「stdout 完全一致」と
「stdout を依頼文に付記」（D3）は、そのままだと両立しない —
完全一致なら stdout は設定値そのものなので、付記しても情報が増えない。

> **判定は stdout の 1 行目（トリム後）と `expect` の完全一致。
> 依頼文へ付記されるのは 2 行目以降。**

**行の定義と正規化（rev2・査読 6。書かないと実装が割れる）**:

- 行区切りは `\n`。**行末の直前に `\r` があれば落とす**（`\r\n` を同じに扱う。
  Windows のスクリプトが主戦場なので `\r` を残すと一致が原理的に成立しない）
- **1 行目 = 最初の改行まで**。先頭が空行なら 1 行目は空文字であり、
  非空の `expect` とは一致しない — **合図は最初の行に書く**（UI の説明文に書く）
- **トリムは 1 行目のみ**（前後空白）。**2 行目以降は原文保持** —
  JSON を付記したいときにインデントが消えると壊れる
- `expect` は**トリムして比較し、空は読み込みで弾く**（`InvalidRecurrence` と
  同じ形 — UI で防ぐだけでは `schedules.json` の手編集で入る）
- 文字数は `chars().count()`（この村は `len()` の罠を査読で 2 回踏んでいる）

**取り込み上限（rev2・査読 5）**: stdout の取り込みは **65,536 字**で打ち切る。

- 打ち切り位置が **1 行目の中**（改行が一度も出ていない）なら
  **`outcome=error`（`reason=signal_truncated`）** — 切り詰められた 1 行目で
  照合すると誤判定するので、判定そのものを不成立にする
- 打ち切り位置が 2 行目以降なら判定は成立し、**付記側だけが切り詰め**られる（D3）

### D3 一致したら stdout の 2 行目以降を依頼文へ付記する

**利用者裁定**（2026-08-08）。付記しないと、サーヴァントが同じ情報を取りに行く
周回が発生してトークン節約の目的と逆行する。

本文の組み立て（既存の由来行の延長）:

```text
【定期実行: 毎週 木曜 17:00】
{message}

【前判定の出力】
{stdout の 2 行目以降（原文保持）}
```

- **付記の本文は 4,000 字まで**（`run.rs` の `STDERR_CHARS` と同じ桁）。
  超過は切って `（全 N 字）` を添える — 打ち切りを黙らせない
  （`compose_room_log` / #58 の規律）
- **注記の定義を固定する**（rev2・査読 12）: **`N` は切る前の元の字数**。
  注記そのものは 4,000 字の**外**（含めると本文の上限が注記の桁数で揺れる）。
  取り込み上限（D2）で既に切れていた場合、真の総数は分からないので
  **`（全 65,536 字以上）`** と書く — 知らない総数を確定値として書かない
- 全文が要る場面はスクリプト側がファイルへ書き、依頼文でパスを指せばよい
  （`file read` の既存経路）
- **これは外部由来の本文がプロンプトへ入る経路だが、新しい攻撃面ではない。**
  スクリプトを書くのは利用者自身（D10 で端末承認済み）で、サーヴァントが
  `run` / `MCP_DOCKER__fetch` で取る内容と同じ棚。ただしスクリプトが web を
  取ってくるなら中身は外部が書いたものになる — これは Live Search の節
  （「取ってきたものが本文として何を名乗れるか」）と同じ問いで、汎用の解は
  本 Spec では作らない。`defuse`（Spec 26）は配送経路で既に効く

### D4 コマンドは argv 配列・シェル非経由。`run.json` の allow/deny は通さない

- **シェル非経由は維持する**（`command` + `args` 配列）。ここを緩めると
  Spec 15 が 3 回の査読で守った境界（パースで守る境界は必ず抜けられる）が
  横から破れる
- **allow/deny（`run.json`）は通さない。** あの囲いは**モデルが書くコマンド**の
  ためのもの。probe のコマンドは人が書く — ただし**「人が書いた」の証明は
  ファイルの存在ではなく端末の承認**（D10。rev1 はここが甘く、配布された村の
  コマンドが無検査で走る穴だった — 査読 4）
- **実行機構は `run.rs` から切り出して 1 実装を共有する**（`env_clear` /
  `group_spawn` / タイムアウト / 木ごと kill / 出力上限）。写して 2 つ目を
  書くと、孫まで kill の修正が片方だけ入る形になる。切り出すのは
  プロセス実行の核だけで、**照合（allow/deny）は `RunTool` 側に残る** —
  共有の単位は述語ではなく実行（Spec 23 の `is_webp` 共有と同じ線引き）
- **PATH 解決は実行時。解決したフルパスを毎回ログへ出す**（Spec 15 の宿題 (a) と
  同じ処方）
- **`command` の空・空白のみは読み込みで弾く**（rev2・査読 7。`expect` と同じ棚）。
  弾かないと「静かに `no_match` で消化され続ける予定」= 会話にもログにも
  出ない静かな死になる
- `timeoutSecs` は probe ごと（既定 60・上限 3600。`run.json` と同じ値域）。
  `cwd` は任意の絶対パス（未指定は `{workspace}`）。**cwd の検査は実行時のみ** —
  存在しない・ディレクトリでない場合は `outcome=error`（`reason=cwd_missing`）。
  読み込みで弾くと、村を配った先でスケジュール全体が壊れる

### D5 probe が走るのは宛先が稼働中のときだけ

D1 の判定列・段 1〜2 の後ろに置くことの帰結（rev1 から維持）:

- **誰も起動していない村では probe のコマンドも走らない。**
  `batch_start_invariant`（開いただけで課金が始まる作りにしない）の延長で、
  「開いただけでコマンドが走る作りにしない」が構造で成立する
- ただし**これは配布の防御ではない**（rev2 で位置づけを訂正 — 査読 4）。
  起動ボタンは村を使うための操作で、コマンド実行への同意ではない。
  配布の防御は D10 が担う

### D6 セッション選択は `sessionMode`: `continue`（既定）| `fresh`

- `fresh` は配送前に `create_session`。**`create_session` は
  `ensure_idle_for_switch` を通らない**（`orchestrator.rs:921` — 検査があるのは
  既存会話を開く側 `:1245`）。Spec 12 P2 の裁定どおり、**他個体が飛行中でも**
  新規チャットは通る（着地先が新しい空の会話なので既存の記録を汚さない）。
  **宛先自身の飛行中は D1 の段 2 で既にスキップ済み** — rev1 はこの 2 つの
  「飛行中」を書き分けておらず矛盾に読めた（査読 1）
- 旧セッションは redb に残り、いつでも開き直せる — **破壊ではなく切り替え**
- **セッションは村全体の単位**なので、`fresh` の予定が発火すると人が見ている
  画面も新しい会話へ切り替わる。UI の説明文に「発火のたびに村全体が新しい会話へ
  切り替わります」と書く（知らずに失う形にしない）
- **同一 tick に複数の予定が発火したときの順序を固定する**（rev2・査読 2）:

  > **全件の判定（D1 の表）を先に済ませて配送候補を集める →
  > 候補に `fresh` が 1 件でもあれば `create_session` を 1 回 →
  > 全候補を一括配送 → 消化 → 保存。**

  - `fresh` が複数あってもセッションは **1 つ**しか作らない（tick ごとに
    N 個作っても空のセッションが挟まるだけで、どの候補も最後の 1 つに積まれる）
  - **`continue` の意味は「切り替えを起こさない」であって「旧セッションを
    指名する」ではない。** 同一 tick に `fresh` と混在した `continue` の配送は
    新しいセッションに積まれる — セッションが村全体の単位である以上、
    同時刻の発火が同じセッションに載るのが一貫した挙動で、途中で画面が
    2 回切り替わる形（1 件ずつ処理）よりも予測できる
- 既定が `continue` なのは S5（既存の予定は変わらず動く）の帰結

### D7 自動要約は `summarizeAfter`（既定 false）。対象は「待って完了した」個体だけ

**利用者裁定**（2026-08-08）— 対象は発火の因果に参加した個体だけ。稼働中全員
（既存の `summarize_session` の単位）だと、関与しなかった個体の要約コストを
予定が払う形になり、Spec 12 P4 の「参加していない個体のぶんまで払わない」規律と
衝突する。

**対象の定義は挙動に置く**（rev2・査読 11）:

> **対象 = 発火の宛先（根）+ その因果の中で `ask` / `plan`
> （`deliver_and_wait`）を通って応答を返し終えた個体。
> `handoff` で渡した先は対象外。**

- rev1 は「予算プールを受け取った個体」と定義していた。**実測では handoff も
  同一 Arc を継承する**（`tests/orchestrator.rs:6415`
  `a_handoff_inherits_the_same_budget_pool` が凍結）ので査読の仮定
  「handoff が別 Arc かも」は成立しないが、**仕様の定義が実装の凍結テストに
  寄りかかる形は指摘どおり誤り** — テストの改訂が仕様を黙って変える。
  挙動（待って完了した）で定義すれば、予算実装がどう変わっても対象は動かない
- **handoff 先を外す根拠**: 待っていないので「終わった」を観測する点が無い。
  根の完了時点でまだ走っているかもしれない個体を要約すると、
  飛行中ターンの畳み込みという別の問題を持ち込む
- **実行時点は根のターン完了後。** 完了検知は配送を `deliver_and_wait` で包んで
  待つ分離タスク（`schedule_tick` 本体は待たない — 待つと予定ループ全体が
  1 件の発火に塞がれる）
- **これは `summarize_session` の doc「自動では要約しない」を明示的に覆す。**
  覆したと分かるように doc と契約の両方に書く（#56）。覆すこと自体は正当 —
  あの規律の本体は「勝手に仕事を増やさない」で、予定ごとのオプトインは
  人が増やすと決めた仕事
- 実装は `summarize_session` を対象指定版（`summarize_agents(ids)`）へ割り、
  既存の全体版はそれを全稼働個体で呼ぶ形に畳む — 規律を 2 箇所に書かない
- **`fresh` と `summarizeAfter` の併用は許す**が、UI で性質の違いを書く —
  新規チャットは*捨てる*（旧セッションに残して切り替える）、要約は*残る固定費*
  （opus が 1 往復を 1,163 字に書いた実測。`folded_chars` WARN が既にある）

### D8 計器 — `schedule probe:` の 1 行に判定・exit・失敗理由まで載せる

```text
schedule probe: id=… outcome=match|no_match|error|timeout|unapproved
                exit=0|N|- reason=spawn_failed|not_found|cwd_missing|signal_truncated|-
                resolved=… stdout_chars=N
```

- **probe 実行（と未承認スキップ）のたびに 1 行**（`run decision:` /
  `grep include:` と同じ形）。stdout の中身は出さない — 字数と列挙値だけ
  （#71: 計器は秘密の転送経路になる。スクリプトの出力に何が入るかを
  機構は決めつけられない）
- **失敗理由は閉じた列挙で載せる**（rev2・査読 10）。`outcome=error` だけでは
  「何を直せばよいか」がログから読めない — 直せる沈黙を作らない
- **`reason` が値を持つのは `outcome=error` のときだけ**（rev3・査読 rev2）。
  timeout は outcome 側で完結する — 1 つの事実を 2 つの欄で言わない
- **不一致・失敗は会話ログへ流さない**（猶予超過と同じ判断 — 5 分ごとの監視で
  毎回 System 行が出ると本物の通知が埋まる）
- **画面はスケジュールダイアログに最後の判定（outcome・reason・時刻）を出す。**
  in-memory の投影（波の記録と同じ寿命）
- **再起動後の診断は `concordia.log` が担う**（rev2 で査読 10 の
  「少なくともログファイルに残す」の側を採った）。**`probe_last.json` のような
  第 2 の永続ファイルは作らない** — reason 付きの `schedule probe:` 行が既に
  永続しており、同じものの複製になる（Release Assets と artifact の二重を
  やめた判断と同型）。機械が書く永続ファイルを増やすことは、人が編集する
  ファイルとの衝突面（Notes 4 の形）を増やすことでもある

### D9 置き場は `schedules.json` へ加算。既存ファイルは保存もバイト等価

`ScheduledTask` へ 3 欄を加算:

  "probe": {                    // null = 前判定なし（従来の無条件発火）
    "command": "python",        // 空・空白のみは読み込みで弾く
    "args": ["watch.py"],

  改修前とバイト等価であることを文字列リテラルで留める（Spec 23 P2 の前例）

### D10 probe の実行には端末側の承認が要る。承認は「その村の、そのコマンド行」に束ねる

**rev1 の穴（rev1 査読 4）**: モデルが書くコマンドは allow/deny で縛るのに、
**他人から貰った村の `schedules.json` に入っていたコマンドは無検査で走る** —
強弱が逆だった。「人が GUI に書くから」という D4 の根拠は、**ファイルの存在からは
「この端末の人が書いた」を導けない**（schedules.json は村の内容物で配布に載る）。

**rev2 の穴（rev2 査読）**: 鍵 `hash(command, args, cwd)` は
**workspace 差し替え攻撃が通る** — 村 A で `python watch.py`（`cwd: null`）を
承認したあと、同じコマンド行 + **悪性の `watch.py`** を含む村 B を入れると、
ハッシュが一致して承認済みとして走る。承認したのはコマンド行だけで、
**そのコマンドが実行する中身（村の側にあるスクリプト）を束ねていなかった**。

**査読の案 A（workspace 絶対パスを salt）は、骨は正しいが実体が効かない**
（rev3 で前提を実測）— この村の workspace は起動時に
`{app_data_dir}/workspace` **固定**（`state.rs:56`）で、村の入れ替えは
パスの変更ではなく**同じパスの中身の差し替え**。同一機では村 A も村 B も
常に同じ絶対パスに住むので、パスを salt にしてもハッシュは 1 ビットも動かない。

> **束縛の実体は村の識別子 `{workspace}/village_id`（UUID v4・無ければ起動時に
> 生成・村の内容物として配布に載る）。
> 鍵 = `SHA-256(canonical_json({ args, command, cwd, villageId }))`。
> 承認の無い probe は実行せず `outcome=unapproved` で消化する。**

- **差し替えた瞬間に全承認が構造的に死ぬ** — 攻撃者の村 B は攻撃者の id
  （または無し → 受け手の起動時に新規生成）を運ぶので、被害者の承認とは
  一致しない。案 A の意図（どの村のものかまで束ねる）を、パスの代わりに
  id で満たす
- **`village_id` の書式（承認時の細部 1）**: UUID v4 を ASCII 小文字・
  ハイフン付きで 1 行。読み込みは `trim()` して `^[0-9a-f-]{36}$` を検査し、
  **不正なら再生成**（書式検査に落ちた id で承認を組むと、その村の承認が
  永遠に組めない）。生成は起動時の `state.rs` 初期化 — **`schedule_tick` の
  開始より前**（発火が id 未確定の窓を持たない）。既存村は初回起動で
  生成されるので S5 は破らない
- **自分の村では id は不変** → 承認は持続（同じコマンド行は 1 回の承認 =
  rev2 の UX を維持）。**村を別の機へ持ち出しても id は付いて回る**ので、
  自分の村の引っ越しやバックアップ復元で承認は外れない（パス salt との差。
  安全性は id が担っているので、位置で縛る理由が無い — 位置縛りは
  摩擦だけ増やして攻撃者を 1 人も止めない）
- **残余を書いておく（保証と書かない — Spec 26 の規律）**: 自分の村を
  配布・公開すると id も配られる。id を知る攻撃者は同じ id + 同じコマンド行 +
  悪性スクリプトの村を作れる。潰しているのは「無差別に配った村が承認を
  素通りする」主要形で、**公開した村の持ち主を狙う標的攻撃までは防がない**。
  怪しい村を入れたと思ったら `probe_approvals.json` を消せば全承認が外れる

**ハッシュの形を固定する**（rev2 査読 — 未定義だと実装が割れる）:

- **`SHA-256`。入力は UTF-8 の canonical JSON**（キーは辞書順・空白なし）:
  `{"args":[…],"command":"…","cwd":"…"または null,"villageId":"…"}`
- **`args` の順序は意味を持つのでそのまま**。`cwd` は書かれた文字列のまま
  （`null` は `null`。**実行時の解決値を入れない** — 解決値は環境で動くので、
  鍵に入れると同じ設定が機会ごとに別の鍵になる）
- **ファイルに保存するのはハッシュだけ**。コマンド行の原文は保存しない —
  承認ファイルを「実行可能なコマンドのインベントリ」にしない（rev2 査読の
  権限の懸念を、守る対象を消す側で潰す）。承認ダイアログが表示する原文は
  `schedules.json` から読む
- **`probe_approvals.json` の構造（承認時の細部 2）**:
  `{"hashes": ["<64 桁 hex>", …]}` の 1 欄のみ。この形も契約に書く
  （欄を増やしたくなったら、それは承認以外の何かを持ち込もうとしている合図）

**承認が書かれるのは GUI の保存操作だけ**（rev2 査読）:

- 経路は保存系 IPC のみ = 人のクリック起点。**モデルが `schedules.json` を
  `file write` で書いても承認は付かない** — モデルは IPC を呼べないので
  構造的に成立するが、**構造で安全なものほどテストで留める**（P2。
  この村の work_dir がリポジトリ直下を指す村では、モデルの手が
  `schedules.json` に実際に届く）
- **実装境界（承認時の細部 3）**: `probe_approvals.json` への書き込み関数は
  **`tauri::command` の層に閉じる**（`pub(crate)` で agent-core 側へ
  広げない）。可視性そのものを境界にする — 「呼ばない約束」ではなく
  「呼べない構造」（コンパイラが守る側に置く）
- **保存順序は 承認 → `schedules.json`**。逆順だと schedules だけ書けて
  承認が書けなかったとき、正当な probe が `unapproved` で due を失う。
  承認だけ書けて schedules が失敗した残骸は**何も参照しない鍵**で無害 —
  失敗時はその場で取り除き、取りこぼしても次の保存の掃除が拾う
- **掃除は保存のたび**: 現在の `schedules.json` のどの probe にも一致しない
  承認を落とす。削除・書き換えに追従するので肥大化しない（時計ベースの
  GC は作らない — 「30 日未参照」は判定に壁時計を持ち込み、
  テストが時刻に依存する）
- **読めない `probe_approvals.json` は空として扱い（全 probe が
  `unapproved` = 安全側）、既定を書き戻さない**（#70 — 読みの安全側と
  書きの安全側は別。書き戻すと壊れる前の承認の記録を捨てる）
- ファイル権限: **Unix ビルドは 0600 を明示。Windows は chmod 相当が無いので
  偽らない** — `{app_data_dir}` が利用者プロファイル配下で OS の既定 ACL が
  利用者に閉じている、が実態（中身がハッシュだけなのはこの前提の保険でもある）

**承認の取り消し UI は作らない**（今は）。probe を書き換えるか予定を消せば
実行は止まり、掃除が承認も落とす。全承認の破棄は `probe_approvals.json` の
削除で足りる。一覧・取り消しの画面は必要が観測されたら足す
（空の欄・使われない画面を先に作らない）

- **P5 実機確認** — 書く前に「その差が観測できるか・ノイズより大きいか」を
  数える（#68 / #80 / #85）:

  1. 不一致で `schedule probe: outcome=no_match` が出て **`turn start:` が
     1 本も出ない**（probe 行の存在と turn 行の不在の対）
  2. 一致で配送され、**依頼文に 2 行目以降が含まれて届く**（`turn start:` の
     `chars=` が計算に合うこと — Spec 24 検収 2 の読み方）
  3. **`echo CHANGED; exit 1` 相当のスクリプトで発火する**（rev1 の逆が
     実機で通ることを 1 回見る。`exit=1` が同じ行に出る）
  4. **`schedules.json` を手で置いた（GUI を通さない）probe が
     `outcome=unapproved` で走らず**、ダイアログの承認後の次の due で走る。
     「走らない」は `unapproved` の行だけでなく **OS のプロセス一覧に
     コマンドが 1 つも現れない**ことまで見る（rev1 査読の読み方 —
     行の存在は「実行してから捨てた」実装と区別が付かない）
  4'. **差し替え攻撃の再現**: 承認済みの村の `village_id` を書き換えて
     再起動 → 同じコマンド行が `unapproved` に落ちる（プロセス不在まで確認）
  5. `timeoutSecs > 間隔` の予定で probe が重なりかけたとき、プロセスが
     1 本のままで次の due がスキップされる（タスクマネージャ or ログの対で読む）
  6. `fresh` の予定で発火後にセッション一覧が 1 つ増え、旧セッションが開き直せる
  7. `summarizeAfter` で参加した個体だけ `summarize:` 行が出る
     （負の対照 = 参加していない稼働中の個体に出ないこと）
  8. probe 失敗（存在しないコマンド）で `reason=not_found` が出て、
     ダイアログに最後の判定が表示される

## Notes

1. **外部トリガー API は対象外**（利用者判断 2026-08-08）。将来やるなら
   Spec 25 の HTTP サーバーに口を足す形になるが、**本 Spec の probe が
   その需要の大半を先に吸う**可能性が高い。README の「意図的に未実装」には
   足さない — 未実装ではなく未起票

2. **RepeatGuard との関係は無い。** probe は LLM のツール呼び出しではなく
   配送前の判定なので、RepeatGuard の数えの外。同じコマンドを 288 回
   走らせるのは probe の正常な仕事

3. **トークン予算（Spec 11）との関係**: probe 自体は予算を 1 つも引かない
   （LLM を呼ばない）。発火した配送は従来どおり `new_root_budget` で満額 —
   probe の有無で予算の形は変わらない

4. **probe の出力とキャッシュ**: 付記は依頼文（user 発話）に入るので
   安定プレフィックスの外。キャッシュの安定境界は動かない（#45 の規律で
   user 発話へ畳まれる側）

5. **「何もしていない時間に圧縮」(dreaming) を idle 検出器で作らない。**
   発火した因果の完了直後 = 次の発火までの空き時間なので、完了駆動で
   意図は満たせる。idle 検出器は「効いているか分からない機構」になる型
   （#47 で L1/L2 を作らなかった判断と同じ）

6. **D10 が塞ぐのは「配布された村のコマンドが黙って走る」経路であって、
   probe の中身の善悪ではない。** 承認は人がコマンド行を見て押す —
   見て分からないコマンドを押せば走る。これは `run.json` の allow と同じ
   性質（1 件ずつ許容を決める手間が閉じた許容の本体）で、機構が肩代わり
   できる範囲の外
