## Goal

**専用ダイアログで全個体を一覧し、チェックした個体の `work_dir` を、
入力した 1 つのパスへまとめて変更する。**

起点は利用者の要望（2026-08-08）—「エージェントにチェックボックスをつけて、
ワークスペースを入力するとチェックされているエージェントのワークスペース
フォルダを一括で変更」。公開までのマイルストーン 7。
要望の字面は「カードにチェック」だが、置き場は D1 で裁定する（rev1 の Goal は
カード前提と読める書き方だった — 査読 #3 で修正）。

**動機は運用の形にある。** この村の実運用は「村ごと 1 つのリポジトリを向く」
使い方が主で（実機の 9 体村では 4 体が `D:\ManualeRAG` を宣言している形と同型）、
対象プロジェクトを切り替えるたびに **8 個の設定ダイアログを 8 回開いて
同じパスを 8 回貼る**ことになる。取り除くのはこの繰り返しであって、
個体ごとに違うフォルダを持てる自由は 1 ミリも狭めない。

## 現況（実測 2026-08-08。**起票時の見立てが 1 つ覆った**）

**マイルストーンの表に「これだけがコアに触る」と書いたが、誤りだった。**
数えたらコアの変更はゼロで済む:

| 部品 | 実測 |
|---|---|
| 変更の経路 | `update_agent` IPC が既にある（`orchestrator:1613`）。**稼働中でも受け付け、次の発話から反映**（プロンプトはメッセージごとに組み直すため）。役職の流し込みもしない（発火点は新規作成ただ 1 つ — `role_contract` 凍結 4） |
| フォルダ選択 | 「参照…」ボタンの機構（2026-08-05・`tauri-plugin-dialog`）がそのまま使える |
| まとめて操作の前例 | 一括起動トグル（`batchStart.ts` 純関数 + カードのスイッチ） |
| 一覧ヘッダの入口の前例 | **「モデル登録」**（モデルテンプレート管理ダイアログはエージェント一覧のヘッダから開く — README 画面構成表） |
| **保存時の実在検査** | **単体の保存も掛けていない**（下記） |

### 境界の定義（査読 #2 で統一）

**`work_dir` の囲いはツール実行時の `resolve_in_work_dir` が持つ。**
同関数は内部で canonicalize + `work_dir` への前方一致を行う（symlink 経由の
脱出をパス文字列の検査では塞げないため — `AgentSpec.work_dir` の doc が正）。
**保存時には検査しない。** rev1 は同じ囲いを「canonicalize + 前方一致」と
「`resolve_in_work_dir`」の 2 つの名前で呼んでいた — 前者は機構、後者が
関数名で、**本 Spec では関数名で統一する**。

この帰結として、「存在しないパスを 8 体へ入れたときどうするか」という
起票前の問いは半分が問いごと消えた。`AgentSettingsDialog` の単体保存は
`trim` して空なら `null` に落とすだけで、実在検査を一切しない（「参照…」
ボタンの節「フロントで先回りすると同じ規律が 2 箇所に生える」）。
**一括だけ検査を足すと、単体と一括で規律が割れる。**

残る失敗は **IPC そのものの失敗**（対象の個体が操作中に削除された等）だけで、
これが D2 の主題になる。

### 踏むと分かっている罠 — snapshot → spec の複製

`update_agent` は **spec 丸ごとの差し替え**なので、呼ぶ側は投影
（`AgentSnapshot`）から全欄を写して組み直す。この「snapshot → spec」の
組み立ては現在 **2 箇所に複製されている** — `AgentSettingsDialog.seed()` と
`useOrchestrator.setBatchStart()`。後者には既に警告コメントがある
（「**写さないと保存で既定へ戻る** — `batchStart` を写し忘れると、設定を
開いて保存しただけで対象へ黙って復帰する」）。**本 Spec で 3 箇所目を作る
ことになるので、複製を増やす前に 1 実装へ寄せる**（D4）。欄の写し忘れは
型検査に掛からず、「保存しただけで別の欄が既定へ戻る」という**読めない形**で
出る（#51 と同じ性質）。

## 設計の核

**新しい型・ワイヤ・コア変更なし。** フロントが `update_agent` を対象の数だけ
順に呼ぶ。それでも Spec を切るのは、**決めどころが 3 つあり、うち 2 つ
（チェックの置き場・部分失敗の見せ方）が後から変えにくい**ため。

## Decisions

### D1. チェックの置き場 — ダイアログ内の一時チェック

| 案 | 形 | 代償 |
|---|---|---|
| A | カードに常設チェックを新設 | カードには既に**一括起動スイッチ・スタンバイボタン・鉛筆・選択**が並ぶ。**年に数回の操作の席を常駐面に置く**ことになり、一括起動のスイッチと並ぶと「どちらが起動でどちらがフォルダか」を毎回読み分けることになる |
| B | 一括起動の対象（`batchStart`）を流用 | **「一括起動に含める」と「フォルダを変える」は別の意図**。流用すると片方のために付けたチェックがもう片方を巻き込む |
| **C（採用）** | **専用ダイアログ内の一時チェック** | ダイアログを開く 1 手が増える。**選択は保存されない**（下記トレードオフ） |

ダイアログは全個体を **`inListOrder`（左ペインと同じ並び）**で列挙し、
チェック + **現在の `work_dir`** を並べて表示する（変更前に現状が見えることが
一括操作の安全側 — どの個体が何を向いているかを知らずに上書きさせない）。

**既定は全チェック ON + 「全解除 / 全選択」の切り替えを 1 つ置く**（査読 #3 を
受けた改訂）。全 ON が既定なのは動機（村ごと切り替え）の主ケースが全員だから。
**ただしこれは選択的ユースケースと緊張する** — 1 体だけ変えたいときは 8 体分
外すことになるので、全解除ボタンで 1 打に縮める。**チェックは永続化しない**
（ダイアログの寿命）ので、選択的変更を繰り返す運用では毎回選び直しになる。
このトレードオフは正直に Notes 1 に書く — 永続化するなら置き場と移行の設計が
要り、観測されていない運用のために席を作らない（D3 と同じ判断基準）。

**入口はエージェント一覧の【フッター】**（2026-08-08 利用者裁定で P2 実装後に
移した。初版はヘッダの「モデル登録」の隣だった）。

**ヘッダと分ける理由は置き場の都合ではなく役の違い** — 利用者の言葉
「モデル登録や追加とは分けたい」。ヘッダの「モデル登録」「追加」は
***作る・登録する*側**、作業フォルダの一括切り替えは
***既にいる個体をまとめて扱う*側**。一覧の直下に置けば、**対象が目の前に
ある状態で押す**形になる。

**このフッターはアプリのステータスバー（`StatusBar.vue`）とは別物** —
左ペインの中に住む帯で、`h-full flex-col` の末尾に `shrink-0` で置く。

Spec 14 P3 の二分法との関係は rev2 で決着済み: rev1 は「どちらでもなく一覧の
道具」と**第三カテゴリを新設していた — これは誤り**（査読 #5）。**ただし
「アプリの設定へ倒す」も誤り** — あの二分法は**タイトルバーとシステム設定の
どちらに置くか**の裁定で、エージェント一覧はその射程の外に**最初から実在する**
（「モデル登録」が前例。README 画面構成表）。**新カテゴリは作らず、
既に一覧が持っている面の中で役ごとに割る**。README の画面構成表へは
「一覧のフッター」として 1 行足す（P3）。

### D2. 適用の実行 — 検査せず、逐次に呼び、通った個体だけ通し、結果を名指しで出す

**パスの実在検査はしない**（境界の定義の節のとおり。存在検査はツール実行時の
`resolve_in_work_dir` に委譲する。単体保存と同じく `trim` のみ行う）。
**D3 の空入力の活性制御は実在検査ではない** — 誤操作防止の UI 制御で、
パスの中身は見ない（査読 #1 の切り分け）。

**正規化はしない**（査読 #8）。フロントは `trim` のみで、スラッシュの向き・
末尾区切り・大文字小文字の正規化は行わない。「参照…」が返す OS ネイティブ
形式のパスはそのまま保存する。帰結として、**一覧の現在値表示では同一フォルダを
指す 2 体が別の文字列に見えることがある**（`D:\ManualeRAG` と
`D:/ManualeRAG/`）。同一性の判定は表示上の文字列一致のみで、実体の同一性は
バックエンドの canonicalize が実行時に吸収する。表示側で正規化を始めると
**保存値と表示が食い違う 2 つ目の真実**が生まれるので、やらない。
改善するなら別 Spec。

**実行は逐次**（`for` + `await` + `try/catch`。`Promise.allSettled` の並列に
しない — `update_agent` は 1 呼び出しごとに persist を含むので、並列にすると
`world.json` の書き込みが交錯する形を自分から作る）。**タイムアウトは
設けない**（査読 #7 の処方は不採用 — 根拠は下記）。**部分成功を許す**:
途中の 1 体が失敗しても残りは続行し、**結果は個体ごとに名指しで出す**
（「変更 7 体 / 失敗 1 体（agent_5: エージェントが見つかりません）」の形。
失敗した個体が**どれで・なぜか**が出ないと直す手掛かりが無い）。
複数個体をまたぐトランザクションは作らない — 8 回の呼び出しのために原子性の
機構をコアへ足すのは費用が逆転している。

**タイムアウトを設けない根拠**: `update_agent` はネットワークを渡らない
ローカル IPC（メモリの `World` 更新 + ローカルディスクへの persist）で、
**この村の `mutate()` 経由の全呼び出しが同じくタイムアウトを持たない**。
ここだけ 5000ms を足すと単体保存と一括で規律が割れる（実在検査で査読自身が
指摘した形と同じ）。コアが固まるならアプリの全操作が固まっており、それは
一括操作固有の failure mode ではない。**UI 側は査読の指摘どおりに固める** —
適用中は適用ボタンを disabled にし進捗（n / N）を出す。キャンセルは付けない
（1 呼び出しが速いローカル操作の列で、中断の席を作るほうが状態を増やす）。

**同時編集は last-write-wins を許容する**（査読 #6）。ダイアログを開いている
間に別経路（設定ダイアログ・MCP 経由の操作等）で同じ個体の spec が変わった
場合、**適用時に読み直した投影から組み立てる**（開いた時点の snapshot を
抱え込まない — 適用の瞬間の `state.agents` から `snapshotToSpec` する）ことで
窓を最小にするが、それでも競合は原理的に残る。バージョン検出は行わない —
`update_agent` 自体が楽観的 last-write-wins で、単体の設定ダイアログにも
同じ競合が最初からある。一括だけ検出を足すと（以下同文）。

### D3. 空入力 — 適用ボタンの活性制御（実在検査ではない）

**空のまま適用ボタンを押せなくする。** これは**パスの実在検査ではなく、
誤操作防止の活性制御**（査読 #1 の切り分け — D2 の「検査しない」はパスの
*中身*を見ないことで、*有無*で押せなくすることとは別の層）。

単体ダイアログでは空 = `null`（未設定へ戻す）だが、一括の空は**入力し忘れの
形**のほうがずっと多い。まとめて未設定に戻したい需要は観測されていないので、
**観測されてから足す**（確かめる前に席を作らない）。

### D4. `snapshotToSpec` — 上書き I/F を持つ 1 実装（査読 #4 で明定義）

`lib/agentSpec.ts`（新設）:

```ts
/** 投影から spec を組み直す。overrides で差し替える欄だけを指定する。 */
export function snapshotToSpec(
  snapshot: AgentSnapshot,
  overrides?: Partial<Omit<AgentSpec, "id">>,
): AgentSpec;
```

（承認時の推奨を反映して **`id` だけ `Omit`** — `id` を上書きすると
`update_agent` の宛先そのものが変わり、正当な使い道が 1 つも無い。
査読の推奨は `'id' | 'createdAt'` だったが **`createdAt` はフロントの
`AgentSpec` に存在しない**ので `id` のみ）

- **P1**: `AgentSettingsDialog.seed()`（overrides なし = 全欄の複写）と
  `useOrchestrator.setBatchStart()`（`{ batchStart: next }`）を置き換える。
  挙動不変
- **P2**: 一括変更が `snapshotToSpec(snap, { workDir: inputPath })` で呼ぶ
- 査読 #4 の処方はシグネチャの欄名が `work_dir` だったが、**フロントの型は
  `workDir`**（ワイヤは serde の camelCase）。趣旨を採り欄名を訂正した
- overrides を `Pick` で 2 欄に絞らない — 絞ると 4 箇所目の呼び出し元が
  別の欄を差し替えたくなったときに型定義へ戻ることになり、閉じる価値が無い
  （spread の複写に欄ごとの危険差は無い）
- テストは**全欄が写ることを `AgentSpec` の欄の列挙**で検査（欄が増えたら
  赤くなる形 — #67 の機械版）。加えて overrides が**指定した欄だけ**を
  変えることを、指定しなかった欄と対で見る（#87 — 欄を選んで検査する）

## Phases

- **P0**: 査読 → rev 改訂（契約は増やさない — 新しい型・ワイヤ・enum なし。
  決定はこの Spec が持つ）
- **P1**: `snapshotToSpec` の切り出しと既存 2 箇所の置き換え + 単体テスト。
  **main へ単独コミット 1 つ**（挙動不変）
- **P2**: ダイアログ（一覧 + チェック + 全解除/全選択 + 現在値表示 +
  パス入力 + 参照… + 適用 + 進捗 + 結果表示）+ 配線 + 辞書 ja/en + vitest。
  **部分失敗の結果表示はここで固定する**（査読 #9 — モックした `update_agent`
  が 1 件失敗を返すケースで「7 体 / 1 体 + 名指し」の表示を検証する。
  実機で削除競合を再現するのは任意）。**別コミット 1 つ**。
  **承認時の注記 2 件をここで満たす**:
  (A) **表示と適用の時刻差** — 現在値表示は開いた時点の値、適用は最新の
  投影から。適用の完了時に一覧を読み直して表示も揃える（表示だけ古い状態を
  適用後に残さない）
  (B) **trim の所在は 1 箇所** — `const trimmed = input.trim()` を適用処理の
  冒頭で 1 回だけ行い、`snapshotToSpec(snap, { workDir: trimmed })` へ渡す。
  D2/D3 の層分け（中身は見ない・有無だけ見る）が実装で崩れない形

  **P2 の実装で 1 つ決まった（`mutate()` を通さない）**: `useOrchestrator` の
  変更系は `mutate` を通り、**`finally` で必ず `refreshAll()` を呼ぶ**。
  8 体を `orchestrator.updateAgent` で回すと**全状態の再同期が 8 回**走り、
  失敗のたびにトーストが 8 枚出る。さらに `updateAgent` は `Promise<void>` で
  **成否を捨てている**ので、個体ごとの成功/失敗が読めない。
  一括は **`ipc.updateAgent` を直接呼び、個体ごとに `try/catch` し、
  最後に `orchestrator.refreshAll()`** を掛ける（承認時の注記 A —
  適用後に一覧の現在値表示も揃う）。

  **ただし「読み直しは最後に 1 回」は不正確だった**（2026-08-08 訂正）。
  `update_agent` は 1 体ごとに **`TopologyChanged` を発行**し、フロントは
  そのイベントで毎回 `refreshAll()` する（`useOrchestrator.ts` の
  `topologyChanged` — 「辺の変化は一覧全体に波及しうるので取り直す」）。
  **`mutate` を避けて消えたのはトースト 8 枚と成否の握り潰しであって、
  再同期の回数ではない。** 最後の 1 回は「イベントを取りこぼしても最終状態へ
  揃える関門」として意味が残る。
  **一般化: 呼び出し側の再同期を止めても、コアがイベントを出していれば
  投影は動く。「何回取り直すか」は呼ぶ側だけを数えても分からない**
- **P3**: 台帳（README 日英の画面構成表・「何ができるか」表・CLAUDE.md の
  マイルストーン 7 の行）
- **P4**: 実機確認

## P4 検収（観測できる項目だけ — #68 / #85。書く前に読み口を数えた）

1. **8 体チェックして適用 → 各個体の設定ダイアログで `work_dir` が変わっている**
   （カードに `work_dir` は出ないので、読み口は設定ダイアログ。2 体で足りる —
   全個体の確認は「同じ 1 本のループ」の反復で、情報が増えない）
2. **稼働中の個体が、適用後の次のターンから新しいフォルダでツールを使う**
   （`fd` を呼ばせて返るパスで読む。再起動不要 — `update_agent` の
   「次の発話から反映」が一括経路でも成立していることの確認）
3. **チェックを外した個体は変わらない**（負の対照。全員変える実装でも
   1 は緑になるため）
4. **存在しないパスを入れても適用は通り、ツールが実行時に名指しで断る**
   （検査しない、が単体と同じ挙動であることの確認。`resolve_in_work_dir` の
   文言が返ること）
5. **進捗と結果表示が出る**（全成功の形でよい — **部分失敗の名指し表示は
   P2 の vitest が固定済み**。実機での削除競合の再現は任意。査読 #9 の裁定）

**P4 結果（2026-08-08）: 5 件とも観測。指摘ゼロ。** 画面の 3 点
（フッターの帯が一覧のスクロールに残る / 一覧が短くても浮かない /
329px 未満でラベルがアイコンへ畳まれる）も同時に確認した。

**利用者から次の要望が 1 つ出た** — 「ワークスペースの履歴があればいい。
そうすれば毎回、探して選ばなくて済む」。下記「追加」で実装。

## 追加: 作業フォルダの履歴（2026-08-08 利用者要望）

**Spec を切らない**（Spec 14 の「追加: 役職の色」と同じ形 — 本体が Done に
なった直後の小さな追補で、フロントだけで閉じ、決めどころが数点しかない）。

起点は利用者の言葉 —「毎回、探して選ばなくて済むので」。**取り除くのは
ネイティブのフォルダ選択ダイアログを開いて辿る手間**であって、パスを
覚えておく機構が欲しいわけではない。

- **原本は適用したパスの履歴**（`localStorage` の
  `fuseforks.workDirHistory.v1`）。**端末の都合なので村には持たせない** —
  `work_dir` は絶対パスで端末ごとに違い、村を配ると壊れる欄
  （`fuseforks.settings.v1` / `fuseforks.chatCleared.v1` と同じ棚）
- **記録するのは「適用した」瞬間だけ。** 入力しただけ・参照…で選んだだけでは
  積まない — 履歴の意味を「使ったことがあるパス」に保つ
- **いま各個体が向いているフォルダは履歴に混ぜない。** それは**すぐ上の
  一覧に出ている**ので、混ぜると同じ情報が 2 箇所に並ぶ。履歴が埋めるのは
  「**いまはもう誰も向いていないが、また戻る先**」
- **上限 8 件・新しい順・重複は上へ寄せる**（同じ場所を何度も往復する
  使い方が主なので、消すのではなく順序で表す）
- **`<datalist>` にしない。** 入力欄に隠れていると「履歴がある」ことが
  画面から読めず、要望（探す手間を消す）を満たさない。**押せる行として出す**
- **削除の導線は付けない。** 8 件で自然に押し出される。付けると
  「履歴を手入れする」という新しい仕事が生まれる

## 追加: 適用中は一覧を出さない（2026-08-08 利用者要望）

起点は実機 —「一括切り替えの処理で上から順に変わっていくところを見せずに、
処理中のプログレスでブロックして、すべて完了してから見せる」。

**途中経過が出るのは実装の漏れではなく、投影の設計の帰結**（上の訂正）。
`update_agent` が 1 体ごとに `TopologyChanged` を出し、フロントがそのたびに
`refreshAll()` するので、逐次適用の途中が一覧にそのまま流れる。

**処方はイベント由来の再同期を止めることではなく、見せないこと。**
再同期は投影の真実性を支えている機構で、一括のためだけに止める口を作ると
**「止め忘れると古い表示が残る」という新しい失敗の形**が生まれる。
`busy` の間は一覧を回転印 + 進捗に差し替えるだけで、機構は 1 つも増えない。

**閉じる導線も塞ぐ**（外側のクリックと ✕ の両方）。閉じても走っている
ループは止まらないので、**結果を見られないまま副作用だけ進む**形になる。
D2 で「キャンセルは付けない」と決めているので、閉じられるのはその決定と
食い違っていた。

## Notes

1. **チェックの寿命のトレードオフ（査読 #3 の帰結）。** チェックは永続化
   しないので、**選択的変更（毎回同じ 1 体だけ変える等）を繰り返す運用では
   毎回選び直しになる**。既定の全 ON + 全解除ボタンは主ケース（村ごと
   切り替え = 全員）を 0 打、選択的ケースを「全解除 + n 打」にする配分。
   選択の永続化は、その運用が観測されてから置き場ごと設計する
2. **既存の一括起動と対比で読める形にする。** 一括起動 = 「チェックは永続
   （`batchStart` 欄）・操作はヘッダの 1 ボタン」、本 Spec = 「チェックは
   一時（ダイアログ寿命）・操作はダイアログ」。永続と一時が分かれる理由は、
   一括起動のチェックが「村の運用の形」であるのに対し、フォルダ変更の
   チェックは「今回の操作の対象」でしかないため
3. **`work_dir` は村を配ると壊れる欄**（絶対パス・端末ごとに違う —
   `AgentRoleDefaults` が排除した理由）。一括切り替えは**配られた村を自分の
   端末に合わせる最初の操作**にもなる — 8 体の壊れたパスを 1 回で直せる
4. **`rag_sources` には触らない。** 同じ「絶対パスの列」だが、あちらは
   個体ごとの専門資料の宣言で「村ごとに揃える」需要の形が違う。
   欲しくなったら別の要望として観測してから
