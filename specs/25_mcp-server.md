# Spec: 外部の LLM から村へ依頼する — Concordia を MCP サーバーにする

**ID**: 25
**Date**: 2026-08-07
**Status**: **rev3 承認 → P0〜P3 完了（2026-08-07）→ 残は P4（台帳）と P5（実機確認）**
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

Claude Code や Copilot、各社の CLI から **Concordia へチャットを 1 本投げ、
窓口のサーヴァントがオーケストレーションして結果を返す**。

起点は利用者の言葉（2026-08-07）:

> オーケストレーションは素のシングルショット推論では弱いし、エージェント的・
> 長ホライズン・コーディング系でもよほどうまく組まないと効果を発揮しない。
> オーケストレーション＋複数パス＋検証が効く領域を選んでワンポイント的に使う。
> **シングルショット業務ではオーケストレーションを頼むより、Neo に頼んだほうが
> 正確だし速い。なので Neo の補完機能として Concordia を使えるようにしたい。**

**この Goal の形が全部の判断を決める**（Spec 23 と同じ構造）。目的は
「Concordia をリモート操作できる汎用 API にする」ではなく、
**効く領域でだけ使える口を 1 つ開けること**。だから:

- **開くのは扉 1 枚だけ** — チャットを投げて答えを受け取る。それ以外は出さない
- **村の状態は外から見えない**（利用者裁定）。呼ぶ側が村を覗く必要は無い —
  必要なら**人が `SKILL.md` や `CLAUDE.md` に「こういうときは村を使え」と書く**
- **既定は OFF。** 開けるのは人の操作で、開けていない村では何も増えない

## 現況（実測 2026-08-07）

### 1. 村は 1 つのプロセスの中にしか居ない — これが設計の大半を決める

- `tauri_plugin_single_instance` が 2 つ目の起動を殺す（Spec 07 P0）
- `sessions.redb` は**単一書き手**
- 稼働中のサーヴァント（受信箱・履歴・予算プール）は**そのプロセスのメモリ**
- workspace は起動時に `app_data_dir()/workspace` へ固定される（`state.rs`）。
  **実行時に別の村へ切り替える機構は存在しない** — ライフサイクルの問いは
  「村をまたぐ」形ではなく「ON のまま窓口が消える」形で出る（P2）

**したがって「MCP サーバーを別プロセスとして立てる」形は採れない。** 立てても
村を持たない空のプロセスになり、workspace を開こうとすれば redb と
single-instance に当たる。**扉は動いている GUI に向かって開くしかない。**

| 案 | 可否 |
|---|---|
| headless の MCP サーバーを別に立てる | **不可**（上記） |
| **GUI の中で HTTP MCP サーバーを開く** | **可**（本 Spec の採用案） |
| stdio のシムが GUI へ中継 | 可だが**シムと GUI の間のプロトコルを別に作る**ことになる |

### 2. オーケストレーション側は何も作らなくてよい — ただし入口の型は 1 つ広げる

```rust
async fn deliver_and_wait(shared, from, to, question, next_hop, parent, budget)
    -> (String, PlanTaskState)
```

**外部の呼び出しは、構造的には「あるサーヴァントが別のサーヴァントへ `ask` する」
のと同じ**。投げて、待って、返る。`ask` / `plan` がこの上に載っているので、
窓口が波を撒いて束ねる部分は**既存の経路がそのまま動く**。

**ただし「そのまま再利用」は 1 行割れる**（rev3 査読 7）— 現行の
`deliver_and_wait` は `from: &AgentId` を受けて `Endpoint::Agent` を
焼き込んでいる（`orchestrator.rs:4761`）。S2（会話ペインに External として残る）を
満たすには **`from` を `Endpoint` で受ける形へ広げる**必要があり、呼び出し元は
`ask` / `plan` の 2 系。待ち方・失敗の分類・予算の検査は 1 字も変えない。

### 3. 依存は +7 crate（実測。全部純 Rust）

`rmcp 2.2` は既にツリーに居る（今は `client` のみ）。
`server` + `transport-streamable-http-server` を足して `cargo tree` を差分した:

```text
chacha20  pastey  rand  rand_core  ref-cast  ref-cast-impl  sse-stream
```

**`tower` / `http` / `http-body` / `bytes` / `tokio-stream` / `schemars` /
`uuid` は既にツリーに居た**（reqwest と tauri と rmcp client の分）。
291 → 298。Spec 23 の +9 と同じ桁で、C 依存は増えない。

### 4. `Endpoint` は 3 種（User / System / Agent）で、4 つ目を足す

外部からの発話をどれとして入れるかが D6。**rev2 で `External` の新設に決まった** —
射程は D6 の表（rev3 で「コンパイラが指す 4 + 指さない 6」へ数え直し）。

## 設計の核

**GUI の中で HTTP の MCP サーバーを開き、ツールを 1 本だけ提示する。**

```text
Claude Code ──HTTP(MCP)──▶ 動いている Concordia
                             └─ 窓口サーヴァント（システム設定で指定）
                                  └─ ask / plan / 検証（既存の経路）
                             ◀── 束ねた答えを 1 本の文字列で返す
```

コアに増えるのは**外部発話の入口 1 本**（`deliver_and_wait` の `from` を
`Endpoint` へ広げて再利用）と**窓口の設定欄 1 つ**だけ。
オーケストレーションの機構は 1 つも増えない。

## 決めること

- **D1 認証はトークン必須。localhost でも省かない。**
  開いた口は**同じ端末の任意のプロセスから叩ける**。そして叩けると
  トークンを使え、`run` の許可リストに載ったコマンドを走らせられ、
  作業フォルダを読める。**`@` の名前空間と同じで、開けてから絞るのは難しい。**

  **置き場は第 3 の棚**（rev3 査読 2）— Spec 13 の 2 棚はどちらも使えない。
  `world.json` は村を配ると鍵も一緒に配られ（`credential` を平文から追い出したのと
  同じ判断）、`localStorage` は検査する側の Rust から読めない。新設するのは
  **`{app_data_dir}/mcp_server.json`**（workspace の**外**・端末側・Rust 可読）。
  ON/OFF・ポートも同じファイル。**この配置の帰結として「村を配っても扉は
  開かない」が構造で成立する**（配るのは workspace だけ）。

  **生成はサーバーを ON にした時点**（rev2 の「起動時に生成」は D5 と矛盾して
  いた — rev3 査読 3）。再生成ボタンを置き、システム設定から見える形にする。
  **毎起動での再生成はしない** — するとクライアント側の設定が毎回無効になり、
  「Neo の補完として気軽に使う」Goal と正面衝突する。

  **bind は 127.0.0.1 固定 + Origin 検査**（rev3 査読 10）。トークン必須でも
  `0.0.0.0` で開けば LAN へ露出する。MCP Streamable HTTP の仕様自体が
  DNS rebinding 対策の Origin 検証を要求している。
- **D2 窓口はシステム設定で決める**（利用者裁定 2026-08-07）。
  **ザリ固定でも `agent_1` 固定でもない** — 進行役はトポロジーの帰結であり、
  どの個体が窓口かは村ごとに違う。**置き場は `world.json`**（窓口は村の内容物 —
  #52 の境界「村の内容物か、アプリの設定か」。ON/OFF・ポート・トークンは
  アプリの設定なので D1 の棚、と振り分けが割れるのは正しい）。
  **未設定でもサーバーは HTTP を受け、ツールが「窓口が決まっていない」を
  理由として返す**（rev2 の「扉は開かない（理由を返す）」は矛盾していた —
  ポートが開いていなければ理由は返せない。rev3 査読 4）。
- **D3 素直に待つ**（利用者裁定）。`start` + `poll` の 2 段にしない。
  `ask` と同じ形で機構が 1 つ少ない。**上限は既存の委譲の待ち時間
  （`shared.config.ask_timeout`）に揃える** — 超えたら「時間内に終わらなかった」を
  返し、**会話ログには途中経過が残る**（人は画面で続きを見られる）。
  **クライアント側にも村が制御できない打ち切りがある**（Claude Code の
  `MCP_TIMEOUT` 系。rev3 査読 9）— 既定が `ask_timeout` より先に切れると
  **S1 が主戦場（分単位のオーケストレーション）でだけ失敗する**ので、
  P0 で「長い呼び出しが切られないか・伸ばせるか」を実測する。
  足りないと実測で出たら 2 段化を別 Spec で。
- **D4 提示するツールは 1 本。名前は `ask_concordia`。引数は `message` だけ。**
  名前は外部 I/F なので P0 で凍結する（rev3 査読 12 — 外部の LLM のツール一覧に
  並ぶので、「村」では何のことか分からない。**製品名が取っ手になる**）。
  **`to`（宛先）も出さない** — 村の状態がブラックボックスなら、呼ぶ側は
  誰が居るか知らないので宛先を選べない。**窓口は村の側の設定で決まる**(D2)。
  `village_roster()` のような覗き口も作らない（利用者裁定）。
  **範囲を絞るのは礼儀ではなく位置づけの問題** — 村の設定・セッション・条例まで
  外から触れると、Concordia は「オーケストレーションの道具」から
  「リモート管理される何か」に変わる。
- **D5 既定 OFF。** サーバーを開くのはシステム設定の明示的な操作。
  開けていない村では**ポートも開かず、トークンも作らない**（生成が ON 時なので
  D1 と整合する）。OFF に戻したらポートを閉じる。
- **D6 `Endpoint::External { client }` を新設する**（rev2。利用者裁定 2026-08-07）。

  **理由は表示ではなく入力。**「人間ユーザーからの命令でないと分かれば、
  LLM も正確に対応できる」（利用者の言葉）。

  **`attribute_sender` が組む `【送り手: X】` はモデルが読むプロンプトの一部**で、
  送り手が誰かによって答え方が変わることを期待して置いてある機構（Spec 06 /
  Spec 19）。**外部の LLM を利用者に見せかけると、その機構を自分で無効化する。**
  外の LLM は噛み砕いた説明も聞き返しも要らず、構造化した答えを受け取れる —
  相手が人間かどうかは**振る舞いを変える情報**であって、記録の飾りではない。

  > **rev1 の提案（`Endpoint::User` + 文脈へ 1 行）は誤っていた。**
  > あれは D6 を「後から人が読むための記録」の問題として立てていたが、
  > 実際は「モデルへ渡す入力」の問題だった。**問いを取り違えると、
  > 安いほうが正しく見える。**

  **`client` は MCP の `clientInfo.name`（`"Claude Code"` など）。**
  ただし**呼び出し側の自己申告で、トークンを持つ任意のローカルプロセスが
  名乗れる**ので、**`normalize_user_name` と同じ検査を必ず通す**
  （Spec 19 凍結 4 — `】` と改行を弾き、字数を切る。**書式が壊れると
  1 つの発話が 2 つに読める**）。ここは**攻撃者が書ける文字列が
  プロンプトへ入る唯一の新しい経路**になるので、正規化は任意ではない。
  **検査に落ちたら拒否ではなく既定ラベル `external` へ落とす**（rev3 査読 11）—
  `clientInfo.name` は呼び出し側が対話的に直せない値で、拒否すると扉ごと
  使えなくなる。落としたことは WARN 1 行で残す。

  **射程（rev3 で数え直し — rev2 の「コンパイラが全部指す・取りこぼし無い」は
  実測と食い違っていた。査読 5）**:

  **コンパイラが指す網羅 match は 4 箇所**（すべて `orchestrator.rs`:
  2772 / 2901 `attribute_sender` / 3473 / 5181）。
  **指さない箇所が 6 箇所あり、そちらが真の盲点** — ワイルドカード・`matches!`・
  `==` は新 variant を黙って吸う。各サイトの挙動をここで決めて P1 で凍結する:

  | 箇所 | 形 | External の挙動（決め） |
  |---|---|---|
  | `model.rs:637` `agent_id` | `_ => None` | `None`（エージェントではない。正） |
  | `compute.rs:90` `count_by_sender` | `_ => None` | **辺の集計外**（利用者ノードを地図に出さない裁定と同じ側 — External も全結線相当で無情報） |
  | `room_log.rs:31,34` 可視述語 | `matches!` | **依頼（from=External）は編集ゼロで不可視**（`from` が `Agent` でない発話は既に落ちる。**手を入れずテストで凍結** — 不要な編集はそれ自体が退行の入口） |
  | `session_store.rs:593,792` fork 候補 | `matches!(from, User)` | **External の依頼は分岐点に出ない**（分岐候補はユーザー発話だけ、の既存規則の帰結。凍結） |
  | `orchestrator.rs:5134` System 行の抽出 | `== System` | 対象外のまま（正） |
  | フロント `chatRows.ts` ほか | 型を返さない switch | 手で数える（下記） |

  **広場ログは依頼と返答を分けて書く**（rev3 査読 6 — rev2 の「窓口以外の
  サーヴァントには見せない」は返答まで含むと User 並置と矛盾していた）:
  **依頼（from=External）は不可視・返答（from=Agent{窓口}, to=External）は
  User 宛の返答と同じ扱いで可視**。村は「窓口が外へ答えた」ことを知ってよい —
  User 宛と同じく、文脈の無い答えだけが見えるのも同じ。対で結合テストに凍結。

  フロントは `ChatPanel.vue` の switch 2 つ / `chatRows.ts` / `types.ts`。
  **戻り値型を持つ switch は TS が落とす**（`strict: true`）。型を返さない
  switch だけ手で数える。redb の `Record::Message` は**移行不要**
  （既存レコードに新しい variant は現れない）。

  **`isMine` は偽。External の発話は相手側（左）に `client` のラベルで出す** —
  外部からの依頼は「自分の発話」ではないので利用者の吹き出しの側に並べない。
  S2 の「後から読める」はラベルと左置きで足りる。
- **D8 外部クライアントの呼び名とアイコンを人が設定できる**（2026-08-07 利用者要望
  「MCP 接続のユーザーのアイコンと名前を変えられるように」）。

  **D6 の延長で、同じ問いの答えを引き継ぐ** — 呼び名は表示だけでなく**封筒**
  （モデルが読む入力）にも効く。`【送り手: Neo（外部クライアント）】` のように
  なり、**種別の注記は残る**ので D6 の性質（相手が人間でないと分かる）は不変。

  **設定は攻撃面を狭める側に効く。** `clientInfo.name` は攻撃者が書ける唯一の
  新しい経路（凍結 6）で、呼び名を設定した村では**その文字列がプロンプトへ
  届かなくなる**。

  - 呼び名 = `world.json` の `external_name`。検証は `normalize_user_name` の
    **同じ述語**（封筒へ入る値、という一点で制約が決まる）。未設定なら
    **名乗りへ落ちる**（既存の挙動を変えない）
  - アイコン = `{workspace}/external/icon.webp`。**`user/` と分ける** —
    共用すると「外の道具が頼んだこと」と「自分の依頼」が同じ顔で並ぶ。
    検証は `validate_icon` の同じ述語（上限が 1 つであること自体が不変条件）
  - 解決は **`external_label` の 1 実装**を封筒と広場ログが共有する。
    2 箇所で組むと「画面では設定名・プロンプトでは名乗り」の食い違いが生まれる
  - **`Endpoint::External` は据え置き。** 記録には名乗りが残る（誰が実際に
    呼んだかは監査の材料で、呼び名はその表示規則にすぎない）
- **D7 同時外部依頼は 1 本まで**（rev3 査読 1・8 で新設）。
  2 本目は「処理中の依頼があります」で**即拒否**する。効き先は 3 つ:

  1. **併走の予算二重消費**を塞ぐ — 外部依頼は因果の根なので、2 本同時に
     受けると新品の予算プールが 2 つ走る
  2. **自己登録の閉路**を塞ぐ — 外部入口は**新しい因果の根**で hop=0・予算も
     新品になるため、**`max_hops` と天井は閉路が扉を通るたびにリセットされ、
     どちらも効かない**（rev2 の Notes 3「既に塞いでいる」は誤りだった）。
     村の `mcp.json` に自分自身を登録すると
     `ask_concordia → 窓口 → 村の MCP クライアント → ask_concordia …` の
     無限連鎖が組めるが、**上限 1 なら 2 周目が必ず busy に当たって切れる**
  3. **自己呼び出しのデッドロック**を解く — 窓口は飛行中ターンの中から
     ツールで自分の受信箱へ配送し、自分のターンの完了を待つ形になる。
     busy の即拒否なら `ask_timeout` を待たずその場で解ける

## Stories

- S1 Claude Code から `ask_concordia("…")` を呼ぶと、窓口のサーヴァントが
  受け取り、必要なら `plan` で撒いて検証し、**束ねた答えが戻り値として返る**
- S2 その依頼と答えが**Concordia の会話ペインにも残る**ので、人は後から
  「外の LLM が何を頼んだか」を読める
- S3 サーバーを開いていない村では、ポートも開かず何も増えない
- S4 トークンが違う呼び出しは拒否される
- S5 窓口が未設定なら、**ツールが**「窓口が決まっていない」を理由として返す
- S6 窓口が停止中なら、その旨が返る（黙って待たない）
- S7 処理中にもう 1 本届いたら、待たせず「処理中」で即返る

## Notes

1. **これは「使わない人は払わない」の 3 例目**（Spec 23 の画像・Spec 24 の補完に続く）。
   OFF の村ではポートも開かず、依存の +7 crate はビルドに入るだけで走らない。
2. **再入は D7 が塞ぐ。** rev2 の「閉路は `max_hops` と予算の天井が既に塞いでいる」は
   **誤りだった** — 外部入口は新しい因果の根で、hop も予算も扉を通るたびに
   新品になる。既存の 2 つの歯止めは**根の中**でしか効かない。閉路・併走・
   デッドロックの 3 つを D7 の同時 1 本が一度に塞ぐ。
3. **stdio シム案を捨て切らない。** P0 で Claude Code が HTTP を受けない
   （または長い呼び出しを保てない）と分かったら倒れる先で、そのときは
   「シムと GUI の間のプロトコル」を 1 つ設計することになる（そこが増える部品）。
4. **`deliver_and_wait` は private のまま。** 公開の入口を 1 本作ることになるが、
   **`ask_agent` と同じ引数を組み立てるだけ**で、待ち方や失敗の分類は
   既存の実装をそのまま通る（`ask` と `plan` で文言と境界を揃えてある理由が
   ここでも効く）。`from` の型だけ `Endpoint` へ広がる（現況 2）。
