# Spec: 外部の LLM から村へ依頼する — Concordia を MCP サーバーにする

**ID**: 25
**Date**: 2026-08-07
**Status**: **rev2（D6 を裁定に合わせて反転。承認待ち → P0 から着手）**。
**rev1 の D6 は誤っていた** — 外部発話の記録先を「後から人が読むための記録」の
問題として立てたが、実際は「モデルへ渡す入力」の問題だった。
**問いを取り違えると、安いほうが正しく見える。**
**Branch**: なし（main へ Phase 単位で直接コミット）

## Goal

Claude Code や Copilot、各社の CLI から **Concordia へチャットを 1 本投げ、
窓口のサーヴァントがオーケストレーションして結果を返す**。

起点は利用者の言葉（2026-08-07）:

> オーケストレーションは素のシングルショット推論では弱いし、エージェント的・
> 長ホライズン・コーディング系でもよほどうまく組まないと効果を発揮しない。
> オーケストレーション＋複数パス＋検証が効く領域を選んでワンポイント的に使う。
> **シングルショット業務ではオーケストレーションを頼むより、Neo に頼んだほうが
> 正確だし速い。なので Neo の補完機能として Concordia を使えるようにしたい。**

**この Goal の形が全部の判断を決める**（Spec 23 と同じ構造）。目的は
「Concordia をリモート操作できる汎用 API にする」ではなく、
**効く領域でだけ使える口を 1 つ開けること**。だから:

- **開くのは扉 1 枚だけ** — チャットを投げて答えを受け取る。それ以外は出さない
- **村の状態は外から見えない**（利用者裁定）。呼ぶ側が村を覗く必要は無い —
  必要なら**人が `SKILL.md` や `CLAUDE.md` に「こういうときは村を使え」と書く**
- **既定は OFF。** 開けるのは人の操作で、開けていない村では何も増えない

## 現況（実測 2026-08-07）

### 1. 村は 1 つのプロセスの中にしか居ない — これが設計の大半を決める

- `tauri_plugin_single_instance` が 2 つ目の起動を殺す（Spec 07 P0）
- `sessions.redb` は**単一書き手**
- 稼働中のサーヴァント（受信箱・履歴・予算プール）は**そのプロセスのメモリ**

**したがって「MCP サーバーを別プロセスとして立てる」形は採れない。** 立てても
村を持たない空のプロセスになり、workspace を開こうとすれば redb と
single-instance に当たる。**扉は動いている GUI に向かって開くしかない。**

| 案 | 可否 |
|---|---|
| headless の MCP サーバーを別に立てる | **不可**（上記） |
| **GUI の中で HTTP MCP サーバーを開く** | **可**（本 Spec の採用案） |
| stdio のシムが GUI へ中継 | 可だが**シムと GUI の間のプロトコルを別に作る**ことになる |

### 2. オーケストレーション側は何も作らなくてよい

```rust
async fn deliver_and_wait(shared, from, to, question, next_hop, parent, budget)
    -> (String, PlanTaskState)
```

**外部の呼び出しは、構造的には「あるサーヴァントが別のサーヴァントへ `ask` する」
のと同じ**。投げて、待って、返る。`ask` / `plan` がこの上に載っているので、
窓口が波を撒いて束ねる部分は**既存の経路がそのまま動く**。

### 3. 依存は +7 crate（実測。全部純 Rust）

`rmcp 2.2` は既にツリーに居る（今は `client` のみ）。
`server` + `transport-streamable-http-server` を足して `cargo tree` を差分した:

```text
chacha20  pastey  rand  rand_core  ref-cast  ref-cast-impl  sse-stream
```

**`tower` / `http` / `http-body` / `bytes` / `tokio-stream` / `schemars` /
`uuid` は既にツリーに居た**（reqwest と tauri と rmcp client の分）。
291 → 298。Spec 23 の +9 と同じ桁で、C 依存は増えない。

### 4. `Endpoint` は 3 種（User / System / Agent）で、4 つ目を足す

外部からの発話をどれとして入れるかが D6。**rev2 で `External` の新設に決まった** —
射程は D6 の表で実測済み。

## 設計の核

**GUI の中で HTTP の MCP サーバーを開き、ツールを 1 本だけ提示する。**

```text
Claude Code ──HTTP(MCP)──▶ 動いている Concordia
                             └─ 窓口サーヴァント（システム設定で指定）
                                  └─ ask / plan / 検証（既存の経路）
                             ◀── 束ねた答えを 1 本の文字列で返す
```

コアに増えるのは**外部発話の入口 1 本**（`deliver_and_wait` の再利用）と
**窓口の設定欄 1 つ**だけ。オーケストレーションの機構は 1 つも増えない。

## 決めること

- **D1 認証はトークン必須。localhost でも省かない。**
  開いた口は**同じ端末の任意のプロセスから叩ける**。そして叩けると
  トークンを使え、`run` の許可リストに載ったコマンドを走らせられ、
  作業フォルダを読める。**`@` の名前空間と同じで、開けてから絞るのは難しい。**
  トークンは起動時に生成してシステム設定から見える形にし、
  **`world.json` には書かない**（村を配ると鍵も一緒に配られる。
  `credential` を平文から追い出したのと同じ判断）。
- **D2 窓口はシステム設定で決める**（利用者裁定 2026-08-07）。
  **ザリ固定でも `agent_1` 固定でもない** — 進行役はトポロジーの帰結であり、
  どの個体が窓口かは村ごとに違う。未設定なら扉は開かない
  （「窓口が決まっていない」を理由として返す）。
- **D3 素直に待つ**（利用者裁定）。`start` + `poll` の 2 段にしない。
  `ask` と同じ形で機構が 1 つ少ない。**上限は既存の委譲の待ち時間に揃える** —
  超えたら「時間内に終わらなかった」を返し、**会話ログには途中経過が残る**
  （人は画面で続きを見られる）。足りないと実測で出たら 2 段化を別 Spec で。
- **D4 提示するツールは 1 本。引数は `message` だけ。**
  **`to`（宛先）も出さない** — 村の状態がブラックボックスなら、呼ぶ側は
  誰が居るか知らないので宛先を選べない。**窓口は村の側の設定で決まる**（D2）。
  `village_roster()` のような覗き口も作らない（利用者裁定）。
  **範囲を絞るのは礼儀ではなく位置づけの問題** — 村の設定・セッション・条例まで
  外から触れると、Concordia は「オーケストレーションの道具」から
  「リモート管理される何か」に変わる。
- **D5 既定 OFF。** サーバーを開くのはシステム設定の明示的な操作。
  開けていない村では**ポートも開かず、トークンも作らない**。
- **D6 `Endpoint::External { client }` を新設する**（rev2。利用者裁定 2026-08-07）。

  **理由は表示ではなく入力。**「人間ユーザーからの命令でないと分かれば、
  LLM も正確に対応できる」（利用者の言葉）。

  **`attribute_sender` が組む `【送り手: X】` はモデルが読むプロンプトの一部**で、
  送り手が誰かによって答え方が変わることを期待して置いてある機構（Spec 06 /
  Spec 19）。**外部の LLM を利用者に見せかけると、その機構を自分で無効化する。**
  外の LLM は噛み砕いた説明も聞き返しも要らず、構造化した答えを受け取れる —
  相手が人間かどうかは**振る舞いを変える情報**であって、記録の飾りではない。

  > **rev1 の提案（`Endpoint::User` + 文脈へ 1 行）は誤っていた。**
  > あれは D6 を「後から人が読むための記録」の問題として立てていたが、
  > 実際は「モデルへ渡す入力」の問題だった。**問いを取り違えると、
  > 安いほうが正しく見える。**

  **`client` は MCP の `clientInfo.name`（`"Claude Code"` など）。**
  ただし**呼び出し側の自己申告で、トークンを持つ任意のローカルプロセスが
  名乗れる**ので、**`normalize_user_name` と同じ正規化を必ず通す**
  （Spec 19 凍結 4 — `】` と改行を弾き、字数を切る。**書式が壊れると
  1 つの発話が 2 つに読める**）。ここは**攻撃者が書ける文字列が
  プロンプトへ入る唯一の新しい経路**になるので、正規化は任意ではない。

  **射程は測った**（実測 2026-08-07）:

  | 層 | 触る箇所 | 取りこぼしうるか |
  |---|---|---|
  | Rust の網羅 `match` | **5 箇所**（`compute.rs` / `orchestrator.rs` ×4） | **無い**（コンパイラが全部指す） |
  | 広場ログの可視述語 | `is_visible_in_room_log` | 手で足す（**`User` と同じ扱い** — 窓口以外のサーヴァントには見せない） |
  | フロント | `ChatPanel.vue` の switch 2 つ / `chatRows.ts` / `types.ts` | **戻り値型を持つ switch は TS が落とす**（`strict: true` の `strictNullChecks`）。**型を返さない switch だけ手で数える** |
  | 永続化 | redb の `Record::Message` | **移行は不要**（既存レコードに新しい variant は現れない） |

  **`isMine` は偽にする** — 外部からの依頼は「自分の発話」ではないので、
  会話ペインでは利用者の吹き出しと同じ側に並べない。

## Stories

- S1 Claude Code から `ask_concordia("…")` を呼ぶと、窓口のサーヴァントが
  受け取り、必要なら `plan` で撒いて検証し、**束ねた答えが戻り値として返る**
- S2 その依頼と答えが**Concordia の会話ペインにも残る**ので、人は後から
  「外の LLM が何を頼んだか」を読める
- S3 サーバーを開いていない村では、ポートも開かず何も増えない
- S4 トークンが違う呼び出しは拒否される
- S5 窓口が未設定なら、扉は開かず理由が返る
- S6 窓口が停止中なら、その旨が返る（黙って待たない）

## Notes

1. **ツール名は `ask_concordia` を推す。** 外部の LLM のツール一覧に並ぶので、
   「村」では何のことか分からない。**製品名が取っ手になる。**
2. **これは「使わない人は払わない」の 3 例目**（Spec 23 の画像・Spec 24 の補完に続く）。
   OFF の村ではポートも開かず、依存の +7 crate はビルドに入るだけで走らない。
3. **再入の可能性を数えておく。** Claude Code → Concordia → 窓口 →（村の MCP
   クライアントが）別のサーバー…と続く。**閉路は `max_hops` と予算の天井が
   既に塞いでいる**が、外部から入る発話が新しい因果の根になることを
   契約に書く（予算が効く = Spec 11 の根が 3 種類目になる）。
4. **stdio シム案を捨て切らない。** P0 で Claude Code が HTTP を受けないと
   分かったら倒れる先で、そのときは「シムと GUI の間のプロトコル」を
   1 つ設計することになる（そこが増える部品）。
5. **`deliver_and_wait` は private**。公開の入口を 1 本作ることになるが、
   **`ask_agent` と同じ引数を組み立てるだけ**で、待ち方や失敗の分類は
   既存の実装をそのまま通る（`ask` と `plan` で文言と境界を揃えてある理由が
   ここでも効く）。
