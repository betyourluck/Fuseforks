# Spec: 予定の後判定 — 検収の probe と、通るまでの再依頼

- 起票: 2026-08-30
- 状態: **rev2 承認（2026-08-30 利用者）→ P0 完了**（`data_contract` へ
  `Acceptance` ブロック — 凍結 7 本・分岐の表・実行順序・再依頼の形・計器。
  `ScheduledTask` の欄へ `acceptance` を加算。ScheduleProbe の隣に置き、
  判定・承認・出力上限の規律は複製せず ScheduleProbe の節を正とした）。
  rev2 = 査読 2 系統 10 点を反映。採用 8 / 明記の側で受けた 2 /
  却下 1（理由つき）。記録は Notes 5
- 起点: 利用者 —「**ワークの質を上げるのが Fuseforks の課題**」（2026-08-30）と、
  Prime Agent（arXiv:2608.23552）の実読。同ハーネスの autonomous mode =
  「**予算の中で、毎ターン後に決定論的な終了条件テストを回し、通るまで続ける**」が、
  同じ Opus 5 の ARC-AGI-3 を 30% → 95.5% へ動かした（ハーネスが質を決める実測）。
  **この形の部品を村は既にほぼ持っている** — 予算 = `tokenBudget` / 周期発火 =
  スケジュール / 決定論テスト = probe（stdout 1 行目の完全一致）。
  **欠けているのは「テストが通るまで続ける」の輪だけ**で、本 Spec はそれを足す。

## Goal

**予定に「後判定」を付けられるようにする。** 発火した依頼の因果が完了したら
検収コマンド（probe と同じ形）を走らせ、**不一致なら同じ依頼を失敗の内容つきで
出し直す**（上限つき）。一致したら通常どおり終わる。

買っているのは「完遂の保証」ではなく **「完遂の機械検証と、安い再試行」**:

- 現状、予定の依頼は**出しっぱなし**で、成果物が出来たかを確かめる機構が無い。
  条例の Verify 段（検証役への ask）は LLM の検証で、費用も判定の揺れも大きい
- 検収は**決定論**（probe = 完全一致）なので、トークンゼロで判定でき、
  同じ成果物に同じ判定が返る。「LLM 判定は最後、機械で決まる軸を先に」
  （評価基盤の裁定）の実行形
- 再依頼には**検収の失敗内容が付く**ので、モデルは何が足りなかったかを読んで
  直せる（#44 —「理由まで伝えると回り道を探す」）

**範囲はスケジュールのみ。** 配送 5 経路（人の発話 / `ask_*` / `transfer_to_*` /
`plan` の波 / スケジュール）のうち、掛けるのはスケジュールの発火だけ。
スイッチの材料（2026-08-22）と同じ判断 — probe の枠組み（ハッシュ承認・
5 値の結末・stdout 規律）が 100% そのまま乗り、**新しい承認機構が 0 個**。
人の依頼への検収は、依頼ごとの検収条件 UI が要るので別 Spec。

## 起票時の実測・数えた部品（2026-08-30）

- **probe の枠組み**（Spec 28）: `ScheduleProbe { command, args, expect,
  timeout_secs, cwd }`。stdout 1 行目（トリム後）の完全一致。exit code は
  判定に使わない。結末は `match / no_match / error / timeout / unapproved` の
  5 値（`schedule_probe.rs`）。承認は
  `SHA-256(canonical_json({args, command, cwd, villageId}))` を
  `probe_approvals.json` に置き、GUI の IPC だけが書く
- **因果の完了検知**（Spec 28 P2b）: `Envelope.participants` に
  `deliver_and_wait` が「答えを受け取った瞬間だけ」参加者を書き、完了は
  `AgentTyping { active: false }` に相乗り。`summarizeAfter` がこの集合を使う —
  **後判定は同じ検知に相乗りする**（別の完了検知を作ると片方だけが取りこぼす。
  Spec 28 P2b の判断そのまま）
- **予算**: スケジュールの発火は新しい因果の根で、`new_root_budget` が新品の
  プールを与える（Spec 11 / 28）
- **再依頼の配送形**: 予定の配送は `from: System, to: Agent`（Spec 28）。
  再依頼も同じ形で出せる — 新しい Endpoint は要らない
- **スイッチ材料の凍結（2026-08-27）がそのまま当たる**: probe の結末 5 値の
  うち**宛先（次の行動）を持ってよいのは match / no_match だけ**。
  `error / timeout / unapproved` は「何もしない + 記録」— 検証機構が壊れた
  ときだけ検証をすり抜ける fail-open（eigent の採点器が 3 回失敗で
  `quality_score=80` を捏造した形）を締め出す

## Design

### D1: 器は `ScheduledTask` に 1 欄 — `acceptance: Option<Acceptance>`

```rust
struct Acceptance {
    #[serde(flatten)]
    probe: ScheduleProbe,   // 判定部は前判定と同じ型を再利用
    max_attempts: u8,       // 再依頼を含めた総試行回数（D5）
}
```

- **`maxAttempts` は `acceptance` の中に住む**（rev2 — 査読 A4）。外に置くと
  `acceptance: None` のときに意味を持たない欄が残り、バリデーションが要る。
  中に置けば **None なら欄ごと無い** — 送れる形が無いほうが強い（#77 の判断）
- **検収専用の判定型は作らない** — 判定部（command / args / expect /
  timeoutSecs / cwd と、承認・stdout の 1 行目完全一致・exit code 不使用）は
  `ScheduleProbe` の 1 実装。`Acceptance` は試行回数を添えた薄い封筒
- 前判定と後判定が同じコマンドなら、承認は 1 個で両方に効く（ハッシュが同じ）
- **`expect` は承認の対象外**（rev2 — 査読 A3 で明記）。承認ハッシュは
  `{args, command, cwd, villageId}` で、`expect` を含まない（実装で確認 —
  `schedule_probe.rs` の canonical JSON）。これは**前判定も元から持つ性質**で、
  承認の対象は「**何が実行されるか**」であって「**何を合格とするか**」ではない。
  `expect` の変更は新しい実行を 1 つも生まない — 判定の意味を変えるのは
  予定を編集できる人（= GUI の利用者）だけで、それは承認で守る脅威ではない
- `acceptance` 未設定の予定は今と 1 ミリも変わらない（既定 OFF・加算的変更）
- **stdout 規律の射程**（rev2 — 査読 A6）: 前判定の「2 行目以降を依頼文へ
  付記」は**前判定だけの規則**。後判定は 1 行目（トリム後）を判定に使い、
  残りは判定に使わず **D4 の抜粋の材料**になる

### D2: 走る時点は「発火した因果の完了」— 検知は `summarizeAfter` と 1 実装共有、**受け手は直列**

発火 → 配送 → 因果の参加者が全員完了（`participants` + `AgentTyping`）→
**後判定を実行** → 結果で分岐。

- **「相乗り」の精密化**（rev2 — 査読 B1）: 完了イベントの**受け手を 1 本**にし、
  `後判定 →（確定したら）要約` の**直列**で呼ぶ。並行に発火させると、
  試行 1 の完了で要約が走り、試行 2 の完了でもう 1 回走る — 要約が
  試行回数ぶん課金される。**要約の発火は後判定ループが確定
  （match / 試行上限 / 判定不能 / 予算枯渇）するまで抑止し、確定後に 1 回**。
  各試行はそれぞれ自分の完了検知の周期を持つ（試行 = 新しい配送。D5）
- **要約は確定の理由を問わず走る**（既存の `summarizeAfter` の意味論を
  本 Spec で変えない — 予算検査を要約へ足す提案は**却下**。変えるなら別 Spec）
- **完了検知が来ない場合の番犬は作らない**（rev2 — 査読 A5 を明記の側で
  受けた）。検知は `summarizeAfter` と 1 実装共有で、ターンの終了は構造で
  有界（周回 36 / 予算 / `ask_timeout` 既定 600 秒 / probe の `timeoutSecs`）。
  2 つ目の検知を作ると**片方だけが取りこぼす**（Spec 28 P2b の判断を維持）。
  新しい沈黙の形が見つかれば `summarizeAfter` も同じ穴なので、直すのは検知の
  1 実装の側

### D3: 分岐の表。**再依頼を生むのは `no_match` だけ — かつ試行と予算の両方が残っているとき**

**語彙は probe の 5 値をそのまま使う**（rev2 — 査読 B5。pass / fail の別名を
ワイヤ・ログ・契約に持ち込まない。散文の説明でだけ「通った / 落ちた」と読む）:

| probe の結末 | 条件 | 行動 |
|---|---|---|
| `match` | — | 記録して確定（要約があれば 1 回） |
| `no_match` | `attempt < maxAttempts` **かつ 予算プールの残 > 0** | **再依頼**（D4） |
| `no_match` | 試行上限 **または** 予算の残ゼロ | 記録して確定 |
| `error` / `timeout` / `unapproved` | — | **記録して確定。再依頼しない**（fail-closed） |

- 予算の条件が表に載るのは rev2（査読 A2）— D5 の「予算が優先」を分岐の
  条件として書かないと、P1 の結合テストが仕様と突き合わせられない。
  残ゼロのまま配送すると、配送 → `try_reserve` 失敗 → 何も作らないターン、を
  試行の数だけ空回りする
- 判定不能を `no_match` 側へ倒すと、検収コマンドが壊れた予定が**毎発火で
  再依頼の輪を回す**。`match` 側へ倒すと、検証が壊れたときだけ検証を
  すり抜ける。どちらも駄目で、**判定不能は判定不能として止まり、ログと画面に
  残る**（Spec 28 D8「直せる沈黙を作らない」— `lastProbe` と同じ器で見せる）
- **非ゼロ exit は `error` ではない** — 判定は stdout のみで、起動失敗だけが
  `error`（Spec 28 の規律のまま。実機の前例 = 検収 3 の `outcome=match exit=1`）

### D4: 再依頼の本文 = **初回の依頼文** + **最新の失敗注記 1 個だけ**

```text
{初回の依頼文（毎回このオリジナルをベースにする — 前の注記は含めない）}

（前回の検収が不一致でした。検収コマンドの出力:
{抜粋}）
```

- **注記は累積しない**（rev2 — 査読 B4）。ベースは常に初回のオリジナル依頼文で、
  注記は直前の試行の 1 個だけを差し替える。`maxAttempts >= 3` で注記が
  二重三重に入れ子になる形を作らない — セッションは continue（下）なので、
  前の試行の経緯は**会話の履歴の側**に全部ある。1 通は自己完結
  （分解の 2 原則）、経緯は履歴、と置き場を分ける
- **抜粋の規則**（rev2 — 査読 B6 / A の 500 字指摘）: **stdout の先頭 500 文字**
  （**文字数であってバイトではない** — `MAX_*_CHARS` をバイト長で数える差分は
  日本語では枠の 1/3 で発火する、の既知の罠）。改行は保持。
  **stdout がトリム後に空なら stderr の先頭 500 文字**へ落とす —
  検収コマンドが異常終了して stderr にだけ理由を書いた場合に、モデルへ届く
  診断が空になる形を塞ぐ（capture 層の `process::Ran::Finished` は stderr を
  既に持っている — 実装で確認）。**判定は今までどおり stdout のみ**
- 検収コマンド自身が stdout に「何が足りないか」を書けば、そのままモデルへ
  届く。**検収コマンドの設計者（人）が、失敗メッセージの設計者を兼ねる**
- **セッションは continue 固定**（予定の `sessionMode` が fresh でも、
  再依頼は初回の試行が作った会話に積む）。前の試行で何をしたかが見えないと、
  同じ失敗を繰り返すだけになる — fresh で再依頼すると RepeatGuard に相当する
  記憶が会話ごと消える

### D5: `maxAttempts` は総試行回数。既定 2・範囲 1..=5。予算が常に優先

- **既定 2（= 再依頼 1 回）**。RepeatGuard の「同じ失敗の 3 回目は実行しない」と
  同じ側の保守性 — 2 回目で直らないものは 3 回目でも直らないことが多く、
  費用だけが線形に増える。深い作業で 3 回以上を望む村は設定で上げる
- `maxAttempts: 1` は「再依頼なし・検収の記録だけ」— 完遂の計器としてだけ
  使う形で、これも正当な使い方
- **予算の枯渇は試行の残りに優先する**（D3 の表の条件）。
- **再依頼は「新しい配送・同じ財布」**（rev2 — 査読 A1 / B2 の矛盾指摘を反映）。
  rev1 の「新しい根にしない」は不正確だった — 正しくは:
  **再依頼は新しい封筒**（新しい cancel token・新しい `participants` 集合 =
  試行ごとに独立した完了検知と打ち切り）**だが、`Envelope.budget` には
  発火時の `Arc<BudgetPool>` をそのまま積む**（`new_root_budget` を呼ばない）。
  機構は封筒への相乗りの既存形そのもの（cancel / budget / participants の
  3 前例と同じ — 後判定ループが封筒を組むときに手持ちの Arc を渡すだけで、
  配送のルーティングにフラグは要らない）。これで Prime Agent の
  「予算 + 終了条件」の形になり、`tokenBudget` が「通るまで続ける」の天井に
  なる。新品にすると毒タスク（永遠に不一致）が 発火 × 試行 × 天井 で漏れる

### D6: 計器は `acceptance:` の 1 行 / 試行

```text
acceptance: schedule=… attempt=1/2 outcome=match|no_match|error|timeout|unapproved
```

**outcome の語彙は `schedule probe:` 行と同一**（rev2 — 査読 B5。書式も判定も
1 実装を再利用するので、パーサが 2 つの語彙を持たない）。

- **完遂の軸に機械で決まる列が 1 本増える** — `reply: to=` / `refusal=` に
  続く 3 本目で、これだけが「成果物の検証」を直接言う
- 判定不能もこの行に出る（沈黙を作らない）

### D7: UI はスケジュールダイアログに後判定の節 — 前判定と同じ 5 欄 + 試行上限

前判定（Spec 28 P3）の形をそのまま写す: コマンド・引数・期待する出力・
タイムアウト・作業フォルダ + `maxAttempts`。承認導線・直近の結果の表示
（`lastAcceptance`）も前判定と同じ器。表示名は「後判定（検収）」を仮置き
（用語は査読で決める — アプリ内で「検収」が Spec の検収項目と紛れるなら
「完了の確認」も候補）。

### D8: 凍結（`data_contract` へ）

1. **後判定の判定部は `ScheduleProbe` の再利用** — 検収専用の判定型を作らない
   （`Acceptance` は判定部 + `maxAttempts` の薄い封筒。rev2 で精緻化）
2. **再依頼を生むのは `no_match` だけ — かつ試行と予算の両方が残っているとき。**
   判定不能 3 値（`error` / `timeout` / `unapproved`）は宛先を持たない
3. **再依頼は新しい封筒（cancel / `participants` は新品）に、発火時の
   `Arc<BudgetPool>` を積む** — `new_root_budget` を呼ばない（rev2 で
   「新しい根にしない」の不正確な文言を置き換え）
4. **範囲はスケジュールのみ** — 他の 4 配送経路に掛けない（掛けるなら別 Spec）
5. **再依頼のセッションは continue 固定**（予定の `sessionMode` は初回だけ）
6. **前判定は発火時に 1 回だけ評価する。再依頼は前判定を通らない**
   （rev2 — 査読 B3。後判定ループは封筒を直接組むので構造で成立する。
   通すと、検収の輪の途中で環境が変わったとき「配送されないまま試行だけ
   数える」形が生まれる）
7. **計器の語彙は probe の 5 値をそのまま**（`match / no_match / error /
   timeout / unapproved`）

## 検収項目（実機）

**各項目に到達経路を明記する**（凍結を精緻化したら到達可能性を数え直す —
#51 (b) / Spec 43 検収 7 / Spec 44 検収 4b の教訓）:

1. **一致**: マーカーを書くだけの依頼 + それを確かめる検収で、
   `acceptance: attempt=1/2 outcome=match` が 1 行出て再依頼が無い
   （`turn start: from=System` が 1 本のまま）
2. **不一致 → 再依頼 → 一致**: 2 回目の試行で初めて成立する検収
   （例: ファイルが 2 行以上あること）で、`outcome=no_match` → 再依頼
   （依頼文に「前回の検収が不一致」と stdout の抜粋が付く）→
   `attempt=2/2 outcome=match`
3. **試行上限**: 常に不一致の検収で `attempt=2/2 outcome=no_match` の後、
   3 本目の配送が**無い**（無いことが判定 — 期限を置いて `turn start:` を数える）
4. **判定不能は再依頼しない**: 実在しないコマンドの検収で `outcome=error` が
   1 行、再依頼ゼロ。画面の直近の結果に理由が出る
5. **未承認**: 未承認の検収コマンドで `outcome=unapproved`、承認導線に載り、
   承認後の次の発火で走る
6. **予算が優先**: 小さい `tokenBudget` の村で、再依頼の前に予算が尽きると
   `outcome=no_match` の後に配送が**無く**、確定の記録が残る
   （予算の残ゼロが D3 の表の条件として効いたことの観測）

   端末承認（ハッシュ）で走り、サーヴァントのツール実行経路を通らない

4. **毒タスクの残余**: 予定そのものは次の周期で再発火するので、

   予算が抑え、`acceptance:` 行の連続 `no_match` が観測に出る — 自動で予定を
   止める機構は作らない（沈黙で止まる予定のほうが害が大きい。頻度を見てから）

6. **continue + 予算継承の相互作用**（査読 A の指摘を Note として採用）:
