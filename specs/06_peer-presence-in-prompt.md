## Goal

進行役のエージェントが、**接続先が今動いているかを投げる前に知る**。

現状、ザリは 4 体と繋がっているが、相手が稼働しているかを知る手段が
「投げてみて結果を見る」しかない。**点呼のためにトークンを払っている。**

起点は実機のザリ本人の申告（2026-07-29）:

> 正直に言うと、事前には分かりません。私が持ってるのは `transfer_to_*` と
> `ask_*` だけで、プロセスの死活監視 API やヘルスチェックの口はないんです。
> 分かるのは「投げてみて返事が返ってきたか／エラーになったか」という事後の結果だけ。

UI は左ペインとトポロジーで各エージェントの状態を色で出している。
**人間には見えていて、エージェントには見えていない。** この非対称が本件の実体。

---

## 現状の構造（接地）

- `AgentStatus` は `Idle` / `Starting` / `Running` / `Stopping` / `Failed` の 5 値。
  変化は `CoreEvent::AgentStatusChanged` で UI へ push されている
- **エージェントはイベントを購読しない。** 受け取るのは自分宛ての発話だけ
- `transfer_to_*` / `ask_*` のツール説明には**表示名しか入っていない**。
  「誰が居るか」は分かるが「今動いているか」は分からない
- `compose_system_prompt` の連結順は
  条例 → 自分について → 作業フォルダ → 接地 → Construct → Skill → **Memory**。
  `stable_len` は Memory の直前で確定し、そこまでがキャッシュ対象になる
  **（変更前の記述。P1.5 が境界を「安定素材の末尾 = 顔ぶれの直前」へ再定義する）**

## Stories

### P0: 表示名の一意性（利用者指示で先行実装・2026-07-30 完了）

> 利用者として、同じ表示名のエージェントを 2 体作れない。なぜなら表示名は
> 会話・束ね・入退室通知・顔ぶれの語彙で、重複するとそれら全部が
> 「どちらの話か」を失うから。

本 Spec の査読中（rev3 指摘 D）に利用者が指示し、承認を待たず先行実装した。
根拠は「起こりうる状態を運用でそうしないに頼らない」（failures.md #1 の
注意書きは制御ではない、の裏返し）。

- `World::register_agent` / `update_agent` の両方で trim 後の完全一致を検査し、
  `DUPLICATE_AGENT_NAME` で拒否（改名経由の穴を作らない）
- **読み込みは寛容**: 重複を含む既存の world.json は開ける。検査の目的は
  新しい重複を作らないことで、既存データへの罰ではない。
  **寛容読み込みで重複が残った村でも、通知・顔ぶれ・束ねは `agent_id` 併記
  なので判別は失われない**（rev4 指摘 8）— 一意性は「新規作成の衛生」で、
  真の識別子は常に id。これが id 併記を維持するもう 1 つの理由になる
- 全角/半角の正規化はしない（線引きが恣意的になり、意図した区別を潰しうる）
- テスト 3 本（登録・改名・寛容な読み込み）

### P1: 入退室を会話ログへ流す

> 進行役として、誰がいつ落ちたかを順序つきで知る。なぜなら「今どうか」だけでは
> **直前の依頼が届いたのかどうか**が分からないから。

**設計の骨子（rev2 で変更）**: 状態を毎ターンのプロンプトに差し込むのではなく、
**チャットの入退室通知と同じ形で会話ログへ 1 行流す。**

```text
（システム）agent_3（ロボットくん1号）が停止しました
（システム）agent_2（ジェミー）が稼働を開始しました
```

rev1 の「毎ターン状態行を差し込む」案より優れている点が 3 つある。

1. **順序が残る。** 発話の間に挟まるので、いつ落ちたかが会話の時系列上で分かる。
   スナップショットには時間軸が無く、「さっき投げた依頼は届いたのか」に答えられない
2. **変化した時だけ**払う。状態行は変化が無くても毎ターン固定費になる
3. **キャッシュに一切触れない。** 会話ログは messages 側で、そもそも
   キャッシュのプレフィックスに入らない。rev1 で最大の制約だった
   `stable_len` の話が丸ごと消える

**仕様**

- `set_status`（状態遷移の単一路。ここを通らない遷移は無い）が
  `Running` / それ以外の境界をまたいだとき、`Endpoint::System` 発の発話を
  1 件ログへ記録する。文言は `agent_id（表示名）` を使う —
  一意性は P0 で保証されたが、モデルが宛先を選ぶ語彙は
  `transfer_to_<agent_id>` の **id** なので、id が無いと二段引きになる
  （P1.5 と同じ根拠。束ね・通知・顔ぶれで形式を揃える）
- **封筒（rev3 指摘 B）**: `from: Endpoint::System`、**`to: Endpoint::User`**。
  `AgentMessage` は `to` が必須で、決めないと実装が散る。User 宛にする理由:
  (a) UI では「システム → あなた」となり、人間への通知という実態と一致する
  (b) System → User の発話は**全エージェントにとって他人の会話**なので、
  `is_mine` 判定（自分が送り手か受け手か）に誰も掛からず、全員の広場ログに
  載る (c) 配送は起きない（`record` のみ。ターンを発火させない）
- **`Endpoint::System` はこの用途の最初の利用者**。型と表示名（当時「システム」、
  2026-07-31 に「Concordia」へ改名 + ブランドマークのアバター）は
  既にプロンプト側・広場ログ側の両方に用意されているが、
  **実際に送出している経路が無い**（テストのみ）。用意されたままの席を使う
- **通知の合成は `hearsRoomLog` の gate の外に置く（rev3 指摘 A）。**
  rev2 の「`compose_room_log` の絞り込みを緩める」だけでは Acceptance を
  満たせない — 呼び出し側が `if spec.hears_room_log && ...` で
  **`compose_room_log` ごとスキップ**するため、緩めても opt-out した個体には
  届かない。実装は 2 節構成にする: 入退室の通知（System 発のみ抽出・gate 無し）
  と広場ログ（従来どおり gate あり）。広場ログのオプトアウトは
  「場の共有が要らない役から**固定費**を外す」機能（Spec 03）であり、
  入退室は場の雑談ではなく**配送先の正しさ**に関わる情報。
  コストの設定が経路の正しさを黙って壊す形にしない
- **文言は状態語彙で統一する（rev4 指摘 4）**: 「オンライン/オフライン」の
  チャット風語彙は捨てる。同じ状態に 2 つの語彙（通知と顔ぶれ）が並ぶと、
  モデルは対応を推測することになる。文言は 3 種:
  - 非稼働 → `Running`: 「〜が稼働を開始しました」
  - `Running` → `Failed`: 「〜が**失敗により**停止しました」（理由は書かない —
    Notes 4 のとおり `last_error` は流さない。だが失敗と正常停止の区別は
    進行役の次の一手を変えるので、事実の種別だけは伝える）
  - `Running` → その他: 「〜が停止しました」
- 起動・停止のたびにログが埋まらないよう、**同じ側への遷移は記録しない**
  （`Starting` → `Running` で 1 件。`Stopping` → `Idle` は両方とも
  非稼働側なので 0 件 — 通知は `Running` → `Stopping` の時点で出ている）。
  **起動失敗（`Starting` → `Failed`）も通知しない（rev4 指摘 5）** —
  まだ場に現れていなかった者の失敗は入退室ではない。進行役から見た世界は
  「来なかった」のままで、誤った信念（居ると思っていた）が発生していない。
  失敗の事実は顔ぶれ（P1.5）に「失敗」として現れる
- **通知の可視範囲は広場ログの窓に従う（rev3 指摘 C）**: `room_log_window`
  （既定 12 件）から押し出された通知は見えなくなる。「順序が残る」の保証は
  **窓の範囲内**。窓の外の状態は顔ぶれ（P1.5）が常に真実を持つので、
  情報が消えるのではなく**時間軸だけが落ちる**。通知を窓の外枠で特別扱い
  しない — 特例を増やすより、権威（顔ぶれ）と語り（通知）の役割分担で守る

**Acceptance**

- Given 稼働中のエージェントを停止、Then ログに
  「`agent_id（表示名）`が停止しました」が 1 件だけ入り、会話ペインにも表示される
- Given 稼働中のエージェントが失敗、Then 「〜が失敗により停止しました」が入り、
  **エラーの理由は含まれない**
- Given `Starting` → `Failed`（起動失敗）、Then 通知は**出ない**
  （顔ぶれには「失敗」が出る）
- Given `hearsRoomLog: false` のエージェント、When 他者が停止、Then
  その通知は**受け取る**（広場ログの他の発話は従来どおり受け取らない）
- Given `Starting` → `Running` の遷移、Then 通知は 1 件（各段階で出さない）
- Given 通知が入っても、Then `stable_len` と安定部分の文字列は変わらない

### P1.5: 最初の顔ぶれ

> 進行役として、起動直後にも全員の状態を知る。なぜなら差分だけでは
> **自分が居なかった間の状態**を再構成できないから。

**仕様**

- 差分（P1）だけでは基準が無い。**現在の顔ぶれを 1 行**、システムプロンプトの
  **可変部分**（`Skill` と `Memory` の間）に置く

  ```text
  ## 今の顔ぶれ
  agent_2（ジェミー）: 稼働中 / agent_3（ロボットくん1号）: 停止中 / agent_4（ロボットくん2号）: 稼働中
  ```

- **`agent_id（表示名）` の併記（rev3 指摘 D → 根拠を更新）**: 当初の根拠は
  「表示名の一意性が保証されていない」だったが、本 Spec の P0（利用者指示で
  先行実装）で**一意性は構造で保証された**。それでも併記を維持する理由は
  もう半分のほう — モデルが宛先を選ぶ語彙は `transfer_to_<agent_id>` の
  **id** であり、顔ぶれに id が無いとモデルは表示名 → id の対応を
  ツール説明から二段引きすることになる。束ね（Spec 04）・通知（P1）・顔ぶれで
  同じ形式に揃える
- 接続先だけを列挙する（自分が話しかけられる相手の集合と一致させる）
- **順序はツール提示順（= `connected_agents` の保存順）と同一（rev4 指摘 7、
  処方変更で採用）**: 並びが不定だと状態が変わっていなくても行が diff になる。
  査読案は `agent_id` 昇順だったが、`transfer_to_*` の提示順は既に保存順で、
  顔ぶれだけ別の整列規則を持つと**同じ相手の並びがツールと顔ぶれで食い違う**。
  決定性はどちらでも得られるので、モデルから見た一貫性を優先する
- 1 行に畳む。rev1 の箇条書きは、変化しない情報に毎ターン数十トークン払う形だった
- **`stable_len` の境界を再定義する（rev4 指摘 1・Critical）**: 現状の定義
  「Memory の直前」は、Skill と Memory が隣接している今だから「Skill の末尾」と
  同じ点を指せている。顔ぶれを間に挟むと 2 つの記述が割れ、「Memory の直前」の
  定義のままでは**顔ぶれが安定部分に入り、状態が変わるたびにキャッシュが割れる**。
  境界の定義を **「安定素材（条例〜Skill）の末尾」= 顔ぶれの直前** へ改める。
  値（文字数）は現状から変わらないので、既存のキャッシュは割れない。
  実装は `compose_system_prompt` が境界を確定させた**後**に顔ぶれを push する形
- 状態の語彙は UI の `STATUS_LABELS` と揃える（画面とプロンプトで
  同じ相手が違う言葉で呼ばれないこと）
- `Failed` は理由まで書かない（`last_error` は利用者向けの診断で、
  相手のエラーメッセージを別エージェントのプロンプトへ流すと、
  会話に出ていない内部情報が横へ漏れる）

**役割分担**: **顔ぶれが権威、通知が語り。** 顔ぶれは常に現在の真実で、
通知は「いつそうなったか」を足す。どちらか片方では足りない。

**Acceptance**

- Given 接続先 4 体のうち 1 体が停止、Then 顔ぶれの行に 4 体全部が載り、
  停止中の 1 体が「停止中」と分かる
- Given 接続先が 0 体、Then この節は出ない（空の見出しを置かない）
- Given 接続先の状態が変わる、Then `stable_len` は変わらず、
  安定部分の文字列も変わらない（キャッシュが割れない）
- Given 停止中の相手を含む顔ぶれ、Then `transfer_to_*` / `ask_*` の
  **ツール定義は従来どおり全接続先ぶん出る**（提示を状態で変えるとツール集合が
  揺れ、キャッシュのプレフィックスごと割れる。提示は静的・状態は動的に保つ）

### P2: 失敗の語彙をエージェントに教える

> 進行役として、依頼が失敗したとき理由を区別する。なぜなら「相手が居ない」と
> 「時間切れ」では次の一手が違うから。

**現状の確認（重要）**: ザリの要望 2 番「転送失敗時のエラーを区別できる形で
返す」は、**既に実装されている**。`ask_agent` は 4 通りを別の文字列で返す。

| 状況 | 返る文字列 |
|---|---|
| hop 上限 | 転送の上限に達したため、これ以上は尋ねられません。 |
| 停止中 / 受信箱が満杯 | 相手に尋ねられませんでした: エージェント `X` は稼働していません |
| 相手が答えず終了 | 相手から答えが返りませんでした。 |
| タイムアウト | 相手からの答えが時間内に返りませんでした。 |

**足りないのはコードではなく周知**。ザリはこれらの経路を一度も踏んでおらず
（村の全員が常時稼働していた）、区別が無いと**推測していた**。

**仕様**

- **追記先は `HandoffTools::protocol_note`（rev3 で明確化）**。転送・委譲の
  手順を説明している既存の system 節で、`use_handoff_tools` の全員に入る。
  1 行足して、失敗が理由つきで返ることを明示する。
  「投げてみないと分からない」という誤解自体を消す
- 文言の追加のみ。`ask_agent` の戻り値は変えない

**Acceptance**

- Given `protocol_note` の出力（rev4 指摘 6 で対象を訂正 — 旧文の「P1 の節」は
  入退室通知の節を指してしまいテストが書けない）、Then 失敗時に理由が
  返る旨が書かれている
- Given `ask_agent` の各失敗経路、Then 戻り文字列は現状から変わらない

### P3（不採用）: 軽量な点呼ツール

ザリの要望 3 番。**採らない。**

- **P1 が成立すれば不要**。プロンプトに状態が載っている相手へ、
  状態を訊くためのツールを別に持つのは二重化
- ツールは 1 本でも**毎ターンの固定費**。この製品はそこを差別化軸に置いており
  （README「提示の絞り込み」）、代替のある道具を増やさない
- ザリ自身の優先度も最下位（1 > 2 > 3）

## Notes（査読論点）

1. **キャッシュ境界の制約は rev2 でほぼ消えた**。通知は messages 側に入るので
   プレフィックスに触れない。残るのは顔ぶれ 1 行だけで、これも可変部分に置く。
   rev1 の「毎ターン箇条書きで差し込む」案は、変化しない情報に固定費を
   払い続ける形だった
2. **ツールの提示は状態で変えない**。停止中の相手の `transfer_to_*` を
   引っ込めたくなるが、それをやるとツール集合が状態で揺れ、キャッシュの
   プレフィックスごと割れる。**提示は静的、状態は動的**に保つ
3. **状態は turn 開始時点のスナップショット**。ターンの途中で相手が落ちる
   可能性は消せないので、P2（失敗の語彙）が訂正経路として要る。
   P1 と P2 は代替ではなく対
4. **`Failed` の理由は載せない**。`last_error` は利用者向けの診断情報で、
   他エージェントのプロンプトへ流すと会話に現れていない内部情報が横へ漏れる
5. **Spec 04（plan）との関係**: `plan` は 1 波を並列配送する。停止中の相手を
   波に含めると、その 1 件は失敗文字列になり波全体の壁時計も伸びる
   （`ask_timeout` はタスクごとなので、停止中 1 体で最大その秒数。起票時の既定 180 秒 — Spec 44 で 600 秒・村の設定になった）。
   **04 は先に着地した**（2026-07-29。実機確認まで完了）ので、本 Spec は
   「後から入って 04 の穴を塞ぐ」位置になる — 進行役が波を組む前に
   停止中の相手を外せるようになり、Spec 04 の実機確認で観測した
