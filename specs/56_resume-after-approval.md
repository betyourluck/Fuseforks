# Spec: 承認して続けさせる — コマンド承認から新しい因果を起こす

- 起票: 2026-09-20
- 状態: **rev2（2026-09-20。査読 8 点 → 採用 4 / 前提を実測で訂正して採用 3 / 反証 1。
  表は Notes 3）→ 承認 → P0 完了**（同日。`command_tool_contract` の末尾へ凍結 10 本。
  追従の grep で 2 件回収 — `AGENT_NOT_ACTIVE` は新設不要（`NOT_RUNNING` が既存）/
  `observability_rule` の計器の列挙が 9 種類のまま実装は 55 種類だった（`failures.md` #129）。
  記録は「P0 契約記録」）
- 起点: 利用者 —「ツール実行の承認に『**承認して続けさせる**』というボタンも欲しい。
  承認して止まったままになっちゃう事が多いので」（2026-09-20）。同日の裁定 3 点
  （送るのは定型文 / まとめて承認は 1 通 / 停止中は押せない）と、予算の決着
  （新しい根・新品の天井。財布は継承しない）を受けて起票。
- 前提: **`failures.md` #128 を先に直してある**（`command` に空白が入った呼び出しは
  照合前に `Malformed` で断る）。直す前にこのボタンを入れると、承認しても永久に
  `Unknown` な呼び出しを続行させ、**同じ拒否を踏みながら回り続ける**形になっていた。

## Goal

1. **承認の直後に、その個体が続きを走れる。** 今は承認が `run.json` の `allow` へ行を
   足すだけで、その個体のターンは拒否を受けた時点で終わっている。人が入力欄へ
   「続けて」と打つまで動かない
2. **送る文はトークンを食わない。** 元の依頼文は依頼主の履歴に残っているので再送しない
3. **押せないときは押せないと分かる。** 相手が停止中なら配送経路が無いので、
   ボタンを `disabled` にして理由を出す

**やらないこと（範囲外）**: 承認以外の場面からの続行（`plan` の編集窓・`pending` の却下・
予定の失敗は別の因果）/ 財布の継承（下の D4）/ 自動での続行（**押すのは人**。
承認を検知して勝手に走らせる経路は作らない）/ 続行した先で再び拒否されたときの再々続行
（人がもう一度押す）。

## 起票時の実測（2026-09-20。コードを読んだ）

1. **配送の雛形は既にある。** `orchestrator/schedules.rs` の `deliver_scheduled` が
   「言語を読む → 本文の先頭へ由来を書く → `new_root_budget` → `Endpoint::System` から
   配送」の 4 段で、**新しいワイヤも新しい封筒も要らない**。写す対象はこの関数。
2. **`new_root_budget` の呼び出し元は 4 箇所**（`orchestrator/mod.rs:1299` に本体）—
   `runtime.rs:364` / `runtime.rs:513`（人の発話と外部依頼）/ `schedules.rs:331`（予定の発火）/
   `mod.rs:1192`。**新しい因果の根を作るたびに `World` から天井を読み直す**ので、
   ここへ 5 本目を足す形になる。
3. **承認の IPC は `approve_command(agent_id, command, args, open)`** で、
   返るのは `ApprovalOutcome` だけ。**配送はしない。** doc に
   「粒度は `open` だけで指定する。パターン文字列を受け取らないのは、受け取ると
   『粒度は機械が決めない』が『粒度を GUI が何でも決められる』へ反転するため」とある —
   **この性質は変えない**（D6）。
4. **`deliver_scheduled` は由来を本文に書いている。** コメントの理由が正
   —「封筒（【送り手: Fuseforks】）だけではモデルが人の発話と区別できない。
   会話ペインにもそのまま出るので利用者も定期発火だと分かる」。**続行も同じ扱いが要る**。
5. **停止中の判定はフロントが既に持っている**（`AgentSnapshot.status`）。
   黒板の列（`lib/blackboardLanes.ts`）が同じ値を読んでいるので、新しい IPC は要らない。

## Design

### D1. ボタンは 1 つ足す。既存の「承認」は残す

`CommandApprovalDialog.vue` に **「承認して続けさせる」を足す**（既存の「承認」「却下」は
そのまま）。押すと **承認を済ませてから 1 通配送する**。

**既存の承認を置き換えない理由**: 承認だけしたい場面が実在する — 複数の判断待ちを
片付けてから自分で依頼を書き直す、承認はするが今は走らせたくない、など。
**「続ける」は承認の意味に含まれない。**

### D2. 送るのは定型文。由来を本文の先頭に書く（利用者裁定 1）

```text
【コマンド承認】
承認しました。続けてください。
```

- **元の依頼文は再送しない**（利用者 —「トークンの無駄」）。依頼主の履歴に残っている
- **由来の印を書く**のは実測 4 の理由がそのまま当たる。封筒は
  `【送り手: Fuseforks】` になるので、**印が無いと人の発話と区別できない**
- 英語は `【Command approval】` + `Approved. Please continue.`。
  **`【】` は両言語で共通**（構造の印。Spec 35 D5 / Spec 28 の予定と同じ判断）

### D3. 「承認して続けさせる」を押した回数 = 配送の通数（利用者裁定 2 を構造で満たす）

**起票時の実測（査読で数え直した）**: `CommandApprovalDialog.vue` に**「まとめて承認」の
ボタンは存在しない**。`v-for` で個体ごとのブロックを出し、その中の判断待ち 1 件ごとに
「承認」「却下」が並ぶ（`decide(view.agentId, request, wide)`）。

だから**ボタンは判断待ち 1 件ごとに置く** — 「承認して続けさせる」は
**その 1 件を承認してから 1 通配送する**。

- 判断待ちが 3 件あるなら、2 件は「承認」で片付けて**最後の 1 件だけ
  「承認して続けさせる」**を押す。配送は 1 通 — **押すのが 1 回だから**
  （利用者裁定 2 が UI の形で自動的に満たされる）
- **複数の個体をまたいだ一括承認は存在しない**ので、「操作 1 回 = 配送 1 通」は
  常に**単一の `agent_id` の中で閉じる**

**3 通送ると受信箱に 3 つ並び、同じターンを 3 回起こす**（2 通目以降は
「続けてください」が重複して届く）。人の操作 1 回に対して因果 1 本が対応する形にする。

### D4. 新しい因果の根・新品の天井。財布は継承しない

```rust
// 承認による続行は新しい因果の根を作る。
let budget = new_root_budget(shared).await;
```

**元の `BudgetPool` は引き継がない。** 実装を数えた結果、**選べる形が 1 つしかない**:

- `BudgetPool` は `Arc` でターンの因果にぶら下がっており、**ターンが閉じれば参照が落ちる**。
  承認を押すのはその後なので、**継ぐべき `Arc` が物理的に存在しない**
- 延命する案は**ターンより長生きする状態**を持つことになり、対話シェル A 案 /
  Realtime API / 永続 REPL を退けてきたのと同じ形。ボタン 1 つのために所有者を再設計しない
- Spec 46 の「新しい封筒・同じ財布」が成立したのは**予定の発火の中**＝財布が飛行中に
  在るからで、今回は**飛行後に人が押す**ので条件が違う

**Non-goal**: 承認チェーンで予算残高を引き継ぐこと。

**Tradeoff**: `tokenBudget` を小さくしている村で「承認 → 続行」を繰り返すと、
**1 回あたりの天井が毎回フルに戻る**。ただし**これは予定の発火と同一の挙動**であり
（`schedules.rs:331` が発火ごとに `new_root_budget` を呼ぶ）、本 Spec で新設された穴ではない。
**人の操作が新しい因果を作る**という解釈で一貫する。`tokenBudget` が `None` の村で
天井なしになるのも同様。

**この節が論じるのは予算だけ。** 本文の組み立て（言語の解決と由来の印）は D2 が正で、
実装は `deliver_scheduled` の **4 段をそのまま写す** — 言語を読む → 由来を書く →
`new_root_budget` → 配送。**擬似コードの 1 行を実装の全部と読まない**（査読 5）。

### D5. 配送できるのは `is_active()` の個体だけ（利用者裁定 3）

**判定は `AgentStatus::is_active()` を流用する**（`Starting | Running`）。
`deliver_scheduled` が同じ述語で守られているので、**2 つ目の判定を書かない**
（可視述語を 1 実装に閉じる = Spec 22 / GSM の「経路ごとに 2 実装へ割れると片方が漏れる」）。

**起票時の実測（査読で数え直した）**: `AgentStatus::Idle` の doc は
「**停止しており、受信箱も存在しない**」。**ターンが終わっても個体は `Running` のまま**で
（受信箱が次のメッセージを待つ）、`Idle` になるのはトグルを OFF にしたとき。
**承認待ちが出るのは `Running` の個体がツールを呼んだときなので、承認の直後も `Running`。**
`Idle` を配送可能にする案は採れない — **受信箱が存在しないので配送先が無い**
（`deliver_scheduled` のエラー処理も「NotRunning: 上の running 判定との間で停止された競合」
と書いている）。

**文言は既存の表示語彙をそのまま使う**（ja「停止中」/ en `Idle`）。
`AgentStatus::label` の doc が「画面とプロンプトで同じ相手が違う言葉で呼ばれると
利用者とエージェントの会話が噛み合わなくなる」と書いており、
**ここで「起動していません」という別の言い方を足すと語彙が 3 つ目になる**。

**実行時の検査も要る**（画面の状態が古いまま押される競合）。コア側で `is_active()` が
偽なら配送せず **既存の `NOT_RUNNING`（`CoreError::NotRunning`）で返す** —
**新しいエラー変種を作らない**。`deliver_and_wait` が停止中の宛先に対して既にこれを
返すので、**受け皿を増やさず既存の経路をそのまま通す**（P0 の追従で数えた）。
**画面の `disabled` は導線であって保証ではない**
（Spec 20 の「fail closed は提示ではなく `decide` が守る」と同じ線）。

### D6. IPC は 1 本新設。承認そのものは既存のまま

```rust
resume_after_approval(agent_id: AgentId) -> CoreResult<()>
```

**`approve_command` に引数を足さない。** 実測 3 のとおりあの IPC は
「粒度を GUI が決めない」を守るために引数を絞ってあり、**配送の有無という別の軸を
足すと、1 本の IPC が 2 つの判断を運ぶ**ことになる。D3（承認 N 回・配送 1 回）とも
噛み合わない。

フロントの流れは **`approve_command` を 1 回 → `resume_after_approval` を 1 回**
（D3 のとおりボタンは判断待ち 1 件ごとなので、押した 1 件を承認してから配送する）。

### D7. 計器

```text
resume after approval: agent=… pending_left=N ceiling=…
```

**人が何回この線を引いたかを後から数えられる**ようにする（利用者の指摘）。
**数えるのは行数**で、1 行 = 1 回押した。

`pending_left` は配送した時点でその個体に残っている判断待ちの件数で、
**コアが `run.json` を読んで自分で数える**。フロントから承認件数を受け取らない理由は
2 つ — **ログのためだけに IPC の表面を増やすことになる** / **フロントが渡す数を
コアは検証できない**（嘘を書ける）。`ceiling` は新しい根に与えた天井（`None` なら `-`）。
書式は `budget stop:` / `schedule probe:` と同じ `key=value` 形式。

### D8. 承認は成功したが配送に失敗したとき（査読 4）

**`allow` は戻さない。** 承認は人の判断で、配送の失敗はその判断を取り消す理由にならない。

IPC が 2 本に分かれているので、**部分的に成功した状態が実在する** —
`approve_command` が通り `resume_after_approval` が `NOT_RUNNING` で落ちる形
（画面の状態が古いまま押した競合）。このとき画面は**何が起きたかを分けて出す**:

> 承認は保存しました。サーヴァントが停止中のため、続行はしていません。
> 起動してから依頼し直してください。

**同一トランザクションにはしない。** 承認は `ConfigStore` のファイル、配送は受信箱で
層が違う。1 つにまとめると「配送に失敗したので承認も無かったことにする」形になり、
**人が押した判断をアプリが取り消す** — Spec 20 の「承認画面は実際に要求されたものだけを
許容へ変える装置」の逆を向く。

## Tasks

### P0 契約

`data_contract.yaml` の `command_tool_contract` の隣（または `settings_contract` の
近く）へ凍結を書く:

1. 承認による続行は**新しい因果の根**。財布は継承しない（D4）
2. 送る本文は定型文 + 由来の印。**元の依頼文を再送しない**（D2）
3. **同一の個体への操作 1 回 = 配送 1 通**（D3）。複数の個体をまたいだ一括承認は
   UI に存在しないので、この規則は常に 1 つの `agent_id` の中で閉じる
4. 送り手は `Endpoint::System`。**`Endpoint::User` を名乗らない** — 利用者が書いた文では
   ないので、`User` にすると封筒が嘘になる（Spec 26 の系譜）。
   **`System` なので封筒は `【送り手: Fuseforks】` になり、だからこそ本文の先頭に
   由来の印（`【コマンド承認】`）が要る** — 封筒だけでは予定の発火と区別が付かない
5. 配送できるのは **`AgentStatus::is_active()` が真の個体だけ**。判定は
   `deliver_scheduled` と**同じ述語を流用し、2 つ目を書かない**（D5）
6. **自動で続行する経路は作らない**（押すのは人）
7. **`failures.md` #128 の修正が前提** — 空白入りの `command` は照合前に `Malformed` で
   断られる。直す前にこの機構を入れると、承認しても永久に `Unknown` な呼び出しを
   続行させ、**同じ拒否を踏みながら回り続ける**
8. **承認と配送は別の操作**（D8）。配送に失敗しても `allow` は戻さない

### P4 実機

## 検収（P4）

1. 判断待ちを 1 件作り、「承認して続けさせる」で**そのターンの続きが走る**
   （`fuseforks.log` に `resume after approval:` の 1 行 → `turn start: from=system`）
2. **3 件まとめて承認しても配送は 1 通**（`turn start:` が 1 本だけ）
3. **停止中の個体ではボタンが押せない**（`disabled` + 理由）
4. 会話ペインに `【コマンド承認】` の由来が出る
5. **続行したターンが新しい天井で走る** — 元のターンが予算切れで終わっていても続行できる
   （`budget stop:` の後に `resume after approval:` → 完走）
6. 既存の「承認」だけを押した場合は**配送が起きない**（退行の確認）

## Notes

### 1. この Spec が触らない「止まったまま」

利用者の言葉「承認して止まったままになっちゃう事が多い」には**2 つの原因が混ざりうる**。
本 Spec が直すのは (a) だけ:

- **(a) 承認は効いたが次のターンが来ていない** — 本 Spec
- **(b) 承認しても呼び出しが永久に一致しない** — `failures.md` #128。
  **2026-09-20 に別途修正済み**（`command` の空白を照合前に断る）

**(b) を先に直していなければ、このボタンは「無限に回るボタン」になっていた。**
起票の順序がそのまま安全性に効いた例として残す。

### 2. 配送経路が 1 本増えることの数え直し

`Endpoint::System` → Agent の配送を**GUI が起こすのは初めて**（既存は内部のティッカー =
予定の発火だけ）。利用者の操作から `System` の発話が生まれる経路なので、
**P0 の凍結 4（`User` を名乗らない）が効く場所**はここ。

なお「GUI から内容を書く経路は作らない」という Spec 54 / 55 の凍結は**黒板の話**で、
発話の配送はもともと GUI からできる（チャット入力欄）。**抵触しない**。

### 3. 査読の反映（2026-09-20・rev1 → rev2）

### 4. 用語の層（査読 6）

- **Spec の地の文・台帳・コメントは「個体」** — CLAUDE.md の用語境界
  （外に見える文言と内部の設計語を分ける）に従う
- **画面に出る文字は「サーヴァント」**（D5 のツールチップ / D8 の文面）—
  利用者が見る語彙は既存の UI に揃える
- **「エージェント」は地の文で使わない**（`AgentId` / `AgentStatus` のような
  型名としては使う）

**D5 の文言は既存の表示語彙をそのまま使う**（ja「停止中」/ en `Idle`）。
査読の「『起動していません』に合わせる」は採らない — `AgentStatus::label` の doc が
**画面とプロンプトで同じ相手を同じ言葉で呼ぶ**ことを要求しており、ここで別の言い方を
足すと語彙が 3 つ目になる。
