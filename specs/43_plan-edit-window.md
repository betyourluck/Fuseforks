# Spec: plan の編集窓 — 計画を提示し、人が直してから撒く

- 起票: 2026-08-24
- 状態: **rev1（査読待ち）**
- 起点: eigent の実読（CLAUDE.md「eigent の実読と突き合わせ（2026-08-24）」
  取り込み 3。利用者裁定「③の編集窓は号令待ち → Spec 化をお願いします」）。
  eigent は camel の一体だった `process_task` を**二分割してまで**
  （`eigent_make_sub_tasks` / `eigent_start`）この窓を開けている —
  分解結果を SSE で見せ、人が編集・削除・追加してから走らせる

## Goal

**LLM が立てた計画を、撒く前に人が確認・編集できる窓を開ける。**
「線は人が引く」の計画への延長 — 誰に頼めるか（線）は既に人が決めている。
この Spec は「今回それぞれに何を頼むか」にも人の手が届くようにする。

- 取り除くのは「LLM が立てた計画が**そのまま**走る」ことであって、
  計画を立てる主体（LLM）は変えない。自動整列を入れなかった絆の地図と同じ向き
- **既定 OFF。** 既存の村の挙動は 1 ミリも変わらない
  （`batch_start_invariant` と同じ判断 — 既定を変えると既存の村が黙って変わる）
- Spec 10 の打ち切り（走り出した後に止める）より**手前**で効くので、
  止めるコストが安い。波 1 本は数万〜数十万トークンの買い物で、
  撒く前の 10 秒の確認はその保険として釣り合う

## 起票時の実測（2026-08-24）

- **`run_plan` はターンの中で一体**（`delegation.rs:198`〜）。検証（tasks の形 /
  接続先か / 宛先重複）→ `plan wave:` 行 → `begin_wave` → 配送と join → 束ね →
  ツール結果の `String` を返し、進行役の LLM がそれを読んで要約する。
  **配送から束ねまでの所有者は進行役のターン**
- **波の記録は in-memory リング**（`PlanWaveStore`・上限 50）。再起動で消える。
  Spec 12 の凍結「復元しないもの: 波・予算・MCP 接続・稼働状態（**作業の寿命**）」
- **HITL の既存判断**（LangGraph 突き合わせ 2026-08-19）: この村は
  「人への質問は**答えて turn を終え、次の発話が次の turn** = 会話そのものが
  resume」。**ターンより長生きする実行状態を持たない**
  （対話シェル A 案の見送り・Realtime API の見送りと同じ根）
- eigent の編集状態は**フロントが持ち**、開始時に編集済みリストを渡して
  コア側は `_pending_tasks.clear()` + 入れ直し（`workforce.py:250-252`）。
  編集の中間状態を保存する API は無い

## Stories

- S1. 進行役に「計画の確認」を付けた村で依頼を出すと、**計画が提示されて波は
  走らない**。進行役は「計画を提示した」と利用者へ返す
- S2. 提示された計画のタスク本文を直し、1 件消し、1 件足して「実行」すると、
  **直した形で**撒かれ、束ねが進行役に届き、要約が利用者へ返る
- S3. 「破棄」すると何も走らず、破棄された事実が会話に残る
  （進行役は次の依頼で別の計画を立てられる）
- S4. 設定 OFF の個体（既定）では今までと 1 ミリも変わらない

## 決めること

### D0. そもそも作るか（収縮側）

**条例で書ける代替が実在する** — 「まず計画を本文で提示し、利用者の承認を
待ってから plan を呼べ」。コード 0 で、今日から使える。ただし穴が 3 つ:

1. **文言は保証ではない**（#84）— 提示せず plan を呼ぶ個体を止められない
2. **提示した計画と実行される計画の同一性が無い** — 承認後に LLM が plan の
   引数を**書き直す**ので、見せた物と走る物が別になりうる。これが本体の穴で、
   eigent のレビュー事故（「作りました」と実物の乖離）と同じ族
3. 編集が「文章で指示し直す」形になり、1 件の削除に 1 往復（= 進行役の
   1 ターン分のトークン）掛かる

機構の価値は **2 の同一性を構造で保証すること**（人が見た計画のデータが
そのまま配送される。LLM は承認後の経路に居ない — スイッチの
「走るときに LLM は居ない」と同じ形）。

**推し: 作る。** ただし査読で「まず条例形を実機で試して穴の頻度を見る」へ
倒すのはあり得る — その場合、2 の穴は頻度ではなく構造なので、
観測すべきは「条例で運用して困るか」ではなく「同一性の乖離が実際に出るか」。

### D1. 形は「二相」であって「保留」ではない

plan は編集窓が有効なとき、**配送せずに提案として記録し、ツール結果で
「提示した」を返して、ターンは正常に終わる**。承認（人の操作）が配送を起こす。

- **ターンを跨いで残るのは「静的な提案」だけで「生きた実行」ではない。**
  提案はトークンを消費せず、タイムアウトも予算も持たない、ただのデータ。
  対話シェル A 案が退けられたのは**実行状態**（プロセス・予算の所有）が
  ターンを跨ぐからで、ここはその線を越えない
- ターンの中で人の入力を**待たない**（eigent の `ask_human_via_gui` は
  Future を無限にブロックする — 上の実測で「人が離席するとサブタスクが
  タイムアウトまで固まる」穴として観測済み。採らない）
- `run` の pending（Spec 20）と同型だが 1 点違う — run は「拒否して積む」
  （初回は必ず失敗する）、plan は「**提示で正常に終わる**」。失敗ではない

### D2. スイッチは個体ごと・既定 OFF

`AgentSpec` に 1 欄（仮名 `planReview`。UI ラベルは「計画の確認」—
用語境界: 分類・ラベルはシステム用語側）。`AgentSettingsDialog` の
`allowHandoff` の隣。

- **per-call（LLM が選ぶ）にしない** — 窓は人のための機構で、LLM に
  「窓を飛ばす」選択肢を与えると #84 の形で必ず飛ばされる
- **村単位にしない** — 窓が要るのは進行役だけ。ワーカーに plan は生えない
  ことが多いが、生える構成でも個体ごとに決められるほうが狭い
- **`AgentSnapshot` にも写す**（Spec 14 P1 の規律 — 投影に無い欄は
  設定ダイアログの保存のたびに既定へ戻る）

### D3. ツール結果の文言に嘘を書かない

編集窓で終わったターンのツール結果は「計画を提示しました。利用者が編集して
実行または破棄します。**このターンでは結果を受け取りません**」。

- 「結果が返ります」と書くと嘘になる（結果は次のターンに別の形で届く）。
  転送の手順文を委譲ターンで分けたのと同じ規律（文言は保証ではないが、
  **嘘を書かないのは別の話**）
- 破棄されたときは System 行で「計画（wave N）は破棄されました」を
  進行役の会話へ 1 行（#44 — 飛ばした相手が居たら System 行に必ず書く、の族）

### D4. 編集状態はフロントが持ち、実行時に最終形を渡す

IPC は **`dispatch_plan(plan_id, tasks)` と `discard_plan(plan_id)` の 2 本**。
編集途中を保存する `update_*` は作らない。

- eigent と同じ判断（編集の中間状態に API を与えない）。画面を閉じたら
  編集は消え、提案は元の形で残る — 「保存されていない編集がある」という
  第 3 の状態を作らない
- `dispatch` が受けた `tasks` が正であり、提案との差分は取らない
  （**人が最後に見て押した形が唯一の真実**）

### D5. 実行は新しい因果の根

`dispatch` は **`new_root_budget` + 新しい root cancel token** で走る。
ユーザー発話・予定の発火に次ぐ**3 つ目の根**。

- 承認は人の操作なので、新しい根として数えるのが実態に合う（元の依頼の
  ターンは既に精算済み。跨いで予算を持ち越すと「終わったターンの予算が
  後から減る」という読めない形になる）
- hop は進行役からの配送として `next_hop = 1`（現行の run_plan と同じ位置）
- 打ち切りは「全ターン停止」（`interrupt_all`）と、波ペインの既存の停止導線が
  この root token を切る

### D6. 束ねは進行役への配送（最大の構造変更 — 正直に書く）

現行の「配送 → join → 束ね」はターンの中に住んでいる。二相形ではその
所有者が居なくなるので、**`dispatch` が波の実行者（spawn タスク）を起こし、
配送・回収・束ねを行い、束ねを進行役への配送として届ける**。進行役は
新しいターンで束ねを読み、要約して利用者へ返す。

- 送り手は `Endpoint::System`（予定の発火と同じ前例。封筒で「これは
  システムが運んだ束ねだ」と分かる）。**#89 の轍を踏まない** — System 発話の
  宛先付き配送は `compose_presence_notices` の抽出条件（`to == User`）を
  既に直してあるので、他の個体の広場ログへは漏れない（P1 でテストに留める）
- **これはターンの外の実行形の 2 つ目**（1 つ目は手動要約 = #50 で計器を
  付けた前例）。同じ轍を踏まないため、波の実行者の消費は最初から
  `TurnSpend` の形で精算し（#103 — 払いはどの出口でも記録される）、
  ログに `plan dispatch:` / 既存の `plan wave:` / `plan bundle:` を出す
- 進行役が束ねを受け取るターンは**普通のターン**（RepeatGuard・予算・
  打ち切りすべて既存のまま）

### D7. 提案の寿命は in-memory（再起動で消える）

`PlanWaveStore` に波レベルの状態（`pending / dispatched / discarded`）を
1 つ足す形。**永続化しない** — Spec 12 の凍結「波は復元しない（作業の寿命）」
に提案も従う。再起動で消えたら頼み直し（既存原則そのまま）。

### D8. dispatch 時の検証は run_plan と 1 実装を共有

受けた `tasks` に run_plan と同じ検証（空でない / 宛先が**その進行役の**
接続先 / 宛先重複なし）を掛ける。検証部を関数に切り出して両経路が呼ぶ。

- **GUI が何でも配送できる形にしない**（Spec 20 rev2 の「IPC が
  `pattern: String` だと『粒度は機械が決めない』が『GUI が何でも決められる』へ
  反転する」と同じ罠）。編集で選べる宛先も接続先に限る — 窓は線を
  引き直す場所ではない
- 提示とディスパッチの間に繋ぎ替えが起きうるのは現行と同じ
  （`run_plan` のコメント「提示はターンの開始時、検証は今」）。検証が今の
  接続で掛かるので、切られた線への配送は構造的に起きない

### D9. 進行役が停止中の dispatch は断る

束ねの届け先が居ないまま撒くと、答えだけが揃って要約されない波になる。
`dispatch` は進行役が稼働中であることを要求し、停止中なら
「進行役を起動してから実行してください」で断る（自動起動はしない —
`batch_start_invariant` の理由がそのまま当たる）。

## 凍結（P0 で `data_contract` へ）

1. 既定 OFF。設定 OFF の個体の plan はバイト等価の挙動（S4）
2. 提案は永続化しない（Spec 12 の凍結へ 1 語足す形）
3. dispatch の検証は run_plan と 1 実装（宛先は接続先に限る）
4. 編集の中間状態に API を与えない（IPC は dispatch / discard の 2 本）
5. dispatch は新しい因果の根（予算・cancel・hop=1）
6. 束ねの送り手は `Endpoint::System`・宛先は進行役のみ
   （他個体の広場ログに漏れない — #89 の回帰をテストで留める）
7. LLM は承認後の経路に居ない（提示された計画のデータがそのまま検証・配送される）

## 検収（実機）

1. S1 — `plan pending:` 行（新計器）が出て、**`plan wave:` 行が出ない**
   （負の対照: `turn start:` がワーカーに 1 本も立たない）
2. S2 — 編集して実行 → `plan dispatch:` の後の `plan wave:` の `to=` /
   `msg_chars=` が**編集後の値**（提示時と違う数字であることが同一性の証拠）
3. S3 — 破棄 → 配送ゼロのまま System 行が会話に出る
4. S4 — OFF の個体（対照）は従来どおり `plan wave:` が即出る
5. 束ねが進行役に届き、要約が利用者へ返る（進行役の `reply: to=user`）
6. 小さい天井を root に掛けて dispatch し、`budget stop:` が出る
   （新しい根に予算が効いている証拠）

## Notes

1. **範囲は plan だけ。`ask_*` に窓は付けない** — 波は 1 回で N 体へ撒く
   1 桁大きい買い物で、単発の ask は会話の速度で流れる（毎回窓を挟むと
   委譲が使い物にならない）。要望が出たら別途
2. 計器は 3 段: `plan pending:`（提示）/ `plan dispatch:`（実行の起点・
   編集の有無は tasks 数と msg_chars の差で読める）/ 既存の `plan wave:` 〜
   `plan bundle:`。破棄は `plan discard:`
3. eigent との対応: 提示 = `eigent_make_sub_tasks` / 実行 =
   `eigent_start`（編集済みリストを渡す）/ 編集状態はフロント持ち（同じ）。
   **違い**は 2 つ — 向こうは分解を LLM 任せの DAG 込みで提示する
   （こちらは 1 段の並列撒きのまま。依存は導入しない）/ 向こうの束ねは
   同一プロセスのask ループ内、こちらは System 配送で新ターン
4. 将来スイッチ（三叉分岐）が入るなら、この「確認待ちの波」は判定コードの
   入力になりうる（人が承認する代わりにコードが承認する形）。ただし本 Spec
   では触れない — 未起票の材料に依存しない
