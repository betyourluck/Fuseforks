# Spec: JSON の配列型で返るツール結果を、要素単位で落とす

- 起票: 2026-09-22
- 状態: **rev1 起票（査読前。未決 5 点）**。**[Spec 59](59_jev-tool-result-pruning.md) が Done に
  なってから着手する**（機構の大半をあちらから借りるので、先に骨格が固まっている必要がある）
- 起点: **Spec 59 の P0 で測った返り値の形**（2026-09-22）。対象の呼び出しのうち 4,000 字以上の
  5,246,474 字を、実際にツールを叩いて分類したら **30.1% が JSON の配列型**だった。
  Spec 59 は「JSON は包装型だけ扱う」で着地したので、この 30.1% は素通しのまま残っている。
  利用者裁定（2026-09-22）—「B は足す、C は別 Spec に切る」
- 覆す凍結: 無い。Spec 59 の `tool_prune_contract` に**足す**形（既存の凍結は 1 つも動かさない）

## Goal

1. **JSON の配列型で返るツール結果から、そのターンの依頼に関係の無い要素を、モデルへ返す前に落とす。**
   落とした後も**JSON として読めるまま**であること
2. **残る要素は逐語。** 要素の中身を要約も言い換えもしない
3. **落としたことと、落としたものへ戻る道を書く**（`failures.md` #44）
4. **Spec 59 の機構を借りる** — `ParagraphScorer` / 閾値 / 設定（`jev.json`）/ `omitted` / 計器。
   新しく作るのは**割り方と組み立て**だけ
5. **形が揃わなければ丸ごと諦める**（`outcome=structured` のまま）。部分的に解釈して構文を壊す
   経路を作らない（AionUi の `toon` と Spec 59 D4b と同じ規律）

**やらないこと（範囲外）**: Spec 59 が扱う範囲（本文と包装型）/ ネストした配列の中の配列 /
要素の中身を切り詰めること（要素は落とすか残すかの 2 値）

## 実測（Spec 59 の P0 から引き継ぐ。**測り直さない**）

| 分類 | 字数 | 割合 | 実測した例 |
|---|---|---|---|
| A. JSON でない（Spec 59 の対象） | 1,283K | 24.5% | `MCP_DOCKER__fetch` / `rag` |
| B. JSON・包装型（Spec 59 D4b の対象） | 291K | 5.5% | `manuale__read` |
| **C. JSON・配列型（本 Spec の対象）** | **1,581K** | **30.1%** | `outcasts__recent_posts` / `memoria__recall_memory` / `manuale__search` |
| D. 同サーバーの他ツール（高確度で JSON） | 949K | 18.1% | `alphaxiv__*` / `manuale__navigate` |
| E. 不明（この端末から叩けない） | 1,142K | 21.8% | `elyth__*` / `browsermcp__*` |

**通しの効き目**（ツール出力 12.25M 字 = 実効コストの 11〜22%。削減率は Spec 59 の実測で 47%）:

```text
Spec 59 だけ（A+B）  1.57M × 47% = 739K   = ツール出力の  6.0% → 実効の 0.7〜1.3%
本 Spec を足す（+C）  3.15M × 47% = 1.48M  = ツール出力の 12.1% → 実効の 1.3〜2.7%
```

**この Spec が動かすのは約 2 倍**。ただし **D と E（合わせて 39.9%）は形を確かめていない**ので、
着手時に `alphaxiv__answer_pdf_queries`（単独最大の 787K）と `elyth__*` を数え直すこと。
包装型なら Spec 59 が既に拾い、配列型なら本 Spec の効き目がさらに伸びる。

## Design（**起票段階。決めどころを挙げるところまで**）

### D1. どれを配列型と認めるか

Spec 59 D4b と同じく**閉じた条件**にする。案:

- トップレベルが配列、**または**トップレベルのオブジェクトの直下に配列が**ちょうど 1 つ**
- その配列の要素が **5 件以上**
- 配列の JSON 表現が本文全体の **60% 以上**
- 入れ子の中は探さない

**実測の 3 例はこの形に収まる** — `{"posts":[…]}` / `{"query":…,"matches":[…]}` /
`{"schema_entries":[…],"semantic_matches":[…],…}`。**ただし 3 例目（`memoria__recall_memory`）は
直下の配列が複数あるので、上の条件では落ちる**（未決 1）。

### D2. 要素をどう採点するか

1 要素 = Spec 59 の「1 段落」として `ParagraphScorer` へ渡す。渡すのは**要素の JSON 表現**か、
**要素の中の文字列を連ねたもの**か（未決 2）。前者は構造が見えるぶん Jev の判断材料が増えるが、
キー名が毎回同じなので雑音にもなる。

6,000 字を超える要素は採点せず残す（Spec 59 D4 と同じ）。

### D3. 落としたことをどこに書くか（**最大の決めどころ**）

JSON の構文を壊さずに印を入れる方法が 3 つあり、どれも代償がある（未決 3）:

| 案 | 形 | 代償 |
|---|---|---|
| A. 配列の中に印の要素 | `[{…}, {"_omitted": 7}, {…}]` | **要素の型が揃わなくなる**。読む側がパースしていれば壊れる |
| B. トップレベルにキーを足す | `{"posts":[…], "_pruned":{"dropped":7,"id":"P2"}}` | **元の JSON に無いキーが生える**。Goal 2 の逐語は要素についてだが、構造は変わる |
| C. JSON の外に印を置く | `【… 7 件を省略 …】\n{"posts":[…]}` | **本文全体が JSON でなくなる**。Goal 1 と正面から衝突 |

**私の推し は B** — 読む側がパースしても壊れず（未知のキーは無視される）、印の置き場が 1 つに定まる。
ただし「元の JSON に無いキーを足さない」を凍結する選択肢もありうる。

### D4. 差し替えの方法

Spec 59 D4b は「**元テキストの上で文字列リテラルだけを差し替える**」形で、再シリアライズを避けた。
配列から要素を**消す**場合は同じ手が使えない（消すとカンマの位置が変わる）。案は 2 つ（未決 4）:

- **位置ベース** — 要素の範囲を元テキストで特定し、その範囲とカンマを消す。他は 1 バイトも
  変わらないが、**JSON のスキャナを自前で書くことになる**
- **再シリアライズ** — parse → 要素を落とす → `to_string`。実装は単純だが、**整形・キーの順序・
  数値の表現が変わりうる**（`serde_json` の `preserve_order` feature の有無を着手時に数える）

### D5. 戻り道

Spec 59 の `omitted { id, from, to }` を共有する。**`from` / `to` は配列の要素の index**
（Spec 59 は段落の index）。同じツールで 2 つの意味を持つことになるので、`id` が指す先が
本文か配列かを置き場（`PrunedRaw`）に持たせる（未決 5）。
