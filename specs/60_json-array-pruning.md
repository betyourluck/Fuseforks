# Spec: JSON の配列型で返るツール結果を、要素単位で落とす

- 起票: 2026-09-22
- 状態: **rev1 + P0 の測定（2026-09-22。査読前）**。Spec 59 は同日 Done。**P0 で D の分類と
  配列型の削減率を実測した**（下の「P0 実測」が正）。**未決 5 点はすべて測定で向きが出た**が、
  裁定は利用者 — rev2 は査読を通してから
- 起点: **Spec 59 の P0 で測った返り値の形**（2026-09-22）。対象の呼び出しのうち 4,000 字以上の
  5,246,474 字を、実際にツールを叩いて分類したら **30.1% が JSON の配列型**だった。
  Spec 59 は「JSON は包装型だけ扱う」で着地したので、この 30.1% は素通しのまま残っている。
  利用者裁定（2026-09-22）—「B は足す、C は別 Spec に切る」
- 覆す凍結: 無い。Spec 59 の `tool_prune_contract` に**足す**形（既存の凍結は 1 つも動かさない）

## Goal

1. **JSON の配列型で返るツール結果から、そのターンの依頼に関係の無い要素を、モデルへ返す前に落とす。**
   落とした後も**JSON として読めるまま**であること
2. **残る要素は逐語。** 要素の中身を要約も言い換えもしない
3. **落としたことと、落としたものへ戻る道を書く**（`failures.md` #44）
4. **Spec 59 の機構を借りる** — `ParagraphScorer` / 閾値 / 設定（`jev.json`）/ `omitted` / 計器。
   新しく作るのは**割り方と組み立て**だけ
5. **形が揃わなければ丸ごと諦める**（`outcome=structured` のまま）。部分的に解釈して構文を壊す
   経路を作らない（AionUi の `toon` と Spec 59 D4b と同じ規律）

**やらないこと（範囲外）**: Spec 59 が扱う範囲（本文と包装型）/ ネストした配列の中の配列 /
要素の中身を切り詰めること（要素は落とすか残すかの 2 値）

## 実測（Spec 59 の P0 から引き継ぐ。**測り直さない**）

| 分類 | 字数 | 割合 | 実測した例 |
|---|---|---|---|
| A. JSON でない（Spec 59 の対象） | 1,283K | 24.5% | `MCP_DOCKER__fetch` / `rag` |
| B. JSON・包装型（Spec 59 D4b の対象） | 291K | 5.5% | `manuale__read` |
| **C. JSON・配列型（本 Spec の対象）** | **1,581K** | **30.1%** | `outcasts__recent_posts` / `memoria__recall_memory` / `manuale__search` |
| D. 同サーバーの他ツール（高確度で JSON） | 949K | 18.1% | `alphaxiv__*` / `manuale__navigate` |
| E. 不明（この端末から叩けない） | 1,142K | 21.8% | `elyth__*` / `browsermcp__*` |

**通しの効き目**（ツール出力 12.25M 字 = 実効コストの 11〜22%。削減率は Spec 59 の実測で 47%）:

```text
Spec 59 だけ（A+B）  1.57M × 47% = 739K   = ツール出力の  6.0% → 実効の 0.7〜1.3%
本 Spec を足す（+C）  3.15M × 47% = 1.48M  = ツール出力の 12.1% → 実効の 1.3〜2.7%
```

**この Spec が動かすのは約 2 倍**。ただし **D と E（合わせて 39.9%）は形を確かめていない**ので、
着手時に `alphaxiv__answer_pdf_queries`（単独最大の 787K）と `elyth__*` を数え直すこと。
包装型なら Spec 59 が既に拾い、配列型なら本 Spec の効き目がさらに伸びる。

## Design（**起票段階。決めどころを挙げるところまで**）

### D1. どれを配列型と認めるか

Spec 59 D4b と同じく**閉じた条件**にする。案:

- トップレベルが配列、**または**トップレベルのオブジェクトの直下に配列が**ちょうど 1 つ**
- その配列の要素が **5 件以上**
- 配列の JSON 表現が本文全体の **60% 以上**
- 入れ子の中は探さない

**実測の 3 例はこの形に収まる** — `{"posts":[…]}` / `{"query":…,"matches":[…]}` /
`{"schema_entries":[…],"semantic_matches":[…],…}`。**ただし 3 例目（`memoria__recall_memory`）は
直下の配列が複数あるので、上の条件では落ちる**（未決 1）。

### D2. 要素をどう採点するか

1 要素 = Spec 59 の「1 段落」として `ParagraphScorer` へ渡す。渡すのは**要素の JSON 表現**か、
**要素の中の文字列を連ねたもの**か（未決 2）。前者は構造が見えるぶん Jev の判断材料が増えるが、
キー名が毎回同じなので雑音にもなる。

6,000 字を超える要素は採点せず残す（Spec 59 D4 と同じ）。

### D3. 落としたことをどこに書くか（**最大の決めどころ**）

JSON の構文を壊さずに印を入れる方法が 3 つあり、どれも代償がある（未決 3）:

| 案 | 形 | 代償 |
|---|---|---|
| A. 配列の中に印の要素 | `[{…}, {"_omitted": 7}, {…}]` | **要素の型が揃わなくなる**。読む側がパースしていれば壊れる |
| B. トップレベルにキーを足す | `{"posts":[…], "_pruned":{"dropped":7,"id":"P2"}}` | **元の JSON に無いキーが生える**。Goal 2 の逐語は要素についてだが、構造は変わる |
| C. JSON の外に印を置く | `【… 7 件を省略 …】\n{"posts":[…]}` | **本文全体が JSON でなくなる**。Goal 1 と正面から衝突 |

**私の推し は B** — 読む側がパースしても壊れず（未知のキーは無視される）、印の置き場が 1 つに定まる。
ただし「元の JSON に無いキーを足さない」を凍結する選択肢もありうる。

### D4. 差し替えの方法

Spec 59 D4b は「**元テキストの上で文字列リテラルだけを差し替える**」形で、再シリアライズを避けた。
配列から要素を**消す**場合は同じ手が使えない（消すとカンマの位置が変わる）。案は 2 つ（未決 4）:

- **位置ベース** — 要素の範囲を元テキストで特定し、その範囲とカンマを消す。他は 1 バイトも
  変わらないが、**JSON のスキャナを自前で書くことになる**
- **再シリアライズ** — parse → 要素を落とす → `to_string`。実装は単純だが、**整形・キーの順序・
  数値の表現が変わりうる**（`serde_json` の `preserve_order` feature の有無を着手時に数える）

### D5. 戻り道

Spec 59 の `omitted { id, from, to }` を共有する。**`from` / `to` は配列の要素の index**
（Spec 59 は段落の index）。同じツールで 2 つの意味を持つことになるので、`id` が指す先が
本文か配列かを置き場（`PrunedRaw`）に持たせる（未決 5）。

## P0 実測（2026-09-22）

### 1. D の分類 — 叩けるものを全部叩いた

母数は `fuseforks.log` 2026-08-09〜09-22 の MCP 由来・4,000 字以上の出力 **4,903,900 字**
（Spec 59 P0 の 5.25M とは期間と `rag` の有無で差がある）。

| ツール | 字数 | 形（実物） | 分類 |
|---|---|---|---|
| `MCP_DOCKER__fetch` | 875K | Markdown（Spec 59 P0） | A |
| **`alphaxiv__answer_pdf_queries`** | **787K** | **XML** `<paper id><page num=N>…</page>…</paper>`。PDF 抽出の行で**空行が無い** | **A'** = JSON でないが D4 で割れない |
| `outcasts__recent_posts` | 485K | `{"posts":[…]}` 配列 1・素の JSON | C |
| `outcasts__read_thread` | 396K | `{"board_slug","id","posts":[…],"title"}` 配列 1・素の JSON・要素は投稿 | C |
| `memoria__recall_memory` | 306K | 配列 **7 つ**（`schema_entries` / `semantic_matches` / … ）・要素は**文字列とオブジェクトが混在**・整形 | **C'**（複数配列） |
| `manuale__read` | 291K | 包装型（Spec 59 D4b） | B |
| `manuale__search` | 204K | `{"query",…,"matches":[…],"next_hints":[…]}` 配列 **2 つ**・整形。`context` に base64 画像（20K 字超）が入ることがある | **C'** |
| `outcasts__list_threads` | 108K | `{"threads":[…]}` 配列 1 | C |
| `manuale__navigate` | 85K | `{"entries":[…],"next_hints":[…]}` 配列 **2 つ**・整形 | **C'** |
| `memoria__list_memories` | 126K（1 回） | 先頭にテキスト行 `Total memories: N` + JSON 配列。要素の 9 割が `embedding`（384 次元） | 対象外（JSON でない） |
| `alphaxiv__discover_papers` | 23K | Markdown の番号付きリスト・空行なし | A |
| **`elyth__get_information`**（`get_notifications` / `get_my_posts` も同じサーバー） | **713K** | `{"data":{…}}` の 1 キー包装。配列は **3 段目**（`data.timeline.items` / `data.trending.items` など）に 5 件ずつ、1 要素 ≈ 350 字で本文は **`truncated: true` の 50 字抜粋**。字数の大半は UUID・時刻・`author` の入れ子（利用者が GUI のツール行で確認・2026-09-22） | **C''** = 入れ子の配列・短い要素 |
| `browsermcp__*` / `admin-procedures__*` | 157K | 未分類 | E |

**分かったこと 3 つ**:

- **D の最大は配列型ではなかった。** 787K は XML で、Spec 60 の効き目は rev1 の見積もり
  （+C で約 2 倍）から**伸びない**。逆にこの 787K は Spec 59 の対象なのに**空行が無いので割れない** —
  `rag` と同じ形。`<page>` 境界で割る腕を D4 に足せば効く余地がある（**Spec 59 の追補の話で、本 Spec の
  範囲外**）
- **複数配列が主流。** C の 1,584K のうち **C' が 595K（38%）**。rev1 の D1「配列がちょうど 1 つ」は
  `memoria` のための例外ではなく、**設計の前提を外していた**
- **配列型の中でも要素の型が 3 種ある** — 投稿（長い散文のオブジェクト）/ 規律文（文字列）/
  ディレクトリ項目（短い構造）。下の採点で**判定の質が型ごとに違った**
- **E の大半（`elyth` 713K = MCP 出力の 15%）は配列型だが本 Spec の効き目に乗らない。**
  配列が 3 段目に居るので D1 のどの案でも届かず、届いても本文が 50 字の抜粋で **Jev に判定材料が無い**
  （下の採点の観測 2 と同じ形）。字数の出どころが本文ではなく構造（id / 時刻 / 入れ子）なので、
  効くとすれば要素を落とす機構ではなく構造を畳む機構（`toon` の系譜）だが、`author` が入れ子なので
  あちらの「フラットな同型配列」の条件も満たさない。**本 Spec では対象外として閉じる**

### 2. 要素単位の採点（3 本・4 依頼文・2 表現・Jev 11 呼び出し）

叩いた実物を scratchpad に置き、Spec 59 と同じ問い（`instructions` / `criteria` は `jev.rs` の逐語）で
要素ごとに Noul 1 問。閾値 0.2。**JSON 表現**（要素をそのまま）と**文字列連結**（要素の中の文字列を
改行で連ねたもの）の 2 通りで採点した（未決 2 の対測）。

| 材料 | 依頼文 | 要素 | 落ちた | 削減率 | Jev |
|---|---|---|---|---|---|
| `read_thread`（12 投稿・12,290 字） | 「管理者（人間・`authored_mode` が master）が何を書いたか**だけ**」 | 12 | **8** | **67.9%** | 11,955 |
| 同 | 「拒否権や権限ゲートの設計についての提案をまとめて」 | 12 | 2 | **12.1%** | 11,946 |
| `recall_memory`（17,441 字） | 「Spec 60 について過去に決めたことを思い出して」 | 20 + 5 | 7〜12 + 2 | **11.1〜17.8%** | 9,897 |
| `navigate`（1,150 字 = 実機では 4,000 字未満で対象外） | 「Fuseforks の仕様書やアーキテクチャの文書を探して」 | 12 + 5 | 9〜10 + 4 | 62〜68% | 3,447 |

**読めたこと 5 つ**:

1. **依頼文で 12% ↔ 68% に割れる**（Spec 59 P0 と同じ性質）。同じ 12 投稿でも「1 人の投稿だけ」なら
   8 本落ち、「設計の提案を全部」なら 2 本しか落ちない。**門（25%）は配列型でも要る** — 後者は
   `below_floor` で止まるのが正しい
2. **要素の型で判定の質が違う。** 投稿（400〜1,500 字の散文）は両端がよく分かれる
   （0.07〜0.10 対 0.93）。**規律文（Mandate）は 0.2〜0.45 の中間帯に溜まる** — 「Spec 60 について」に
   対して規律が「関係ある」と判定されがち（Jev が判断型に弱い側）。**ディレクトリ項目（`{"type":"dir",
   "path":"spec","name":"spec"}` = 40 字）は全部 0.05〜0.23 で、依頼文が名指しした `spec` / `architecture`
   も 0.20 / 0.21** — 閾値ぎりぎりで残った。**短い要素は判定材料が無く、Jev は決められない**
3. **「要素 5 件以上」の門は逆効果の実例がある。** `recall_memory` の `semantic_matches` は **3 件**だが
   1 件 4,000〜6,000 字で、17K 字のうち **12K 字を占める**。うち 2 件（Spec 35 / 38 の索引）は依頼と
   無関係で、落とせれば削減率は 11% → **60% 超**に跳ねる。**門は要素数ではなく配列の字数で切る**
4. **JSON 表現と文字列連結の差は小さく、文字列連結がやや落とす側。** `read_thread` は落ちる本数が
   一致（スコアの差 0.01〜0.2）、`recall_memory` は 7 対 12。**採るなら JSON 表現** — 差し替え（D4）で
   落とすのは要素の JSON 表現そのものなので、**採点に送ったものと落とすものが同一物**になる
5. **Jev は構造の条件を読み分けなかった。** 依頼文に `authored_mode` が master と書いたのに、
   `author_name` が「Outcasts@管理者」のサーヴァント投稿 2 本（post 7 / 11）が 0.61 / 0.62 で残った。
   **配列型の売りは構造があることだが、Jev が見ているのは本文の語**。構造の条件で落とす期待は持たない

### 3. 正味の収支（Spec 59 P4 実機記録 3 と同じ形）

`read_thread` の依頼 1 では 8,346 字（日本語・約 8,000 トークン）が落ち、Jev は 11,955 トークン。
`gpt-5.6-terra` の書き込み単価で節約 ≈ $0.020 対 Jev ≈ $0.0005 = **約 40 倍の黒字**。
依頼 2 では 1,486 字で門に届かず、Jev 11,946 トークン（$0.0005）が捨て金。
**Spec 59 と同じ結論** — 効くかどうかは依頼文と要素の形が決め、門が赤字を止める。

### 4. 未決 5 点への向き（裁定は利用者。査読へ）

| 未決 | 測定が指した向き |
|---|---|
| 1. 複数配列 | **直下の配列すべてを対象**にし、門は要素数ではなく**配列の JSON 表現が 1,000 字以上**。`next_hints` のような小さい配列は自然に外れる。トップレベルが配列（包装なし）の実例は **0 件**なので、その形は**対象外として閉じる**（印の置き場 B が使えない形を作らない） |
| 2. 表現 | **JSON 表現**（差は小さく、落とすものと同一物） |
| 3. 印の置き場 | **B（トップレベルに `_pruned` 1 キー）** — 未決 1 でトップレベルが必ずオブジェクトになるので置き場が定まる。複数配列を 1 つのキーで記述できる（`{"_pruned":{"id":"P2","arrays":{"schema_entries":{"dropped":[…]},…}}}`） |
| 4. 差し替え | **位置ベース**。実物は整形あり（`memoria` / `manuale`）と素（`outcasts`）が混在し、再シリアライズは整形を必ず変える = 「圧縮した文字列以外は 1 バイトも変わらない」を破る。**着手時に Spec 59 D4b の文字列リテラルの位置探索が再利用できるか数える** |
| 5. `omitted` | `PrunedRaw` に種別を持たせ、印の文面で「要素」と書く。`from` / `to` は要素の index（段落と同じ意味の別名） |

**効き目の見積もりの訂正**: rev1 は「+C で約 2 倍」と書いたが、C 1,584K のうち実際に効く形は
`outcasts` の 989K（長い投稿・配列 1 つ）と `memoria` の `semantic_matches`（長い文字列）まで。
`manuale__navigate` は要素が短く、`elyth` は届かない。**伸びるのは MCP 出力の 20〜25% ぶんで、
かつ依頼が狭いときだけ**（P0 の依頼 1 と 2 の差）。

**測っていないこと**: `browsermcp__*` / `admin-procedures__*` の 157K（3%）の形 / 実機の `manuale__navigate`（21K 字・深い階層）で要素が
短いまま 4,000 字を超えたときの判定 / `search` の base64 画像（6,000 字超の要素として採点対象外に
なるはずだが、実物で確かめていない）。
