## Goal

1. **トップレベルがオブジェクトで、その直下に配列を持つ JSON のツール結果から、そのターンの依頼に
   関係の無い要素を、モデルへ返す前に落とす。** 落とした後も**JSON として読めるまま**で、
   **配列の要素の型は揃ったまま**であること（印を要素として混ぜない）
2. **残る要素は逐語。** 要素の中身を要約も言い換えもしない
3. **落としたことと、落としたものへ戻る道を書く**（`failures.md` #44）
4. **Spec 59 の機構を借りる** — `ParagraphScorer` / 閾値 / 設定（`jev.json`）/ `omitted` / 計器。
   新しく作るのは**割り方と組み立て**だけ
5. **形が揃わなければ丸ごと諦める**（`outcome=structured` のまま）。部分的に解釈して構文を壊す
   経路を作らない（AionUi の `toon` と Spec 59 D4b と同じ規律）

**やらないこと（範囲外）**: Spec 59 が扱う範囲（本文と包装型）/ **トップレベルが配列の JSON**
（実例 0 件。印の置き場が無い）/ **直下より深い配列**（`elyth` の 3 段目。P0 実測 1）/
要素の中身を切り詰めること（要素は落とすか残すかの 2 値）

## Design（rev2。P0 の実測と査読で確定した側。rev1 の文面は Notes 5）

### D1. 対象の形（**対象の門**）

**閉じた条件 3 つ**をすべて満たす本文だけを対象にする（Spec 59 D4b と同じ流儀 — 外れたら
`outcome=structured` のまま素通し。部分的に解釈しない）:

1. **トップレベルがオブジェクト**（配列なら対象外 — 印の置き場が無い。実例 0 件）
2. **直下に配列が 1 つ以上**あり、そのうち **JSON 表現が 1,000 字以上の配列**を対象にする。
   **門は要素数ではなく字数**（P0 実測 2-3: 3 件で 12K 字を占める配列が実例）。1,000 字未満の配列
   （`next_hints` / `capabilities` / `counts_by_type`）は触らない
3. **直下より深い配列は探さない**（`elyth` の `data.timeline.items`。届いても要素が 50 字の抜粋で
   Jev に判定材料が無い = P0 実測 1・2-2）

**複数の配列が対象になりうる**（`memoria__recall_memory` は 7 つ、`manuale` は 2 つ）。
対象の配列それぞれが独立に採点・判定される（D6）。**対象の配列が 0 なら `structured`**。

### D2. 要素をどう採点するか

**要素の JSON 表現**（`serde_json` の compact 表現ではなく、**元テキストの上でその要素が占める
範囲の逐語**）を Spec 59 の「1 段落」として `ParagraphScorer` へ渡す。

- 採るのは JSON 表現。~~構造が見えるぶん判断材料が増える~~ **→ P0 実測 2-5 で否定**（Jev は
  `authored_mode` のような構造の条件を読み分けない。見ているのは本文の語）。**採る理由は
  「落とすものと採点に送ったものが同一物」の 1 つだけ**（文字列連結との差は小さい = 2-4）
- 6,000 字超の要素は採点せず残す（Spec 59 D6 の凍結をそのまま借りる）。`search` の base64 画像
  （20K 字超）はここで自然に外れる。**6,000 字の崖は Spec 59 の凍結で、本 Spec では動かさない**
- **全対象配列の要素を 1 本の候補列に平坦化して `prune::batch` へ渡す**（束ね方の唯一の実装。
  Spec 59 D4 の 6）。戻ったスコアは `(配列の鍵, 要素の index)` の対応表で戻す — Spec 59 の `Prepared`
  が段落の index でやっていることと同じで、鍵が 1 つ増えるだけ

### D3. 落としたことをどこに書くか（**B で確定。A と C は除外**）

**トップレベルに `_pruned` を 1 キー足す。** 配列の中に印の要素は入れない（A — 要素の型が揃わず
`Post[]` として読む側が壊れる = Goal 1 / Goal 5 違反）。JSON の外にも置かない（C — 本文が JSON で
なくなる = Goal 1 違反）。

```json
{"posts":[…残った要素…],
 "_pruned":{
   "note":"関連度で要素を省略しています。omitted(id, from, to) で逐語が読めます",
   "arrays":{
     "posts":{"id":"P2","total":12,"dropped":[0,3,11]}
   }}}
```

- **配列ごとに `id` を 1 つ振る**（`P{n}` の通し番号。Spec 59 の `self.pruned.len() + 1` をそのまま使う）。
  `omitted { id, from, to }` の引数は**変えない** — `id` が配列を、`from` / `to` がその配列の要素の
  index を指す（査読 #2 矛盾 1 の解）
- **`note` はモデルへの案内**（Spec 59 の印の文面と同じ役割。`【…】` の代わりに JSON の値で運ぶ。
  ~~ja / en は `Language` で選ぶ~~ **→ P1 で訂正**: Spec 59 の印も日本語固定で `prepare` / `apply` は
  `Language` を受け取らない。2 つの印を同じ規律にそろえ、本 Spec だけ二言語にしない）
- **元の JSON に `_pruned` が既にあれば丸ごと諦める**（`structured`）。上書きも改名もしない（Goal 5）
- **これは「元の JSON に無いキーを足す」変更で、Spec 59 の「圧縮した文字列以外は 1 バイトも
  変わらない」より一段ゆるい。** 要素を消す以上、構造は必ず変わる（カンマが動く）ので、
  「変わるのは対象の配列の中身と `_pruned` の 1 キーだけ」を凍結の文面にする（**未決 1 = 利用者裁定**）

### D4. 差し替えの方法（**位置ベースで確定。再シリアライズは除外**）

**元テキストの上で、落とす要素の範囲（先行または後続のカンマ 1 つを含む）を消し、末尾の `}` の
直前に `,"_pruned":{…}` を挿入する。** 他は 1 バイトも触らない。

- 再シリアライズは除外 — `serde_json` はキー順・空白・数値表現（`1.0` と `1`）を変える（Goal 2 違反。
  実物は整形あり / なしが混在するので、整形も必ず変わる）
- **要素の範囲は自前のスキャナで取る**（文字列リテラルとエスケープ・括弧の深さだけを追う）。
  Spec 59 D4b が「最長の文字列リテラルの位置」を探す走査を既に持っている — **着手時に共有できる
  部分を数える**（P1 の 1 本目）
- **カンマの規則**: 落とす要素が末尾なら**先行**のカンマを、それ以外なら**後続**のカンマを消す。
  空白・改行は触らない（整形が崩れて見えても JSON として正しい — 崩れ方は fixture で焼く）
- **バイト golden**: 素の JSON（`outcasts`）と整形 JSON（`memoria` / `manuale`）の 2 fixture で、
  「対象の配列の中身と `_pruned` 以外は 1 バイトも変わらない」を留める（Spec 59 の
  `everything_outside_the_compressed_string_is_byte_identical` と同じ形）

### D5. 戻り道

Spec 59 の `omitted { id, from, to }` と `PrunedRaw { id, paragraphs, dropped }` を**無改変で共有する**。
`PrunedRaw.paragraphs` に**要素の逐語**を入れれば、`omitted` は段落と同じ経路で返す —
`PrunedRaw` は中身が段落か要素かを知らない（`kind` 欄は要らない。査読 #1 矛盾 9 の訂正）。
モデルが読む区別は `_pruned.note` と `arrays` の鍵が担う。

### D6. 配列ごとの判定と、全部落ちたとき

**判定は配列ごと**（Spec 59 の `apply` を配列 1 つに 1 回）:

- ある配列で**採点した要素がすべて閾値未満**なら、**その配列は触らない**（Spec 59 の `all_dropped` と
  同じ理由 — 依頼と噛み合っていないか採点の失敗。**空配列 `[]` は作らない**）
- ある配列で**1 つも落ちなければ**、その配列は触らない
- **対象の配列がすべて「触らない」なら、本文全体を素通し**。`outcome` は全配列が all_dropped なら
  `all_dropped`、それ以外は `nothing_dropped`
- **1 つ以上の配列で落ちたら組み立て**、正味の門（D7）へ

### D7. 2 つの門を分ける

| 門 | 何を見るか | どこで |
|---|---|---|
| **対象の門**（D1） | 配列の JSON 表現が 1,000 字以上か | 採点の**前**。外れた配列は Jev へ送らない |
| **正味の門**（Spec 59 D6b） | 組み立てた**本文全体**の削減率が 25% 以上か | 組み立ての**後**。`MIN_REDUCTION` をそのまま借りる |

**正味の門は本文全体で測る**（配列ごとではない）。固定欄が大きくて届かなければ `below_floor` で
素通しになるが、**それが正しい** — モデルに届くのは本文全体で、そこが 25% 減らないなら印を足す
価値が無い（Spec 59 rev4 の論拠そのまま。査読 #2 不整合 5 は「明記されていない」の指摘として採り、
配列ごとに測る案は採らない）。

## P1 実装記録（2026-09-22）

core 810 / 結合 47 バイナリ 全緑（+14）・clippy 0。新しい依存は 0。次に触る人が要る判断だけを置く。

- **Spec 59 D4b と共有できる走査は無かった。** D4b は「`serde_json` で読み、最長の文字列を
  再シリアライズして `match_indices` で位置を探す」形で、**スキャナを持っていない**。要素は整形
  （改行・インデント）されていると再シリアライズと一致しないので、配列型は **`JsonScanner`
  を新設**した（文字列リテラルとエスケープ・括弧の深さだけを追う約 100 行。`serde_json` が
  読めた本文にだけ掛けるので構文の誤りは想定せず、形が合わなければ `None` → `structured`）
- **分岐は `prepare` の 1 箇所**（Notes 1）。順は 包装型 → 配列型 → `structured`。包装型が先なのは、
  巨大な文字列 1 つを持つ本文は配列があってもそちらが本体だから（`arrays_yield_to_the_wrapper_shape`）
- **`Prepared` の `wrapper: Option<WrapperSlot>` を `layout: Layout` の 3 値へ**（Text / Wrapper /
  Arrays）。配列型は要素 1 つが段落 1 つで、**空行で割らず短い要素も寄せない**（境界は JSON が
  決めている）。`candidates` / `batches` / `spread` は無改変で乗った
- **`apply` の `id: &str` を `first_seq: usize` へ変えた。** 配列型は落とした配列ごとに id を 1 つ
  使うので、番号は `apply` が振る。**帰結として `Pruned` が `entries: Vec<PrunedEntry>` を持ち、
  呼び出し側（`turn.rs`）は落とした index を数え直さずにそれを積むだけ**になった — rev4 までは
  `turn.rs` が `scores < threshold` で `dropped` を再計算しており、規律が 2 箇所にあった。
  Spec 59 の段落型・包装型は 1 件の entry で、`omitted` も `PrunedRaw` も無改変
- **カンマの規則は「隙間」で書いた**（D4 の精緻化）。`[` と最初の要素の間を g0、要素 i-1 と i の
  間（カンマ入り）を g_i、最後の要素と `]` の間を g_n とし、出力は `[` + g0 + 残す要素を出現順に
  （最初に残す要素の前には何も置かず、2 つ目以降は自分の前の g_i を置く）+ g_n + `]`。
  **どの落とし方でも余分なカンマが出ず、1 つも落とさなければ入力と同一バイト**。契約の
  「先行または後続のカンマ 1 つ」はこの規則の帰結で、「空白・改行は触らない」は**落とした要素に
  付随する隙間は消える**と読む（整形は崩れて見えるが JSON として正しい）
- **`below_floor` の `ratio` は実測値のまま返す** — 一度 `net_ratio` を `Option` にして門の外で

5. **rev1 の Design の写し**（P0 で前提が覆った側。何を覆したかが読めるように残す）:

   > ## Design（**起票段階。決めどころを挙げるところまで**）
   >
   > ### D1. どれを配列型と認めるか
   >
   > Spec 59 D4b と同じく**閉じた条件**にする。案:
   >
   > - トップレベルが配列、**または**トップレベルのオブジェクトの直下に配列が**ちょうど 1 つ**
   > - その配列の要素が **5 件以上**
   > - 配列の JSON 表現が本文全体の **60% 以上**
   > - 入れ子の中は探さない
   >
   > **実測の 3 例はこの形に収まる** — `{"posts":[…]}` / `{"query":…,"matches":[…]}` /
   > `{"schema_entries":[…],"semantic_matches":[…],…}`。**ただし 3 例目（`memoria__recall_memory`）は
   > 直下の配列が複数あるので、上の条件では落ちる**（未決 1）。
   >
   > ### D2. 要素をどう採点するか
   >
   > 1 要素 = Spec 59 の「1 段落」として `ParagraphScorer` へ渡す。渡すのは**要素の JSON 表現**か、
   > **要素の中の文字列を連ねたもの**か（未決 2）。前者は構造が見えるぶん Jev の判断材料が増えるが、
   > キー名が毎回同じなので雑音にもなる。
   >
   > 6,000 字を超える要素は採点せず残す（Spec 59 D4 と同じ）。
   >
   > ### D3. 落としたことをどこに書くか（**最大の決めどころ**）
   >
   > JSON の構文を壊さずに印を入れる方法が 3 つあり、どれも代償がある（未決 3）:
   >
   > | 案 | 形 | 代償 |
   > |---|---|---|
   > | A. 配列の中に印の要素 | `[{…}, {"_omitted": 7}, {…}]` | **要素の型が揃わなくなる**。読む側がパースしていれば壊れる |
   > | B. トップレベルにキーを足す | `{"posts":[…], "_pruned":{"dropped":7,"id":"P2"}}` | **元の JSON に無いキーが生える**。Goal 2 の逐語は要素についてだが、構造は変わる |
   > | C. JSON の外に印を置く | `【… 7 件を省略 …】\n{"posts":[…]}` | **本文全体が JSON でなくなる**。Goal 1 と正面から衝突 |
   >
   > **私の推し は B** — 読む側がパースしても壊れず（未知のキーは無視される）、印の置き場が 1 つに定まる。
   > ただし「元の JSON に無いキーを足さない」を凍結する選択肢もありうる。
   >
   > ### D4. 差し替えの方法
   >
   > Spec 59 D4b は「**元テキストの上で文字列リテラルだけを差し替える**」形で、再シリアライズを避けた。
   > 配列から要素を**消す**場合は同じ手が使えない（消すとカンマの位置が変わる）。案は 2 つ（未決 4）:
   >
   > - **位置ベース** — 要素の範囲を元テキストで特定し、その範囲とカンマを消す。他は 1 バイトも
   >   変わらないが、**JSON のスキャナを自前で書くことになる**
   > - **再シリアライズ** — parse → 要素を落とす → `to_string`。実装は単純だが、**整形・キーの順序・
   >   数値の表現が変わりうる**（`serde_json` の `preserve_order` feature の有無を着手時に数える）
   >
   > ### D5. 戻り道
   >
   > Spec 59 の `omitted { id, from, to }` を共有する。**`from` / `to` は配列の要素の index**
   > （Spec 59 は段落の index）。同じツールで 2 つの意味を持つことになるので、`id` が指す先が
   > 本文か配列かを置き場（`PrunedRaw`）に持たせる（未決 5）。
